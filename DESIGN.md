# Miksy — дизайн

> Этот документ — контракт. Любой агент, который пишет или меняет часть miksy
> (в том числе свой адаптер), сначала читает его целиком и не отступает от него
> без явного согласования с владельцем репо. Изменения дизайна — сначала здесь,
> потом в коде. Как пользоваться — `README.md`; возможности агентов —
> `adapters/<агент>/CAPABILITIES.md`.

## 1. Назначение

Miksy — мета-слой над готовыми AI-агентами (Claude Code, Codex, opencode,
Antigravity). Он хранит правила, skills и MCP-серверы в одном месте и
раскладывает их в нативные конфиги каждого агента (имя и чем miksy не является — README).

Miksy — **генератор, а не рантайм**. Он не работает в фоне и не участвует в
сессии агента: запустили `miksy sync` → файлы разложены → агент читает их сам.
Единственное исключение — мост MCP (§8.6): маленький процесс, который агент сам
запускает как stdio-сервер, если иначе секрет HTTP-сервера не доставить.

## 2. Термины

| Термин | Значение |
|---|---|
| **Движок** | Этот репо: код, адаптеры, документация, примеры. Общий, без личных данных |
| **Конфигурация** | Личный каталог пользователя (обычно `miksy-config`, свой приватный репо): `map.yaml`, `layers/`, `local/` |
| **Workspace** | Каталоги с проектами на машине — один корень (например, `~/Projects` или `D:\work`) или несколько не связанных; у каждого корня — место в дереве слоёв (§6b). Задаётся на машину |
| **Слой (layer)** | Каталог конфигурации с правилами, skills и MCP (§5) |
| **Цель** | Куда miksy пишет: домашний каталог агентов (`--global`), проект (git-репо в workspace или каталог, где уже работал агент) или цель без git |
| **Цель без git** | Каталог workspace, помеченный `target: true` в своём слое дерева (§6a): miksy пишет ему настройки, как проекту. Частные случаи — **группа** (каталог над проектами) и рабочий каталог без git |
| **Адаптер** | Модуль, переводящий собранный конфиг в файлы конкретного агента (§8) |
| **Собранный конфиг** | Результат склейки всех слоёв цели (`Resolved`) |
| **Учёт** | `local/state/manifest.json`: что miksy записал, с какими хешами (§8.8) |
| **Обёртка, helper, мост** | Сгенерированные скрипты `local/run/…`, через которые агент получает секреты (§8.6) |
| **Выпуск** | Версия движка `X.Y.Z`: тег `vX.Y.Z`; ветка `stable` — последний выпуск, с неё обновляет `miksy update` (§12) |

## 3. Принципы (принятые решения)

1. **Единственный источник истины — конфигурация miksy.** Агенты читают только
   то, что miksy сгенерировал, а не слои.
2. **Собственный формат описания** — с аварийным выходом `raw` для возможностей,
   специфичных для одного агента (§7). Где уже есть общий стандарт (`SKILL.md`,
   markdown-инструкции), он используется как есть.
3. **Нативные файлы агентов — только в целях:**
   - в домашнем каталоге (`~`) — из глобальных слоёв (`map.yaml: global`);
   - в проекте — всё остальное, уже склеенное, через локальные (неотслеживаемые
     git) каналы агента — см. принцип 9, класс «командное».

   Выше проекта (в workspace и промежуточных каталогах) **наследуемых** нативных
   файлов нет — кроме явно помеченных целей (`target: true`, §6a). Так исключается двойная
   загрузка через встроенный в агентов поиск вверх по дереву. Если внутри цели есть
   другие проекты (родительское репо, каталог без git над проектами —
   `Target.nested`), адаптер не пишет туда файлы, которые агент наследует вниз (у
   Claude — `CLAUDE.local.md`); MCP и skills — можно. Цель-группа пишет и
   наследуемые файлы, а цели ниже получают для таких агентов только свой отрезок
   слоёв (правило разности, §6a).
4. **Привязка к путям следует структуре.** Слои организаций и проектов — в дереве
   `layers/tree/`, повторяющем workspace (§6); пути относительны корню workspace (у корня не в
   корне дерева — вместе с его местом, §6b), поэтому на другой машине workspace может лежать где угодно.
5. **Сначала показать, потом записать.** `explain`, `projects`, `skills`, `doctor`,
   `sync --dry-run` и `sync --out` в настоящие конфиги ничего не пишут. `sync`
   меняет только то, что учтено как своё; чужое — конфликт.
6. **Секреты — только ссылками** `${ИМЯ}`. Значений нет ни в слоях, ни в одном
   конфиге агента: только в `local/secrets.env` и `local/secrets/<ИМЯ>` (§8.6).
7. **Миграция без удаления.** Чужой файл, который miksy берёт под учёт,
   сохраняется как оригинал; `clean` возвращает его (§8.9).
8. **Кроссплатформенность:** Windows, macOS, Linux. TypeScript на Bun, только
   встроенные модули Bun/Node, **без npm-зависимостей**. Запуск — `bun src/cli.ts`
   (команда `miksy` — обёртка, которую создаёт `setup`).
9. **Четыре класса содержимого:**
   - *наше* — генерирует miksy: инструкции, MCP, собственные skills;
   - *внешнее* — ставится своим установщиком (наборы skills и т. п.): miksy его
     не копирует и не обновляет; `doctor` справочно показывает глобальные skills не от
     miksy;
   - *агентское* — создано самим агентом (модель, тема, авторизация, встроенные skills
     и MCP, доверие проектов): miksy добавляет только отсутствующее доверие целям, куда
     доставил конфигурацию (§8.7);
   - *командное* — агентный слой, закоммиченный в репо проекта (`AGENTS.md`,
     `.mcp.json`, `.agents/`…): принадлежит команде, miksy его не трогает даже с
     `--force`. Miksy пишет в проект **только через локальные каналы** агента —
     файлы, которые не отслеживаются git. Если у агента такого канала нет —
     предупреждение, а не правка закоммиченного файла.
10. **Владение на уровне ключей.** В общих файлах (`~/.claude.json`,
    `~/.codex/config.toml`, `opencode.jsonc`) miksy меняет только объявленные
    адаптером ключи; в общих файлах инструкций — только свой блок. Целиком
    перезаписываются только файлы, полностью принадлежащие miksy.
11. **Никаких машинных путей в слоях.** Пути вычисляются при генерации под текущую
    машину (`${HOME}`, `${WORKSPACE}`, `vars` машины).
12. **Накопленные allowlists прав не мигрируют** — это состояние сессий, а не
    конфигурация.

## 4. Структура: движок и конфигурация

```
miksy/                   движок (этот репо)
├── DESIGN.md, README.md, LICENSE
├── install.sh, install.ps1  стартовые скрипты: git, Bun, клон движка, мастер setup (§9)
├── src/                   ядро: загрузка, склейка, план и запись, CLI, мост
├── adapters/<агент>/      адаптеры (§8) + CAPABILITIES.md
├── test/                  bun test (песочница — test/preload.ts)
└── examples/
    ├── config/            стартовая конфигурация — из неё setup создаёт новую
    ├── local/             шаблоны machine.yaml и secrets.env
    └── extra/             дополнительные примеры слоёв (группа, trust, MCP с секретами)

miksy-config/            конфигурация пользователя (приватный репо)
├── map.yaml               глобальные слои, особые привязки, skill_prefix, tools (§6)
├── layers/
│   ├── global/, env-*/    → ~ (домашний каталог агентов)
│   └── tree/              → проекты и цели без git; дерево повторяет workspace (§6)
└── local/                 (gitignore) только эта машина:
    ├── machine.yaml       workspace, vars, agents, trust
    ├── secrets.env        значения секретов (ИМЯ=значение; dotenv: export, #, кавычки)
    ├── secrets/<ИМЯ>      файлы секретов для обёрток (создаёт sync)
    ├── run/<агент>/<цель>/ обёртки, helper-ы, запуск моста
    ├── state/manifest.json учёт (+ manifest.json.bak)
    ├── trust.json         решения пользователя о доверии
    └── backups/           бэкапы запусков и originals/
```

Где движок ищет конфигурацию: переменная `MIKSY_CONFIG` → путь из файла
`~/.miksy` → соседний каталог `miksy-config` → сам движок (всё в одном репо).
`miksy setup` создаёт конфигурацию из `examples/config`, если её нет. Корень
конфигурации определяется при каждом обращении (`configRoot()` в `src/load.ts`):
тесты подменяют его, `HOME` и tmp в `test/preload.ts` и не касаются настоящих файлов.
Подпроцессы тестов получают то же песочное окружение и без `env` (`test/guard.ts` подставляет его: Bun на
Windows отдал бы такому подпроцессу исходное окружение — настоящий домашний каталог), git в тестах не
читает настройки машины (системный конфиг выключен, глобальный — пустой файл песочницы), а запуск CLI с
записью мимо песочницы `test/guard.ts` останавливает. Перед изменением движка — `bun test`.

`local/machine.yaml`: `workspace` (строка — один корень, или список корней: путь либо
`{ path, tree }`, §6b), `vars` (пути к программам: `${ИМЯ}` в слоях), `agents` (для них работают
`sync`/`clean`/`doctor` без `--agent`; идентификаторы — `claude`, `codex`, `opencode`, `antigravity`),
`trust` (§8.7). Встроенные переменные: `${HOME}`, `${WORKSPACE}` — основной (первый) корень workspace, у
целей любого корня и в глобальных настройках (§6b).

**Идентификаторы агентов** (`src/agentid.ts`). Прежнее имя — рабочий синоним во всех входных данных:
`gemini` = `antigravity` в `agents` машины, `--agent`, `agents:` в MCP слоёв (`loadLayerDir`; новое имя
важнее прежнего) и в учёте (`normalizeManifest`: записи `gemini|…` переходят к `antigravity|…` со всем
владением). Служебное под новым именем: `local/run/antigravity/`, блок `miksy:antigravity` в
`.git/info/exclude` (блок прежнего имени план считает текущим и заменяет). `doctor` в «Справочно»
перечисляет, где осталось прежнее имя (`legacyAgentNames`). Пути самого агента (`~/.gemini`,
`GEMINI.md`, `GEMINI_CLI_HOME`) — его, не идентификатор.

## 5. Слой

```
<каталог слоя>/
├── layer.yaml             description, exclude, import_skills, trust, target
├── instructions/*.md      фрагменты правил, склеиваются по имени файла
├── skills/<skill>/SKILL.md
└── mcp/<server>.yaml
```

Все части необязательны. Имена `instructions`, `mcp`, `skills`, `hooks`, `policies`
зарезервированы: в дереве `layers/tree/` так нельзя назвать организацию или проект.
`hooks/` и `policies/` **не реализованы**: каталог с ними считается слоем, но
содержимое не читается — `sync` и `doctor` предупреждают (`ignoredLayerParts`).

`layer.yaml`:

| Ключ | Значение |
|---|---|
| `description` | описание (для `explain`) |
| `exclude` | `[mcp.<имя>, skill.<имя>, instructions.<файл>]` — убрать пришедшее сверху (§7) |
| `import_skills` | `auto` (до 30), `all`, список имён или `false` — импорт командных skills (§10) |
| `trust` | `{ claude?: bool, codex?: bool }` — доверие целям слоя (§8.7) |
| `target` | `true` — каталог этого слоя дерева становится целью без git (§6a); ставит и снимает `miksy target` |

Неизвестные ключи YAML не проверяются (схема YAML — не реализована, §11); типы
известных ключей проверяются при загрузке.

## 6. Порядок слоёв: дерево и `map.yaml`

**Дерево.** `layers/tree/` повторяет workspace: корень — слой всех проектов
(`workspace`), `tree/Org/` — слой всего внутри `<workspace>/Org`, `tree/Org/proj/` —
одного проекта. Для проекта `Org/Team/svc` применяются каталоги `tree/` → `tree/Org/` →
`tree/Org/Team/` → `tree/Org/Team/svc/` — те, что существуют и содержат что-то из §5.
Имена сравниваются без учёта регистра. Имя слоя в выводе — путь (`Org/Team`). `doctor`
сообщает о каталогах дерева без каталога в workspace (с подсказкой похожего имени).

**`map.yaml`** — то, что от пути не зависит:

```yaml
global:                    # → домашний каталог агентов, применяется всегда
  - { use: global }
  - { use: env-windows, os: windows }
  - { use: env-macos, os: macos }
  - { use: env-linux, os: linux }
layers: []                 # особые случаи: { match: "<glob>", use: <слой в layers/>, os? },
                           # применяются после слоёв дерева
skill_prefix: miksy-       # префикс своих skills: подсказка adopt (нет — miksy-)
tools:                     # программы машины для ${ИМЯ} в MCP: что ищет setup
  GITHUB_MCP_SERVER: { find: [github-mcp-server], install: { macos: brew install … } }
```

- `match` — glob по месту в дереве (путь от корня workspace; у корня с `tree` — вместе с ним, §6b;
  `/` как разделитель); `os` — `windows`, `macos`, `linux` или список.
- Применяются все слои по порядку: дерево сверху вниз, затем совпавшие записи `layers`;
  нижний слой перекрывает верхний.
- `tools` (`src/load.ts: loadMap`, `src/setup.ts`): для каждой переменной, на которую
  ссылаются MCP слоёв и которой нет в `vars` машины, `setup` ищет команду из `find` в
  PATH и пишет путь в `local/machine.yaml`; не нашёл — показывает `install` для ОС.
  Встроен только `PYTHON` (`python3`/`python`); `tools` его перекрывают. Переменная не
  из `tools` и не из `vars` считается секретом.
- `packs` (слои по стеку проекта) — **не реализовано и не планируется**; ключ
  игнорируется.
- **Проект** — ближайший git-корень вверх от указанного пути (в пределах его корня workspace);
  если его нет — сам каталог. Подкаталог проекта получает конфиг своего проекта. Путь
  сравнивается с корнями после realpath (симлинк наружу — «вне workspace»). Сам корень — не цель:
  `sync` без пути (текущий каталог) и `sync <корень>` отказывают с подсказкой (`--all`, `--global`). Без
  пути цель ищется строже (проект или цель `target: true` вверх от текущего каталога, §6b).
- **Обход workspace** (`listProjects`, по каждому корню): git-репо до глубины 6, кроме скрытых каталогов,
  `node_modules`, `worktrees`, `dist`, `build`, `vendor` и служебных каталогов miksy
  (`out/`, `local/`, `dist/` движка и конфигурации); плюс каталоги, где уже работал
  агент (`Adapter.knownDirs`). Нечитаемые каталоги пропускаются с предупреждением.
- **Вложенные проекты** (`nested`): внутри цели есть git-репо. Каталог без git и без
  проектов внутри остаётся целью; секреты в его файлах ничем не защищены — `sync`
  предупреждает, `doctor` показывает справочно.

## 6a. Цели без git (`target: true`)

**Слой ≠ цель.** Слой — источник (`layers/tree/Org/`), цель — куда пишем
(`<workspace>/Org/`). Проекты miksy находит сам (git-репо и каталоги из реестров проектов
агентов, `knownDirs`); любой другой каталог workspace становится **целью без git** пометкой
`target: true` в `layer.yaml` своего слоя дерева (`treeGroups`, `listGroups`; в коде — `Group`,
`Target.group`). Частные случаи: **группа** — каталог над проектами (`~/Projects/Acme`, задача на
несколько репо; `Target.nested`), и рабочий каталог без git (`~/Projects/Acme/MyTasks`). Цель получает
слои от workspace до своего уровня включительно (дерево по её пути + совпавшие `map.yaml`), без
слоёв ниже; git не нужен. Пометка не действует (предупреждение в `projects`, `sync --all`,
`doctor`), если каталога нет, это служебный каталог miksy, каталог выходит за свой корень workspace или
содержит домашний, лежит внутри проекта, путь ведёт через симлинк, это корень дерева или сам корень
workspace. Каталог ищется во всех корнях, смонтированных на это место дерева или выше (§6b).
Git-репо с вложенными проектами тоже можно пометить.

Цель без git — обычная проектная цель: все агенты, MCP с обёртками, skills, доверие; exclude —
только если она сама git-репо. Цели `sync --all` — помеченные сверху вниз, затем проекты
(`allTargets`). В выводе помеченный каталог с проектами внутри — «группа», без них — «цель без
git» (`markedKind`).

**`miksy target [<путь>] [--remove] [--dry-run]`** (`src/target.ts`) ставит и снимает пометку:
путь (без пути — текущий каталог) → `layers/tree/<место в дереве>/layer.yaml` (§6b); существующие
каталоги слоёв — без учёта регистра, как `treeLayers`. Файл правится строкой: нет — создаётся,
есть — дописывается `target: true` (`target: false` меняется на `true`), снятие убирает строку;
комментарии, порядок и остальные ключи остаются (проверка разбором до записи; пометку, которую
строкой не изменить, — вручную). Пустой после снятия файл и опустевшие каталоги слоя удаляются.
Ошибка — путь вне всех корней workspace, сам корень, внутри git-репо проекта, проект (git-репо без
вложенных проектов), служебный каталог, каталог с домашним, зарезервированное имя слоя. После
пометки — вопрос (Enter — «да») о `sync` цели, у группы — `sync --all` (правила Claude целей ниже
пересчитываются с отрезком); без терминала — подсказка команды. После снятия — как у бывшей
группы: `clean` каталога (у группы — `sync --all`, он убирает её файлы по учёту и пересчитывает
цели ниже). Каталог, где агент работал сам (запись в его реестре проектов не только от miksy),
и без пометки остаётся проектом — об этом предупреждение. Запись `projects[<путь>]` в
`~/.claude.json`, созданную самим sync (доверие), `clean` убирает (§8.8) — такой каталог перестаёт
быть проектом.

**Каталоги без git на уровне проектов** (`plainDirs`) — их легко не заметить: агент там без
правил и MCP. Уровень проектов — непосредственные подкаталоги корня workspace, а также
каталогов слоёв дерева и групп, если в них есть проекты (`containsProjects`): рядом с
проектами. Не считаются: скрытые (`.…`), системные и служебные (`SKIP_DIRS` — `node_modules`,
`dist`, `build`, `vendor`, `worktrees`; `$…` и `System Volume Information` корня диска;
служебные каталоги miksy), ссылки, сами каталоги слоёв дерева (организации — их настраивают
явно), git-репо и каталоги с git-репо внутри, цели (помеченные и проекты из реестров агентов),
всё внутри git-репо (кроме корня workspace). Каталоги внутри цели без проектов (подкаталоги
рабочего каталога) — не уровень проектов. `sync --all` печатает их одной строкой, `doctor` — в
«Справочно» (не проблема), с подсказкой `git init` или `miksy target <путь>`.

**Наследование агентами** (проверено вживую, CAPABILITIES):

| Агент | Правила | Skills | MCP |
|---|---|---|---|
| Claude | все родительские каталоги, склеиваются | родители до git-корня (без git — все), одноимённый — ближний | только точный путь |
| opencode 2.x | относительный `instructions` — только каталог сессии | все родители; ближний | `opencode.json` всех родителей сливаются; ближний |
| opencode 1.x | без git — `.opencode/miksy.md` всех родителей; git — до корня | так же | так же |
| Codex, Antigravity | без git — только cwd; git — до git-корня | так же | только cwd / доверенный путь |

Адаптер объявляет это `inherits(target): { rules?, skills?, mcp? }`.

**Правило разности.** Для агента с `inherits.rules` (Claude) цель ниже групп получает
только свой отрезок: слои между ближайшей группой выше (не включая) и собой (включая);
без групп выше — от workspace. Ядро считает отрезок (`Resolved.below`) и подставляет
адаптеру `instructions` и `layers` отрезка (`renderFor`); остальное — полный набор.
Сливаемое по имени (skills, MCP) — полным набором; исключённое `exclude` в отрезке всё
равно придёт из файла группы — `Below.leaked`, предупреждение «exclude … не действует для
<агент>» (по всем группам выше). opencode получает полную цепочку правил (в 2.x
относительный путь читается только из каталога сессии); в 1.x во вложенной группе без
git правила групп выше придут дважды — известное ограничение.

Пример: группы `Acme` и `Acme/US`, проекты `Acme/US/infra` и `Personal/site`.

| Цель | Слои правил Claude в её `CLAUDE.local.md` |
|---|---|
| `Acme` (группа) | workspace + Acme |
| `Acme/US` (группа) | US |
| `Acme/US/infra` (проект) | infra |
| `Personal/site` (групп выше нет) | workspace + Personal + site |

**Группа выше без правил.** `groupRulesDelivered(adapter, manifest, dir)` — файл правил
группы (`Adapter.rulesFiles`: у Claude `CLAUDE.local.md`, `.claude/rules/miksy.md`) в
учёте и на диске, блок разбирается и хеш совпадает. Если ближайшая группа правила не
получила, цель берёт отрезок от ближайшей группы, у которой они есть (или полную
цепочку), и `sync <цель>`/`doctor` предупреждают (`unsyncedGroups`). В `--dry-run` —
по плану группы этого запуска.

**Снятая пометка.** Учёт помнит группы (`TargetState.group`, ставит `sync` группы,
снимает `sync` обычной цели; `clean` — нет). `formerGroups` — записанные как группа без
пометки: `sync --all` убирает их файлы по учёту до остальных целей, `sync <цель>` и
`doctor` предупреждают.

## 6b. Несколько корней workspace

**Модель.** `workspace` в `local/machine.yaml` — строка (один корень в корне дерева, как раньше) или
список; элемент — путь или `{ path, tree }`: `tree` — ветка корня в дереве слоёв (`E:/Clients` →
`Clients`). Первый корень — основной: без `tree` — корень дерева. Дерево одно на все корни:
`layers/tree/instructions/` — для всех, `layers/tree/<tree>/…` — для своего корня. Конфигурация от машины
не зависит (на другой машине тот же `Clients` лежит в другом пути). Две копии miksy задачу не решали бы:
глобальные файлы агентов общие. Разбор и проверка — `parseRoots` (`src/load.ts`); добавить и убрать
корень — `miksy root add|remove` (правит только ключ `workspace`, `src/rootfile.ts`).

**Ветка обязательна и своя.** У дополнительных корней `tree` обязателен, у всех корней ветки разные (без
учёта регистра) — иначе ошибка загрузки. Цель — чтобы правила не перетекали между корнями **молча** из-за
совпадения имён папок: папка `Acme` в основном корне не должна получить MCP с токенами из
`layers/tree/Acme/`, задуманные для корня клиентов. Общее для нескольких корней — явно: корень дерева,
глобальный слой или именованный слой `map.yaml` (`match: "{Clients,Archive}/Acme/**"`).
**Совпадение ветки с папкой другого корня** (ветка `Clients` у корня, а в основном корне есть папка
`Clients`; вообще — место ветки корня занято существующим каталогом другого корня, `treeClashes`) —
предупреждение: проблема в `doctor`, строка в `sync` (`--all` и цели в этом месте), `projects`, `root add`.
Исключение — вложенный корень на своём естественном месте (ветка = его путь во внешнем корне): это он сам.

**Две функции** (`src/roots.ts`; на них же ляжет будущий каталог workspace):
- `locate(путь, корни)` — путь → корень, путь от корня (`rel`) и **место в дереве** (`tree` + `rel`).
  Корень — самый глубокий из содержащих путь (realpath). Место в дереве — то, что раньше было «путём
  от workspace»: по нему выбираются слои (`treeLayers`), `match` в `map.yaml`, заголовок цели, `adopt
  --to`, `target`.
- `dirsOf(место, корни)` — обратно: каталоги этой машины для места в дереве — по каждому корню, чьё
  место — это или выше; имена без учёта регистра (как `treeLayers`); каталог, который относится к более
  глубокому корню, — не этого корня. Им пользуются группы (`listGroups`) и `treeClashes`; `orphanTreeDirs`
  и `plainDirs` идут по тем же правилам. Пути внутри корня строятся `child()` (`src/paths.ts`): корень на
  корне диска (`D:/`, `/`) не даёт `D://x`, который не совпал бы с `D:/x`. Косая в конце пути срезается
  одной функцией `trimSlash` — кроме корня (`/`, `X:/`); `X:` без косой — корень диска (`driveRoot`), а не
  текущий каталог диска (так его понял бы `resolve` на Windows): мастер, `machine.yaml`, `target`, `clean`.

**Исключения и почему так:**
- **Вложенные корни** — разрешены: каталог относится к самому глубокому; обход внешнего корня
  (`reposUnder`, `plainDirs`, `orphanTreeDirs`) внутренний пропускает — иначе один проект попал бы в два
  места дерева. Законный сценарий — одна облачная папка на двух машинах: на одной лежит отдельно, на другой
  клиент облака положил её внутрь основного корня; вложенный корень «перевешивает» её в ту же ветку, и
  конфигурация общая. Простое вложение — справка (`explain`: «внутри корня …», `doctor` — «Справочно»,
  `projects` — у корня). Слои внешнего и внутреннего места не суммируются (решено): у папки одно место.
- **Один каталог дважды** (повтор в другом написании, junction, симлинк) — сравнение настоящих путей при
  загрузке, ошибка «корень … указан дважды (… — один и тот же каталог)»: цели и учёт задвоились бы.
- **Корень внутри git-проекта** другого корня и **внутри его группы** — предупреждение (`rootNotes`:
  `projects`, `sync --all`, `root add`, «Справочно» `doctor`), не ошибка: машина пользователя — его выбор, а
  последствия (файлы в чужом репо без exclude; правила группы, которые Claude прочитает сам) названы.
  Корень = домашний каталог или его родитель — как раньше: подтверждение `sync --all` (`unsafeWorkspace`,
  по каждому корню); проект, содержащий дом, отклоняется.
- **`target: true`** действует по месту в дереве; корень сам целью не бывает (пометка его места —
  предупреждение).
- **`${WORKSPACE}`** — всегда основной корень: у целей любого корня и в глобальных настройках, как до
  нескольких корней — смысл переменной не «плавает» от цели к цели. Путь в другой корень — своей
  переменной в `vars` (`CLIENTS: "E:/Clients"`); на машине без неё сервер пропускается с сообщением.
  `adopt` сворачивает в `${WORKSPACE}` только пути основного корня (и не путь во вложенный корень) при
  любом `--to`, по границе имени (`D:/Work` не задевает `D:/Work2`); пути в другие корни — как есть, с
  подсказкой завести переменную.
- **Группы и «Claude читает родительские каталоги»** — в пределах корня цели: `Resolved.below` считают
  группы того же корня. Вложенный корень внутри группы внешнего получает полную цепочку своего места,
  а `rootNotes` предупреждает, что Claude прочитает и файл группы. `nested` (внутри есть проекты) —
  физически, как раньше: файлы, которые агент наследует вниз, не пишутся над любыми проектами.
- **Недоступный корень** — нет каталога, нет диска (нет даже корня диска: отключённый сетевой диск, не
  запущенное облачное хранилище), ссылка или junction ведёт в никуда, путь не каталог. Загрузка не падает:
  корень помечается `away` (с причиной), остальные команды работают. Обход пропускает его с
  предупреждением; учёт его целей не «пропал» — не переносится (`loadManifestMoved` считает такие каталоги
  существующими), не попадает в «Учёт ссылается на несуществующие каталоги» (в «Справочно» — отдельной
  строкой) и не снимается `sync --all` как бывшая группа. Мастер такой путь добавляет как есть.
  *Путь недоступного корня.* Учёт хранит цели по настоящим путям; у корня-ссылки это путь назначения, а
  `resolve(путь из machine.yaml)` дал бы путь самой ссылки — цели не нашлись бы под корнем и стали бы
  «пропавшими». Поэтому учёт помнит последний известный настоящий путь каждого корня (`manifest.roots`:
  путь, как записан, → realpath; обновляется в памяти при каждом чтении учёта командой; `sync` и `clean`
  без `--dry-run` сохраняют учёт и тогда, когда цели не изменились, если запомненное разошлось с диском). Это надёжнее, чем раскрывать битую ссылку (`readlink`): работает и для смены регистра на macOS,
  и для junction с префиксами `\??\`, и для цепочек ссылок. Целей под корнем в учёте не бывает без записи
  в момент, когда корень был доступен, — а эта же запись запоминает его путь. Учёта нет или в нём нет
  корня — путь как записан.
  Пути корней и каталоги обхода сравниваются `sameKey` (`src/paths.ts`): путь, который не раскрывается,
  — как записан, без отказа (`samePath` бросил бы исключение и уронил `projects`, `doctor`, `sync`).
  Недоступный основной корень: `plan` не канонизирует `${WORKSPACE}` (`pathKey`) — запись остальных целей
  работает.
- **Ветка внутри чужого места** — справка с рекомендацией, не проблема (решение владельца): место-предок
  ветки (кроме корня дерева — он общий по замыслу) со своими слоями или с каталогом другого корня — ветка
  другого корня (`tree: Clients/Sub` при `tree: Clients`) или папка основного (`tree: Org/Sub` при папке `Org`).
  Проекты такого корня получают слои предка: правила не суммируются, у проекта одна цепочка слоёв по месту
  в дереве, общее с другим корнем — места выше точки ветвления. Справка (`branchNote`) перечисляет, что
  унаследуется (правила, MCP, skills слоёв предка — без рендера целей), и советует ветку вне предка и общее —
  слоем `map.yaml`; где — `root add`, «Справочно» `doctor`, `explain` проекта. Вложенный корень, физически
  лежащий в каталоге своего места-родителя, — его естественное место, не справка. Точное совпадение ветки с
  папкой — по-прежнему предупреждение (`treeClashes`).
- **Пустая точка монтирования** (`/mnt/data` есть, диск не смонтирован): «каталога нет» не скажешь, а
  обход нашёл бы ноль проектов — и `sync --all` счёл бы группы бывшими, `doctor` — цели пропавшими. Поэтому
  корень, в котором нет ничего, кроме скрытых записей, **а в учёте есть цели под ним**, считается
  недоступным («пуст, а в учёте есть его цели — диск не смонтирован?»). Пустой корень без целей в учёте —
  обычный пустой корень. Ограничение: если пользователь сам удалил всё содержимое корня, miksy будет
  считать его недоступным, пока цели не убраны из учёта (`miksy clean <путь> --forget`).
- **`clean` каталога, до которого не дотянуться** (`stranded`: под недоступным корнем или вне всех корней и
  каталога нет — после `root remove` неподключённый диск не отличить от удалённых данных). Учёт цели
  делится (`splitState`) на записи внутри каталога (far: файлы, блоки, слияния в файлах проекта, exclude,
  одобрения) и остальные (near: ключи MCP в домашних конфигах, доверие Claude, обёртки `local/run`). `clean`
  убирает near; far **оставляет** — по путям и хешам miksy узнает свои файлы, когда диск вернётся, и
  повторный `clean` их уберёт (изменённое пользователем — нет), — и пишет, сколько осталось и как убрать.
  «Данных больше нет» — `--forget` или «да» на вопрос в терминале (по умолчанию «нет»: потерять владение
  хуже, чем подождать): far стирается целиком, «отпечатков» не остаётся. **Отметка «проект забыт»** (круг 6x,
  `manifest.forgotten`, ключ — как у цели): учёт помнит только факт и, для Claude, ставил ли miksy доверие
  (`trusted`: ответы пользователя в окне Claude — его, §8.7) — без файлов, хешей и оригиналов; ставит её «забыть»
  цели, у которой на недоступном диске было что забывать (`clean --forget`, `root remove --forget`, «да» на
  вопрос; не `--dry-run`). Только с ней план убирает файлы miksy без учёта, которые miksy больше не пишет (ниже).
  Снимает её первый `sync` или `clean` этой цели, дошедший до проекта (каталог доступен — не `stranded`: `clean`
  недоступного каталога, у которого на диске уже нет записей, до проекта не доходит; не `--dry-run`, без ошибки
  цели) — вместе с отметками того же каталога у агентов, которых больше нет в `agents` (их цели не обходятся, и
  отметка сработала бы через месяцы, когда агента вернут); при переезде каталога (§8.8, `applyMoves`) отметка
  переезжает с ним. К этому
  моменту план с отметкой уже убрал ненужное по уликам, совпадающее взял, отличающееся показал конфликтом, а
  дальше у проекта снова есть учёт (или он чист) — работают обычные правила; повторный `sync`/`clean` — «изменений
  нет». Выбор «первый `sync` или `clean`», а не «только `clean`»: проект, который продолжают использовать, иначе
  держал бы отметку навсегда. Навсегда она остаётся только у проекта, чей диск так и не вернулся (или чей корень
  не вернули в workspace). 0.1.x отметку не знает и, записав учёт, стирает (README, «Откатиться»). `root remove` недоступного корня —
  тот же вопрос (один на корень) или `--forget`; без согласия корень убирается, учёт его целей остаётся.
  Каталог удалён при доступном корне — данных точно нет, забывается без вопроса (как раньше). `doctor`
  показывает оставленное («Учёт целей недоступного корня»; цели вне всех корней без каталога — нейтрально:
  «каталога нет — диск не подключён или папку удалили») с обеими подсказками; слияния целей под недоступным
  корнем не проверяет («Ключи пропали» было бы ложным). После «забыть» сообщение говорит, как вернуть файлы
  под учёт, если диск найдётся: `sync` проекта (корень в workspace), а если корня уже нет (`root remove`, цель
  вне всех корней) — сначала `root add <путь> --tree <ветка>` (`sync` вне workspace не работает); не нужны —
  затем `clean` или `root remove` с согласием. `clean` без учёта уберёт только файлы с меткой под точной строкой
  exclude (ниже) — поэтому сначала `sync`. Готовую команду `root add` с путём и веткой печатает `root remove
  --forget` (корень он знает); `clean … --forget` цели вне всех корней печатает шаблон: какой корень был у
  цели и его ветку учёт не хранит (`manifest.roots` помнит только нынешние корни). **«Забыть» значит забыть**
  (решение 6w): оригиналы забываемых целей (miksy когда-то заменил файлы пользователя) сами на место не
  вернутся — сообщение «забыто» говорит, сколько их и что копии остаются в `local/backups/originals/`
  (`strandedText`). `root remove <недоступный корень> --dry-run` показывает план: почему корень недоступен,
  будет ли вопрос (в терминале) и что останется в учёте; с `--forget` — по проектам, как `clean … --forget
  --dry-run`, и итог.
  Диск нашёлся после «забыть»: учёта нет, но файл проекта, явно сделанный miksy, узнаётся (`miksyMade`, только
  улики самого miksy, решение 6v): шапка «Сгенерировано miksy» в начале файла (`src/marks.ts: headerMark`);
  у файла с блоком инструкций — блок miksy как блок (пара маркеров на своих строках); собственный
  `opencode.json` — только `$schema`, `instructions` → `.opencode/miksy.md`, `mcp`, не отслеживается git
  (`miksyOpencodeJson`; адаптер opencode считает такой файл своим, если серверы в нём — те, что miksy пишет
  сейчас, или файл скрыт строкой блока miksy opencode, а учёт о файлах цели ничего не помнит — набор серверов
  мог измениться, пока диск был отключён; отслеживаемый git — всегда файл команды); файл без метки (skills,
  `plugin.json`, `mcp_config.json` плагина) — только если его текст тот же, что miksy записал бы сейчас, **и**
  его покрывает строка блока miksy этого агента в `.git/info/exclude` проекта (блок остаётся на диске после
  «забыть»: до него miksy не дотянулся), **и** учёт ничего не помнит о файлах цели в проекте (`fresh`): когда
  учёт цели есть, незаписанный файл под строкой каталога (`/.claude/skills/sk/`, `/.agents/plugins/miksy/`
  скрывают весь каталог) — файл пользователя, например его заметки в каталоге skill, позже перенесённые в слой.
  Путь (каталог `.agents/plugins/miksy/`) и совпадение текста сами по себе — не улика: такой файл мог положить
  пользователь (принял skill через `adopt`, положил свой файл в каталог плагина) — он берётся с оригиналом,
  `clean` его вернёт. Домашние файлы не узнаются вовсе (забыть можно только цель проекта); в цели без git нет
  exclude — файлы без метки там не узнаются (README: убрать вручную). `doctor` не считает «добавкой агента»
  skill, чей каталог скрыт строкой блока miksy (после «забыть» до `sync`). Узнанный файл, совпадающий с выводом, `sync` **берёт обратно сам** (`adopt`/
  `block` с `known`, строка «взять под учёт — файл (блок) miksy, которого не было в учёте»), блок инструкций —
  так же; отличающийся — конфликт «файл (блок) miksy, которого нет в учёте, отличается…», `--force`
  перезаписывает с бэкапом. Узнанный берётся **без оригинала** (восстанавливать нечего — иначе `clean` вернул
  бы на место сгенерированный файл). Решение владельца — удобство: при таких уликах ошибиться можно разве что
  на файле, который записал miksy (здесь или на другой машине); содержимое при взятии не меняется, удаляет
  только явный `clean` с бэкапом. Не узнаются файлы без метки, которые с тех пор поменялись или пропали из
  вывода (skill, изменённый или убранный в слоях; свой `opencode.json` без инструкций) — README говорит убрать
  вручную (решение 6w: так и оставить). **Файл (блок) miksy без учёта, который miksy больше не пишет**
  (решение 6w, A.3: слои поменялись, пока диск был отключён; в проекте появился вложенный репо) — **только в
  проекте с отметкой «проект забыт»** (круг 6x, A.2: учёт у каждой машины свой, а `.git/info/exclude` одной
  облачной папки проекта на двух машинах — общий, и файл, записанный miksy другой машины, выглядит так же; машина,
  которая его не пишет, удаляла бы его, а другая писала бы снова) — убирается,
  как свой ненужный: `delete` / `block` без хеша с `known`, бэкап, строка «удалить … (файл miksy, которого не
  было в учёте, — больше не нужен)»; у блока — только блок, текст вне блока остаётся. Улики — обе сразу: блок
  miksy как блок или шапка в начале файла, **и** точная строка этого файла в блоке miksy этого агента в
  `.git/info/exclude` (её miksy пишет только для своего файла); файл не отслеживается git, не во вложенном
  репо, не ссылка, не в учёте другой цели. Без точной строки (файл скопирован из другого проекта, строка
  каталога, цель без git) и домашние файлы — не трогаются. Строка уходит вместе с файлом (у удаляемого — после
  удаления). `clean` цели, о которой учёт ничего не помнит, делает то же по тем же уликам (вывод miksy не нужен),
  а остальные строки блока exclude не трогает: файлы без метки без вывода miksy не узнать, а снятые строки
  открыли бы их git; оставшиеся строки в учёт не пишутся (`exclude` с `unrecorded`) — цель остаётся «без учёта»,
  и повторный `clean` их тоже не снимет. У файлов плагина Antigravity точной строки нет (каталог
  `.agents/plugins/miksy/` скрыт одной строкой): ненужные файлы плагина после «забыть» не убираются — пока
  строка каталога нужна взятым файлам плагина, они скрыты и Antigravity их читает; после `clean` git их видит
  (README: удалить вручную; рецензия 6w, вынесено владельцу). **Узнанный файл — свой и для проверки доверия** (`trustPlan`: действия с `known` — взять,
  перезаписать, конфликт, убрать): его прежний текст — не «конфиг Codex не от miksy», вопроса о доверии нет, а
  доверие встаёт в том же `sync --force`, который файл перезаписал. **Одобрения серверов `.mcp.json`** (решение
  6w, A.4): учёт их забыл, а файл одобрений `.claude/settings.local.json` покрыт точной строкой блока miksy claude
  (её miksy пишет, только пока в файле его одобрения) и не отслеживается git — одобренные в нём серверы
  командного `.mcp.json`, которые miksy одобрил бы сейчас (основание — `trust: true` в слое или «да»
  пользователя; отпечаток решения сверяется так, будто они свои), берутся обратно: в учёт (`approve` с `known`,
  «взять под учёт — одобрения miksy, которых не было в учёте»), файл не меняется, строка остаётся; `clean` потом
  снимает их как обычно. Без основания или без строки — чужие (одобрения пишет и сам Claude, когда пользователь
  одобряет сервер в его окне). Одобрение пользователем тех же серверов в окне Claude от одобрения miksy без учёта
  не отличить — оно тоже берётся (решение A.4; README говорит, что `clean` его снимет). **Строки exclude
  узнанных файлов, которые план пишет, но не берёт** (конфликт с нынешним выводом), не снимаются (решение 6v):
  снять — открыть git сгенерированный файл, и его можно закоммитить в чужой репо. Новых строк для них miksy не
  добавляет. Строка каталога, в котором лежит чужой конфликтный файл, сужается до строк файлов miksy из учёта и
  взятых планом: чужой файл виден git (С8); узнанный файл вне учёта точной строки при этом не получает (точная
  строка — улика «файл miksy», по ней ненужный файл с меткой убирается; рецензия 6w: иначе файл пользователя с
  шапкой в каталоге плагина получил бы её и был бы удалён следующим `sync`). Узнанный файл, которого нет в
  выводе: в забытом проекте с меткой под точной строкой его план убирает; `sync` проекта без отметки его точную
  строку оставляет (файл miksy другой машины в общей облачной папке: снять строку — открыть его git; круг 6x);
  под строкой каталога и при `clean` своей строкой не держится. `root remove` недоступного корня, лежащего внутри другого корня,
  без «забыть» корень не убирает: его каталоги стали бы каталогами доступного внешнего корня, где «каталога
  нет» значит «удалён», и учёт забылся бы без вопроса (`clean`, бывшие группы в `sync --all`).
- **Корень убран из `workspace`** (`root remove` или правка файла): его цели учёта — «вне workspace»:
  `sync --all` их не трогает (и не снимает как бывшие группы), `doctor` перечисляет справочно, `clean
  <путь>` убирает записанное по учёту (`vanishedTarget` — и для существующего каталога вне корней; путь в другом
  регистре; путь через корень-ссылку в никуда, как он записан в `machine.yaml`, — по запомненному пути
  назначения корня).
  `root remove` основной корень не убирает (на нём `${WORKSPACE}` и ветка без префикса; сменить —
  `setup --force`); записанное в проекты убираемого корня — `clean` с согласия в терминале, без терминала —
  подсказка команд. Остался один корень без ветки — `workspace` пишется строкой, как в мастере (0.1.x список
  не понимает).
- **Откат на 0.1.x** (решение владельца: рецепт в README, команды `downgrade` в 0.2.0 нет). 0.1.x не знает
  списка корней, веток и имени `antigravity`: до переключения новой версией — корни убрать, ветку основного
  снять, `gemini` вернуть, записанное Antigravity убрать (`clean --agent antigravity`); затем 0.1.x пишет его
  заново под своим именем без конфликтов. Проверено тестом настоящим движком v0.1.1 (`test/downgrade.test.ts`,
  тег разворачивается во временный каталог; без тега — пропуск). Недоступный корень до отката: 0.1.x не знает
  «недоступен» и снимет записанное в его группы как бывшие — README советует подключить диски или отложить
  откат. **Учёт новее движка** (`newerLedger`,
  `manifest.engine` — номер X.Y.Z из `package.json`, поэтому сборка `0.2.0-3-g…` не «новее» выпуска 0.2.0) —
  сообщение со ссылкой на README «Откатиться», запись **не блокируется**: рецепт отката заканчивается `sync`
  прежней версией, а учёт совместим вперёд — чужое не перезаписывается, лишние поля прежняя версия
  отбрасывает.
- **`doctor`** («лишние» каталоги дерева, `orphanTreeDirs`) проверяет только ту часть дерева, куда
  смонтированы корни этой машины; ветка, над которой нет корня, — справочно «для других машин», часть
  недоступного корня — не проверяется. Мастер `setup` не спрашивает секреты и программы MCP для слоёв,
  которые здесь ни к чему не применяются (`applicableLayers`: глобальные и привязки `map.yaml` этой ОС,
  корень дерева, слои дерева с каталогом в корнях машины).
- `explain` показывает корень и место в дереве; путь вне всех корней — глобальный срез; сам корень —
  его слои без цели. `projects` перечисляет корни, `sync --all` — их в заголовке.
- Мастер после основного корня спрашивает «Есть ещё папки с проектами?» (путь и ветка: Enter — имя папки,
  `suggestTree`; повтор и занятая ветка — не добавляются; каталога пока нет — добавляется: его пропускают,
  пока не появится); `--yes` не спрашивает. Один корень пишется строкой, несколько — списком;
  `setup --force` сохраняет ветку основного корня и форму записи (список); основным выбран бывший
  дополнительный корень — он уходит из дополнительных (иначе один каталог дважды) и сохраняет **свою**
  ветку (его проекты получали слои своей ветки). Недоступный основной корень мастер не создаёт
  (`mkdirSync` упал бы), а только предупреждает; файл записывается.

**`sync` без пути** (и `sync --out` без пути) — только то, что и так цель: проект (git-репо или каталог из
реестра проектов агента) или цель `target: true` — от текущего каталога вверх до корня, ближайшее. Корень,
каталог без git, который не цель, и каталог вне workspace — ошибка с подсказкой (`git init`, `miksy target`,
`--all`, `--global`, `miksy root add .`), без записи: новую цель создают явно. `root add .` советуется,
только если каталог не содержит корень (иначе корнем стал бы весь диск, а прежний — вложенным) и не дом и
не корень диска. В git-репо (или его подкаталоге) вне workspace — не `root add .` (корнем репо стал бы папкой с
проектами, а не проектом), а корнем папку, в которой репо лежит (`outsideRepoAdvice`), или, если она — диск, дом
или каталог всех пользователей, перенести репо в папку с проектами (круг 6y, рецензия 6x B3). `root add` каталога,
который сам проект (`projectRoot`: git-репо без проектов внутри, проект или группа другого корня, каталог с учётом),
— справка с верной командой; в терминале вопрос («нет» по умолчанию), без терминала — ошибка использования без
`--yes` (предсказуемо и безопасно: корень не меняется молча). Добавленный всё же: учёт цели, чей каталог теперь
корень (`rootedTargets`), — предупреждение `sync --all` и проблема `doctor` с советом (`root remove` — его
собственный каталог `root remove` не убирает и не забывает; `clean`). Служебный каталог miksy (`serviceDir`: `out/`, `local/`, `dist/` движка и конфигурации —
их пропускают `projects`, `sync --all`, `target`) без пути — ошибка у `sync`, `--out` и `explain`. Подмены
на `--global` нет — это осознанное действие. Явный путь — как в 0.1.1: `sync <каталог без git, не цель>` —
запись с предупреждением, что `sync --all` его не обновит; явный путь в служебный каталог — запись, как и
раньше.

## 7. Правила склейки

| Сущность | Как склеивается |
|---|---|
| Инструкции | Конкатенация по порядку слоёв, внутри слоя — по имени файла |
| Skills | Объединение по имени; одноимённый skill нижнего слоя заменяет верхний |
| MCP | Объединение по `name`; нижний слой заменяет определение целиком |
| Исключение | `exclude` в `layer.yaml`; действует на пришедшее из слоёв выше, не на своё |
| Ограничение по ОС | `os: [windows]` в MCP — на других ОС сервер пропускается |
| `trust`, `import_skills` | Самый конкретный слой, где задано |

Формат MCP-сервера:

```yaml
name: gitlab
command: npx                 # либо url: для удалённых (HTTP) серверов
args: [-y, "@zereight/mcp-gitlab"]
env:
  GITLAB_PERSONAL_ACCESS_TOKEN: ${ACME_GITLAB_TOKEN}
headers: { … }               # только для url
os: [windows, macos]         # необязательно
agents:                      # необязательно
  claude: { raw: { … } }     # подмешивается в нативный конфиг как есть
  antigravity: skip          # этому агенту не подключать (прежнее имя gemini — синоним)
```

Переменные `${ИМЯ}` разбираются в `command`, `args`, `url`, `env`, `headers` и
`agents.*.raw` (`src/vars.ts: substitute`). Встроенные (`${HOME}`, `${WORKSPACE}`) и
машинные (`vars`) подставляются значениями. **Секреты** (`local/secrets.env`) — ссылками
`secretRef(ИМЯ)` (метка с NUL, без значения): адаптер доставляет секрет механизмом агента
(§8.6). Серверу не хватает переменной или его секрет нельзя доставить выбранным способом —
пропускается **только он** («пропущен сервер …», не конфликт); уже записанное раньше
определение остаётся как было (`RenderResult.keep`) вместе с его обёрткой. Сервер со
`skip` для агента у этого агента переменных не требует.

## 8. Контракт адаптера

Адаптер **не пишет на диск сам**. Он получает собранный конфиг и возвращает список
файлов; план, запись, учёт, бэкапы, доверие — забота ядра (`src/apply.ts`,
`src/trust.ts`, `src/manifest.ts`).

### 8.1. Типы

Актуальные типы — `src/adapter.ts`, `src/types.ts`. Суть:

```ts
interface Adapter {
  id: string;                                   // "claude", "codex", "opencode", "antigravity"
  render(cfg: Resolved, target: Target, machine: Machine, ctx?: RenderContext): RenderResult;
  nativeMcp(s: McpServer, launch?: Launcher): object | null; // MCP в формате агента (null — skip);
                                                // секрет — только через launch, иначе DeliveryError
  current?(target, machine): CurrentState;      // что агент видит сейчас (doctor, adopt, --out)
  skillDirs?: string[];                         // где агент САМ находит skills проекта
  internalMcp?: string[];                       // свои MCP агента — doctor их не показывает
  knownDirs?(machine): string[];                // каталоги, где агент уже работал
  inherits?(target): { rules?; skills?; mcp? }; // что агент читает из родительских каталогов (§6a)
  rulesFiles?: string[];                        // файлы правил, наследуемые вниз
  httpSecrets?: "helper" | "file" | "bridge";   // как агент получает секрет заголовка HTTP
  homeConfig?: string[];                        // глобальные файлы настроек агента (от ~): копия setup
}

type Target =
  | { scope: "global" }                         // глобальные слои → ~
  | { scope: "project"; dir; rel; nested?; git?; group? };

interface RenderContext { ownedFiles: string[]; keep?: string[]; launch?: Launcher;
  skipped?: SkippedMcp[]; deliveredSkills?: string[] }

interface RenderResult {
  files: RenderedFile[]; warnings: string[];
  keep?: string[];      // пропущенные ядром MCP: записанное не удалять
  noKeep?: string[];    // адаптер запрещает keep (opencode: {file:} без файла ломает весь конфиг)
  clean?: boolean;      // явная очистка
  // заполняет ядро: secrets, servers, advice, trust, trustPending
}

type RenderedFile =                             // base: "home" | "project" | "local" (local — только own)
  | { base; path; mode: "own"; content; block?; executable?; team?; sensitive?; mcp?: { format; key } }
  | { base; path; mode: "merge"; format: "json" | "toml"; key: string[]; data; optional?; sensitive?; secretKeys? };
```

- `own` — файл целиком (`block: true` — только управляемый блок в общем файле
  инструкций, §8.4); `merge` — ключ `key` в общем файле, `data` — объект, которым
  miksy владеет поимённо; `optional` — не создавать, если родителя по `key` нет.
- `path` — относительно `base`. Проектный конфиг может писаться и в домашний каталог
  (local scope MCP у Claude — `~/.claude.json → projects[путь]`). `base: "local"` —
  `local/` конфигурации (обёртки секретов).
- `sensitive` и `secretKeys` ставит ядро; `team` — файл импортированного командного skill.
- `ctx.ownedFiles` — файлы цели в учёте: «наш ли файл» адаптер решает по учёту, не по
  содержимому. Own-файл MCP ради keep рендерится, только если он уже в учёте (`keepOwn`).

Требования к адаптеру:

- Неподдерживаемая агентом возможность → `warning`, а не молчаливый пропуск.
- Сгенерированные файлы — с шапкой «Сгенерировано miksy (слои: …). Не править
  вручную — изменения вносить в конфигурацию miksy (слои).», если формат допускает
  комментарии.
- `CAPABILITIES.md` — таблица «что агент умеет и как miksy это использует»,
  **проверено вживую** (агент запущен в тестовом проекте и подтвердил, что конфиг
  подхватился), с версией клиента. Источник — документация агента, а не память модели.
- Учтены режимы запуска агента (CLI, Zed через ACP, IDE) — §10.

### 8.2. План и действия

`plan(result, target, machine, prev, force, owner, owners)` (`src/apply.ts`) строит
список действий; `apply` выполняет его. Вывод `sync` — описание каждого действия.

| Действие | Что делает |
|---|---|
| `write` | own-файл: новый или обновление (бэкап, атомарная запись) |
| `adopt` | взять под учёт чужой файл с тем же содержимым (`--force` — с другим; оригинал сохраняется) |
| `block` | записать/обновить/снять управляемый блок инструкций (§8.4) |
| `merge` | установить/снять ключи в общем JSON/TOML-файле |
| `toml` | таблицы `mcp_servers.<имя>` глобального TOML Codex (§8.5) |
| `forget-merge` | снять с учёта исчезнувший optional-ключ без записи файла |
| `chmod` | исправить только права (без перезаписи и бэкапа) |
| `delete` | удалить свой файл, ставший ненужным (хеш совпадает с учтённым) |
| `restore` | вернуть оригинал own-файла при `clean` (§8.9) |
| `release` | снять файл с учёта, не удаляя: им владеет другая цель |
| `exclude` | блок агента в `.git/info/exclude` проекта (до записи файлов) |
| `trust` | доверие проекта в `~/.claude.json` / `~/.codex/config.toml` (§8.7) |
| `approve` | одобрение серверов `.mcp.json` в `.claude/settings.local.json` (§8.7) |
| `conflict` | ничего не делать, сообщить причину (чужое, правлено вручную, git, границы) |

Порядок в `apply`: exclude (с удаляемыми строками на время apply) → файлы, слияния,
TOML, доверие, одобрения → удаления скриптов `local/run` последними (после всех их
потребителей: сбой записи конфига оставляет и прежний скрипт). Учёт меняется после
успешной записи; при ошибке выполненное до неё сохраняется (`partialState`). Перед
каждой записью сверяется хеш, запомненный планом: не совпал — `StaleError`, ядро один
раз строит план заново (`applyPlanned`), затем отказ.

### 8.3. Запись и безопасность

- **Атомарность** (`writeAtomic`, `src/manifest.ts`): временный файл с уникальным именем
  рядом с целью (сразу 0600) и rename. Права существующего файла сохраняются, кроме
  `sensitive`: 0600 (исполняемый — 0700); `executable` несекретному — `+x` там, где есть
  чтение. Симлинк не заменяется файлом — пишется его цель (битый — отказ). Если rename
  не удаётся (Windows: файл открыт другим процессом), ядро повторяет его и отказывает;
  прямой записи поверх нет. Сообщение называет держателя файла (`src/locks.ts`: Windows —
  Restart Manager через Bun FFI, macOS/Linux — `lsof`): «файл занят … — его держит Zed
  (PID …) — закройте эту программу и повторите». То же при удалении.
- **Права.** `sensitive` ставит ядро: всем MCP-файлам (merge, own с `mcp`, файлы, где
  учёт держит наши MCP) и файлам, где встречается реально подставленное значение секрета
  от 8 символов. Закрыт — `(mode & 0o077) === 0` (на exFAT 0700 — тоже). Отличаются
  только права — действие `chmod`. Windows: POSIX-биты не проверяются; `local/` закрыт ACL.
- **Границы ФС.** Перед записью и удалением путь канонизируется (realpath существующей
  части + хвост) и обязан остаться в своём корне: `project` — каталог цели, `home` — `~`,
  `local` — `local/` конфигурации; пути из учёта — в цели и в `local/` (слитые ключи —
  ещё и в `~`). Симлинк/junction наружу, `..`, другой диск — конфликт; apply
  перепроверяет перед каждой записью. Симлинк из учёта не удаляется (ни ссылка, ни цель).
- **Git** (`src/git.ts`). Файл, отслеживаемый git проекта или любым репо вокруг `~`
  (dotfiles), не пишется и не удаляется — даже с `--force`. Проверяются логический путь,
  цель ссылки, отслеживаемые ссылки выше по пути и прежние логические пути из учёта
  (`aliases`). Так же — файл внутри вложенного git-репо цели и личный файл в каталоге
  skills/plugins, который версионирует команда (С22: Codex тогда берёт `.codex/skills`).
  Совпадение с индексом только регистром — отслеживаемое, если это не два разных
  существующих файла. Сбой git (не запускается, битый индекс, dubious ownership) —
  отказ, а не «не отслеживается». `gitEnv` убирает переменные репо/индекса/pathspec,
  `GIT_CONFIG_*` сохраняет. **Кеш:** CLI включает `cacheGit()` — на время одной команды
  корень репо каталога (и его родителей до корня) и индекс каталога (`ls-files` одним
  запросом) запоминаются; разбор командных skills — тоже (`gitMemo`). miksy индекс не
  меняет, поэтому снимок внутри команды верен. В тестах кеш выключен.
- **Exclude** пишется до файлов и только для own-файлов miksy; строка — и по
  физическому пути своей ссылки; каталог skill/плагина — одной строкой, если внутри нет
  чужого файла с конфликтом. Строка записанного раньше файла не снимается, пока файл
  лежит в проекте. Worktree с общим `info/exclude` ведёт свой блок
  `miksy:<агент>@<каталог worktree>`. Exclude обязан быть в git-dir/common-dir.
- **JSON-merge.** Битый JSON — конфликт этого файла. Удаление и слияние одного пути в
  одном плане — конфликт. В чужой файл git-проекта (не скрытый exclude) серверы с
  подставленными секретами (`secretKeys`) не сливаются — конфликт; без секретов —
  сливаются.
- **Один владелец.** `owners` — канонические файлы других целей: чужой — конфликт
  «уже принадлежит цели …»; записанный обеими раньше — `release` у той, которой он не
  нужен.
- **Отказ одной цели** (битая ссылка, нет доступа) — её конфликт; остальные цели
  обрабатываются.
- `verifyMerges(state, actions?)` — записанные ключи на месте: `sync` проверяет ключи
  этого запуска сразу после записи (без паузы); `doctor` — весь учёт («ключи пропали» —
  перезаписала открытая сессия агента).

### 8.4. Инструкции и skills

- **Управляемый блок.** В общих файлах инструкций (`~/.claude/CLAUDE.md`,
  `CLAUDE.local.md`, `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`) miksy владеет только
  текстом между `<!-- miksy:begin … -->` и `<!-- miksy:end -->` (`src/instructions.ts`).
  `RenderedFile` с `block: true` — текст правил без маркеров; ядро ведёт
  `TargetState.blocks` (sha256 LF-формы блока). Чужой текст вокруг сохраняется побайтно;
  ручная правка блока — конфликт (`--force` заменяет только блок); блок удалён из
  существующего файла — конфликт; файла нет — пишется заново; файл с CRLF получает блок с
  CRLF. Строка правил, совпадающая с маркером, сдвигается пробелом. `clean` удаляет блок,
  файл — только если вне блока пусто; при снятии блока на стыке вставляется `\n`.
  Прежний целиком управляемый файл мигрирует в блок, если совпадает с учётом.
- Если команда отслеживает `CLAUDE.local.md`, правила Claude идут в
  `.claude/rules/miksy.md`; если и `.claude/rules` командный — правил проекта для
  Claude нет (предупреждение).
- **Skills.** Адаптер раскладывает все файлы `Skill.dir` (или `Skill.files` — импорт из
  git) через `skillFiles` (`src/skillfiles.ts`); `patch` подменяет содержимое файла;
  бинарный файл без `patch` пропускается с предупреждением; `+x` источника — `executable`.
  `skillDirs` — по нему ядро решает, видит ли агент командный skill сам. opencode
  доставляется последним (`deliveryOrder`) и пропускает проектную копию, если skill уже
  доставлен в читаемый им каталог (`.claude/skills`, `.agents/skills`) этим запуском или
  раньше (`ledgerSkills`).

### 8.5. Глобальный TOML Codex

- Проектный `.codex/config.toml` — own-файл miksy (`developer_instructions` и
  `mcp_servers`), скрыт exclude; отслеживаемый git — конфликт.
- Глобальный `~/.codex/config.toml` — `merge`, `format: "toml"`, `key: ["mcp_servers"]`.
  Владение — по учёту: `TargetState.toml[path] = {hash, names, definitions}`
  (`definitions` — имя → sha256 нормализованного значения: ключи сортируются, пустой
  `args` опускается). Маркеры `# >>> miksy …` / `# <<< miksy` — подсказка; после
  переписывания Codex (`codex mcp add`) учтённые таблицы находятся без них. Изменение
  значения — конфликт одной таблицы, остальные обновляются; `--force` перехватывает только
  учтённые имена; чужое имя — сначала `adopt` (с бэкапом). Сканер заголовков исключает
  строки и комментарии; inline-формы, которые нельзя безопасно править, — конфликт; чужие
  таблицы не сериализуются заново. Полный TOML проверяется `Bun.TOML.parse` до и после
  записи. Это ограниченный механизм MCP-таблиц, не универсальный редактор TOML.

### 8.6. Секреты: обёртки, helper-ы, мост

- **Ссылки вместо значений.** `substitute` возвращает определения, где секрет —
  `secretRef(ИМЯ)`; значения проверяет ядро. Метка ссылки в любом файле или значение
  используемого секрета (от 8 символов, как есть и в JSON-форме) в MCP-файле или скрипте
  — ошибка цели (конфликт), не запись.
- **Способ** — по паре «агент × тип сервера» (`deliver`): без секретов — как есть; stdio —
  обёртка у всех; HTTP с секретом в `headers` — способ агента (`httpSecrets`: Claude
  `headersHelper`, Codex `http_headers_helper` — `helper`; opencode — `{file:путь}`;
  Antigravity — мост); секрет в `url` — мост у всех. Секрет в `env` HTTP-сервера —
  пропуск (мосту передаются только ключи `BRIDGE_RESET`); `env` без секретов —
  предупреждение.
- **Ограничения значения** (`src/vars.ts`, по способу и ОС машины): общее — одна строка
  без NUL; `.cmd` (`set /p`) — не длиннее 1023 байт, `"` в аргументах и составных
  переменных — отказ; helper — `"`, `\`, не-ASCII в заголовке — отказ; мост и `{file:}`
  читают файл сами (длинные значения и `"`/`\` в заголовке доставляются). Секрет в
  `command` или `raw` — пропуск. Значение короче 4 символов — предупреждение (маскируется
  только целой строкой). Секрет в `args` — предупреждение (виден в списке процессов).
- **`Launcher`** (`src/launch.ts`, `RenderContext.launch`): `stdio(s)` — путь обёртки,
  `helper(s)` — команда helper заголовков, `bridge(s)` — путь обёртки моста,
  `secretPath(ИМЯ)` — файл секрета, `files()` — сгенерированные скрипты (own,
  `base: "local"`, `executable`), `kept(имя)` — уже записанные скрипты сервера.
  Имя скрипта — `<читаемое>-<stdio|headers|bridge>-<sha8(вид\0сервер)>` (без коллизий
  регистра и вида). Адаптер добавляет `launch.files()`, только когда пишет конфиг MCP.
- **Скрипты.** sh: `IFS= read -r` из файла секрета, `export`, `exec` (аргументы — в
  одинарных кавычках). `.cmd`: `chcp 65001`, `setlocal DisableDelayedExpansion`, проверка
  файлов (нет — текст в stderr, код 1), переменная целиком из секрета — `set /p`,
  составная и аргументы — через `%h.ИМЯ%` в `"…"`. Строка-команда helper-а экранируется
  для shell агента (sh — `'…'`, cmd — `"…"` с `^%`); `"` и перевод строки в пути — отказ.
  Bun моста — по стабильному пути без версии (`stableBun`).
- **Файлы секретов** (`src/secretfiles.ts`): `local/secrets/<ИМЯ>` = значение + LF;
  0600/0700 или ACL только текущего пользователя (`icacls`). Пишутся до apply цели, без
  бэкапа и без хеша значения в учёте. `TargetState.secrets` — нужные имена,
  `TargetState.servers` — секреты записанной версии каждого сервера (при конфликте или
  ошибке записи — объединение старой и новой). `Manifest.secretFiles` — созданные miksy
  файлы: лишние удаляются только из них (не ссылки, не файлы пользователя).
- **`local/`** закрывается целиком (`ensurePrivateLocal`): проверка одним снимком,
  исправление только при открытых путях; ссылки внутри `local/` не обходятся и права их
  цели не меняются — открытая или битая ссылка: предупреждение, а для `local/secrets` и
  `local/backups` — отказ записи.
- **Мост** (`src/bridge.ts`): `bun --no-env-file --config=src/bridge.bunfig.toml bridge.ts
  --name --secrets <каталог> --url <шаблон> [--header Имя=<шаблон>] [--timeout <с>]`,
  шаблон — `{secret:ИМЯ}`. Обёртка запускает его из каталога секретов и сбрасывает
  `BRIDGE_RESET` (прокси, TLS, `BUN_OPTIONS`, `BUN_CONFIG_VERBOSE_FETCH`, `NODE_OPTIONS`),
  кроме заданных в `env` сервера. POST Streamable HTTP с `redirect: "manual"` (3xx —
  ошибка); ответ JSON или SSE того же запроса; `mcp-session-id`, `mcp-protocol-version`.
  initialize и initialized — по порядку, остальное параллельно. Каждый запрос с id
  получает результат или ошибку JSON-RPC (сбой, редирект, HTTP-ошибка, 202/204, поток
  закрыт, таймаут — по умолчанию 600 с). Уведомление завершается по статусу. 404 —
  восстановление сессии с барьером (повтор не чаще раза в 5 с). После EOF stdin — до
  5 с на незавершённые, затем DELETE сессии. Всё, что мост пишет, маскируется
  (`src/mask.ts`, `<secret:ИМЯ>`; `jsonrpc`/`id`/`method` не трогаются).
  **Не поддерживается:** отдельный GET-поток сервера; транспорт HTTP+SSE 2024-11-05.

### 8.7. Доверие проектов и одобрение `.mcp.json`

- **По умолчанию** (`trustPlan`, `src/trust.ts`) miksy добавляет доверие Claude и
  Codex цели, куда успешно доставил конфигурацию агента (Codex — свой
  `.codex/config.toml`; Claude — инструкции, skills или локальные MCP). Только добавляет;
  своё — в учёте (`TargetState.trust[JSON([файл,…ключ])] = {format, key, value,
  previous?}`), `clean` снимает только своё; явный `untrusted` Codex не меняется.
- **Исполняемые настройки агента не от miksy** (`executableSettings`): Claude —
  `.claude/settings*.json` (hooks, `permissions`, `env`, helpers, `statusLine`/
  `fileSuggestion` с командой, `enableAllProjectMcpServers`, `enabledMcpjsonServers`) и
  `.mcp.json`; Codex — `.codex/config.toml`. В git-цели — закоммиченные (в том числе за
  ссылкой) и неотслеживаемые, кроме своих по учёту (`ownFiles`: свой
  `.codex/config.toml` с записанным хешем, свои одобрения). Вне git — `.claude/settings.json` и
  `.mcp.json` на диске целиком, `.claude/settings.local.json` — как неотслеживаемый в git-цели (круг 6y, рецензия
  6x A1: до этого он вне git не проверялся вовсе, и чужой хук в папке, общей с коллегой, получал доверие без
  решения): свои одобрения и ответы пользователя в окне Claude — по `ownFiles`/`dialogOwn`, остальные ключи —
  всегда; `.codex/config.toml` — тоже как неотслеживаемый (круг 6z, рецензия 6y A1): свой только с записанным
  хешем, правка или подмена после доверия miksy — чужие настройки (вопрос, доверие снимается; раньше файл вне git
  не проверялся, и `rendered` оставлял доверие при конфликте). Подкаталоги группы без git (`inheritedExec`, `doctor`): хуки, `env` и прочие не-`DIALOG` ключи их
  `settings.local.json` — да; ответы в окне Claude там не показываются (их пишет Claude по ответу того, кто там
  работает; совет раздела «удалите их» к ним не относится); группа с запретом доверия Claude не проверяется.
  `sync` подкаталоги не проверяет — только справка `doctor` (README так и говорит).
  **Просмотр `miksy trust <проект>` — своё то, что план берёт** (круг 6z, рецензия 6y A4): `RenderResult.trustOwn` —
  учёт и файлы, узнанные планом после «забыть» (`known`), кроме конфликтных: шапку «Сгенерировано miksy» мог
  оставить кто угодно (копия папки, архив), и файл, который `sync` не берёт, просмотр показывает чужим — решение о
  нём записывается (`--confirm`, `--deny`). `sync` о таком файле не спрашивает (рецензия 6w, п. 3: свой файл после
  «забыть» при изменившихся слоях — конфликт без вопроса) и доверия по нему не ставит: конфликт — не доставка.
  Файл, который этот же план записывает (`write`: `--force` поверх правки), для проверки доверия свой
  (`OwnFiles.written`): после записи в нём вывод miksy — доверие в том же запуске, без вопроса о стёртом содержимом
  (рецензия 6z, п. 3). Решения, сохранённые до 6y, совпадают, если в `settings.local.json` нет
  исполняемых ключей кроме `DIALOG` (отпечаток тот же); иначе — один вопрос. Такая цель получает доверие, только
  если `trust: true` в слое или есть «да» пользователя с тем же отпечатком.
- **Ответы пользователя в окне Claude** (круг 6x) — ключи, которые Claude сам пишет в неотслеживаемый
  `.claude/settings.local.json` по ответу в своих диалогах (`DIALOG`: `permissions.allow/ask/deny/
  additionalDirectories`, `enabledMcpjsonServers`, `disabledMcpjsonServers`, `enableAllProjectMcpServers`).
  **В отпечаток решения они не входят никогда**: раньше входили, пока доверие ставил не miksy, и «да» совпадало
  только при том же состоянии доверия — `sync` то ставил доверие, то снимал и спрашивал снова (качели, ошибка
  0.1.1). В показ (вопрос) — только когда они не свои пользователя (`dialogOwn`). Свои — если доверие этой цели
  ставил miksy (`trustedByMiksy`: учёт доверия; `TargetState.everTrusted` — стояло раньше и снято, например пока
  исполняемые настройки команды ждут решения; отметка «проект забыт» с `trusted`), в слое `trust: true` для Claude
  или у проекта есть «да» доверию Claude (`local/trust.json`, любой отпечаток: команда с тех пор что-то поменяла —
  в вопросе только её изменения). Иначе (папку скопировали, она общая с коллегой) — в вопросе, один раз: после
  «да» они свои. В показе они — под отдельным заголовком `DIALOG_TITLE` («ответы в окне Claude …»), а не среди
  настроек команды (круг 6y). Отслеживаемый git `settings.local.json`, хуки, `env`, `defaultMode` и прочие ключи — настройки
  команды, как раньше; `false` в слое и `machine.yaml` — окончательно (исполняемые настройки при запрете не
  считаются).
- **Отпечаток** — `v2:` + sha256 канонического JSON полной структуры учтённых настроек;
  показ — отдельно (значения целиком, похожие на секрет — скрыты с длиной, пути файлов). **Прежний
  расчёт** (`legacy`: с ответами Claude — 0.1.x и круги до 6x, когда доверие ставил не miksy): «да» с ним
  принимается без нового вопроса, `sync` переносит его на новый отпечаток (`renewDecision`: ответ и дата те же;
  `doctor` и `--dry-run` — не переносят). Решение, сохранённое прежней версией при доверии miksy, совпадает с
  новым расчётом и так. Прежний отпечаток совпадёт, только если ответы Claude с момента «да» не менялись; иначе —
  один вопрос (в нём только настройки команды): старый отпечаток — хеш, исходных данных из него не восстановить.
- **Решения** — `local/trust.json` (`{version: 1, decisions: {<путь>: {rel, claude?,
  codex?, mcpjson?: {answer, fingerprint, date}}}}`). `sync` в терминале спрашивает в
  конце (`--yes` не отвечает), без терминала и в `--dry-run` — блок «Нужно решение
  пользователя» с текстом для агента; `miksy trust [<путь>] [--confirm|--deny]`.
- **Запрет.** `false` в `machine.yaml` окончателен; слой может запретить (`false`) или
  разрешить исполняемые настройки (`true`), где машина не запретила.
- **Снятие своего** — когда пропало основание: `clean`, запрет, появились или изменились
  исполняемые настройки без решения, отказ, miksy больше ничего не доставляет.
- **Одобрение серверов `.mcp.json`** (Claude): `<проект>/.claude/settings.local.json`
  `enabledMcpjsonServers` (действие `approve {add, remove, own}`, учёт
  `TargetState.approvals`). Основание — как у доверия (`trust: true`, «да» доверию Claude,
  отдельное решение `mcpjson`); условие — доверие после плана, файл не отслеживается git,
  нет `enableAllProjectMcpServers`. Чужие одобрения и отказы не трогаются; файл одобрений
  скрыт exclude с момента одобрения (`approvalExclude`).
- **Группы без git:** доверие Claude группы наследуют её подкаталоги без git — `doctor`
  ищет там исполняемые настройки (`inheritedExec`).
- Предупреждение Claude о `headersHelper` без доверия — по итогу плана (`advice`).

### 8.8. Учёт

`local/state/manifest.json` (`src/manifest.ts`), версия 1:

```ts
interface Manifest { version: 1; engine?: string; targets: Record<string, TargetState>; secretFiles?: string[];
  roots?: Record<string, string>;            // §6b: корень, как записан → последний настоящий путь
  forgotten?: Record<string, { trusted?: true }> } // §6b: отметка «проект забыт» (ключ — как у цели)
// engine — версия движка, который последним записал учёт (§12)
interface TargetState {          // ключ цели — "<агент>|<каталог или ~>"
  files: Record<string, string>; // own-файл → sha256 записанного
  merges: Record<string, Record<string, string[]>>; // файл → JSON(key) → свои имена
  exclude: Record<string, string[]>;                // .git/info/exclude → свои строки
  toml?; blocks?; originals?; trust?; approvals?;   // §8.4, 8.5, 8.7, 8.9
  links?; aliases?;              // исходная ссылка own-файла; прежние логические пути
  secrets?; servers?;            // §8.6
  group?: true;                  // §6a
  everTrusted?: true;            // §8.7: доверие Claude ставил miksy (и снял) — не запись учёта
}
```

- Ключи — канонические пути; старые написания мигрируют в памяти (без записей при
  dry-run и без перезаписи файлов из-за одного alias). Разные хеши одного пути —
  `UNKNOWN_HASH` («хеш неизвестен»): конфликт только этого файла.
- Цель sync, у которой всё — конфликты, сохраняется пустым состоянием: её конфликты —
  «известные». Перед первой записью учёта за запуск — копия `manifest.json.bak`.
- Повреждённый учёт (`ManifestError`): `sync`/`clean` отказывают, `doctor` продолжает
  диагностику без сведений о владении.
- **Переезд каталогов** (`src/relocate.ts`; `loadManifestMoved` в `src/registry.ts` — его
  используют все команды): каталог учёта пропал → ищется новое место. Конфигурация — по
  обёрткам: пути `<корень>/local/run/…` под единственным пропавшим корнем, а те же файлы с теми
  же хешами — в `local/` нынешней конфигурации. Каталог цели — под переехавшим родителем на
  том же относительном пути, иначе единственная цель workspace без записей учёта, где все
  own-файлы и блоки, записанные в прежний каталог, лежат на тех же относительных путях с теми
  же хешами (нет таких файлов, правлены, кандидатов два — не переносится). Цель с отметкой «проект забыт»
  (`Manifest.forgotten`, §6b) — не кандидат (круг 6y, рецензия 6x B1): файлы miksy без учёта в ней — от «забыть», а
  не от переезда, и перенос учёта удалённого проекта туда вернул бы в неё «оригинал» из чужого проекта. Перенос меняет пути
  всех структур учёта (`applyMoves`: файлы, слияния, exclude, TOML, блоки, оригиналы, ссылки,
  одобрения, id цели), но не ключи внутри конфигов агента: `projects[<прежний путь>]` и доверие
  остаются в учёте как записанное под прежним путём — план цели снимает их как ненужное
  (`trustPlan` снимает своё доверие ключа, который больше не ключ цели) и ставит под новым.
  Решения `local/trust.json` переносятся тем же отображением. `doctor`/`--dry-run` — в памяти;
  `sync`, `clean`, `trust`, `adopt` сохраняют перенос до записи целей (`saveMoves`).
  Состояние агентов по пути каталога (история сессий, память, разрешения) — их, не miksy, и
  не переносится: Claude Code — `~/.claude/projects/<путь, где / \ : . заменены на ->` и
  `projects[<путь>]` в `~/.claude.json` (кроме ключей miksy), Codex и opencode — история с
  путём внутри.
- **Пропавший каталог без нового места** — «Учёт ссылается на несуществующие каталоги» в
  `doctor`; `clean <прежний путь>` (`vanishedTarget` → цель как у бывшей группы) убирает
  записанное вне каталога (ключи, доверие, обёртки) и записи учёта; exclude репо, которого нет,
  из учёта уходит. `sync --all` такие записи сам не снимает: недоступный диск не отличить от
  удалённого каталога.
- Ключ слияния, опустевший после снятия своих имён, и опустевшие объекты над ним (кроме
  верхнего уровня) удаляются: запись `projects[<путь>]`, созданная sync, не остаётся пустой.

### 8.9. Бэкапы и оригиналы

- **Бэкап запуска** — `local/backups/<метка запуска>/<путь>`: одна метка на запуск, одна
  копия файла за запуск (состояние до него), хранятся последние 20 запусков (только
  каталоги с меткой; ручные не трогаются), 0700/0600. Значения из `secrets.env`
  заменяются на `<secret:ИМЯ>` без порчи данных (`scrubbedCopy` → `src/mask.ts`: JSON/TOML
  — только строки и комментарии TOML, копия разбирается; прочее — байтовые диапазоны;
  значение короче 4 символов — только целой строкой). Копии, сделанные до маскировки,
  могут содержать значения.
- **Оригинал** — `local/backups/originals/<путь>`: точная копия чужого файла при захвате
  (включая совпадение содержимого), вне ротации; копии неизменяемы, новый захват с другим
  содержимым — `<путь>.miksy-<sha16>`; `TargetState.originals[путь] = {path, hash,
  restoreBlock?}`. `clean` восстанавливает оригинал own-файла (`restore` сверяет оба
  хеша); если файл менялся после захвата — конфликт с путём оригинала.
- Файлы секретов и `secrets.env` в бэкапы не попадают.

## 9. CLI

Команды и их флаги — справочник в README; здесь — контракт. Пишут на диск только `sync`
(без `--dry-run`; с `--out` — только в песочницу), `clean`, `adopt` (слой и
`local/secrets.env`), `trust` (`local/trust.json`, доверие агентов), `target` (`layer.yaml` слоя
дерева, §6a; после «да» — то же, что `sync`/`clean`) и `setup` (конфигурация,
`local/`, команда `miksy`; после «y» — копия настроек агентов, PATH, установка программ, а через
`adopt` и `sync` — то же, что они) и `update` (git-клон движка — только fast-forward; затем — как
`setup --yes`, после «y» — как `sync`, §12); остальные только читают (принцип 5).

- `sync --out <dir>` пишет только в песочницу: `<dir>` — путь от текущего каталога, новый,
  пустой или с меткой `.miksy-sandbox` (создана miksy); иначе — отказ.
- `sync --all` перед записью печатает корни workspace и цели и спрашивает подтверждение, если
  новых целей больше 10 или какой-то корень опасный (корень диска, `~`, его родитель); `--yes`
  снимает только это подтверждение, не вопрос о доверии (§8.7).
- `sync` без пути (и без `--global`/`--all`; и `sync --out`) — проект или цель `target: true` текущего
  каталога (из подпапки — тоже, ближайшая вверх); корень workspace (любой), каталог без git, который не
  цель, и каталог вне корней — ошибка использования с подсказкой, до учёта и записи (`syncProject`, §6b).
  Явный путь каталога без git, который не цель, — запись с предупреждением. `explain` без пути — текущий
  каталог (подпапка цели — сама цель), `--global` — домашние настройки.
- `root` — корни workspace: список, `add [<путь>] [--tree <ветка>]` (проверки как при загрузке; пишет только
  `workspace` в `local/machine.yaml`, строку превращает в список, затем предлагает `sync --all`), `remove
  <путь>` (только дополнительный; записанное в его проекты — `clean` с согласия). `--dry-run` — план.
  `clean` — только с явной целью (он удаляет записанное); каталог цели недоступен — убирает достижимое,
  записи внутри каталога оставляет до повторного `clean` или `--forget` (§6b).

Флаги разбираются строго по команде (`src/args.ts`): `--flag <значение>` или
`--flag=<значение>`; неизвестный флаг, флаг без значения, повтор, лишний аргумент,
несовместимые цели — ошибка с кодом 2 до любых действий. Коды выхода: 0 — успех, 1 —
ошибка (или проблемы `doctor`), 2 — ошибка использования, 3 — были конфликты.

**Мастер `setup`** (`src/setup.ts`) — установка одним диалогом: конфигурация (из git или примера),
workspace и агенты, копия настроек агентов до первой записи (`Adapter.homeConfig` →
`local/backups/before-miksy-<метка>/`, пути от `~`, точная копия вне ротации), программы MCP
(`tools` и встроенная таблица `PROGRAMS`), команда `miksy` и PATH, добавки агентов (`adopt`), секреты,
план (`sync --dry-run`), запись (`sync`), итог `doctor`. Шаг сделан или нет — по состоянию (есть
конфигурация, `machine.yaml`, копия, непустой учёт; добавки, оставленные у агента, —
`local/state/setup.json`), поэтому повторный запуск продолжает с несделанного. Изменения системы —
только после вопроса; Enter — «да» у безопасной части (копия, `machine.yaml`, команда, PATH: `[Y/n]`),
«нет» у остального (`[y/N]`). Без вопросов (`--yes`, нет терминала) — только конфигурация, `local/`,
`machine.yaml` и команда, а о программах серверов и секретах — отчёт (что поставить, каких имён нет);
`--yes --backup` — ещё копия настроек агентов: так агент-установщик делает этот шаг после «да»
пользователя в чате ([INSTALL-AGENT.md](INSTALL-AGENT.md)). Секреты и программы MCP (`tools`) мастер
спрашивает и перечисляет только для слоёв, которые на этой машине к чему-то применяются (§6b,
`applicableLayers`). PATH для команды `miksy` (macOS, Linux) — по содержимому rc-файла оболочки, а не
только PATH процесса: строка, уже добавляющая каталог (`export PATH="$BUN_INSTALL/bin:$PATH"` от
установщика Bun, `$HOME`, `~`, `fish_add_path`; переменные, заданные в файле выше, раскрываются —
`rcAddsDir`), — второй не дописывается.

Проверка раскладки (`layoutWarning`, в обоих режимах, после выбора workspace): в дереве слоёв есть
каталог, где на первой машине лежали движок и конфигурация, — слой `Miksy` (группа
`…/Miksy/{miksy,miksy-config}`, без учёта регистра) или родитель слоя с точным именем движка или
конфигурации, — а здесь ни движок, ни конфигурация не в нём. Одно сообщение, ничего не меняется; если
каталог слоя на этой ФС совпадает с самим движком (регистр не различается) — ещё строка о
переименовании через временное имя. Слой `miksy` (точное имя движка) — слой самого движка, не группа.

YAML конфигурации читается с BOM и без (`parseYaml`): PowerShell 5.1 (`Set-Content -Encoding utf8`) и
Блокнот пишут BOM, и первый ключ иначе получил бы невидимый префикс.

Программы серверов, перенесённых `adopt` (шаг 6), проверяются сразу после переноса — только команды,
которых шаг 4 ещё не видел; установка, уже предложенная на шаге 4 (Node.js для `npx` и для `node`),
не спрашивается снова. Команда `miksy` (shim в `$BUN_INSTALL/bin`, по умолчанию `~/.bun/bin`:
`miksy` — sh, `miksy.cmd` — Windows) запускает Bun, которым её создал `setup`, по пути без версии
(`stableBun`, как у мостов): при двух Bun на машине (Homebrew и `~/.bun/bin`) sync из команды всегда
пишет обёрткам моста один и тот же путь. Этого Bun нет — `bun` из PATH с предупреждением в stderr.
Повторный `setup` обновляет команду, если изменился путь движка или Bun; своей считается только
команда, совпадающая с генерируемой (`ourShim`), и команда прежнего формата (`bun` из PATH). `.cmd`
— ASCII; путь с не-ASCII (кириллица в имени пользователя) — под `chcp 65001` с возвратом прежней
страницы; код выхода — явно (`exit /b %errorlevel%`: `exit /b` без кода после `setlocal` даёт 0).

**Окружение** (`src/environ.ts`) — одна проверка для `doctor` («Справочно», не проблема) и мастера
(шаг программ, и с `--yes`); только сообщения, ничего не удаляется. (1) Несколько установок
программы: Bun, `claude`, `codex`, `opencode`, `agy`, `node`, `uv`, `python3`/`python` — по одной на
каталог PATH (первая используется), Bun — ещё каталог официального установщика (`$BUN_INSTALL/bin`,
`~/.bun/bin`: его подхватывает `install.sh`, туда `setup` кладёт команду), а «используется» у Bun —
тот, которым запущен miksy. Другие места вне PATH (Homebrew, scoop) не ищутся: оттуда программу не
запускает ни терминал, ни агент, а результат зависел бы от машины. Один файл — одна установка
(realpath; scoop shim и каталог версии). Не установки: псевдонимы Windows `Microsoft\WindowsApps`
(заглушки магазина). `npx` отдельно не проверяется — npm обновляет себя в свой каталог
(`%APPDATA%\npm`) при одном Node.js. Версия opencode — без запуска (opencode 2.x при запуске поднимает
фоновый сервис, а проверка не должна ничего запускать и менять): по пакету (`opencode-ai` — 1.x,
`@opencode/cli` — 2.x, `Cellar/opencode/<в>`), а у официального установщика (`~/.opencode/bin/opencode`)
— по команде `opencode2` рядом: установщик 2.x (`opencode.ai/v2/install`) всегда пишет её маленьким
скриптом, запускающим `opencode`, установщик 1.x — нет (а большой `opencode2` — сама 2.x рядом с 1.x);
1.x — сообщение (miksy пишет формат 2.x). (2) Переменные каталога
настроек у агентов машины: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME` (opencode),
`GEMINI_CLI_HOME` — заменяют стандартный каталог (значение, равное стандартному, — молча);
`OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR` — дополнительный конфиг поверх глобального (документация
opencode: config, precedence). (3) Конфигурация задана `MIKSY_CONFIG` или `~/.miksy`, а рядом с
движком лежит другая `miksy-config`. `install.sh`/`install.ps1` отдельно (до Bun движок не
запустить) предупреждают о нескольких установках Bun.

Ввод-вывод отделён от логики: вопросы — интерфейс `Ask` (`src/ask.ts`: да/нет, выбор, строка;
`terminalAsk` — `prompt` Bun, в тестах — сценарий ответов), действия с системой — `System` (поиск и
установка программ, git, пользовательский PATH Windows через реестр — не `setx`), команды miksy —
`runCommand` (`src/commands.ts`) в том же процессе: CLI (`src/cli.ts`) — тонкая обёртка над ним, а
`sync`, `adopt`, `trust` задают свои вопросы (подтверждение, доверие) через тот же `Ask`. Стартовые
скрипты `install.sh`/`install.ps1` проверяют git, ставят Bun официальным установщиком (после «y»),
клонируют движок, если запущены не из клона, и запускают `setup`; в `curl … | bash` вопросы — через
`/dev/tty`.

Не реализовано и не планируется: `miksy diff` (его роль — `sync --dry-run` и
`sync --out`), `miksy.lock` в проекте (собранный конфиг показывает `explain`).

## 10. Режимы запуска агентов и skills

| Агент | Режимы |
|---|---|
| Claude Code, Codex, opencode | CLI, Zed (через ACP) |

Особенности, которые адаптер обязан проверить: рабочий каталог в IDE — открытая папка
(проект открывается сам по себе); окружение IDE может отличаться от консольного (секреты

**Размещение skills.** Собственные skills — с префиксом (`skill_prefix` в `map.yaml`,
по умолчанию `miksy-`), чтобы не совпадать с командными. Личные приёмы — слой `global`;
общие для организации — её слой; нужные всей команде проекта — в репо проекта (их получат
и коллеги), а не в miksy.

**Импорт командных skills** (`src/teamskills.ts`, `import_skills` в слое; включён для
агентов из `TEAM_IMPORT` в `src/registry.ts`). Команда держит skills в репо под свой агент
и нередко раскладывает их неправильно (нестандартные пути, двойная вложенность, копии под
каждый агент, симлинки). Miksy читает их и доставляет вашим агентам, которые их сами не
видят, через локальные каналы:

1. **Поиск** во всех известных местах (`.agents/skills/*`, `.agents/*`, `.claude/skills/*`,
   `.claude/commands/**`, `.codex/skills/**`, `.gemini/skills/**`, `.opencode/skill(s)/*`,
   `.opencode/command/*`) — только файлы в индексе git. Содержимое — из последнего коммита
   (`git ls-tree HEAD` + `cat-file`): неотслеживаемое, ignored и незакоммиченное не
   попадает; переводы строк — как в выгрузке git; симлинки раскрываются по объектам git
   только внутри репо.
2. **Склейка копий** по приоритету (`.agents/skills` > `.agents` > `.claude/skills` > …);
   расходящиеся копии — предупреждение.
3. **Проверка** (frontmatter `name`, `description`; имя = каталог) и механическая
   нормализация имени (`patch`).
4. **Ручные исправления** — в слое проекта: `skills/<имя>/` перекрывает импортированный,
   `exclude: [skill.<имя>]` — не доставлять.
5. **Доставка** через адаптеры (вне git), с именами команды; размещение — по правилам
   личных skills (командный каталог-коллекция — конфликт). `auto` — не больше 30 на проект.
6. **Актуальность**: после `git pull` с изменёнными skills `doctor` показывает устаревшие
   копии.

Импорт ничего не добавляет к тому, что уже лежит в репо, и не «улучшает» скрипты skills.

## 12. Версии, ветки и обновление

**Версия** — `version` в `package.json`, SemVer. Пока 0.x, MINOR (`0.2.0` → `0.3.0`) может ломать —
но только с записью «После обновления» (что сделать пользователю); PATCH — только исправления. После
1.0 ломающее — только в MAJOR. Выпуск — тег `vX.Y.Z` (аннотированный) на коммите «Release X.Y.Z».
`miksy --version` (`src/version.ts`) — в духе `git describe --tags --match v*.*.* --dirty`: на теге —
`0.2.0`, после него — `0.2.0-3-gabc1234`, правки в отслеживаемых файлах — `-dirty`; тегов нет —
версия из `package.json` и коммит; движок не корень своего git-клона (скачан архивом, лежит внутри
чужого репо) — только версия. Версия — в `help`, заголовке `doctor` и `setup`.

**Ветки.** `main` — разработка владельца (промежуточные коммиты). `stable` — всегда последний выпуск:
её клонируют установщики (`install.sh`/`install.ps1` клонируют ветку по умолчанию и, если в репо есть
`stable`, переходят на неё — один сетевой запрос, без второго запроса учётных данных; README и
INSTALL-AGENT — `git clone -b stable`), с неё обновляет `update`. `stable` двигается только вперёд
(команда выпуска проверяет, что прежняя `stable` — предок нового выпуска), поэтому у пользователя
всегда fast-forward: обычная ветка с upstream, без detached HEAD (почему не «только теги»: `checkout`
тега оставил бы пользователя на отдельном коммите, а `git pull` и сам `update` пришлось бы учить
переключаться между тегами).

**CHANGELOG.md** (`src/changelog.ts`) — в духе Keep a Changelog, по-русски; строгий формат, чтобы
`update` и выпуск вырезали записи надёжно: вступление; `## Не выпущено`; записи
`## X.Y.Z — ГГГГ-ММ-ДД` от новых к старым; внутри — только `### Новое`, `### Исправлено`, `### Ломает`,
`### После обновления` (другой заголовок `##`/`###` — ошибка разбора с номером строки). Строка в
«Не выпущено» пишется в том же коммите, что и изменение, если пользователь заметит разницу или ему
нужно что-то сделать. Номер выпуска — из непустых разделов «Не выпущено»: 0.x — «Ломает» или
«Новое» → MINOR, иначе PATCH; с 1.0 — «Ломает» → MAJOR, «Новое» → MINOR.

**Выпуск** — `bun run release` (`scripts/release.ts`, не команда `miksy`; для владельца —
[RELEASING.md](RELEASING.md)): ветка `main` (или `stable` для срочного исправления), чистое дерево;
номер по «Не выпущено» (пусто — отказ); показ номера и текста; после «да» (`--yes` без терминала):
`version` в `package.json` (только эта строка), «Не выпущено» → «X.Y.Z — дата» (пустые разделы
убираются), сверху — пустая «Не выпущено», коммит, тег (аннотация — текст записи, `--cleanup=verbatim`),
`stable` → тег. Пуш (`git push --atomic origin main stable vX.Y.Z`) и `gh release create
--notes-from-tag` — отдельным «да» или `--push`; `--dry-run`
— только показать. Первый выпуск: версия `package.json` без тега, её запись в CHANGELOG есть,
«Не выпущено» пуста — выпускается она (дата — сегодняшняя).

**`miksy update`** (`src/update.ts`):

1. Проверки: движок — корень своего git-клона; на ветке (не detached HEAD); у ветки есть удалённый
   репо (`branch.<ветка>.remote`, иначе `origin`). Ветка `stable` — обычное обновление; `main` без
   `--main` — переход на `stable` (п. 5); `--main` — только на `main`; другая ветка — отказ.
2. `--check` — `git ls-remote` (без `fetch`: в репо ничего не меняется): версия — тег, на который
   указывает удалённая `stable`; есть ли она уже в HEAD. Без терминала сетевые команды не спрашивают
   учётные данные (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`) и ограничены по времени.
3. Нет незакоммиченных изменений в отслеживаемых файлах (`status --untracked-files=no`), иначе отказ:
   правки пользователя живут в конфигурации, а не в движке. `git fetch --tags <remote>
   +refs/heads/<ветка>:refs/remotes/<remote>/<ветка>`; HEAD уже содержит новую — «последняя версия»;
   HEAD — не предок новой — отказ «разошлась» (и безопасный путь: сохранить коммиты веткой, затем
   `checkout -B`).
4. Изменения — по CHANGELOG **новой** версии (`git show <ref>:CHANGELOG.md`): записи (текущая, новая],
   отдельно «Ломает» и «После обновления» по версиям. Подтверждение `[y/N]`; без терминала — только
   `--yes`. Обновление — `git merge --ff-only`.
5. Переход с `main`: `stable` в удалённом репо нет — остаться на `main`; есть — после «да» `checkout -b
   stable --track <remote>/stable` (локальная `stable` уже есть — `checkout` и fast-forward; разошлась —
   отказ). Коммиты `main`, которых нет в выпуске, остаются в ветке `main`.
6. Шаги после обновления — **новым кодом**: новый процесс Bun `<движок>/src/cli.ts update --finish
   --from <прежняя версия>` (контракт: любая версия понимает `update --finish --from`). Он напоминает
   «После обновления» из CHANGELOG, выполняет безопасную часть `setup` (как `--yes`: команда `miksy`,
   `local/`, новые агенты в `machine.yaml`), `doctor` (строки разделов) и сводку `sync --global
   --dry-run` / `sync --all --dry-run` (та же, что шаг 8 мастера); изменений нет — всё; есть — в
   терминале вопрос «Записать настройки агентам?» (`sync --global`, `sync --all`), без терминала —
   только команды.

**Совместимость.** Учёт (`local/state/manifest.json`) хранит `engine` — версию движка, который его
последним записал (только при записи учёта). Учёт **новее** движка (другая копия движка с той же
конфигурацией уже обновилась) — предупреждение в `sync` и в «Справочно» `doctor` («обновите движок:
miksy update»), ничего не блокируется. Неизвестный ключ верхнего уровня `map.yaml`, его привязок
(`global[i]`, `layers[i]`) или любого `layer.yaml` (`unknownKeys`, известные ключи — из кода загрузки)
— предупреждение с файлом и ключом в `sync` и в «Справочно» `doctor`: опечатка или ключ более новой
версии.
