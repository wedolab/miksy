# Несколько папок с проектами

Проекты лежат в нескольких местах (второй диск, облачное хранилище) — как подключить их все, сменить основную папку и
что делать, если диск не подключён или потерян.

← [README](../README.md)

## Несколько корней workspace

Обычно все проекты лежат в одной папке — workspace (`workspace: ~/Projects` в `local/machine.yaml`). Если мест
несколько, каждое становится **корнем** workspace; первый — основной. «Папка с проектами» и «корень» здесь — одно и то же.

**Добавить папку с проектами** (облачную — сначала прочтите [ниже](#папки-облачных-хранилищ)):

```
miksy root add "E:\Clients"
```

miksy спросит **раздел** дерева слоёв для папки — имя её папки в `layers/tree/`, где будут её слои (раньше его
называли веткой; это не ветка git). Обычно
нажмите Enter: он предложит имя папки (`Clients`; знаки `[ ] { } * ?` и `!` в начале уберёт — с ними не работали бы
привязки `match:` в `map.yaml`). Папка уже подключена на другой машине — введите её раздел оттуда, иначе слои того раздела
сюда не дойдут. Без терминала (скрипт, агент): `miksy root add "E:\Clients" --tree Clients`. Сменить раздел потом можно,
но слои придётся перенести в папку с новым именем.

Команда допишет корень в `local/machine.yaml`, скажет, сколько проектов нашлось, и предложит `miksy sync --all`. Папка
пока пустая — miksy так и скажет: положите в неё проекты (git-репо) и запустите `miksy sync --all`, он их найдёт.
`--yes` — «да» на все вопросы команды, и `sync --all` запускается сразу (и без терминала — в скрипте тоже); раздел тогда
укажите в `--tree` (без него miksy напишет готовую команду с предложенным разделом). Один вопрос `--yes` не снимает: если
корень — домашний каталог или диск целиком, `sync` спросит, писать ли во все git-репо внутри (без терминала — не
запишет и напишет команду; корень при этом уже добавлен). Путь —
как удобно: `"E:\Clients"`, `E:/Clients`, `~/Cloud` (с пробелами — в кавычках). В мастере (`miksy setup`) то же —
вопрос «Есть ещё папки с проектами?». В `machine.yaml` это выглядит так:

```yaml
workspace:
  - D:/Projects                             # основной корень — в корне дерева слоёв (layers/tree/)
  - { path: "E:/Clients", tree: Clients }   # ещё корень — его раздел: layers/tree/Clients/
```

Дерево слоёв одно на все корни: `E:/Clients/Acme/site` получает `layers/tree/` (общее для всех), `layers/tree/Clients/`
и `layers/tree/Clients/Acme/`; `D:/Projects/Org/app` — `layers/tree/` и `layers/tree/Org/`. На другой машине пути могут
быть другими — там в `machine.yaml` свои пути с теми же `tree`.

**Убрать папку** — `miksy root remove <путь>`; записанное в её проекты miksy уберёт только с вашего согласия (вопрос,
«да» по умолчанию; без терминала — подскажет команды). Заранее посмотреть — `--dry-run`. Основной корень убрать нельзя.
Список корней — `miksy root`.

Сам корень настройки не получает — их получают проекты в нём (git-репо) и папки с пометкой `target: true`
(`miksy target E:/Clients/Acme` — пометка ляжет в `layers/tree/Clients/Acme/layer.yaml`).

### Как miksy ищет проекты

`miksy sync --all` и `miksy doctor` просматривают каждый корень и считают проектом каждую папку с git (`.git`), а также
папки, где агент уже работал.

- **Глубина.** Первые 7 уровней папок от корня — полностью: `D:/Projects/1/2/3/4/5/6/7`. Глубже — не больше
  10 000 папок за один просмотр, сначала менее глубокие. Обычно этого хватает с запасом; предел нужен, чтобы большая
  папка с данными (сотни тысяч вложенных папок) не замедляла каждую команду на десятки секунд.
- **Не просматриваются:** скрытые папки (имя с точки), `node_modules`, `dist`, `build`, `vendor`, `worktrees`,
  служебные папки miksy (`out/`, `local/`, `dist/` движка и конфигурации), ссылки на папки (симлинки, junction) и
  папки без доступа (о них — «Пропущено при поиске проектов» в `miksy doctor`). Внутри проекта поиск продолжается:
  вложенные репо тоже находятся.
- **Упёрлось в предел** — `miksy doctor`, раздел «Справочно»: «Поиск проектов остановлен» с корнем и папками, где
  глубоких папок больше всего. `sync --all` об этом не пишет. Что делать:
  - проект глубже — запустите `miksy sync` в его папке: miksy найдёт его поиском вверх, без предела;
  - большие папки без проектов (данные, архивы, выгрузки) лучше держать вне workspace — тогда и сообщение уйдёт.

### Папки облачных хранилищ

Google Drive, Яндекс Диск, OneDrive, Dropbox, iCloud Drive и т. п.: всё, что miksy туда запишет (`CLAUDE.local.md`,
`.claude/`, `.agents/`, `.codex/`, `opencode.json` — правила, список MCP-серверов, skills), уйдёт в облако, на ваши
устройства и всем, с кем папка расшарена. Значений секретов там нет (они в `local/` вашей машины), но правила и названия
серверов увидят. Подключайте такую папку, только если это вас устраивает. Одна папка на двух машинах (облако, сетевой
диск) — [подробнее](#одна-облачная-папка-на-двух-машинах).

## Правила нескольких корней

- **У каждого корня, кроме основного, свой раздел дерева слоёв (`tree`) — обязательно.** Иначе слои одной папки молча доставались бы
  одноимённой папке другого корня (`Acme` в основном корне получила бы MCP-серверы с токенами клиента из
  `layers/tree/Acme/`). Без `tree` или с занятым разделом `machine.yaml` не загрузится — ошибка скажет, что поправить.
  У основного `tree` можно не указывать; указан — тоже должен быть своим.
- **Общее для нескольких корней — явно.** Для всех проектов всех корней — `layers/tree/instructions/` (и остальное в
  корне дерева) или `layers/global/`. Для отдельных папок в разных корнях — свой слой в `map.yaml`:

  ```yaml
  # map.yaml — слой layers/acme/ для Acme в обоих корнях (Clients и Archive)
  layers:
    - { match: "{Clients,Archive}/Acme", use: acme }      # сама папка Acme
    - { match: "{Clients,Archive}/Acme/**", use: acme }   # и всё внутри неё
    # Acme и в основной папке с проектами — там место без раздела: добавьте "Acme" и "Acme/**"
    # (или шаблоны {Acme,Clients/Acme,Archive/Acme})
  ```

  Шаблоны сравниваются без учёта регистра, как и слои дерева.
- **`${WORKSPACE}`** в определениях MCP — всегда основной корень. Путь в другой корень — своей переменной машины:

  ```yaml
  # local/machine.yaml (на каждой машине — свой путь)
  vars:
    CLIENTS: "E:/Clients"
  # в слое: args: ["${CLIENTS}/tools/report.py"]
  ```

  Где переменная не задана, сервер пропускается с сообщением. `miksy adopt` сворачивает в `${WORKSPACE}` только пути
  основного корня, для других подсказывает завести переменную.

## Сменить основной корень

`miksy setup --force`, вопрос «Корень workspace». Нужен, когда папку с проектами перенесли или скопировали в другое
место. **Завели ещё одну папку, а прежняя нужна** — основной менять не надо: мастер увидит, что прежняя на месте и в
ней есть проекты, и спросит «Оставить её основной, а <новую> добавить ещё одной папкой с проектами?». «Да» (по
умолчанию) — прежняя остаётся основной со своими слоями и `${WORKSPACE}`, новая становится ещё одним корнем со своим
разделом, как в `miksy root add` (выше). «Нет» — основной станет новая, как при переносе. Если мастер запущен из новой папки
(движок miksy лежит в ней — её скопировали или перенесли вместе с ним), по умолчанию «нет».

Что будет с прежним основным, мастер скажет сам:

- основным стал **дополнительный корень** — его раздел дерева слоёв остаётся прежним;
- основным стал **новый каталог** — раздел прежнего основного (если он у него был) забирает он;
- прежний основной **уходит из workspace**, его проекты miksy больше не обновляет. Лежит внутри нового основного или
  другого корня — его проекты остаются и получают слои по пути от того корня; новый основной внутри прежнего — уходят
  только проекты прежнего вне нового.

`${WORKSPACE}` в слоях после смены — новый основной корень.

**Прежней папки нет или она пуста** (перенесли) — возвращать нечего, мастер так и скажет («прежнего основного … нет на
месте», «в прежнем основном … проектов нет»). Учёт (список записанного miksy) обычно переезжает сам —
[«Переименовали или перенесли каталог»](../README.md#переименовали-или-перенесли-каталог).

**Диск прежней не подключён** — мастер так и скажет («сейчас недоступен (нет диска)»). Менять основной из-за этого не
нужно: недоступный корень miksy пропускает, пока диск не подключат. Уже сменили — верните: `miksy setup --force` ещё
раз, корень — прежняя папка (на «Оставить её основной…», если спросит, — «нет»).

**Передумали** после смены основного на новый каталог — так же: `miksy setup --force`, корень — прежняя папка, на
«Оставить её основной…» — «нет».

**Внутри прежней была ещё папка с проектами** (свой корень) — мастер назовёт её и, если её перенесли, где она теперь.
Перенесли в новую основную:

1. На вопрос «Записать настройки агентам сейчас?» в конце мастера — «нет».
2. Поправьте её `path:` в `local/machine.yaml`.
3. `miksy sync --global` и `miksy sync --all`.

До этого `--force` из строки конфликта о её проектах не выполняйте. Новая основная — не та, куда перенесли прежнюю, или
не её копия — `path:` не меняйте: одноимённая папка там не та же самая. Тогда вложенная остаётся в workspace по
прежнему пути.

**Прежняя на месте, но не нужна** (папку скопировали или завели новую вместо неё; на «Оставить её основной…» — «нет») —
в каждом её проекте `miksy clean "<путь проекта>"` (работает и вне workspace). Новая — копия прежней: файлы miksy в ней с
путём папки (например, `.codex/config.toml` с `${WORKSPACE}`) — конфликт, пока не выполните в её проектах
`miksy sync "<путь проекта>" --force` (бэкап будет). Внутри прежней была вложенная папка с проектами
со своим разделом, а вы переходите на копию целиком — сначала так же, как при переносе: шаги 1–3 выше (её `path:` в
`local/machine.yaml` — на её копию), и только потом `clean` и `sync … --force`: иначе `--force` заменил бы правила её раздела
правилами основной папки.

### Вернуть прежний основной дополнительным корнем

Нужно, когда основным стал бывший дополнительный корень, а прежний основной тоже нужен (основным стал новый каталог —
проще [«Передумали»](#сменить-основной-корень) выше). По шагам из сообщения мастера («Вернуть его: 1) … 2) …»), если он
их печатал. Иначе:

- У него свой раздел, и новый основной его не занял, — `miksy root add "<прежний основной>" --tree <его раздел>`.
- Иначе сначала перенесите его слои в новый раздел (ниже), затем `miksy root add "<прежний основной>" --tree <раздел>`
  и «да» на `sync --all`. В обратном порядке `sync --all` снимет с его проектов ещё не перенесённые слои — тогда после
  переноса ещё раз `miksy sync --all`.

Перенос слоёв меняет конфигурацию на всех машинах, где она есть:

- **Раздела не было** — перенесите папки организаций и проектов (`layers/tree/Org/…` → `layers/tree/<раздел>/Org/…`). Общие
  `instructions/`, `mcp/`, `skills/`, `layer.yaml` в самой `layers/tree/` и папки разделов других корней не трогайте.
  Привязки `map.yaml` (`match:`) — раздел в начало: `Org/**` → `<раздел>/Org/**`, `*/infra-*` → `<раздел>/*/infra-*`; в
  `{…}` — к каждой его папке (`{Org,Lab}/**` → `{<раздел>/Org,<раздел>/Lab}/**`).
- **Раздел забрал новый каталог** (`Main`) — переименуйте `layers/tree/Main` в новый раздел, в привязках `Main/` →
  `<раздел>/`. Только если раздел из одной части и внутри нет разделов других корней; иначе (`Clients/Home`; у другого корня
  `Main/Drive`) переносите вручную только слои и привязки проектов прежнего основного.
- **У нового основного папки с теми же именами** (`Org` и там, и там; мастер тогда шагов не печатает) — их не переносите,
  а скопируйте (`layers/tree/Org` → `layers/tree/<раздел>/Org`; дальше правки — в обеих), а привязки к ним не меняйте, а
  допишите рядом такие же с разделом (`Org/**` и `<раздел>/Org/**`).
- В имени раздела запятая или `}` — вместо `{…}` отдельная привязка на каждую папку.
- Шаблоны, которые начинаются с `**`, не меняйте.

Без этого привязки перестанут совпадать, и `sync` снимет эти слои молча.

## Выбрали основным не ту папку

Верните прежний `local/machine.yaml` — `setup` сохранил его копию. «Вернуть его» из сообщения мастера не выполняйте.

1. Копия — в `<конфигурация>/local/backups/<дата и время>/` (не `before-miksy-…`); путь внутри повторяет путь
   конфигурации, на Windows — без двоеточия: `…\<дата и время>\C\Users\you\Projects\miksy-config\local\machine.yaml`.
   Все копии:

   ```
   Get-ChildItem -LiteralPath '<конфигурация>\local\backups' -Recurse -Filter machine.yaml | ForEach-Object FullName   # Windows (PowerShell)
   find '<конфигурация>/local/backups/' -name machine.yaml                                                              # macOS, Linux
   ```

   Нужна последняя, где первым в `workspace` ещё прежний основной (после ошибки `setup`, `update` или `root add` могли
   скопировать файл уже с ошибочной папкой). Встретится `<secret:ИМЯ>` (в пути корня или `tree:`) — впишите значение
   из `local/secrets.env`.
2. Скопируйте её на место:

   ```
   Copy-Item -LiteralPath '<копия>' -Destination '<конфигурация>\local\machine.yaml'   # Windows (PowerShell)
   cp '<копия>' '<конфигурация>/local/machine.yaml'                                     # macOS, Linux
   ```

3. `miksy sync --global` и `miksy sync --all`. Записанное в проекты ошибочной папки `miksy doctor` покажет в разделе
   «Цели учёта вне workspace»: для путей внутри ошибочной папки — `miksy clean "<путь>"`, другие не трогайте. Если там
   есть проекты, где вы нарочно оставили настройки miksy (например, `root remove` без «убрать записанное»), miksy их не
   отличит — их не чистите, а не помните какие — не чистите ничего: настройки вне workspace ничего не ломают, `clean`
   можно и позже (он вернёт ваши файлы, но снимет настройки miksy).

## Особые случаи

### Корень недоступен

Нет его папки, нет диска (не подключён, облако не запущено, на Linux ничего не смонтировано в `/media/<пользователь>/…`
или `/mnt/…`) или ссылка ведёт в никуда. Так же — **пустая папка корня, если miksy уже писал в его проекты** (на Linux и
macOS обычно точка монтирования без диска). `projects`, `sync --all` и `doctor` пропускают его с предупреждением,
записанное туда не трогается. Подключите диск — всё вернётся.

**Убрать записанное в его проекты** — `miksy clean "<путь проекта>"`: уберёт, до чего дотянется (MCP-серверы проекта в
настройках агентов, доверие, свои скрипты), а записи о файлах на диске оставит — по ним узнает свои файлы, когда диск
вернётся; тогда повторите `clean`. Данных больше нет (диск потерян, папку удалили) — ответьте «да» на «Забыть записанное
туда?» (по умолчанию — нет) или, без терминала, добавьте `--forget`. Пустую точку монтирования, очищенную вами, — тоже
`clean … --forget`.

**Убрать сам корень** — `miksy root remove <путь>` спросит то же. «Нет» — корень уходит из списка, записанное и учёт
остаются: когда диск вернётся, `miksy clean "<путь проекта>"`, а для агентов, убранных из `agents`, —
`miksy clean "<путь проекта>" --agent <имя>` (команды — в выводе `root remove`). Корень внутри другого корня без
«забыть» не убирается. `--dry-run` (можно с `--forget`) покажет заранее, почему корень недоступен, будет ли вопрос и
сколько файлов забудется.

### Диск нашёлся после «забыть»

Учёта этих файлов больше нет, но свои miksy узнаёт сам. Папка проекта в workspace — `miksy sync "<путь проекта>"`.
Корень убирали (`root remove` с «забыть») — сначала `miksy root add "<путь корня>" --tree <раздел>`, затем
`miksy sync --all` (готовую команду miksy печатает после `root remove`; после `clean … --forget` — шаблон, путь и
раздел подставьте сами).

- Совпадающие файлы `sync` берёт обратно сам («взять под учёт — файл miksy, которого не было в учёте»). Изменившиеся —
  конфликт: `miksy sync "<путь проекта>" --force` перезапишет их (прежние — в бэкап). Ненужные теперь (правила убрали из
  слоёв) первый `sync` или `clean` уберёт с бэкапом; в файле правил — только блок miksy, ваш текст остаётся.
- Файлы не нужны — после `sync` выполните `miksy clean "<путь проекта>"` (или `root remove` с согласием убрать). `clean`
  без `sync` может оставить skills, плагин Antigravity и `opencode.json` — он скажет.
- Файлы агента, убранного из `agents` до «забыть», без `--agent` не трогаются: `miksy clean "<путь проекта>" --agent <имя>`
  (агента назовут сообщение «забыто», `miksy doctor` — «Учёт агентов, которых нет в agents» — и подсказка `clean`;
  выполните и её строки с `--agent`).
- **Ваши прежние файлы**, которые miksy когда-то заменил (`--force`), сами не вернутся: копии — в
  `local/backups/originals/` (сколько — скажет сообщение «забыто»), а `clean` удалит файл miksy на их месте — нужное
  верните из копии. Копия `CLAUDE.local.md`, куда miksy лишь дописал блок, — не для возврата: miksy уберёт из файла
  только блок.
- Файл с пометкой miksy, который он больше не пишет, miksy убирает, только если строка этого файла есть в его блоке
  `.git/info/exclude` (такой же файл в другом проекте — скорее всего, ваша копия: его miksy не трогает).
- Вручную уберите: файлы miksy без пометки «Сгенерировано miksy» (skill, `plugin.json`), которые с тех пор поменялись
  или пропали из слоёв; файлы в папке без git (там нет `.git/info/exclude`); ненужные файлы плагина Antigravity (`.agents/plugins/miksy/`) — после
  `sync` они остаются и Antigravity их читает, после `clean` их покажет git. Ваш файл, даже совпадающий, miksy своим не
  считает и при `clean` вернёт.
- Доверие Claude `sync` ставит снова без вопроса, если раньше его ставил miksy, вы отвечали «да» или в слое `trust: true`
  (и не появилось новых хуков и т. п.). Одобрения серверов командного `.mcp.json` miksy берёт обратно, если одобрил бы
  их и сейчас; такие же одобрения, данные вами в окне Claude, станут его, и `clean` их снимет (Claude спросит снова).
  Остальные одобрения — ваши, их он не трогает. См. «[Доверие проектам](trust.md)».
- Всё это — только в проекте, который на этой машине «забыли». В остальных файлы miksy вне учёта этой машины не
  трогаются: в облачной папке на двух машинах так выглядят файлы другой машины.

### Одна облачная папка на двух машинах

Папка проекта в облаке или на сетевом диске (NAS: на Windows `Z:\…` или `\\NAS\…`, на Mac `/Volumes/…`), miksy на
обеих машинах, конфигурация одна (один репо слоёв). Подключите папку корнем на каждой машине с одним и тем же разделом
(`tree`) — тогда у проекта одно место в дереве, и miksy пишет в него одинаковые файлы.

- **Файлы в папке проекта без путей машины** — у всех агентов. У Claude MCP-серверы лежат в домашнем `~/.claude.json`.
  У Codex, opencode и Antigravity серверы с секретами и путями машины записаны командой `miksy mcp <агент> <место>
  <сервер>`: при запуске она берёт настройки своей машины (пути, секреты). Вторая машина видит тот же файл и берёт его
  под учёт молча.
- **Обе машины — на версии miksy с `miksy mcp`** (`miksy update`). Старая версия пишет пути своей машины, и файлы
  начнут перетягиваться; новая в таком случае скажет «похоже, его переписала другая машина со старой версией miksy».
- **Агентам нужна команда `miksy`** — её ставит `miksy setup`. Проверка — `miksy doctor` (раздел «Команда miksy»).
  Codex, запущенный не из терминала на Mac, находит её через `~/.codex/.env` — строку туда дописывает `miksy sync
  --global`.
- **Имя сервера или папки** со знаками вроде `%`, `^`, `!`, `$`, кавычек команде не передать — для такого сервера в файле
  будет путь этой машины, и `sync` предупредит (переименуйте). То же — если одно место в дереве есть у двух корней.
- **Машины не мешают друг другу.** Файлы miksy в проекте скрыты от git строками в `.git/info/exclude`, и у каждой машины
  там свой блок с её номером (`# >>> miksy:claude (машина 7f3a9c41d2e0; …)`; номер вычисляется на машине, в общую
  папку попадает только эта метка). Машина не снимает строки другой, поэтому git на обеих чист, даже если skills у
  машин разные. `clean` (или `root remove` с согласием убрать) на одной машине убирает только то, что нужно лишь ей:
  файлы и одобрения серверов командного `.mcp.json`, которые записала и другая машина, остаются.
- **После обновления miksy выполните `miksy sync --all` на обеих машинах, до этого `clean` не делайте ни на одной.**
  Прежние версии писали блок без номера; первый `sync` новой версии тихо записывает блок машины (вывод тот же) и
  убирает из прежнего блока строки, которые теперь есть в блоках с номером. Пока `sync` сделала только одна машина,
  `clean` любой из них может убрать файлы, нужные другой (`sync` той машины их вернёт).
- **Номер машины сменился** — прежний блок этой машины считается блоком другой, и `clean` не убирает файлы под его
  строками. `miksy doctor` покажет номер и две команды: переустановили систему или пропал `local/state/machine-salt` —
  `miksy sync --all --machine-was <номер>` (блоки снова свои); `local/` перенесён с другого компьютера — `miksy sync
  --all --machine-other <номер>` (это блоки той машины: учёт перестанет считать номер своим, блоки не тронет). Номер
  другой машины эти команды не принимают. Выбрали `--machine-other` по ошибке — `--machine-was` с тем же номером его
  отменит.

Что остаётся разным на машинах:
- **Секрет есть только на одной машине** — это нормально. Codex, opencode и Antigravity берут MCP-серверы проекта из
  файла в папке проекта, и miksy пишет туда все серверы из слоёв, на обеих машинах одинаково. На машине без секрета
  `sync` скажет «на этой машине не запустится — не заданы переменные …», а агент при запуске покажет эту причину у
  сервера. Сервер, заданный в слое только для другой ОС (`os:`), на этой машине молча работает пустым — без
  инструментов и без ошибки. Исключение — HTTP-сервер без секретов и переменных, у которого во всех слоях один и тот
  же адрес: он записывается как есть, чтобы работал вход агента в сервер (OAuth), и на другой ОС тоже работает. У
  Claude серверы проекта лежат в домашнем `~/.claude.json`, общую папку они не задевают.
- **Сервер на этой машине не нужен** (секрета здесь нет и не будет) — `miksy mcp off <имя>` на ней. Файл проекта
  остаётся тем же, а агенты этой машины видят сервер пустым — без инструментов и без ошибки; Claude и домашние
  настройки агентов его не получают. Вернуть — `miksy mcp on <имя>`. Сервер без секретов и переменных (просто
  команда или адрес) в файле проекта записан как есть — файл ведь общий — и запустится и здесь; убрать его из
  проекта можно только в слое (`exclude: [mcp.<имя>]`). Какие серверы на этой машине не запустятся — `miksy doctor`,
  раздел «Справочно».
- **Пределы.** Файлы всё же различаются, если имя сервера или папки нельзя передать команде miksy (`sync` предупреждает
  об этом), и если в
  `agents.<агент>.raw` сервера есть `${HOME}` или переменные машины — raw идёт в файл значениями этой машины.
- **Разные слои** (или разная `tree` у корня) дают разные файлы — у второй машины будет конфликт. Держите слои
  одинаковыми. Разный `agents` можно: машина пишет файлы только своих агентов и чужие не трогает. Одно отличие: если
  на одной машине нет Claude, opencode на ней кладёт skills в `.opencode/skills`, и opencode увидит skill дважды
  (предупреждение в его логе, работе не мешает).
- **Конфликт «файл переписала другая машина»**: `sync` видит, что файл в папке проекта записала другая машина, а у этой
  он получается другим, — конфигурации машин различаются. Где причину видно, `sync` её называет: разные MCP-серверы
  (слои), другой агент пишет этот файл (разный `agents`), старая версия miksy там. Приведите машины к одному: `miksy
  update` на обеих, `git pull` в каталоге конфигурации на обеих, тот же раздел корня (`tree`), затем `miksy sync` на
  обеих. `--force` перезапишет файл версией этой машины, но другая при своём `sync` перепишет его обратно.
- **Переводы строк.** Правила и skills попадают в файлы проекта как есть. Если на Windows git выгружает конфигурацию
  с CRLF (`core.autocrlf=true`), а на Mac — с LF, файлы проекта у машин разные — будет конфликт. Конфигурация,
  созданная `miksy setup` из примера, уже содержит `.gitattributes` с `* text=auto eol=lf`. Своя, созданная иначе, —
  добавьте в её корень такой `.gitattributes`, затем `git add --renormalize .` и коммит; на других машинах — `git
  pull`.
- **Бит исполнения на сетевом диске** (SMB, NAS): там `chmod` может не сработать, и `sync` при каждом запуске
  повторяет строку «права …» для скриптов skills. Это не конфликт и работе не мешает: файлы те же на обеих машинах.
- **Машина со старой версией miksy** (до блока у каждой машины) пишет свой блок без номера и может снимать строки
  другой машины — обновите обе (`miksy update`). Новая версия из её блока убирает только строки, которые есть и в блоках
  с номером, и строки без файлов; остальные её строки остаются, а старая версия на каждом `sync` переписывает свой блок
  заново (до обновления в выводе обеих машин — строки `.git/info/exclude`).
- **Worktree в общей папке**: блок worktree помечен ещё и путём к нему, а он на машинах разный — машины не узнают
  блоки друг друга, и защита выше для worktree не действует. Держите worktree вне общей папки.
- **Недоступная папка**: если на одной машине диск не подключён, `sync` там считает проекты недоступными или
  переехавшими — подключайте диск до `sync`.

### Другие случаи

- **Вложенный корень** (внутри другого) — можно: папка относится к самому глубокому корню. Пример: на Mac облачная папка
  лежит отдельно (`~/Library/CloudStorage/…/Clients`), на Windows — внутри основного корня (`D:/Projects/Cloud/Clients`);
  на Windows она — вложенный корень с той же `tree: Clients`, конфигурация общая. Предупреждение — только если он внутри
  проекта или группы внешнего корня. Что ещё учесть — [см. выше](#одна-облачная-папка-на-двух-машинах).
- **Раздел внутри чужого места** — `tree: Clients/Sub`, когда `Clients` — раздел другого корня, или `tree: Org/Sub` при
  папке `Org` в основном корне: проекты получат и всё заданное для `Clients` (`Org`). Задумано — ничего не делайте; нет —
  возьмите раздел вне этого места (`tree: Clients-Sub`), общее — слоем в `map.yaml`. `root add` и `doctor` подскажут и
  перечислят, что унаследуется.
- **Один каталог дважды** — ошибка: оставьте одну запись. Сюда же другое написание пути (`D:/Projects` и
  `d:\Projects\`) и ссылка (симлинк, junction) на каталог, уже указанный корнем.
- **Раздел совпадает с папкой основного корня** (`tree: Clients` и папка `Clients`) — слои `layers/tree/Clients/` получат
  обе (`doctor` — проблема, `sync`, `projects`, `root add` — предупреждение). Переименуйте раздел или папку; общее —
  [явно](#правила-нескольких-корней). Вложенный корень на своём же месте (`D:/Projects/Clients` с `tree: Clients`) — не
  совпадение.
- **`target: true`** действует по месту в дереве: `layers/tree/Clients/Acme/layer.yaml` делает целью `E:/Clients/Acme`.
  Группы считаются в пределах своего корня.
- **`doctor`** ищет «лишние» разделы (слой есть, папки нет) только в корнях этой машины; разделы других машин и разделы
  верхнего уровня, похожие на папку основного корня (`layers/tree/Clients` и `Clients-old`), — справочно: это может быть
  и опечатка, и корень другой машины.
