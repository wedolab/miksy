# Несколько папок с проектами

Проекты лежат в нескольких местах (второй диск, облачное хранилище) — как подключить их все, сменить основную папку и
что делать, если диск не подключён или потерян.

← [README](../README.md)

## Несколько корней workspace

Обычно все проекты лежат в одной папке — workspace (`workspace: ~/Projects` в `local/machine.yaml`). Если мест
несколько, каждое становится **корнем** workspace; первый — основной. «Папка с проектами» и «корень» здесь — одно и то же.

**Добавить папку с проектами** (облачную — сначала прочтите [ниже](#папки-облачных-хранилищ)):

```
miksy root add "E:\Clients"
```

miksy спросит **ветку** папки — имя её папки в `layers/tree/`, где будут её слои (не путать с веткой git). Обычно
нажмите Enter: он предложит имя папки (`Clients`; знаки `[ ] { } * ?` и `!` в начале уберёт — с ними не работали бы
привязки `match:` в `map.yaml`). Папка уже подключена на другой машине — введите её ветку оттуда, иначе слои той ветки
сюда не дойдут. Без терминала (скрипт, агент): `miksy root add "E:\Clients" --tree Clients`. Сменить ветку потом можно,
но слои придётся перенести в папку с новым именем.

Команда допишет корень в `local/machine.yaml`, скажет, сколько проектов нашлось, и предложит `miksy sync --all`. Путь —
как удобно: `"E:\Clients"`, `E:/Clients`, `~/Cloud` (с пробелами — в кавычках). В мастере (`miksy setup`) то же —
вопрос «Есть ещё папки с проектами?». В `machine.yaml` это выглядит так:

```yaml
workspace:
  - D:/Projects                             # основной корень — в корне дерева слоёв (layers/tree/)
  - { path: "E:/Clients", tree: Clients }   # ещё корень — его ветка: layers/tree/Clients/
```

Дерево слоёв одно на все корни: `E:/Clients/Acme/site` получает `layers/tree/` (общее для всех), `layers/tree/Clients/`
и `layers/tree/Clients/Acme/`; `D:/Projects/Org/app` — `layers/tree/` и `layers/tree/Org/`. На другой машине пути могут
быть другими — там в `machine.yaml` свои пути с теми же `tree`.

**Убрать папку** — `miksy root remove <путь>`; записанное в её проекты miksy уберёт только с вашего согласия (вопрос,
«да» по умолчанию; без терминала — подскажет команды). Заранее посмотреть — `--dry-run`. Основной корень убрать нельзя.
Список корней — `miksy root`.

Сам корень настройки не получает — их получают проекты в нём (git-репо) и папки с пометкой `target: true`
(`miksy target E:/Clients/Acme` — пометка ляжет в `layers/tree/Clients/Acme/layer.yaml`).

### Папки облачных хранилищ

Google Drive, Яндекс Диск, OneDrive, Dropbox, iCloud Drive и т. п.: всё, что miksy туда запишет (`CLAUDE.local.md`,
`.claude/`, `.agents/`, `.codex/`, `opencode.json` — правила, список MCP-серверов, skills), уйдёт в облако, на ваши
устройства и всем, с кем папка расшарена. Значений секретов там нет (они в `local/` вашей машины), но правила и названия
серверов увидят. Подключайте такую папку, только если это вас устраивает. Одна облачная папка на двух машинах пока
надёжно работает только для Claude — [подробнее](#одна-облачная-папка-на-двух-машинах).

## Правила нескольких корней

- **У каждого корня, кроме основного, своя ветка (`tree`) — обязательно.** Иначе слои одной папки молча доставались бы
  одноимённой папке другого корня (`Acme` в основном корне получила бы MCP-серверы с токенами клиента из
  `layers/tree/Acme/`). Без `tree` или с занятой веткой `machine.yaml` не загрузится — ошибка скажет, что поправить.
  У основного `tree` можно не указывать; указан — тоже должен быть своим.
- **Общее для нескольких корней — явно.** Для всех проектов всех корней — `layers/tree/instructions/` (и остальное в
  корне дерева) или `layers/global/`. Для отдельных папок в разных корнях — свой слой в `map.yaml`:

  ```yaml
  # map.yaml — слой layers/acme/ для Acme в обоих корнях (Clients и Archive)
  layers:
    - { match: "{Clients,Archive}/Acme", use: acme }      # сама папка Acme
    - { match: "{Clients,Archive}/Acme/**", use: acme }   # и всё внутри неё
    # Acme и в основной папке с проектами — там место без ветки: добавьте "Acme" и "Acme/**"
    # (или шаблоны {Acme,Clients/Acme,Archive/Acme})
  ```

  Шаблоны сравниваются без учёта регистра, как и слои дерева.
- **`${WORKSPACE}`** в определениях MCP — всегда основной корень. Путь в другой корень — своей переменной машины:

  ```yaml
  # local/machine.yaml (на каждой машине — свой путь)
  vars:
    CLIENTS: "E:/Clients"
  # в слое: args: ["${CLIENTS}/tools/report.py"]
  ```

  Где переменная не задана, сервер пропускается с сообщением. `miksy adopt` сворачивает в `${WORKSPACE}` только пути
  основного корня, для других подсказывает завести переменную.

## Сменить основной корень

`miksy setup --force`, вопрос «Корень workspace». Что будет с прежним основным, мастер скажет сам:

- основным стал **дополнительный корень** — его ветка остаётся прежней;
- основным стал **новый каталог** (например, перенесли папку с проектами) — ветку прежнего основного забирает он;
- прежний основной **уходит из workspace**, его проекты miksy больше не обновляет. Лежит внутри нового основного или
  другого корня — его проекты остаются и получают слои по пути от того корня; новый основной внутри прежнего — уходят
  только проекты прежнего вне нового.

`${WORKSPACE}` в слоях после смены — новый основной корень.

**Прежней папки нет или она пуста** (перенесли) — возвращать нечего, мастер так и скажет («прежнего основного … нет на
месте», «в прежнем основном … проектов нет»). Учёт (список записанного miksy) обычно переезжает сам —
[«Переименовали или перенесли каталог»](../README.md#переименовали-или-перенесли-каталог). «Нет на месте» потому, что
диск не подключён, — подключите и [верните его дополнительным корнем](#вернуть-прежний-основной-дополнительным-корнем).

**Внутри прежней была ещё папка с проектами** (свой корень) — мастер назовёт её и, если её перенесли, где она теперь.
Перенесли в новую основную:

1. На вопрос «Записать настройки агентам сейчас?» в конце мастера — «нет».
2. Поправьте её `path:` в `local/machine.yaml`.
3. `miksy sync --global` и `miksy sync --all`.

До этого `--force` из строки конфликта о её проектах не выполняйте. Новая основная — не та, куда перенесли прежнюю, или
не её копия — `path:` не меняйте: одноимённая папка там не та же самая. Тогда вложенная остаётся в workspace по
прежнему пути.

**Прежняя на месте, но не нужна** (папку скопировали) — в каждом её проекте `miksy clean "<путь проекта>"` (работает и
вне workspace). В новой копии файлы miksy с путём папки (например, `.codex/config.toml` с `${WORKSPACE}`) — конфликт, пока
не выполните в её проектах `miksy sync "<путь проекта>" --force` (бэкап будет). Внутри прежней была вложенная папка с проектами
со своей веткой, а вы переходите на копию целиком — сначала так же, как при переносе: шаги 1–3 выше (её `path:` в
`local/machine.yaml` — на её копию), и только потом `clean` и `sync … --force`: иначе `--force` заменил бы правила её ветки
правилами основной папки.

### Вернуть прежний основной дополнительным корнем

По шагам из сообщения мастера («Вернуть его: 1) … 2) …»), если он их печатал. Иначе:

- У него своя ветка, и новый основной её не занял, — `miksy root add "<прежний основной>" --tree <его ветка>`.
- Иначе сначала перенесите его слои под новую ветку (ниже), затем `miksy root add "<прежний основной>" --tree <ветка>`
  и «да» на `sync --all`. В обратном порядке `sync --all` снимет с его проектов ещё не перенесённые слои — тогда после
  переноса ещё раз `miksy sync --all`.

Перенос слоёв меняет конфигурацию на всех машинах, где она есть:

- **Ветки не было** — перенесите папки организаций и проектов (`layers/tree/Org/…` → `layers/tree/<ветка>/Org/…`). Общие
  `instructions/`, `mcp/`, `skills/`, `layer.yaml` в самой `layers/tree/` и папки веток других корней не трогайте.
  Привязки `map.yaml` (`match:`) — ветку в начало: `Org/**` → `<ветка>/Org/**`, `*/infra-*` → `<ветка>/*/infra-*`; в
  `{…}` — к каждой его папке (`{Org,Lab}/**` → `{<ветка>/Org,<ветка>/Lab}/**`).
- **Ветку забрал новый каталог** (`Main`) — переименуйте `layers/tree/Main` в новую ветку, в привязках `Main/` →
  `<ветка>/`. Только если ветка из одной части и внутри нет веток других корней; иначе (`Clients/Home`; у другого корня
  `Main/Drive`) переносите вручную только слои и привязки проектов прежнего основного.
- **У нового основного папки с теми же именами** (`Org` и там, и там; мастер тогда шагов не печатает) — их не переносите,
  а скопируйте (`layers/tree/Org` → `layers/tree/<ветка>/Org`; дальше правки — в обеих), а привязки к ним не меняйте, а
  допишите рядом такие же с веткой (`Org/**` и `<ветка>/Org/**`).
- В имени ветки запятая или `}` — вместо `{…}` отдельная привязка на каждую папку.
- Шаблоны, которые начинаются с `**`, не меняйте.

Без этого привязки перестанут совпадать, и `sync` снимет эти слои молча.

## Выбрали основным не ту папку

Верните прежний `local/machine.yaml` — `setup` сохранил его копию. «Вернуть его» из сообщения мастера не выполняйте.

1. Копия — в `<конфигурация>/local/backups/<дата и время>/` (не `before-miksy-…`); путь внутри повторяет путь
   конфигурации, на Windows — без двоеточия: `…\<дата и время>\C\Users\you\Projects\miksy-config\local\machine.yaml`.
   Все копии:

   ```
   Get-ChildItem -LiteralPath '<конфигурация>\local\backups' -Recurse -Filter machine.yaml | ForEach-Object FullName   # Windows (PowerShell)
   find '<конфигурация>/local/backups/' -name machine.yaml                                                              # macOS, Linux
   ```

   Нужна последняя, где первым в `workspace` ещё прежний основной (после ошибки `setup`, `update` или `root add` могли
   скопировать файл уже с ошибочной папкой). Встретится `<secret:ИМЯ>` (в пути корня или `tree:`) — впишите значение
   из `local/secrets.env`.
2. Скопируйте её на место:

   ```
   Copy-Item -LiteralPath '<копия>' -Destination '<конфигурация>\local\machine.yaml'   # Windows (PowerShell)
   cp '<копия>' '<конфигурация>/local/machine.yaml'                                     # macOS, Linux
   ```

3. `miksy sync --global` и `miksy sync --all`. Записанное в проекты ошибочной папки `miksy doctor` покажет в разделе
   «Цели учёта вне workspace»: для путей внутри ошибочной папки — `miksy clean "<путь>"`, другие не трогайте. Если там
   есть проекты, где вы нарочно оставили настройки miksy (например, `root remove` без «убрать записанное»), miksy их не
   отличит — их не чистите, а не помните какие — не чистите ничего: настройки вне workspace ничего не ломают, `clean`
   можно и позже (он вернёт ваши файлы, но снимет настройки miksy).

## Особые случаи

### Корень недоступен

Нет его папки, нет диска (не подключён, облако не запущено, на Linux ничего не смонтировано в `/media/<пользователь>/…`
или `/mnt/…`) или ссылка ведёт в никуда. Так же — **пустая папка корня, если miksy уже писал в его проекты** (на Linux и
macOS обычно точка монтирования без диска). `projects`, `sync --all` и `doctor` пропускают его с предупреждением,
записанное туда не трогается. Подключите диск — всё вернётся.

**Убрать записанное в его проекты** — `miksy clean "<путь проекта>"`: уберёт, до чего дотянется (MCP-серверы проекта в
настройках агентов, доверие, свои скрипты), а записи о файлах на диске оставит — по ним узнает свои файлы, когда диск
вернётся; тогда повторите `clean`. Данных больше нет (диск потерян, папку удалили) — ответьте «да» на «Забыть записанное
туда?» (по умолчанию — нет) или, без терминала, добавьте `--forget`. Пустую точку монтирования, очищенную вами, — тоже
`clean … --forget`.

**Убрать сам корень** — `miksy root remove <путь>` спросит то же. «Нет» — корень уходит из списка, записанное и учёт
остаются: когда диск вернётся, `miksy clean "<путь проекта>"`, а для агентов, убранных из `agents`, —
`miksy clean "<путь проекта>" --agent <имя>` (команды — в выводе `root remove`). Корень внутри другого корня без
«забыть» не убирается. `--dry-run` (можно с `--forget`) покажет заранее, почему корень недоступен, будет ли вопрос и
сколько файлов забудется.

### Диск нашёлся после «забыть»

Учёта этих файлов больше нет, но свои miksy узнаёт сам. Папка проекта в workspace — `miksy sync "<путь проекта>"`.
Корень убирали (`root remove` с «забыть») — сначала `miksy root add "<путь корня>" --tree <ветка>`, затем
`miksy sync --all` (готовую команду miksy печатает после `root remove`; после `clean … --forget` — шаблон, путь и
ветку подставьте сами).

- Совпадающие файлы `sync` берёт обратно сам («взять под учёт — файл miksy, которого не было в учёте»). Изменившиеся —
  конфликт: `miksy sync "<путь проекта>" --force` перезапишет их (прежние — в бэкап). Ненужные теперь (правила убрали из
  слоёв) первый `sync` или `clean` уберёт с бэкапом; в файле правил — только блок miksy, ваш текст остаётся.
- Файлы не нужны — после `sync` выполните `miksy clean "<путь проекта>"` (или `root remove` с согласием убрать). `clean`
  без `sync` может оставить skills, плагин Antigravity и `opencode.json` — он скажет.
- Файлы агента, убранного из `agents` до «забыть», без `--agent` не трогаются: `miksy clean "<путь проекта>" --agent <имя>`
  (агента назовут сообщение «забыто», `miksy doctor` — «Учёт агентов, которых нет в agents» — и подсказка `clean`;
  выполните и её строки с `--agent`).
- **Ваши прежние файлы**, которые miksy когда-то заменил (`--force`), сами не вернутся: копии — в
  `local/backups/originals/` (сколько — скажет сообщение «забыто»), а `clean` удалит файл miksy на их месте — нужное
  верните из копии. Копия `CLAUDE.local.md`, куда miksy лишь дописал блок, — не для возврата: miksy уберёт из файла
  только блок.
- Файл с пометкой miksy, который он больше не пишет, miksy убирает, только если строка этого файла есть в его блоке
  `.git/info/exclude` (такой же файл в другом проекте — скорее всего, ваша копия: его miksy не трогает).
- Вручную уберите: файлы miksy без пометки «Сгенерировано miksy» (skill, `plugin.json`), которые с тех пор поменялись
  или пропали из слоёв; файлы в папке без git (там нет `.git/info/exclude`); ненужные файлы плагина Antigravity (`.agents/plugins/miksy/`) — после
  `sync` они остаются и Antigravity их читает, после `clean` их покажет git. Ваш файл, даже совпадающий, miksy своим не
  считает и при `clean` вернёт.
- Доверие Claude `sync` ставит снова без вопроса, если раньше его ставил miksy, вы отвечали «да» или в слое `trust: true`
  (и не появилось новых хуков и т. п.). Одобрения серверов командного `.mcp.json` miksy берёт обратно, если одобрил бы
  их и сейчас; такие же одобрения, данные вами в окне Claude, станут его, и `clean` их снимет (Claude спросит снова).
  Остальные одобрения — ваши, их он не трогает. См. «[Доверие проектам](trust.md)».
- Всё это — только в проекте, который на этой машине «забыли». В остальных файлы miksy вне учёта этой машины не
  трогаются: в облачной папке на двух машинах так выглядят файлы другой машины.

### Одна облачная папка на двух машинах

Папка проекта в облаке, miksy на обеих машинах:

- **Claude** — работает, если конфигурация одна: в папке проекта только `CLAUDE.local.md` и skills (MCP Claude — в
  домашнем `~/.claude.json`). Оговорки: одобрения серверов командного `.mcp.json` лежат в `.claude/settings.local.json`
  проекта — ответили на машинах по-разному, и машины будут по очереди менять его строку в `.git/info/exclude`, а git
  второй — показывать файл. И `clean` (или `root remove` с согласием убрать) на одной машине убирает правила Claude и у
  другой — до её следующего `sync`.
- **Codex, opencode, Antigravity** — нет: их файлы (`.codex/config.toml`, `opencode.json`, плагин Antigravity) содержат
  пути своей машины, у второй будет конфликт «файл miksy, которого нет в учёте, отличается»; `--force` лишь перетягивает
  файл между машинами. Разные skills на машинах — git может показывать файлы другой. Доработка — в следующих выпусках;
  пока включайте эти агенты для такого проекта на одной машине.

### Другие случаи

- **Вложенный корень** (внутри другого) — можно: папка относится к самому глубокому корню. Пример: на Mac облачная папка
  лежит отдельно (`~/Library/CloudStorage/…/Clients`), на Windows — внутри основного корня (`D:/Projects/Cloud/Clients`);
  на Windows она — вложенный корень с той же `tree: Clients`, конфигурация общая. Предупреждение — только если он внутри
  проекта или группы внешнего корня. Надёжно пока только для Claude — [см. выше](#одна-облачная-папка-на-двух-машинах).
- **Ветка внутри чужого места** — `tree: Clients/Sub`, когда `Clients` — ветка другого корня, или `tree: Org/Sub` при
  папке `Org` в основном корне: проекты получат и всё заданное для `Clients` (`Org`). Задумано — ничего не делайте; нет —
  возьмите ветку вне этого места (`tree: Clients-Sub`), общее — слоем в `map.yaml`. `root add` и `doctor` подскажут и
  перечислят, что унаследуется.
- **Один каталог дважды** — ошибка: оставьте одну запись. Сюда же другое написание пути (`D:/Projects` и
  `d:\Projects\`) и ссылка (симлинк, junction) на каталог, уже указанный корнем.
- **Ветка совпадает с папкой основного корня** (`tree: Clients` и папка `Clients`) — слои `layers/tree/Clients/` получат
  обе (`doctor` — проблема, `sync`, `projects`, `root add` — предупреждение). Переименуйте ветку или папку; общее —
  [явно](#правила-нескольких-корней). Вложенный корень на своём же месте (`D:/Projects/Clients` с `tree: Clients`) — не
  совпадение.
- **`target: true`** действует по месту в дереве: `layers/tree/Clients/Acme/layer.yaml` делает целью `E:/Clients/Acme`.
  Группы считаются в пределах своего корня.
- **`doctor`** ищет «лишние» ветки (слой есть, папки нет) только в корнях этой машины; ветки других машин и ветки
  верхнего уровня, похожие на папку основного корня (`layers/tree/Clients` и `Clients-old`), — справочно: это может быть
  и опечатка, и корень другой машины.
