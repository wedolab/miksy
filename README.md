# Miksy

Один источник правил, skills (готовых инструкций для отдельных задач, которые агент подключает сам, когда задача
подходит) и MCP-серверов (программ и сервисов, через которые агент получает инструменты: трекер, документацию, базу)
для нескольких AI-агентов: **Claude Code, Codex, opencode, Antigravity**.

Вы описываете настройки один раз — правила, MCP-серверы, skills, — а miksy записывает их каждому агенту в
каждом проекте: правила — в его файлы инструкций, MCP-серверы — в его конфиг, skills — в его каталог. Miksy не
работает в фоне: поменяли настройки — запустите `miksy sync`.

**Miksy — не агент.** Он ничего не выполняет вместо агентов и не стоит между вами и ними: это генератор
настроек для агентов, которые у вас уже стоят. Имя — от того, что он раскладывает: **M**CP, **I**nstructions,
**K**eys (секреты), **S**kills.

Этот репо — **движок** (программа miksy). Ваши правила, секреты и настройки машин живут отдельно — в
**конфигурации**: личном каталоге (обычно `miksy-config` рядом с движком; лучше — в своём приватном git-репо).
Движком можно делиться: ваших данных в нём нет.

## С чем работает miksy

**Агенты** — четыре: **Claude Code**, **Codex**, **opencode** (версии 2.x) и **Antigravity**. Ставить всех не
нужно: miksy пишет настройки только тем, что у вас есть. Других агентов (Cursor, GitHub Copilot, Windsurf и т. п.)
он не поддерживает и их настройки не трогает. В конфигурации и командах агенты называются `claude`, `codex`,
`opencode`, `antigravity` (прежнее имя Antigravity — `gemini` — тоже работает).

**Где запускать агентов — где удобно.** miksy только раскладывает файлы настроек, а агент читает их сам. Проверено:
- в терминале — все четыре агента;
- в редакторе Zed через ACP (так редактор подключает агентов) — Claude Code, Codex и opencode;
- Antigravity — в его IDE и в его CLI (`agy`), в том числе в терминале Zed. Через ACP в Zed Antigravity настройки
  от miksy пока не получает.

Другие редакторы (Claude Code в VS Code или JetBrains и т. п.) читают те же файлы — скорее всего, всё работает,
но это не проверялось.

**ОС** — Windows, macOS и Linux (Ubuntu 24.04): проверено на настоящих машинах и автоматическими тестами.

**Нужны** git и [Bun](https://bun.sh) 1.3.14 или новее — программа, которая запускает miksy (Bun установщик предложит
поставить сам).

## Как устроен miksy

Слова, которые встречаются дальше везде.

- **Конфигурация** — ваш каталог с настройками (`miksy-config`). В нём слои и `local/` — то, что только для этой
  машины.
- **Слой** — папка с правилами (`instructions/*.md`), MCP-серверами (`mcp/*.yaml`) и skills (`skills/`) для
  какого-то места: для всех агентов везде, для всех проектов, для организации, для одного проекта.
- **Workspace** — папка с вашими проектами (например, `~/Projects` или `D:\Projects`). Таких папок может быть
  несколько (второй диск, облачная папка) — каждая называется **корнем** workspace.
- **Проект** — git-репо внутри workspace, а также папка внутри workspace, где агент уже работал (она есть в списке
  проектов любого из четырёх агентов — например, вы открывали в ней Claude; помечать её `miksy target` не нужно).
  Сама папка с проектами и папки внутри репо — не отдельные проекты.
- **Цель** — куда miksy пишет настройки: проекты, домашний каталог агентов и папки без git, которые вы отметили сами
  (`miksy target`).
- **Организация** — папка в workspace, в которой лежат проекты: `~/Projects/Acme/app` — проект `app` организации
  `Acme`. Правила организации получают все её проекты.
- **Ветка** (дерева слоёв) — имя папки в `layers/tree/`, где лежат слои второй и следующих папок с проектами
  (`--tree Clients` → `layers/tree/Clients/`). Это не ветка git. Нужна, чтобы слои разных папок с проектами не
  смешивались: папка `Acme` может быть и в `D:\Projects`, и в `E:\Clients`, а правила у них разные.
- **Команда проекта** — коллеги, которые ведут репо проекта. «Настройки команды» — то, что они закоммитили в репо
  (хуки, `.mcp.json` и т. п.); miksy их не трогает.
- **`sync`** — команда, которая записывает настройки. Пока вы её не запустили, агенты ничего нового не получат.
- **Доверие** — отметка агента (Claude, Codex) «этому проекту можно доверять»: без неё агент не применяет
  настройки проекта. Обычно его ставит сам miksy; если в проекте есть то, что агент выполнит без вопроса и что
  ставил не miksy (например, **хуки** — программы, которые агент запускает сам), решаете вы
  («[Доверие проектам](#доверие-проектам)»).

В путях команд miksy можно писать `~` — домашний каталог (`miksy root add ~/Cloud`), и в PowerShell тоже. Путь с
пробелами берите в кавычки: `miksy sync "D:\My Projects\app"`.

```
miksy-config/                 конфигурация
├── map.yaml                  какие слои глобальные, особые привязки (редко нужно)
├── layers/
│   ├── global/               ваши правила для всех агентов везде → домашний каталог
│   ├── env-windows/, env-macos/, env-linux/   правила про ОС (shell, синтаксис команд)
│   └── tree/                 → все проекты workspace — дерево слоёв
│       ├── instructions/     правила всех проектов
│       ├── mcp/context7.yaml MCP-сервер для всех проектов
│       ├── Acme/             → всё внутри ~/Projects/Acme
│       │   └── billing-api/  → только проект ~/Projects/Acme/billing-api
│       └── Personal/         → всё внутри ~/Projects/Personal
├── local.example/README.md   заметка о подготовке машины: что miksy не настраивает сам (профили облачных CLI и т. п.)
└── local/                    только эта машина, не в git:
    ├── machine.yaml          где workspace, какие агенты, пути к программам (vars)
    ├── secrets.env           значения секретов: ИМЯ=значение
    ├── secrets/, run/        файлы секретов и скрипты-обёртки для агентов (создаёт sync)
    ├── state/manifest.json   учёт — что miksy записал (ниже)
    ├── trust.json            ваши решения о доверии проектам
    └── backups/              копии файлов перед изменением и оригиналы
```

**Дерево слоёв** (`layers/tree/`) повторяет workspace: проект получает все слои по своему пути сверху вниз —
`tree/`, затем `tree/Acme/`, затем `tree/Acme/billing-api/`. Правила всех слоёв складываются: сначала верхних, внутри
слоя — по имени файла (файлы с одним именем в разных слоях — оба). MCP-сервер или skill с тем же именем в нижнем
слое заменяет верхний. Нет папки в дереве — нет слоя. Регистр букв в именах не важен (`Acme` и `acme` — один слой;
если в `layers/tree/` окажутся две папки, которые отличаются только регистром, — так бывает на Linux, —
применяется одна из них, и `miksy doctor` скажет какая).

Что получит проект и из какого слоя — `miksy explain <путь>` (без пути — текущий каталог; папка вне workspace
получает только домашние настройки — их и покажет; `--global` — домашние настройки агентов).

Что лежит в слое, как убрать пришедшее сверху, куда miksy пишет файлы каждого агента и как он помнит записанное —
«[Устройство подробнее](#устройство-подробнее)».

## Установка

Одна инструкция для всех случаев: первая машина или вторая, агенты чистые или уже настроены руками. Ваши ручные
настройки не пропадут: чужие файлы miksy не трогает, а если заменяет файл — сохраняет оригинал и возвращает его
при удалении miksy. Исключение — то, что вы сами перенесёте в конфигурацию (мастер, `miksy adopt`): это miksy берёт
себе, и удаление miksy убирает его у агентов («[Как удалить miksy](#как-удалить-miksy)»).

**Что нужно:** git и хотя бы один агент («[Установка агентов](#установка-агентов)»). Bun установщик предложит
поставить сам.

**Перед установкой решите, какая папка — с проектами** (workspace). Настройки получат все git-репо в ней, в том
числе рабочие: в репо miksy кладёт только файлы, которые git не отслеживает, и прячет их от git
(`.git/info/exclude`), — в коммиты они не попадут. Исключить отдельный репо внутри этой папки нельзя: репо, которым
настройки не нужны, держите вне её.

**Поручаете установку агенту** (Claude Code, Codex и т. п.)? Дайте ему ссылку на [INSTALL-AGENT.md](INSTALL-AGENT.md):
там шаги для агента — что он делает сам, а что только после вашего «да» в чате.

**Шаг 1. Скачайте miksy в папку с проектами.** Пример — для `~/Projects`; своя папка — подставьте её в обе строки
команды. Рядом мастер положит вашу конфигурацию (`miksy-config`). Можно и в другое место — мастер всё равно спросит, где ваши
проекты (будет вторая машина — раскладывайте на обеих одинаково: «[Вторая машина](#вторая-машина)»).

macOS и Linux:

```
git clone -b stable https://github.com/wedolab/miksy.git ~/Projects/miksy
cd ~/Projects/miksy && ./install.sh
```

Windows (PowerShell):

```
git clone -b stable https://github.com/wedolab/miksy.git $HOME\Projects\miksy
cd $HOME\Projects\miksy; powershell -ExecutionPolicy Bypass -File .\install.ps1
```

`-b stable` — ветка git с последним выпуском: с неё miksy обновляется командой `miksy update`.

Или одной строкой — скрипт сам спросит, куда скачать miksy (по умолчанию `~/Projects/miksy`), и поставит последний
выпуск (сам скрипт берётся из ветки `main`, а движок — из `stable`, как у команд выше):

```
curl -fsSL https://raw.githubusercontent.com/wedolab/miksy/main/install.sh | bash      # macOS, Linux
irm https://raw.githubusercontent.com/wedolab/miksy/main/install.ps1 | iex             # Windows (PowerShell)
```

**Шаг 2. Ответьте на вопросы мастера** — программы настройки `miksy setup`, которую запустит установщик (сначала он
проверит git и поставит Bun — покажет команду и спросит). Мастер идёт по своим вопросам (ниже — «вопрос 1» … «вопрос
10»), у каждого — короткое пояснение; любой, кроме первого, можно пропустить, а повторный `miksy setup` продолжит с
несделанного.
Перед каждым изменением он спрашивает. У **безопасных вопросов** — они только создают своё и ничего не меняют у
агентов: 2 (запись `local/machine.yaml`), 3 (копия настроек агентов), 5 (команда `miksy` и PATH) — Enter значит
«да» (`[Y/n]`); у вопросов с изменениями — 4 (установка программ), 6 (перенос ваших настроек), 9 (запись настроек
агентам), а также «сделать конфигурацию git-репо» в вопросе 1 — «нет» (`[y/N]`). В вопросе 1 выбирают вариант
цифрой, вопросы 7, 8 и 10 только ждут Enter.

**Есть свои правила** в `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` и т. п.? На вопрос 9 ответьте «n» и перенесите их
до записи — «Сначала посмотреть, потом записать» и «Свои правила» ниже.

1. **Конфигурация** — выбор цифрой (Enter — отмена: мастер остановится). «1» — своя в git (с другой машины): дайте
   адрес, мастер скачает её рядом с движком («[Вторая машина](#вторая-машина)»). «2» — новая из примера; затем
   вопрос «Сделать конфигурацию git-репо и записать первый коммит?» — ответьте «y»: без git конфигурацию не
   перенести на другую машину (удалённый репо заведите сами — мастер подскажет, как подключить). В примере: общие правила для агентов (как
   работать с конфигурацией miksy и где что лежит в workspace; `layers/global/instructions/` — для всех агентов
   везде, `layers/tree/instructions/` — для всех проектов), MCP-сервер context7 (документация библиотек) для всех
   проектов и skill `miksy`, который объясняет агентам, как менять конфигурацию. Вопрос 9 запишет это всем агентам
   во все проекты. Хотите сначала посмотреть и поправить — см. «Сначала посмотреть, потом записать» ниже.
2. **Workspace и агенты.** Папка с проектами (Enter — предложенная), по желанию — ещё папки с проектами
   («[Несколько корней workspace](#несколько-корней-workspace)»; путь можно вставить в кавычках, как его копирует
   Проводник), и найденные агенты. Агентов мастер не ставит — только говорит, каких нет. (При повторном запуске
   вопрос «Добавить … новых агентов» называет и тех, кого вы убрали из `agents` сами, — тогда «n», а нового допишите
   в `agents` в `local/machine.yaml` руками.)
3. **Копия настроек агентов** — один раз, до первой записи: в `local/backups/before-miksy-<метка>/`.
4. **Программы для MCP-серверов** (`npx`, `uvx`, `docker`…) — чего не хватает: покажет команду и выполнит после «y».
5. **Команда `miksy`** — создаст её (`~/.bun/bin/miksy`, на Windows — `miksy.cmd` там же) и, если надо, добавит
   этот каталог в PATH: строкой в `~/.zshrc` (оболочка zsh), `~/.bash_profile` (bash на macOS) или
   `~/.bashrc` (bash на Linux), на Windows — в PATH пользователя. Новый PATH действует в новых окнах терминала: откройте новое окно, чтобы `miksy` нашлась.
6. **Ручные настройки агентов** — MCP-серверы (домашние и проектов) и skills проектов, которые вы добавляли агентам
   сами: по каждому спросит, куда перенести его в конфигурацию (его получат все агенты) — цифрой: глобально (все
   агенты везде), workspace (все проекты), организация или проект, где он найден; «0» — оставить у агента, «s» —
   пропустить остальные. Покажет, где первая
   запись столкнётся с вашими файлами. Свои **правила** (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` и т. п.) и
   домашние skills агентов (`~/.claude/skills/…` и т. п.) мастер не переносит — как перенести, ниже; лучше сделать
   это до вопроса 9.
7. **Секреты** — каких токенов не хватает и куда их вписать (`local/secrets.env` в конфигурации, на Windows —
   `$HOME\Projects\miksy-config\local\secrets.env`; другая папка с проектами — путь другой, мастер его печатает).
   Подождёт: заполните файл и нажмите Enter (или «s» — позже: сервер без секрета `sync` пропустит с сообщением, пока
   не впишете значение). Значения мастер не спрашивает и не показывает. Стартовой конфигурации секреты не нужны
   (context7 работает без токена).
8. **План** — что будет создано и обновлено (`v` — полный план).
9. **Запись** — «Записать настройки агентам сейчас? [y/N]»: Enter значит «нет», для записи ответьте «y».
   `sync --global` и `sync --all` — настройки во все git-репо папок с проектами. О доверии проектам,
   где в репо есть хуки или свои MCP-серверы, спросит по каждому («[Доверие проектам](#доверие-проектам)»).
10. **Проверка** — итог `miksy doctor` и вопрос для агента: перезапустите его (шаг 3 ниже), откройте проект и
   спросите «Процитируй первую строку раздела „## MCP“ в твоих инструкциях и вызови context7 для „bun“». Ответ
   «MCP-серверы подключает miksy по слоям…» и найденная библиотека — всё работает (так — со стартовой
   конфигурацией; со своей спросите о своём правиле и сервере).

**Шаг 3. Перезапустите открытые сессии агентов** — настройки читаются при старте.

**Сначала посмотреть, потом записать.** Хотите до записи поправить стартовые правила или перенести свои (ниже) — на
вопрос 9 ответьте «n», поправьте файлы в конфигурации (на Windows — `$HOME\Projects\miksy-config\layers\…`), затем
в новом окне терминала (команда `miksy` найдётся только там) снова `miksy setup`: он продолжит с несделанного и
дойдёт до записи.

**Свои правила**, которые вы писали агентам руками (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` и т. п.), остаются
у того агента, где были, а остальные агенты их не получат. Перенесите их в `layers/global/instructions/<имя>.md`
(для всех агентов), удалите из файлов агентов (miksy пишет свой блок между `<!-- miksy:begin … -->` и
`<!-- miksy:end -->`, ваш текст — вне его), затем `miksy sync --global` (или сделайте это до вопроса 9 — абзац выше).
Пока не удалите, у этого агента правило будет дважды. Свои **домашние skills** агентов (`~/.claude/skills/<имя>/` и т. п.) так же: скопируйте папку skill в
`layers/global/skills/<имя>/` и удалите у агента, затем `miksy sync --global`.

**Вернуть всё как было** — «[Как удалить miksy](#как-удалить-miksy)»: там же — как вернуть копию из вопроса мастера
«Копия настроек агентов».

Для скриптов, CI и агентов (без терминала — когда команду запускает скрипт или агент, а не вы):
`miksy setup --yes` — без вопросов, только безопасные шаги, кроме копии настроек агентов и PATH (конфигурация из
примера, `local/`, `local/machine.yaml`, команда `miksy`); чего не хватает (программы, секреты, каталог в PATH) —
напишет. `--yes --backup` — ещё и копия настроек агентов. `setup --force` спрашивает workspace и агентов заново
(прежние ответы — по умолчанию).

### Вторая машина

На второй машине можно взять ту же конфигурацию или завести другую.

- **Те же проекты и правила** — берите свою конфигурацию из git (вопрос 1 мастера, вариант 1) и разложите папки так
  же, как на первой машине (ниже).
- **Другой набор** (личная машина вместо рабочей, у коллеги свой) — новая конфигурация из примера (вопрос 1, вариант
  2). Нужные правила переносятся копированием слоёв.

**Правку конфигурации на одной машине — на другую:** на первой закоммитьте и отправьте её (`git add -A`,
`git commit`, `git push` в каталоге конфигурации), на второй — `git pull` там же, затем `miksy sync --global` и
`miksy sync --all`.

Для первого случая главное — **раскладка папок**: всё, на что ссылаются слои дерева (проекты, организации, папка
движка и конфигурации), должно лежать относительно workspace так же, как на первой машине. Было
`~/Projects/miksy`, `~/Projects/miksy-config` и `~/Projects/Acme/app` — так же и здесь (сама папка workspace может
называться иначе). Иначе слои применятся не к тем папкам. Мастер предупредит, если в конфигурации есть слой папки
движка, а движок лежит не в нём; сам он ничего не переносит.

**macOS и Windows не различают регистр в именах:** `miksy` и `Miksy` — одна папка, и `mv miksy Miksy/miksy`
переносит папку «в саму себя». Меняйте регистр через временное имя:

```
mv miksy miksy.tmp && mkdir Miksy && mv miksy.tmp Miksy/miksy                    # macOS, Linux
Rename-Item miksy miksy.tmp; mkdir Miksy; Move-Item miksy.tmp Miksy\miksy        # Windows (PowerShell)
```

Перенесли движок или конфигурацию — запустите `miksy setup` снова (обновит команду `miksy`), затем `miksy doctor`:
учёт найдёт новое место сам («[Переименовали или перенесли каталог](#переименовали-или-перенесли-каталог)»).

### Установка вручную

Если мастер не подходит (нестандартная машина, хочется пройти шаги по отдельности) — те же шаги командами. Ставили
мастером — этот раздел пропустите.

**1. Поставьте git, Bun (1.3.14 или новее) и агентов** ([выше](#установка-агентов)).

| ОС | Bun | Или менеджером пакетов |
|---|---|---|
| Windows | `powershell -c "irm bun.sh/install.ps1 \| iex"` | `scoop install bun` |
| macOS | `curl -fsSL https://bun.sh/install \| bash` | `brew install oven-sh/bun/bun` |
| Linux | `curl -fsSL https://bun.sh/install \| bash` | — |

Откройте новое окно терминала, чтобы команда `bun` нашлась.

**2. Скачайте miksy** в папку с проектами:

```
mkdir -p ~/Projects && cd ~/Projects                                     # macOS, Linux
mkdir -Force $HOME/Projects; Set-Location $HOME/Projects                 # Windows (PowerShell)
git clone -b stable https://github.com/wedolab/miksy.git miksy
```

Нужна та же конфигурация, что на другой вашей машине, — скачайте её рядом: `git clone <адрес вашего репо
конфигурации> miksy-config`, а проекты, движок и конфигурацию разложите так же, как там («[Вторая
машина](#вторая-машина)»). Нужна новая — пропустите, `setup` создаст её из примера.

**3. Сохраните нынешние настройки агентов** — чтобы вернуть всё как было даже без miksy:

```
tar czf ~/agents-before-miksy.tgz -C ~ \
  .claude.json .claude/CLAUDE.md .claude/settings.json .claude/skills \
  .codex/config.toml .codex/AGENTS.md .codex/AGENTS.override.md .agents/skills \
  .config/opencode .gemini/GEMINI.md .gemini/config \
  .gemini/antigravity-ide/mcp_config.json .gemini/antigravity-cli/mcp_config.json
```

Windows (PowerShell; `tar` есть в Windows 10 и новее):

```
tar czf "$HOME/agents-before-miksy.tgz" -C $HOME .claude.json .claude/CLAUDE.md .claude/settings.json .claude/skills .codex/config.toml .codex/AGENTS.md .codex/AGENTS.override.md .agents/skills .config/opencode .gemini/GEMINI.md .gemini/config .gemini/antigravity-ide/mcp_config.json .gemini/antigravity-cli/mcp_config.json
```

Если каких-то файлов нет, tar напишет об этом, но архив создаст.

**4. Настройте машину без вопросов:**

```
cd ~/Projects/miksy
bun src/cli.ts setup --yes
```

Будут созданы конфигурация из примера (если её нет; по умолчанию — `miksy-config` рядом с движком),
`local/machine.yaml` (workspace — папка, где лежит движок, или выше: `~/Projects/miksy` → `~/Projects`; агенты —
те, что нашлись) и команда `miksy`. Workspace, агентов и пути к программам можно поправить прямо в
`local/machine.yaml`; секреты — в `local/secrets.env` (переносите их через менеджер паролей, не через git или
чат). Команда `miksy` не находится — добавьте `~/.bun/bin` в PATH (на Windows: Пуск → «Изменение переменных среды
текущего пользователя» → Path → «Создать» → `%USERPROFILE%\.bun\bin`) и откройте новое окно терминала.

**5. Посмотрите, что у агентов уже настроено руками:** `miksy doctor`.

- «Добавлено агентами в обход слоёв» — MCP-серверы и skills проектов, которые вы добавляли сами. Нужные перенесите в
  конфигурацию: `miksy adopt --global <имя> --to global` (из проекта — `miksy adopt <проект> <имя> --to …`).
  Домашние skills агентов (в «Справочно») `adopt` не берёт — их папки скопируйте в `layers/global/skills/` сами.
  Остальные можно не трогать — miksy их не удалит.
- «Конфликты первого sync» — ваши файлы там, куда miksy хочет писать (например, свой skill с тем же именем).
  Перенесите нужное из них в конфигурацию.

Что получит агент — `miksy explain --global` и `miksy explain ~/Projects/Acme/app`.

**6. Проверьте план, ничего не записывая:**

```
miksy sync --global --dry-run
miksy sync --all --dry-run
```

Хотите увидеть сами файлы — `miksy sync --global --out ~/miksy-preview`: miksy сложит их в отдельную папку и
покажет разницу с нынешними настройками. Повторяйте шаги 5–6, пока план не устроит.

**7. Запишите настройки:**

```
miksy sync --global
miksy sync --all
```

Первая команда пишет домашние настройки агентов (они действуют во всех каталогах), вторая — настройки каждого проекта. Проектов много —
miksy сначала покажет список и спросит подтверждение. В конце может спросить, доверять ли проектам, где команда
настроила хуки или свои MCP-серверы, — ответьте по каждому. Остались конфликты «файл существует и создан не miksy»,
а нужное из таких файлов уже в конфигурации — повторите с `--force`: miksy заменит файл, оригинал сохранит.

**8. Проверьте, что всё работает:** `miksy doctor` пишет «Всё синхронизировано»; перезапустите сессии агентов;
откройте проект и спросите агента: «Процитируй первую строку раздела „## MCP“ в твоих инструкциях и вызови
context7 для „bun“» (раздел — из стартовой конфигурации, `layers/tree/instructions/`). Ответ «MCP-серверы подключает
miksy по слоям…» и найденная библиотека — всё работает.

**9. Вернуть всё как было** — «[Как удалить miksy](#как-удалить-miksy)», затем копия из шага 3:
`tar xzf ~/agents-before-miksy.tgz -C ~ --exclude=.claude.json` (Windows:
`tar xzf "$HOME/agents-before-miksy.tgz" -C $HOME --exclude=.claude.json`) — `~/.claude.json` не возвращайте, почему —
там же, шаг 3.

## Повседневные задачи

Общее правило: поменяли конфигурацию — запустите `sync`. `miksy sync --global` — если меняли `layers/global/` или
`layers/env-*/` (домашние настройки агентов — действуют во всех каталогах); `miksy sync --all` — если меняли
`layers/tree/` (проекты). Сначала посмотреть план — `--dry-run`. После записи перезапустите сессии агентов.
Коммитить конфигурацию перед `sync` не нужно — коммит нужен, только чтобы перенести правку на другую машину
(«[Вторая машина](#вторая-машина)»).

### Добавить или изменить правило

Правило — обычный markdown-файл в папке `instructions/` нужного слоя:

| Для кого правило | Где действует | Куда положить | Затем |
|---|---|---|---|
| Все агенты везде (язык, стиль) | везде, и вне проектов (агент, открытый в любой папке) | `layers/global/instructions/*.md` | `miksy sync --global` |
| Про ОС (shell, синтаксис команд) | везде на машинах с этой ОС | `layers/env-windows/instructions/*.md` (и `env-macos/`, `env-linux/`) | `miksy sync --global` |
| Все проекты | только в проектах папок с проектами | `layers/tree/instructions/*.md` | `miksy sync --all` |
| Организация или проект | только в её (его) проектах | `layers/tree/<Организация>[/<проект>]/instructions/*.md` | `miksy sync --all` |

Пути — от папки конфигурации (`miksy-config`). Не уверены, куда, — `layers/tree/instructions/`. Организация во
второй папке с проектами — под её веткой: `layers/tree/<ветка>/<Организация>/`
(«[Несколько корней workspace](#несколько-корней-workspace)»).

Папки в `layers/tree/` повторяют папки проектов: для `~/Projects/Acme/app` — `layers/tree/Acme/app/`. Нужных папок
нет — создайте их сами: например, `~/Projects/miksy-config/layers/tree/Acme/instructions/` (Windows —
`$HOME\Projects\miksy-config\layers\tree\Acme\instructions\`). Внутри файла — обычный текст markdown, заголовок и разделители
не нужны (файлы слоёв miksy склеит сам). Имя файла — любое; файлы слоя идут по имени, поэтому число в начале (`20-style.md`) задаёт порядок.
Проверить, что правило дошло, — `miksy explain <путь проекта>`.

Каждое правило кладите в одно место: правило «для всех агентов везде» действует и в проектах — повторять его в
`layers/tree/` не нужно, иначе агент получит его дважды.

Проекты лежат прямо в папке с проектами, без папок организаций (`D:\Projects\app1`, `D:\Projects\app2`)? Для
правила нескольких из них создайте папку организации и перенесите репо в неё (`D:\Projects\Acme\app1` → слой
`layers/tree/Acme/`; историю сессий и разрешения агентов при переносе папки miksy не переносит — «[Переименовали или
перенесли каталог](#переименовали-или-перенесли-каталог)») или, не трогая папки, привяжите слой шаблоном в
`map.yaml` — слой тогда лежит вне дерева, в `layers/acme/`:

```yaml
# map.yaml — для app1 и app2 слой из layers/acme/
layers:
  - { match: "{app1,app2}", use: acme }      # сами проекты
  - { match: "{app1,app2}/**", use: acme }   # и папки внутри них (если в них открывают агента)
```

### Подключить MCP-сервер

Сервер — файл `mcp/<имя>.yaml` в нужном слое. Секреты — **только ссылкой** `${ИМЯ}`, а значение — в
`local/secrets.env` этой машины (в git оно не попадёт):

```yaml
# layers/tree/Acme/mcp/gitlab.yaml — сервер, который запускается у вас (stdio)
name: gitlab
command: npx
args: [-y, "@zereight/mcp-gitlab"]
env:
  GITLAB_PERSONAL_ACCESS_TOKEN: ${ACME_GITLAB_TOKEN}
  GITLAB_API_URL: https://gitlab.acme.example/api/v4
```

```yaml
# layers/tree/Acme/mcp/tracker.yaml — удалённый сервер (HTTP)
name: tracker
url: https://tracker.acme.example/mcp
headers:
  Authorization: Bearer ${ACME_TRACKER_TOKEN}
agents: { antigravity: skip } # необязательно: этому агенту не подключать
```

```
# local/secrets.env
ACME_GITLAB_TOKEN=glpat-…
ACME_TRACKER_TOKEN=…
```

Затем `miksy sync --all` (сервер в `layers/global/` — `miksy sync --global`). Пути этой машины пишите через
`${HOME}`, `${WORKSPACE}` (основная папка с проектами) или свои переменные `vars` из `local/machine.yaml`
(например, `${PYTHON}`). Готовые примеры — `examples/extra/`.

**Значений секретов нет ни в одном конфиге агента.** `sync` кладёт каждый секрет в файл `local/secrets/<ИМЯ>`
(доступ только у вас), а агенту записывает путь к своему скрипту-обёртке в `local/run/…`, который передаёт секрет
серверу. Сервер, секрет которого не задан или не доставить, `sync` пропускает с сообщением (что делать — в
«[Если что-то пошло не так](#если-что-то-пошло-не-так)»). Файлы в `local/secrets/` руками не удаляйте (opencode без
них не запустится): уберите секрет или сервер из слоя и запустите `sync` — лишнее он удалит сам.

### Добавить свой skill

Папка `skills/<имя>/SKILL.md` в нужном слое, затем `miksy sync --global` или `--all`:

```markdown
---
name: miksy-contract-review
description: Разбор договора перед подписанием — риски, спорные пункты, правки. Используй, когда просят проверить договор, оферту или соглашение, найти подвохи, подготовить протокол разногласий, поработать как юрист.
---

Порядок работы…
```

Агент заранее видит только `name` и `description`, а остальной текст читает, когда решит, что skill подходит. Поэтому
от описания зависит, вспомнит ли агент о skill:

- пишите, **когда** его использовать, словами, которыми вы ставите задачу («проверь договор», «как юрист»), — а не
  только что он делает;
- добавьте синонимы и близкие запросы;
- одна-три фразы, без общих слов вроде «помогает с документами».

Свои skills называйте с префиксом, чтобы не совпасть с skills команды в репо проектов: по умолчанию `miksy-`, свой
— в `map.yaml`: `skill_prefix: acme-`. Дошёл ли skill до агента — `miksy explain <путь>`, раздел Skills.

### Добавить новый проект

Склонировали репо в папку с проектами — запустите `miksy sync` в его каталоге (или в любой его подпапке); сам по
себе miksy не запускается. То же — `miksy sync <путь>` из другого места, а `miksy sync --all` обновит все проекты
сразу (новые git-репо в папке с проектами он находит сам). Затем перезапустите сессию агента в этом репо.

`miksy sync` без пути пишет только туда, что уже цель: в проект (git-репо или каталог, где агент уже работал) или
в папку с пометкой `target: true` — и из их подпапок. В самой папке с проектами, в папке без git и вне workspace он
ничего не пишет, а подсказывает, что сделать.

**Репо вне папки с проектами** (например, склонировали в `~/Downloads/new-repo`). Проектом он станет внутри
workspace. Перенесите его в папку с проектами (`~/Projects/new-repo`), затем `miksy sync` в нём.

Если репо лежит в папке, где у вас и другие проекты (второй диск, облачная папка), её можно сделать ещё одной папкой с
проектами: `miksy sync` в репо подскажет готовую команду `miksy root add "<папка>" --tree <имя>`
(«[Несколько корней workspace](#несколько-корней-workspace)»), затем `miksy sync` в репо. Для домашнего каталога или
корня диска (`E:\`) это не годится — `sync` так и скажет и посоветует перенести репо. `~/Downloads` корнем сделать
можно, но настройки тогда получат все git-репо в ней — обычно репо лучше перенести. Сам репо корнем не делайте:
корень — папка с проектами, а не проект (`root add` объяснит это и спросит).

Если в репо есть хуки или MCP-серверы, которые закоммитила команда проекта, доверие проекту без вашего решения не ставится — `sync` спросит
(«[Доверие проектам](#доверие-проектам)»).

### Папка без git: заметки, выгрузки, группа проектов

Настройки получают git-репо и каталоги, где агент уже работал (вы открывали в них Claude, Codex и т. п. — они в
списке проектов агента; такие `sync --all` обновляет сам). Папка без git, где агента ещё не открывали
(`~/Projects/Acme/MyTasks` — заметки, выгрузки), настроек не получит: агент откроется там без ваших правил. Чтобы miksy писал туда, как в
проект, отметьте её **целью** (в сообщениях miksy — «цель без git», над проектами — «группа»):

```
miksy target ~/Projects/Acme/MyTasks      # без пути — текущий каталог
```

Команда допишет в `layer.yaml` её слоя (`layers/tree/Acme/MyTasks/`; остальное в файле не тронет) строку
`target: true` и предложит сразу записать настройки. Цель получает те же слои, что проект на её месте: правила, MCP,
skills, доверие. `miksy target <путь> --remove` снимает пометку (и без подключённого диска) и предлагает убрать
записанное. `miksy projects` показывает такие папки с пометкой; `sync --all` и `doctor` подсказывают папки без git
рядом с проектами — их легко не заметить.

**Группа** — цель над проектами. Открываете агента в `~/Projects/Acme`, когда задача задевает несколько репо, —
отметьте её (`miksy target ~/Projects/Acme`), затем `miksy sync --all`. Claude читает файлы правил и во всех
**родительских** папках, поэтому проект ниже группы получает для Claude только **свою часть** слоёв, остальное
Claude возьмёт из файла группы. По той же причине `exclude` для Claude делайте в слое группы. Остальные агенты
получают полный набор в каждой цели.

### Настроить организацию или проект отдельно

Создайте в `layers/tree/` папку по тому же пути, что в workspace (`layers/tree/NewOrg/`,
`layers/tree/NewOrg/some-project/`), и положите туда `instructions/`, `mcp/`, `skills/` или `layer.yaml`. Затем
`miksy sync --all`. Больше ничего настраивать не надо.

### Добавить или убрать агента

Поставили нового агента — запустите `miksy setup` ещё раз: он найдёт агента и предложит добавить его в
`local/machine.yaml` (остальное не изменится). Затем `miksy sync --global` и `miksy sync --all`.

Перестали пользоваться агентом — сначала уберите записанное ему: `miksy clean --all --agent <имя>` и
`miksy clean --global --agent <имя>`, потом удалите его из `agents` в `local/machine.yaml`. Убрали без `clean` —
`miksy doctor` перечислит, что осталось («Учёт агентов, которых нет в agents»), и даст команды
`miksy clean … --agent <имя>`, которые это уберут.

**Внимание:** `miksy update` и `miksy setup --yes` (в том числе в шагах отката) дописывают в `agents` всех агентов,
которые найдены на машине, — и убранного вами («✓ в local/machine.yaml добавлены агенты: …»). После них уберите его
из `agents` снова, до `sync`; мастер в терминале об этом спрашивает — ответьте «n».

### Подключить skills команды из репо проекта

Команда положила skills в репо, а ваш агент их не видит (другой агент, нестандартный путь)? miksy доставит их
вашим агентам, если включить в слое:

```yaml
# layer.yaml
import_skills: auto     # до 30 на проект; all — без лимита; [имя1, имя2]; false — выключено
```

В стартовой конфигурации импорт выключен. Доставляется только **закоммиченное** (не незакоммиченные правки, не
игнорируемые файлы, не ссылки за пределы репо). Что лежит в проекте и кто что видит — `miksy skills <путь>`,
`miksy skills --all`.

### Поручить изменения агенту

Правила, MCP и skills удобно добавлять, попросив агента: «подключи MCP sentry для всей организации Acme».
Глобальный skill **`miksy`** из стартовой конфигурации объясняет агентам, куда что класть.

Добавил агент что-то по-своему (`claude mcp add`, skill в папке проекта) — это получит только он. `miksy doctor`
покажет такие добавки («Добавлено агентами в обход слоёв»), а перенести их в конфигурацию для всех агентов — одна
команда:

```
miksy adopt <путь проекта> <имя> --to <уровень>   # из проекта
miksy adopt --global <имя> --to <уровень>         # из домашних настроек агента
miksy sync --all
```

`<уровень>` — `global` (`layers/global/`), `workspace` (`layers/tree/` — все проекты) или путь в дереве (`Acme` →
`layers/tree/Acme/`, `Acme/mobile`). `adopt` переводит MCP-сервер в
формат miksy, выносит секреты в `local/secrets.env` (в слое — ссылка), пути машины — в переменные; skill проекта копирует в
слой (домашние skills агентов `adopt` не переносит — скопируйте папку в `layers/global/skills/<имя>/` сами). Сначала показывает план (и что похоже на секрет, но не распознано), записывает после подтверждения (без
терминала — только с `--yes`; `--dry-run` — только план). Для глобального Codex (`--global … --agent codex`) исходная
запись переходит к miksy с бэкапом.

### Проверить, всё ли в порядке

```
miksy doctor
```

Покажет, что не записано, что устарело (в том числе skills команды после `git pull`), что правили вручную, каких
секретов и программ не хватает, где нужно ваше решение о доверии. Ничего не меняет. Запускайте после правок
конфигурации, после `git pull` в проектах и время от времени.

В «Справочно» (не ошибки) — папки без git рядом с проектами и **окружение**: несколько установок одной программы
(Bun, агенты, Node.js, uv, Python — какая используется и где ещё есть; версия opencode), переменные, которые уводят
настройки агента в другой каталог (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME`, `OPENCODE_CONFIG`,
`OPENCODE_CONFIG_DIR`, `GEMINI_CLI_HOME`), и конфигурация не та, что рядом с движком (`MIKSY_CONFIG`, `~/.miksy`).
miksy ничего из этого не удаляет и не меняет.

### Переименовали или перенесли каталог

**Папку с проектами (корень workspace)** — поправьте её путь в `local/machine.yaml` (ключ `workspace`), затем
`miksy sync --all`. Внутри неё была ещё одна папка с проектами со своей веткой (в том же списке `workspace` —
`{ path: …, tree: … }` с путём внутри перенесённой) — поправьте и её `path:` до `sync --all`. Иначе её проекты на новом
месте станут проектами основной папки: `sync` покажет конфликт, а `--force` из строки конфликта заменил бы правила её
ветки правилами основной. Обычно учёт переезжает сам, вслед за файлами miksy: `sync` напишет «Учёт miksy перенесён вслед
за каталогами» (`doctor` до этого — «Каталоги переехали»). Не переедет, если miksy не может однозначно узнать проекты по их файлам: в папке несколько проектов с
одинаковыми настройками или вы переименовали сразу две папки с проектами. Тогда `sync --all` назовёт проекты
новыми («новые — miksy в них ещё не писал»), а `miksy doctor` покажет прежние пути в «Учёт целей вне workspace без
каталога». Сделайте для каждого прежнего пути `miksy clean "<прежний путь проекта>"` и на вопрос «забыть?»
ответьте «да» (без терминала — `--forget`): miksy уберёт записанное под прежним путём (серверы, доверие) и забудет
его; подсказку «Если диск найдётся: сначала верните прежний корень…» в выводе пропустите — она для отключённого
диска. Свои совпадающие файлы в новой папке тот же первый `sync --all` уже взял обратно («взять под учёт»),
изменённые показал конфликтом — `miksy sync "<проект>" --force`. Ответы в окне Claude на новом месте он может один раз спросить («[Доверие
проектам](#доверие-проектам)»). Не через `miksy root remove`: его вопрос «забыть?» —
для отключённого диска (при переименовании ответ — «нет»), а `root add` нового пути без правки файла оставит
прежний путь недоступным корнем.

**Проект, папку без git или конфигурацию** (проект и папку — в пределах workspace) можно переименовать или
перенести: следующий `sync` (или `clean`) сам найдёт новое место по файлам, которые miksy туда записал, перенесёт
учёт, ключи MCP и доверие и напечатает «Учёт miksy перенесён вслед за каталогами»; `doctor` и `--dry-run` только показывают найденное.
Пометку `target: true` перенесите сами: `miksy target <новый путь>`. Не нашёл — `miksy clean <прежний путь>` уберёт
записанное вне папки, а новая папка получит настройки как новый проект. Историю сессий, память и разрешения агентов
(агенты хранят их по пути папки) miksy не переносит.

## Несколько корней workspace

Обычно все проекты лежат в одной папке — workspace (`workspace: ~/Projects` в `local/machine.yaml`). Если они
разбросаны по нескольким местам — папка на втором диске, папка облачного хранилища, — каждое место становится **корнем**
workspace. Первый корень — основной.

**Добавить папку с проектами** (облачную — сначала прочтите «Папки облачных хранилищ» ниже):

```
miksy root add "E:\Clients"
```

В терминале miksy спросит **ветку** этой папки — обычно просто нажмите Enter (предложит имя папки, здесь
`Clients`; знаки `[ ] { } * ?` и `!` в начале имени он уберёт — с ними привязки `match:` в `map.yaml` по этой ветке
не работали бы). Эта папка уже есть на другой машине — введите её ветку оттуда (имя папки в `layers/tree/`), а не Enter:
иначе слои той ветки сюда не дойдут. Без терминала (скрипт, агент) — укажите сами: `miksy root add "E:\Clients" --tree Clients`.
`--tree` — ветка этой папки: имя новой папки в `layers/tree/`, где будут её слои (`layers/tree/Clients/`; не
путать с веткой git). Поменять
ветку потом можно, но слои придётся перенести в папку с новым именем. Команда допишет корень в `workspace` файла
`local/machine.yaml`, остальное в нём не тронет, скажет, сколько проектов нашлось, и предложит `miksy sync --all`.
Путь — как удобно: `"E:\Clients"`, `E:/Clients`, `~/Cloud` (с пробелами — в кавычках). В мастере (`miksy setup`) то
же — вопрос «Есть ещё папки с проектами?».

В `local/machine.yaml` это выглядит так:

```yaml
workspace:
  - D:/Projects                             # основной корень — в корне дерева слоёв (layers/tree/)
  - { path: "E:/Clients", tree: Clients }   # ещё корень — его ветка: layers/tree/Clients/
```

Дерево слоёв одно на все корни: проект `E:/Clients/Acme/site` получает слои `layers/tree/` (общие для всех
проектов), `layers/tree/Clients/` и `layers/tree/Clients/Acme/`; проект `D:/Projects/Org/app` — `layers/tree/` и
`layers/tree/Org/`. Конфигурация от машины не зависит: на другой машине те же папки могут лежать в других местах —
там в её `machine.yaml` свои пути с теми же `tree`.

**Убрать папку** — `miksy root remove <путь>`: записанное miksy в её проекты он уберёт (`clean`) только с вашего
согласия (в терминале — вопрос, «да» по умолчанию; без терминала — подскажет команды). Посмотреть заранее —
`--dry-run`. Основной корень убрать нельзя. Список корней — `miksy root`.

**Сменить основной корень** — `miksy setup --force`, вопрос «Корень workspace». Что будет с прежним основным, мастер
скажет сам:
- основным стал **дополнительный корень** — его ветка остаётся прежней;
- основным стал **новый каталог** (например, вы перенесли папку с проектами) — ветку прежнего основного, если она была,
  забирает он: слои идут за перенесённой папкой;
- прежний основной **уходит из workspace**: его проекты miksy больше не обновляет. Если он лежит внутри нового основного
  или другого корня, его проекты остаются в workspace, а слои получают по своему пути от того корня; если новый
  основной лежит внутри прежнего — уходят только проекты прежнего вне нового.

Перенесли папку, и прежней больше нет (или осталась пустая — перенесли её содержимое), — возвращать нечего, мастер так и
скажет («прежнего основного … нет на месте», «в прежнем основном … проектов нет»); учёт обычно переезжает сам
(«[Переименовали или перенесли каталог](#переименовали-или-перенесли-каталог)»). Внутри неё была ещё одна папка с
проектами — мастер назовёт её (и где она теперь, если папку перенесли в новую основную). Перенесли в новую — на вопрос
«Записать настройки агентам сейчас?» в конце мастера ответьте «нет», после мастера поправьте её `path:` в
`local/machine.yaml`, затем `miksy sync --global` и `miksy sync --all`; `--force` из строки конфликта о её проектах до
этого не выполняйте. Новая основная — не та, куда перенесли прежнюю: `path:` не меняйте. Если «нет на месте» — это диск,
который не был подключён: когда подключите, верните прежний основной дополнительным корнем по шагам ниже.

Прежняя папка на месте, но её проекты miksy больше не нужны (например, папку скопировали), — уберите записанное туда:
`miksy clean "<путь проекта>"` в каждом (работает и вне workspace). В новой копии файлы miksy, где записан путь папки
(например, `.codex/config.toml` с `${WORKSPACE}`), — конфликт, пока не выполните `miksy sync "<путь проекта>" --force` в
её проектах (бэкап будет). Внутри прежней папки была ещё одна папка с проектами со своей веткой — мастер назовёт её
(и где была бы её копия, если новая папка — копия прежней): она остаётся в workspace по прежнему пути. Новую папку
скопировали с прежней и переходите на неё целиком — сначала так же, как при переносе: «нет» на «Записать настройки агентам сейчас?», её `path:` в `local/machine.yaml` — на копию, `miksy sync
--global` и `miksy sync --all`; `clean` и `sync … --force` в её проектах — только после этого (иначе `--force` заменил
бы правила её ветки правилами основной папки). Новая папка — не копия прежней: `path:` вложенной не меняйте — одноимённая
папка в новой не её копия.

Выбрали основным не ту папку — верните прежний `local/machine.yaml`: `setup` сохранил его копию перед записью.
«Вернуть его» из сообщения мастера при этом не выполняйте.

1. Копия — в папке запуска `<конфигурация>/local/backups/<дата и время>/` (не `before-miksy-…`); путь внутри повторяет
   путь конфигурации, на Windows — без двоеточия: `…\<дата и время>\C\Users\you\Projects\miksy-config\local\machine.yaml`.
   Все копии покажет:

   ```
   Get-ChildItem -LiteralPath '<конфигурация>\local\backups' -Recurse -Filter machine.yaml | ForEach-Object FullName   # Windows (PowerShell)
   find '<конфигурация>/local/backups/' -name machine.yaml                                                              # macOS, Linux
   ```

   Нужна последняя по дате, где первым в `workspace` ещё записан прежний основной: после ошибки `setup`, `update` или
   `root add` могли скопировать файл снова — уже с ошибочной папкой. В копии вместо значений секретов —
   `<secret:ИМЯ>`: встретится такое (в пути корня или ветке `tree:`) — впишите значение из `local/secrets.env`.
2. Скопируйте копию на место:

   ```
   Copy-Item -LiteralPath '<копия>' -Destination '<конфигурация>\local\machine.yaml'   # Windows (PowerShell)
   cp '<копия>' '<конфигурация>/local/machine.yaml'                                     # macOS, Linux
   ```

3. `miksy sync --global` и `miksy sync --all`. Мастер успел записать в проекты ошибочной папки — `miksy doctor` покажет
   их полными путями в разделе «Цели учёта вне workspace»: в тех из них, что лежат в ошибочной папке, —
   `miksy clean "<путь>"` (работает и вне workspace; другие пути раздела не трогайте).

Вернуть прежний основной дополнительным корнем — по шагам из сообщения мастера, если он их печатал («Вернуть его: 1) …
2) …»); иначе — по шагам ниже. Не печатал он их, если у нового основного есть папки с теми же именами, что у прежнего
(`Org` и там, и там): перенос `layers/tree/Org` под новую ветку снял бы эти слои и с проектов нового основного. Тогда
такие папки не переносите, а скопируйте (`layers/tree/Org` → `layers/tree/<ветка>/Org`; дальше правки — в обеих), а
привязки `map.yaml` к ним не меняйте, а допишите рядом такие же с веткой в начале (`Org/**` и `<ветка>/Org/**`). У него своя ветка,
и новый основной её не занял, — достаточно `miksy root add "<прежний основной>" --tree <его ветка>`. Иначе сначала перенесите
его слои под новую ветку, затем `miksy root add "<прежний основной>" --tree <ветка>` и «да» на `sync --all`. В
обратном порядке `sync --all` успеет снять с его проектов слои, которые ещё не перенесены (тогда — ещё раз
`miksy sync --all` после переноса).
- У прежнего основного ветки не было — перенесите папки организаций и проектов (`layers/tree/Org/…` →
  `layers/tree/<ветка>/Org/…`); общие `instructions/`, `mcp/`, `skills/` и `layer.yaml` в самой `layers/tree/` не
  трогайте, папки веток других корней (`layers/tree/<их ветка>/`) — тоже. Перенос слоёв меняет конфигурацию на всех
  машинах, где она есть. Привязки `map.yaml` (`match:`) к его проектам — ветку в начало: `Org/**` → `<ветка>/Org/**`,
  `*/infra-*` → `<ветка>/*/infra-*`; в `{…}` — к каждой его папке внутри скобок (`{Org,Lab}/**` →
  `{<ветка>/Org,<ветка>/Lab}/**`).
- Его ветку забрал новый каталог (`Main`) — переименуйте папку `layers/tree/Main` целиком в новую ветку, а в
  привязках замените начало `Main/` на `<ветка>/`. Так мастер подсказывает, только если ветка из одной части и внутри
  неё нет веток других корней. Иначе (`Clients/Home`; у другого корня ветка `Main/Drive`) переименование задело бы
  слои нового основного, предка ветки или другого корня — переносите вручную только слои и привязки проектов прежнего
  основного.
- В имени новой ветки запятая или `}` — вместо `{…}` по отдельной привязке на каждую папку: внутри скобок они делят
  варианты.
- Шаблоны, которые начинаются с `**`, не меняйте.

Без этого привязки перестанут совпадать, и `sync` снимет эти слои молча. `${WORKSPACE}` в слоях после смены — новый
основной корень.

Сам корень — не цель: настройки получают проекты в нём (git-репо) и папки с пометкой `target: true`
(`miksy target E:/Clients/Acme` — пометка ляжет в `layers/tree/Clients/Acme/layer.yaml`).

**Папки облачных хранилищ** (Google Drive, Яндекс Диск, OneDrive, Dropbox, iCloud Drive и т. п.): всё, что miksy в
них запишет (`CLAUDE.local.md`, `.claude/`, `.agents/`, `.codex/`, `opencode.json` — правила, список MCP-серверов,
skills), уйдёт в облако и на ваши устройства, а если папка расшарена — всем, у кого к ней доступ. Значений
секретов в этих файлах нет (они в `local/` вашей машины), но правила и названия серверов увидят. Подключайте такую
папку, только если это вас устраивает. Одна облачная папка проекта на двух машинах с miksy пока надёжно работает
только для Claude — «[Одна облачная папка проекта на двух машинах](#одна-облачная-папка-на-двух-машинах)».

### Правила нескольких корней

- **У каждого корня, кроме основного, своя ветка (`tree`) — обязательно.** Иначе слои одной папки молча
  доставались бы папке с тем же именем в другом корне (папка `Acme` в основном корне получила бы MCP-серверы с
  токенами из `layers/tree/Acme/`, задуманные для клиента). Без `tree` или с занятой веткой `machine.yaml` не
  загрузится — ошибка скажет, что поправить. У основного корня `tree` можно не указывать; если указан — он тоже должен быть своим.
- **Общее для нескольких корней — явно.** Для всех проектов всех корней — `layers/tree/instructions/` (и остальное
  в корне дерева) или `layers/global/` (действует везде). Для отдельных папок в разных корнях — свой слой в
  `map.yaml`:

  ```yaml
  # map.yaml — слой layers/acme/ для Acme в обоих корнях (Clients и Archive)
  layers:
    - { match: "{Clients,Archive}/Acme", use: acme }      # сама папка Acme
    - { match: "{Clients,Archive}/Acme/**", use: acme }   # и всё внутри неё
    # Acme и в основной папке с проектами — там место без ветки: добавьте "Acme" и "Acme/**"
    # (или шаблоны {Acme,Clients/Acme,Archive/Acme})
  ```

  Шаблоны сравниваются без учёта регистра, как и слои дерева.
- **`${WORKSPACE}`** в определениях MCP — всегда основной корень, у проектов любого корня. Путь в другой корень —
  своей переменной машины:

  ```yaml
  # local/machine.yaml (на каждой машине — свой путь)
  vars:
    CLIENTS: "E:/Clients"
  # в слое: args: ["${CLIENTS}/tools/report.py"]
  ```

  На машине, где переменная не задана, сервер пропускается с сообщением. `miksy adopt` сворачивает в
  `${WORKSPACE}` только пути основного корня; путь в другой корень оставляет как есть и подсказывает завести
  переменную.

Корень недоступен (диск не подключён), диск нашёлся после «забыть», одна облачная папка на двух машинах и другие
особые случаи — «[Особые случаи нескольких папок с проектами](#особые-случаи-нескольких-папок-с-проектами)» в конце.

## Доверие проектам

**Главное.** Обычно miksy сам ставит агентам (Claude, Codex) доверие проектам, куда записал настройки, — без него
агент их не применит. Если в проекте есть то, что агент выполнит без вопроса, а поставил это не miksy (хуки, серверы
`.mcp.json` коллег и т. п.), `sync` покажет это и спросит вас — ответьте по каждому проекту. «Да» — если доверяете
тем, кто коммитит в этот репо: агент будет запускать их хуки и серверы без вопроса. «Нет» — miksy доверие не ставит,
и агент не применит настройки проекта, пока вы не доверитесь ему сами. Доверять проектам организации без вопроса или
запретить — строкой `trust` в её слое (ниже).

Подробнее. Claude и Codex применяют настройки проекта (хуки, разрешения, серверы `.mcp.json`, конфиг Codex проекта)
только в **доверенном** проекте. Обычно доверие спрашивает сам агент в терминале; Claude в редакторе (например, Zed)
не спрашивает и без доверия этих настроек не применит. Поэтому `sync` по умолчанию сам ставит доверие Claude и Codex
там, куда записал этому агенту настройки; своё снимает, когда основание пропало; ваше не трогает.

**Исполняемые настройки не от miksy.** Хуки, разрешения, серверы `.mcp.json`, переменные окружения в
`.claude/settings.json` или `.claude/settings.local.json`, чужой `.codex/config.toml` — с доверием агент выполнит их
без вопроса, поэтому решаете вы. `sync` в терминале в конце покажет, что будет выполняться, и спросит `[y/N]`; то же
— `miksy trust [<проект>]`. «Да» — miksy ставит доверие и одобряет для Claude серверы `.mcp.json`; доверие стоит,
пока команда проекта не добавит или не поменяет такие настройки (или в том же файле не появятся новые хуки и т. п.) —
тогда `sync` спросит снова. «Нет» — не ставит и отзывает одобрение серверов (доверитесь
потом проекту сами в окне Claude — miksy их не одобрит и сам спрашивать не будет; передумали — `miksy trust <проект>`
спросит о них заново; ответили серверам «да» отдельно — одобрение держится, пока проект доверенный в Claude: сняли
доверие в окне Claude — `sync` снимет и одобрение, доверились снова — вернёт). Без терминала
(агент, скрипт) — `miksy trust <проект> --confirm` только после вашего явного «да», иначе `--deny`.

**Ваши ответы в окне Claude** («да, больше не спрашивать», одобрение серверов — Claude сам записывает их в
`.claude/settings.local.json` проекта) miksy считает вашими, а не настройками команды проекта, если доверие этому
проекту ставил miksy, вы уже ответили «да» на его вопрос или в слое `trust: true`: их нет в вопросе, и доверию они не
мешают. После `miksy clean` (и `root remove` с согласием убрать) miksy помнит, что доверие ставил он, и какие ответы
были в папке (пока цел каталог `local/`): если с тех пор они не менялись, следующий `sync` вопроса о них не задаст.
Появились новые ответы или на месте папки другая (копия коллеги) — они в вопросе. Если папка в момент `clean` была
недоступна (диск отключён), miksy сравнит с ответами на момент последнего `sync`; проект, где `sync` новой версией
ещё не было, — один вопрос. Переименовали проект после `clean` — на новом месте тоже один вопрос. В проекте, которому
miksy не доверял (папку скопировали у коллеги), ответы в окне Claude в вопросе — отдельной строкой «ответы в окне
Claude («да, больше не спрашивать» и т. п.)», один раз.

Доверие Claude на месте папки остаётся, пока miksy его не снял: после `root remove` без согласия убрать записанное,
после `root remove` недоступной папки с проектами и после `clean --all`, когда папка с проектами недоступна. Claude
доверяет любой папке на этом месте, в том числе чужой копии (так было и в 0.2.0). Снять — `miksy clean "<путь
проекта>"`.

**Папки без git** (`target: true`, например общая с коллегой) — так же: хуки, переменные окружения и подобное в их
`.claude/settings.local.json` требуют вашего решения; `.codex/config.toml`, который не совпадает с записанным miksy
(его поправили или подменили), — чужой, и доверие Codex без вашего решения снимается. Их **подкаталоги** `sync`
не проверяет, а Claude применяет к ним доверие папки: хуки и подобное в их `.claude/settings*.json` и серверы их
`.mcp.json` показывает `miksy doctor` (раздел «Исполняемые настройки в подкаталогах групп без git»). Если там
чужое — удалите это, сделайте подкаталог отдельным проектом (`git init`) или запретите доверие папке
(`trust: { claude: false }` в её слое).

**Без вопроса или запрет — в слое:** `trust: { claude: true, codex: true }` в `layer.yaml` организации или проекта
— доверять без вопроса; `false` — запрет. `trust: { claude: false }` в `local/machine.yaml` — окончательный запрет
на этой машине. `miksy trust <проект> --confirm` при запрете запишет «да» и скажет, где запрет; доверие поставит
следующий `miksy sync` после того, как запрет снимут.

**Отозвать доверие проекту** — `trust: { claude: false }` (или `codex`) в его слое: работает всегда.
`miksy trust <проект> --deny` помогает, только когда у проекта есть исполняемые настройки не от miksy и miksy ждёт
(или уже получил) ваше решение о них; в проекте без таких настроек он ответит «решение не нужно» и ничего не
изменит. `false` в самом агенте `sync` вернёт.

## Обновление miksy

```
miksy --version          # какая версия стоит
miksy update --check     # есть ли новая (ничего не меняет и не скачивает)
miksy update             # что изменилось — и после «y» обновить
```

Номер нынешней версии (`miksy --version`) перед обновлением запишите — он понадобится, если захотите откатиться.

`miksy update` берёт новую версию из ветки `stable` (на ней — последний выпуск) и сначала показывает, что
изменилось: записи [CHANGELOG.md](CHANGELOG.md) между вашей версией и новой. Отдельно выделено **«Ломает»** (что
будет работать иначе) и **«После обновления»** (что запустить или поправить в конфигурации). После «y»:

1. обновляет движок — только «вперёд» (`git merge --ff-only`): ничего не перезаписывает и не удаляет;
2. уже новой версией: безопасная часть `setup` (команда `miksy`, `local/`), `doctor` и сводка плана `sync --global`
   и `sync --all` — что изменится у агентов;
3. спрашивает «Записать настройки агентам?» — `sync --global` и `sync --all`. Затем перезапустите сессии агентов.

Файлы, которые miksy пишет в папку самого движка (`CLAUDE.local.md` и т. п.), спрятаны от git — обновлению они не
мешают.

**Убирали агента из `agents`?** Шаг 2 дописывает в `agents` всех агентов, которые найдены на машине, — и его (в
выводе: «✓ в local/machine.yaml добавлены агенты: …»). Так же делает `miksy setup --yes`, в том числе в шагах
отката. На вопрос «Записать настройки агентам?» тогда ответьте «n», уберите агента из `agents` в
`local/machine.yaml` снова и только потом `miksy sync --global` и `miksy sync --all` — иначе `sync` снова запишет ему
настройки.

Без терминала (скрипт, агент) — обновление только с `--yes`, а настройки агентам `update` не пишет: печатает
команды `sync`.

**Откажет и объяснит**, если в движке есть свои правки (не правьте и не коммитьте файлы движка — всё своё живёт в
конфигурации), если в ветке свои коммиты или движок скачан не через git.

### Откатиться на прежнюю версию

Новая версия мешает — верните прежнюю. **Windows, откат с 0.2.2:** сначала шаги «до отката» из «[Особенности
версий](#особенности-версий)» (ссылки в `local/`) — иначе прежняя версия сбросит права ваших dotfiles. Понадобятся:
- **`<каталог движка>`** — папка, куда вы скачали miksy (например, `~/Projects/miksy`); путь показывает `miksy explain`
  (строка «Движок miksy …»);
- **номер прежней версии** — той, что стояла до `miksy update`: его вы записали перед обновлением (`miksy --version`);
  `update` печатал его и сам: «движок обновлён: 0.2.0 → 0.2.1» —
  прежняя первая; в команде она с буквой `v` — `v0.2.0`. Вывод не сохранился — спросите git, на каком выпуске ветка
  `stable` движка была до последнего обновления (кавычки нужны в PowerShell):

  ```
  git -C "$HOME\Projects\miksy" describe --tags 'stable@{1}'     # Windows (PowerShell), движок в $HOME\Projects\miksy
  git -C ~/Projects/miksy describe --tags 'stable@{1}'            # macOS, Linux
  ```

  Ответ — номер прежней версии (`v0.2.0`). Нужна версия ещё раньше — та же команда с `'stable@{2}'`, `'stable@{3}'`
  (`@{1}` — состояние ветки до последнего её изменения, `@{2}` — до предпоследнего). Git ответил ошибкой:
  - `log for 'stable' only has 1 entries` — ветку `stable` создал сам последний `miksy update`: до него движок был на
    ветке `main` (`update` предлагал «перейти на stable»). Вернитесь на неё: `git -C <каталог движка> checkout main`
    вместо первой команды ниже, затем остальные три;
  - `not a git repository` или `cannot change to …` — неверен `<каталог движка>` (проверьте путь в `miksy explain`);
    движок скачан не через git — откатиться можно, только скачав нужный выпуск заново (раздел «Установка»);
  - `log for refs/heads/stable is empty` — git этого не помнит: обновлялись давно, больше 90 дней назад. Список выпусков —
    `git -C <каталог движка> tag --sort=-v:refname`, сверху новые; нынешний показывает `miksy --version`. Какой стоял
    раньше, git уже не скажет — выберите выпуск, на котором всё работало: в [CHANGELOG.md](CHANGELOG.md) найдите
    выпуск, с которого началось то, что мешает, и возьмите следующий под ним (более старый). Не знаете — возьмите
    выпуск сразу под нынешним; не помогло — ещё на один ниже, команды те же (на 0.1.x — сначала «Особенности версий» ниже).

```
git -C <каталог движка> checkout -B stable v0.2.0
miksy setup --yes
miksy sync --global
miksy sync --all
```

Например, движок в `$HOME\Projects\miksy` (Windows, PowerShell) или `~/Projects/miksy` (macOS, Linux):

```
git -C "$HOME\Projects\miksy" checkout -B stable v0.2.0      # Windows (PowerShell)
git -C ~/Projects/miksy checkout -B stable v0.2.0               # macOS, Linux
```

- `git … checkout -B stable v0.2.0` ставит ветку `stable` на прежний выпуск (незакоммиченные правки не теряются: если
  мешают, git откажет — это правки в файлах движка, а свои настройки держите в конфигурации; не нужны — `git -C
  <каталог движка> stash`, затем команду ещё раз); следующий `miksy update` снова предложит новую версию — чтобы остаться на прежней, отвечайте
  «n»;
- `miksy setup --yes` — безопасная часть мастера, уже прежней версией: обновит под неё команду `miksy` и `local/`.
  Убирали агента из `agents` — она допишет его снова («✓ в local/machine.yaml добавлены агенты: …»): уберите его из
  `agents` ещё раз до `sync`;
- `sync --global` и `sync --all` перепишут настройки агентов так, как их пишет прежняя версия.

Если по разделу «После обновления» новой версии (CHANGELOG) вы что-то меняли в конфигурации — например, переименовали
агента в `local/machine.yaml`, — верните, как было. И напишите в [issue](https://github.com/wedolab/miksy/issues/new/choose),
что пошло не так.

**Сообщение «учёт … записан более новой версией движка»** после отката — если шаги выше сделаны, ничего делать не
нужно, всё работает. Учёт (`local/state/manifest.json`) последней писала новая версия. Откатились на 0.2.2 или новее — его убирает `miksy setup --yes` из шагов выше (если команда
`miksy` ведёт на этот движок). На 0.2.1 и старше оно остаётся, пока прежняя версия сама не запишет учёт — при первом
`sync` или `clean`, который что-то изменит, — или до возврата на новую версию.

Откат с 0.2.x на 0.1.x требует шагов до переключения — «[Особенности версий](#особенности-версий)» ниже.

### Особенности версий

**С 0.2.1 на 0.2.2 (обновление)** — обычно делать ничего не нужно. Если `local/backups` — ваша ссылка на папку на другом
томе, открытую другим или несуществующую, команды, которые пишут, теперь остановятся в начале, ничего не записав: в
строке отказа — что сделать (закрыть папку готовой командой или заменить ссылку обычной папкой; «[Если что-то пошло не
так](#секреты-и-mcp-серверы)», строка «… miksy не пишет туда бэкапы»). То же на Windows, если `local/backups` — ссылка
на папку, закрытую только для вас без наследования прав, и 0.2.1 оставила в ней папки без доступа даже для вас: одна
готовая команда в строке отказа.

**С 0.2.2 на 0.2.1** — команды выше; на Windows — ещё шаги до и после них (ниже). Если командам нечего менять,
сообщение «учёт … записан более новой версией движка» останется до первого `sync` или `clean` с изменениями: убирать
его при `setup` умеет только 0.2.2 и новее. Откатываетесь сразу на 0.2.0 — прочтите и «С 0.2.1 на 0.2.0» ниже.

**Windows: откат с 0.2.2 на 0.2.1, 0.2.0 или 0.1.x, когда в `local/` есть ссылки.** Прежние версии проверяют права
`local/` сквозь ссылки: если за ссылкой что-то открыто другим, каждая их команда падает с «local/ не закрыт» и
сбрасывает права файлов за ссылкой — ваших dotfiles. Ссылки там бывают: в копии «до miksy», если ваши настройки
агентов — ссылки на папку dotfiles (при включённом режиме разработчика мастер копирует их ссылками), и `local/secrets`,
`local/backups` или сама `local`, если вы перенесли их на другой том. Не знаете, есть ли они, — сделайте шаги всё
равно: без ссылок шаг 1 ничего не меняет, а шаг 2 выносит копию «до miksy» рядом с конфигурацией — шаг 5 её вернёт.
Останетесь на прежней версии — копия так и лежит рядом (путь печатает шаг 2: «вынесена: …»): его подставьте в команду
возврата из «Как удалить». Ссылки `local/secrets`, `local/backups` заменять папками не нужно: прежние
версии работают с ними, если их цели закрыты так, как закрывает miksy.

Все команды — в одном окне PowerShell, по порядку. Сначала найдите пути — первая строка с вашей папкой конфигурации
(например, `C:\Users\you\Projects\miksy-config`; кавычку в пути — `'`, `’`, `‘` — удвойте), остальные — как есть:

```
$c = [IO.Path]::GetFullPath('<конфигурация>').TrimEnd('\')
function T($p) { $i = Get-Item -LiteralPath $p -Force -ErrorAction SilentlyContinue; if ($i -and $i.Target) { $t = @($i.Target)[0]; if (-not [IO.Path]::IsPathRooted($t)) { $t = Join-Path (Split-Path $p) $t }; [IO.Path]::GetFullPath($t).TrimEnd('\') } }
$l = T "$c\local"; $d = if ($l) { $l } else { $c }; if (-not $l) { $l = "$c\local" }
$b = T "$l\backups"; if ($b) { $d = $b } else { $b = "$l\backups" }; $s = T "$l\secrets"
```

`$l` — папка `local` (или цель ссылки `local`), `$b` — папка бэкапов (или цель ссылки `local/backups`), `$s` — цель
ссылки `local/secrets`, если это ссылка.

1. **Закройте цели ссылок так, как закрывает miksy** — даже если они уже закрыты. Цель, закрытую только записью
   `<вы>:F` без пометки `(OI)(CI)` (так её закрывают вручную: `icacls … /inheritance:r /grant:r <вы>:F`), прежняя версия
   сломает: её новые папки там не получат вашего доступа. Команда оставляет доступ к цели только вам, с пометкой
   `(OI)(CI)` — её наследует всё внутри, включая новые папки; ссылки внутри не трогает:

   ```
   $me = [Security.Principal.WindowsIdentity]::GetCurrent().User.Value
   function Reset-MiksyTree($p) { Get-ChildItem -LiteralPath $p -Force | Where-Object { -not ($_.Attributes -band 1024) } | ForEach-Object { icacls $_.FullName /reset /q | Out-Null; if ($_.PSIsContainer) { Reset-MiksyTree $_.FullName } } }
   $all = @(); if ($l -ne "$c\local") { $all += $l }; if ($b -ne "$l\backups") { $all += $b }; if ($s) { $all += $s }
   foreach ($t in $all) { if (-not (Test-Path -LiteralPath $t)) { "битая ссылка, цели нет: $t"; continue }; icacls $t /reset | Out-Null; icacls $t /inheritance:r /grant:r "*${me}:(OI)(CI)F" | Out-Null; Reset-MiksyTree $t; "закрыта: $t" }
   ```

   Ссылок нет — команда ничего не печатает. «битая ссылка, цели нет» — исправьте ссылку или замените её обычной папкой
   (строка `doctor` о ней скажет как) и выполните шаг ещё раз: с битой ссылкой прежняя версия падает на каждой команде.
   Проверка: `miksy doctor` — без строк «закройте вручную», «битая ссылка» и «miksy не пишет
   туда бэкапы».
2. **Вынесите копию «до miksy»** из `local/` (и из цели `local/backups`) — рядом, на тот же диск. Команда только
   переименовывает папку: ссылки в ней остаются ссылками. На другой диск она откажет, ничего не тронув (`Move-Item` в
   этом случае переносил бы сквозь ссылки и удалял бы ваши файлы — не используйте его):

   ```
   if ($d -match '^[A-Za-z]:$') { "цель ссылки — корень диска ${d}\: вынести копию некуда" } elseif (Test-Path -LiteralPath $b) { Get-ChildItem -LiteralPath $b -Force -Filter 'before-miksy-*' | ForEach-Object { [IO.Directory]::Move($_.FullName, "$d-$($_.Name)"); "вынесена: $d-$($_.Name)" } }
   ```

   Копии нет (или нет и самой папки `local\backups`) — команда ничего не печатает. Вынесенная копия, пока лежит рядом, — не проект (не git-репо): `sync` её
   не трогает; её путь — в строке «вынесена: …». «цель ссылки — корень диска» — весь диск виден прежней версии, вынести
   копию некуда: с такой ссылкой откат на Windows не поддерживается.
3. **Проверьте, что других ссылок не осталось** — до первой команды прежней версии. Команда обходит `local/` и цели
   ссылок, не заходя в ссылки, и печатает каждую ссылку на папку, кроме самих `local\backups` и `local\secrets`. Ссылки
   на файлы (например, `local\secrets.env` или файл секрета на другом томе) она не показывает: прежние версии в них не
   заходят и права их целей не меняют — их не трогайте:

   ```
   function L($p) { Get-ChildItem -LiteralPath $p -Force | ForEach-Object { if ($_.Attributes -band 1024) { if ($_.PSIsContainer) { $_.FullName } } elseif ($_.PSIsContainer) { L $_.FullName } } }
   @(L $l; if ($s) { L $s }; if ($b -ne "$l\backups") { L $b }) | Where-Object { $_ -notin "$l\backups", "$l\secrets" }
   ```

   Пусто — можно откатываться. Путь внутри папки `before-miksy-…` — копия «до miksy» не вынесена: сначала шаг 2, затем
   проверку снова (такие ссылки по одной не выносите). Напечатала другой путь — это ваша ссылка (например, папка внутри `local\backups`, которую вы
   сами сделали ссылкой): с ней прежняя версия сбросит права за ней. Вынесите и её — туда же, куда шаг 2 вынес копию
   (тот же диск): `[IO.Directory]::Move('<путь из проверки>', "$d-<имя ссылки>")`, если путь начинается с `$b`; иначе —
   `"$c-<имя ссылки>"` (а если сама `local` — ссылка, — `"$l-<имя ссылки>"`); после шага 5 верните так же, поменяв пути
   местами (пока она вынесена, `clean` прежней версии не вернёт оригиналы, которые в ней лежат). Или не откатывайтесь:
   с такой ссылкой откат на Windows не поддерживается.
4. **Команды отката выше.** Проверка: `miksy --version` — прежняя версия; `setup --yes` и `sync` — без «local/ не
   закрыт» и «icacls не закрыл». Появилась такая строка — больше команд прежней версии не запускайте: вернитесь на 0.2.2 (команды
   отката с `v0.2.2`, затем шаг 5) и запустите `miksy doctor`. Строка с готовой командой в конце («закройте вручную
   (PowerShell): …», «Закройте папку бэкапов и всё в ней (PowerShell): …») — выполните её: так чинится и пропущенный
   шаг 1. Затем шаги 1–3 снова — шаг 3 покажет ссылку, если осталась она; права за ссылками проверьте
   (`icacls '<цель ссылки>' /T`): прежняя версия могла их сбросить.
5. **Вернувшись на 0.2.2** (`miksy update`; на его вопрос о записи настроек можно ответить «да» — копию это не
   трогает) — первый блок (пути), затем верните копию на место:

   ```
   $n = Split-Path $d -Leaf; Get-ChildItem -LiteralPath (Split-Path $d) -Force -Filter "$n-before-miksy-*" | ForEach-Object { [IO.Directory]::Move($_.FullName, (Join-Path $b $_.Name.Substring($n.Length + 1))); "возвращена: $($_.Name.Substring($n.Length + 1))" }
   ```

   Проверка: `miksy doctor` — без «Небезопасные права»; команда шага 3 показывает ссылки копии — они на месте.

На macOS и Linux прежние версии в ссылки не заходят — только команды выше.

**С 0.2.0 на 0.2.1 (обновление)** — что можно заметить:
- проект, где вы в 0.2.0 сказали «нет» доверию, а серверы `.mcp.json` команды проекта одобрены (вы доверились
  проекту сами в окне Claude): первый `sync` снимет одобрение и тут же спросит о серверах — «да», если одобряли их
  вы. Тот же вопрос будет и у тех, кто в 0.2.0 сказал «нет» доверию, а потом «да» отдельно серверам: в
  `local/trust.json` 0.2.0 эти случаи не различить. Один раз;
- файл miksy в проекте (`opencode.json`, `.codex/config.toml` и т. п.), куда вы дописали свой MCP-сервер ещё при
  0.2.0: `miksy doctor` может показывать серверы miksy в нём в разделе «Добавлено агентами в обход слоёв». Свой сервер перенесите в
  слои (`miksy adopt`), затем `miksy sync <проект> --force`.

**С 0.2.1 на 0.2.0** — только команды выше. Не запускали `miksy clean` или `root remove` и не правили своими руками
файлы miksy в проектах — остальное пропустите. 0.2.0 не помнит двух вещей, которые помнит 0.2.1. Первая — что доверие проекту ставил miksy, когда записанное
туда уже убрано (`clean`, `root remove` с согласием убрать) или когда `clean` запускали при отключённом диске (записанное
ещё не убрано); 0.2.0 не помнит и того, какие ответы были в окне Claude при последнем `sync`. Поэтому первый `sync` такого проекта в
0.2.0 может спросить о ваших ответах в окне Claude. Если это ваши ответы и других настроек в вопросе нет — ответьте
«да» ещё в 0.2.0: на вопрос `sync` в терминале или командой `miksy trust "<путь проекта>"`. Не ответите — 0.2.0 при
первой записи учёта сотрёт отметку, и после возврата на 0.2.1 тот же вопрос будет снова. Вторая — какие MCP-серверы
miksy записал в свои файлы проектов (`opencode.json` и т. п.); после возврата на 0.2.1 первый `sync` её восстановит.
Если такой файл вы правили, пока стояла 0.2.0, `miksy doctor` будет показывать серверы miksy в нём в
разделе «Добавлено агентами в обход слоёв» — это не так; свой сервер из этого файла перенесите в слои (`miksy adopt`), затем
`miksy sync <проект> --force` перезапишет файл.

#### Редко: откат на 0.1.x

**С 0.2.x на 0.1.x** — сначала подключите диски всех папок с проектами (если какая-то сейчас недоступна, откат лучше
отложить: 0.1.x забудет, что miksy записал в её проекты, и, когда диск вернётся, часть файлов, возможно, придётся
убирать вручную). Затем, ещё новой версией, приведите конфигурацию к тому, что понимает 0.1.x:

0. Если вы что-то «забывали» (диск был отключён, а потом нашёлся) — сначала `miksy sync --all`: проекты с такого
   диска снова получат учёт. Если «забывали» целую папку с проектами (`miksy root remove … --forget`), сначала
   верните её — `miksy root add "<путь>" --tree <ветка>`, затем `miksy sync --all`; шаг 1 уберёт её снова. 0.1.x о

2. В `local/machine.yaml` `workspace` должен остаться одной строкой: `workspace: <путь>`. Если там список (даже из

3. Если переименовывали агента `gemini` в `antigravity` (`agents` в `local/machine.yaml`, `agents:` у MCP в слоях) —
   верните `gemini`.
4. Уберите записанное для Antigravity: `miksy clean --all --agent antigravity` и
   `miksy clean --global --agent antigravity`. 0.1.x запишет его заново под своим именем.

Затем — команды выше с `v0.1.1`.

Что 0.1.x не сохранит и как поведёт себя иначе:
- Отметки о проектах, которые вы «забыли» и чей диск ещё не вернулся, — первая же её запись учёта их сотрёт. Если

Claude…»; если это ваши ответы и других настроек там нет — ответьте «да» (на вопрос `sync` в терминале или командой

## Устройство подробнее

### Что лежит в слое

Всё необязательно:

| Что | Зачем |
|---|---|
| `instructions/*.md` | правила — обычный markdown; склеиваются по порядку слоёв и по имени файла |
| `mcp/<имя>.yaml` | MCP-сервер («[Подключить MCP-сервер](#подключить-mcp-сервер)») |
| `skills/<имя>/SKILL.md` | skill («[Добавить свой skill](#добавить-свой-skill)») |
| `layer.yaml` | особые настройки слоя: `exclude`, `import_skills`, `trust`, `target`, `description` |

Эти имена заняты — так нельзя назвать организацию или проект (как и `hooks/` и `policies/`: их miksy не читает).

Убрать то, что пришло из слоя выше, — в `layer.yaml` нижнего слоя:

```yaml
exclude: [mcp.linear, skill.deploy, instructions.20-style.md]
```

Слой не по пути, а по шаблону — привязка в `map.yaml`: `layers: [{ match: "*/infra-*", use: infra }]` — слой
`layers/infra/` получат все проекты, чьё место в дереве подходит под шаблон; такой слой идёт после слоёв дерева и
перекрывает их. Место в дереве — путь от корня workspace, у проектов других корней — вместе с их веткой: проект
`E:/Clients/infra-x` корня с `tree: Clients` — это `Clients/infra-x` (шаблон `*/infra-*` подходит, `infra-*` — нет).

Ещё в `map.yaml`: `global` — какие слои домашние (по умолчанию `global` и `env-<ОС>`), `skill_prefix` — префикс
ваших skills, `tools` — программы, на которые ссылаются MCP-серверы слоёв (`${ИМЯ}`): мастер ищет их на машине и
записывает путь в `vars` файла `local/machine.yaml`, а не нашёл — подсказывает, как поставить. Примеры — в
`map.yaml` стартовой конфигурации.

### Куда miksy записывает настройки

В проект miksy пишет только файлы, которые git не отслеживает, и прячет их от git (`.git/info/exclude`) — в репо
проекта ничего не попадает. Файлы, которые закоммитила команда проекта, он не трогает никогда.

| Агент | Домашний каталог (действует везде) | В проекте |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md`, MCP в `~/.claude.json`, `~/.claude/skills/` | `CLAUDE.local.md`, `.claude/skills/`, MCP проекта — в `~/.claude.json` |
| Codex | `~/.codex/AGENTS.md`, MCP в `~/.codex/config.toml`, `~/.agents/skills/` | `.codex/config.toml` (правила и MCP), `.agents/skills/` (или `.codex/skills/`) |
| opencode | `~/.config/opencode/AGENTS.md`, MCP в `opencode.json(c)`, `~/.config/opencode/skills/` | `opencode.json`, `.opencode/miksy.md`, `.opencode/skills/` |
| Antigravity | `~/.gemini/GEMINI.md`, MCP в `mcp_config.json`, `~/.gemini/config/skills/` | плагин `.agents/plugins/miksy/` (правила, skills, MCP) |

Полностью (запасные пути, скрипты в `local/run/`) — в `adapters/<агент>/CAPABILITIES.md`.

В общих файлах miksy меняет только своё: в файле правил — свой блок между `<!-- miksy:begin … -->` и
`<!-- miksy:end -->` (ваш текст вокруг остаётся), в общих конфигах агентов (`~/.claude.json`,
`~/.codex/config.toml`, `opencode.json`, `mcp_config.json`) — только свои ключи. Записанное miksy руками не
правьте — меняйте слои: правка внутри его блока или файла станет конфликтом.

### Учёт, бэкапы, оригиналы

**Учёт** (`local/state/manifest.json`, рядом копия `.bak`) — что и с каким содержимым записал miksy. По нему он
отличает свои файлы от ваших и от правок руками. Перед изменением файла miksy кладёт его копию в
`local/backups/<метка запуска>/` (хранятся 20 последних запусков; секреты в копиях заменены на `<secret:ИМЯ>`).

Если miksy заменяет чужой файл (вы разрешили `--force` или содержимое совпало), он сохраняет **оригинал** в
`local/backups/originals/` — вне очереди удаления, со всеми значениями; `miksy clean` вернёт его на место.
Для разработчиков — [DESIGN §8.8–8.9](DESIGN.md#88-учёт).

## Справочник команд

Кратко — `miksy help`. Что запускать после изменений:

| Что изменилось | Что запустить |
|---|---|
| `layers/global/`, `layers/env-<ОС>/` — домашние настройки агентов, действуют во всех каталогах | `miksy sync --global` |
| `layers/tree/…` — настройки проектов по их месту | `miksy sync --all` или `miksy sync <путь>` (один проект) |
| `map.yaml`: `global` — `--global`; привязки `layers` — `--all` | соответственно |
| Новый проект (склонировали репо), новая папка без git (`miksy target`) | `miksy sync` в его каталоге или `miksy sync <путь>` |
| Новая папка с проектами (`miksy root add` или `workspace` в `local/machine.yaml`) | `miksy sync --all` (`root add` предложит сам) |
| Секреты (`local/secrets.env`), новый агент (`local/machine.yaml`), первая установка | оба: `miksy sync --global` и `miksy sync --all` |
| Вышла новая версия miksy | `miksy update` (он сам предложит `sync`) |

Не уверены — `miksy doctor`: он покажет, что устарело и какой командой это записать.

Явный `<путь>` папки без git, которая не цель, — запись с предупреждением: `sync --all` её не обновит | да |

Без терминала — подсказка команды | `layer.yaml` слоя; после «да» — как `sync`/`clean` |
| `trust [<путь>] [--agent <id>] [--confirm \| --deny]` | Решение о доверии проектам с исполняемыми настройками не от miksy («[Доверие проектам](#доверие-проектам)»); без терминала — только `--confirm` (после явного «да» пользователя) или `--deny` | `local/trust.json`, доверие агентов |
| `adopt <путь> \| --global <имя> --to <уровень> [--agent <id>] [--dry-run] [--yes]` | Перенести MCP-сервер или skill, добавленный агенту напрямую, в конфигурацию | слой, `local/secrets.env` |

| `update [--yes] [--main]` | Обновить движок до последнего выпуска («[Обновление miksy](#обновление-miksy)»); без терминала — только с `--yes`, `sync` не пишет | движок (git); после — как `setup --yes`; после «y» — как `sync` |

| `version`, `--version` | Версия движка (`0.2.2`) | нет |

### Файлы, конфликты, учёт

| Сообщение | Что значит и что делать |
|---|---|
| `КОНФЛИКТ … создан не miksy` | На этом месте чужой файл. Проверьте содержимое; если оно уже в слоях — `sync … --force` |
| `КОНФЛИКТ … изменён вручную` / `управляемый блок изменён вручную` | Кто-то поправил сгенерированное. Перенесите правку в слои, затем `--force` |
| `… отслеживается git-репо … — принадлежит команде` | Файл команды в репо (или dotfiles в `~`) — miksy его не трогает никогда. Агент получит остальное |
| `каталог … версионирует команда` | Личные и импортированные skills не кладутся в командный каталог. Codex возьмёт `.codex/skills`; если и он командный — skill в этом проекте не доставляется |
| `путь внутри вложенного git-репо` | Каталог внутри проекта — отдельный репо (submodule): exclude проекта на него не действует, miksy туда не пишет |
| `каталоги hooks/ и policies/ miksy не читает` | Хуки и права через miksy не настраиваются; содержимое этих каталогов агенты не получат |
| `файл занят другим процессом … его держит <программа> (PID …)` | Файл открыт программой (агент, IDE). Закройте её и повторите `sync`; файл остался прежним. Держатель не определился — «закройте программу и повторите» |
| `ВНИМАНИЕ: часть ключей пропала` / `ключи пропали` (doctor) / `изменился после планирования` / `план пересчитан` | Открытая сессия агента (или другой процесс) переписала конфиг во время или после sync; план miksy один раз пересчитывает сам. Закройте сессии и повторите `sync` |
| `путь вне …` / `… через симлинк … — вне …` | Конфиг агента или проект — ссылка за пределы дома/проекта. Miksy туда не пишет |
| `симлинк указывает на несуществующий файл` | Конфиг агента — битая ссылка (dotfiles). Почините ссылку |
| `сбой git: …` | git не запустился или репо повреждено (индекс, `safe.directory`). Проверьте `git status` в проекте |
| `файл не разбирается как JSON` | Конфиг агента битый — исправьте его; остальные цели синхронизированы |
| `уже принадлежит цели …` | Через вашу ссылку каталогов два агента пишут один файл. Уберите ссылку |
| `хеш неизвестен` | В учёте для файла разные записи (две копии проекта стали одной). Проверьте файл; верный — `sync … --force` |
| `учёт повреждён или недоступен` | Восстановите `local/state/manifest.json` из `manifest.json.bak` рядом. `doctor` работает и без учёта; `sync`/`clean` откажут |
| `каталог не пуст и не песочница miksy` | `--out` указывает на чужой каталог — укажите новый, пустой или созданный раньше `sync --out` |
| `Конфликты первого sync` (doctor) | Чужой файл мешает первой синхронизации цели. После первого sync такие конфликты — «известные» |
| `Claude ещё не открывал …` | MCP записаны под настоящим путём папки (без ссылок, с регистром букв как на диске). Открыли проект по другому пути (симлинк, регистр) — повторите `sync` |
| `Учёт miksy перенесён вслед за каталогами` (sync) / `Каталоги переехали` (doctor) | Каталог проекта, группы или конфигурации переименован или перенесён — см. «[Переименовали или перенесли каталог](#переименовали-или-перенесли-каталог)». Ничего делать не нужно |
| `Учёт ссылается на несуществующие каталоги` (doctor) | Каталог удалён или переехал, но не найден по файлам. `miksy clean <прежний путь>` уберёт записанное под ним вне каталога и запись учёта |
| Агент не видит изменений | Перезапустите сессию агента — конфиги читаются при старте |

### Секреты и MCP-серверы

| Сообщение | Что значит и что делать |
|---|---|
| macOS: MCP-сервер с `npx`/`uvx` у агента в графической программе (Zed, IDE Antigravity, Codex Desktop) падает — `Connection closed`, а в терминале тот же агент работает | Программы, запущенные из Dock, Finder или Spotlight, получают урезанный PATH (`/usr/bin:/bin:/usr/sbin:/sbin`) — без Homebrew (`/opt/homebrew/bin`), `~/.bun/bin`, nvm, и `npx` не находится. Укажите программу абсолютным путём через `vars` в `local/machine.yaml` (`NPX: /opt/homebrew/bin/npx` — путь из `which npx`; в слое `command: ${NPX}`); `npx` и `uvx` сами ищут `node`/`python` по PATH — добавьте серверу `env: { PATH: "${BREW_BIN}:/usr/bin:/bin" }` (`BREW_BIN: /opt/homebrew/bin` в `vars`). Затем `sync`. Или запускайте программу из терминала, если она это умеет (её команда унаследует PATH оболочки) |
| `пропущен сервер … — не заданы переменные` | Не хватает секрета или пути: допишите в `local/secrets.env` или `vars` в `local/machine.yaml`. Записанный раньше сервер остался |
| `многострочное значение секрета` / `… длиннее 1023 байт` / `… содержит "` | Значение нельзя доставить этим способом (файл секрета — одна строка; ограничения `.cmd` на Windows; JSON заголовков HTTP-сервера). Сервер пропущен, значение никуда не записано |
| `секрет … в command` / `в agents.….raw не поддерживается` | Секрет можно передать только через `env`, `args`, `headers`, `url` |
| `секрет … в env HTTP-сервера … не доставляется` | Удалённому серверу переменные окружения не передаются — перенесите секрет в `headers` |
| `секрет передаётся аргументом` | Значение видно в списке процессов. Перенесите его в `env` сервера, если сервер это умеет |
| `секрет ИМЯ короче 4 символов` | Короткое значение маскируется только как целая строка; проверьте, секрет ли это |
| `секрет … пустой в local/secrets.env` | Сервер получит пустое значение (на Windows `.cmd` пустое значение не задаёт переменную вовсе) — задайте секрет |
| `секреты открытым текстом в слоях` | В `mcp/*.yaml` значение вместо ссылки — уйдёт в git конфигурации. Перенесите в `local/secrets.env`, в слое — `${ИМЯ}` |
| `… вне учёта, а в нём значение секрета` / `Значение секрета в ключе вне учёта` (doctor) | Сервер в конфиге агента не из учёта и хранит токен как есть. Если это сервер miksy — `sync <цель> --agent <агент> --force` заменит его обёрткой; глобальный Codex — `adopt` |
| `Значения секретов в конфигах агентов` (doctor) | Конфиг записан старой версией miksy или до появления секрета. Обычный `sync` заменит серверы обёртками |
| `Файлы секретов: нет файла / лишний / устарел / доступ не только у владельца` (doctor) | `local/secrets/` разошёлся с учётом. `sync` исправит (лишние удаляет только свои). «Не от miksy» — справочно. `local/secrets` — ссылка: что сделает `sync`, сказано в самой строке — файл за ссылкой он закрывает только при записи, а пока цель ссылки открыта, туда не пишет |
| `… ссылка на …: … закройте вручную (PowerShell): <команда>` / `битая ссылка внутри local/` | Ссылка внутри `local/` (например, `local/secrets` на другом томе) ведёт на открытый другим каталог или файл (открытый — доступный не только вам) или никуда. miksy в ссылки не заходит и права за ними не меняет. Готовая команда — в конце самой строки, после двоеточия (пометка «(PowerShell)» — где её выполнять), с вашим путём и SID вашей учётной записи (`*S-1-5-…`, свой SID покажет `whoami /user`): выполните её как есть, затем `miksy sync --global` и `miksy sync --all`; проверка — `miksy doctor`: строки больше нет. Windows (PowerShell): `icacls '<цель>' /reset; icacls '<цель>' /inheritance:r /grant:r '*<ваш SID>:(OI)(CI)F'` (файлу — `:F`) — сначала снимает все явные записи, в том числе ваши, затем оставляет доступ только вам (у системы и администраторов тоже снимает); macOS, Linux: `chmod 700 '<цель>'` (файлу — `600`). Битая ссылка — исправьте или удалите её; убрать саму ссылку, не трогая цель, — `(Get-Item -LiteralPath '<ссылка>' -Force).Delete()` (Windows, PowerShell; ссылка на папку или файл), `rm '<ссылка>'` (macOS, Linux). Ссылки в копии «до miksy» (`local/backups/before-miksy-…`, ваши dotfiles) miksy не проверяет: они ведут к вашим файлам, как до установки |
| `… ссылка на …: … miksy не пишет туда бэкапы и копии ваших файлов` (все команды, которые пишут, и doctor) | Папка бэкапов `local/backups` или папка либо файл в ней (например, `originals`) — ссылка на открытую другим или несуществующую цель (бэкапы на другом томе). Все команды, которые пишут, останавливаются в начале, ничего не записав. Выхода два. Обычно — первый: закройте цель (папку, куда ведёт ссылка) готовой командой в конце строки — одна команда, ничего не переносится, бэкапы остаются на другом томе. Второй — если цель должна остаться открытой (общая папка) или её диска больше нет: замените эту ссылку (путь — в начале строки) обычной папкой с содержимым цели (ссылку на файл — обычным файлом; там оригиналы ваших файлов, по ним `clean` их возвращает). Ссылка внутри `originals` (например, `originals/C`) — только замена: сквозь неё miksy не пишет, даже если цель закрыта. Заменить — скопировать цель рядом, убрать саму ссылку и переименовать копию — `Copy-Item -Recurse -LiteralPath '<цель>' -Destination '<ссылка>.new'`, `(Get-Item -LiteralPath '<ссылка>' -Force).Delete()`, `Rename-Item -LiteralPath '<ссылка>.new' -NewName '<имя ссылки>'` (PowerShell; не убралась ссылка — переименование откажет, ничего не испортив); macOS, Linux: `cp -R '<цель>' '<ссылка>.new' && rm '<ссылка>' && mv '<ссылка>.new' '<ссылка>'`. Windows: если в цели есть копия «до miksy» (папка `before-miksy-…`), второй выход не подходит — `Copy-Item` превратит её ссылки на ваши dotfiles в копии файлов, и команда возврата из «Как удалить» затёрла бы ими нынешние dotfiles; закройте цель (первый выход). Прежнюю цель после замены оставьте как есть, а если она была открыта — закройте (команда — как в строке «закройте вручную» выше): в ней остались копии ваших файлов. Затем повторите команду miksy, которая остановилась; проверка — `miksy doctor`: строки больше нет. `… Закройте папку бэкапов и всё в ней (PowerShell): <команда>` (или `… папку оригиналов …`) — Windows: цель закрыта, но папка miksy за ней открыта другим или недоступна даже вам (так их оставляли 0.2.1 и раньше, если цель закрыта без наследования прав). Команда закрывает папку и всё в ней, ссылки внутри не трогает. Если такая папка глубже, отказ — на записи: `ОШИБКА (цель синхронизирована частично): <папка>: …` — выполните команду из строки и повторите |
| `Небезопасные права` … `доступ есть не только у владельца` (doctor; путь внутри `local/`, не ссылка) | Файл или папка в `local/` открыты другим учётным записям. miksy закроет их сам при следующей команде, которая пишет: `miksy sync --global`. Проверка — `miksy doctor`: строки больше нет |
| `Нет исполняемого файла обёртки` (doctor) | Программу сервера удалили или обновили (новый путь): поправьте `command` в слое или выполните `sync` |
| `… убран из конфига opencode (с {file:} …)` | Секрета нет — `{file:}` на отсутствующий файл сломал бы весь opencode. Задайте секрет и повторите `sync` |
| `miksy bridge: … редиректом` | Мост (bridge) — программа miksy, через которую агент подключается к удалённому (HTTP) серверу с секретом. Сервер ответил 3xx — мост редиректам не следует. Укажите в слое конечный `url` |
| `miksy bridge: … GET-потоку` / `… не ответил за … с` / `… закрыл ответ` | Сервер отдаёт результат отдельным GET-потоком (не поддерживается), не ответил за 10 минут или оборвал поток |
| `miksy bridge: HTTP 401 …` | Сервер отклонил токен: проверьте значение в `local/secrets.env`, затем `sync` |
| Сервер с секретом «Connection closed» в агенте | Обёртка не нашла файл секрета или скрипт, который подставляет токен в заголовок (headersHelper), вернул неверный. `miksy doctor`; ручной запуск обёртки из `local/run/…` покажет причину |

### Сообщения о доверии

| Сообщение | Что значит и что делать |
|---|---|
| `Нужно решение пользователя о доверии` (sync, doctor) | В проекте исполняемые настройки агента, которые ставил не miksy: команды проекта (хуки, `.mcp.json`, чужой `.codex/config.toml`), чужой `.claude/settings.local.json` или неодобренные серверы `.mcp.json`. Строка «ответы в окне Claude («да, больше не спрашивать» и т. п.)» — разрешения, которые Claude записал по ответу в своём окне: ваши или того, кто работал в этой папке до вас. Решите в терминале: `miksy trust <проект>`; для организации — `trust` в её слое. Агенту — не подтверждать самому |
| Серверы `.mcp.json` в Claude — `Pending approval` | Серверы командного `.mcp.json` не одобрены: решите `miksy trust <проект>` (или `trust: true` в слое). Одобренные и отклонённые вами miksy не трогает |
| `Claude: проект не доверенный — headersHelper …` | Доверия после sync не будет (запрет, нужно решение, отказ) — HTTP-сервер с секретом получит 401. Причина — в строке «нет доверия» |
| `Исполняемые настройки в подкаталогах групп без git` (doctor) | Доверие группы распространяется на них. Удалите их, сделайте каталог git-репо или запретите доверие группы |
| `проект не доверенный в Claude: одобрение серверов .mcp.json (…) снимается` (sync, doctor) | Вы сказали «нет» доверию Claude, но отдельно одобрили серверы `.mcp.json`, а потом сами сняли доверие в окне Claude: без доверия Claude серверы всё равно не запускает, и miksy снимает своё одобрение. Доверитесь проекту в окне Claude снова — следующий `sync` вернёт одобрение (если серверы сменились — спросит о них). Ничего делать не нужно |
| `доверие не меняется — запрет trust: { claude: false } в …` / `доверие не ставится — запрет …` (trust) | «Да» записано, но доверие запрещено в слое или в `local/machine.yaml` (если оно стояло — снимается). Нужно доверие — снимите запрет (место — в сообщении), затем `miksy sync` |

### Папки с проектами, корни, «забыть»

| Сообщение | Что значит и что делать |
|---|---|
| `взять под учёт … файл miksy (блок miksy), которого не было в учёте` (sync) | Учёт этого проекта был забыт («забыть» при отключённом диске), а файл — miksy и совпадает с тем, что miksy записал бы сейчас: miksy взял его обратно. Ничего делать не нужно. Так же — в облачной папке проекта, которую раньше записал miksy другой машины |
| `КОНФЛИКТ … файл miksy (блок miksy), которого нет в учёте, отличается …` | Файл miksy после «забыть», но с тех пор слои поменялись (или файл правили). `sync … --force` перезапишет его (прежний — в бэкап). Исключение — облачная папка проекта, которую пишет miksy и другой машины: у Codex, opencode, Antigravity файл с путями машины, `--force` будет перетягивать его между машинами — включайте эти агенты для такого проекта на одной машине («[Одна облачная папка проекта на двух машинах](#одна-облачная-папка-на-двух-машинах)») |
| `удалить … (файл miksy, которого не было в учёте, — больше не нужен)`, `убрать только блок — блок miksy, которого не было в учёте, больше не нужен` (sync, clean) | Учёт проекта был забыт, а miksy этот файл (блок) больше не пишет — например, правила убрали из слоёв, пока диска не было. miksy убирает его сам, прежний — в бэкап. Ничего делать не нужно |
| `одобрение .mcp.json … взять под учёт — одобрения miksy, которых не было в учёте` (sync) | Учёт проекта был забыт, а одобрения серверов командного `.mcp.json` ставил miksy и одобрил бы их сейчас: miksy взял их обратно. Ничего делать не нужно |
| `Записанное в … забыто. Если диск найдётся: …` (clean, root remove) | miksy больше не помнит своих файлов в этих проектах. Когда диск вернётся — команды из сообщения: вернуть корень (если убирали), `sync`, а если файлы не нужны — затем `clean` («[Диск нашёлся после «забыть»](#диск-нашёлся-после-забыть)»). `Копии ваших прежних файлов (N) … остаются в …/local/backups/originals/` — miksy когда-то заменил ваши файлы; после «забыть» он их сам не вернёт, нужное возьмите из копии. `В N файлах (CLAUDE.local.md и т. п.) miksy только дописал свой блок` — файл ваш и на месте, miksy уберёт из него только свой блок; копию «до блока» поверх него не возвращайте — потеряете дописанное позже |
| `группа X выше не получила правила Claude` | Её правила записаны в цель ниже. `miksy sync X` (или `sync --all`), затем `sync` цели |
| `пометка группы … снята, а её файлы остались` | `miksy sync --all` уберёт файлы бывшей группы |
| `не git-репо — настроек не получат (N): …` (sync --all) / `Каталоги без git на уровне проектов` (doctor) | Агент в этих каталогах — без ваших правил и MCP. Нужны настройки — `git init` в каталоге или `miksy target <путь>` («[Папка без git](#папка-без-git-заметки-выгрузки-группа-проектов)»); не нужны — ничего не делайте |
| `новых целей: … подтвердите: --yes` | `sync --all` нашёл много репо, куда ещё не писал. Проверьте workspace и план (`--dry-run`), затем `--yes` |
| `нет доступа (права каталога)` / `пропущен при поиске проектов` | Каталог без прав чтения: проекты внутри не видны, остальное работает |
| `Похоже на опечатку или переименование` (doctor) | Слой в `layers/tree/` не нашёл свой каталог, рядом есть похожий — переименуйте каталог слоя |
| `Каталоги слоёв отличаются только регистром` (doctor) | В `layers/tree/` две папки с одним именем в разном регистре (`Clients` и `clients`; бывает на Linux): применяется одна — она в сообщении. Перенесите файлы в одну папку и удалите остальные, затем `miksy sync --all` |
| `Ветки дерева слоёв без папки на этой машине, но с похожей папкой` (doctor, справочно) | Ветка верхнего уровня (`layers/tree/Clients`), а в основной папке есть похожая (`Clients-old`). Если это ветка корня другой машины — ничего не делайте; если опечатка — переименуйте каталог слоя |
| `… — git-репо / проект корня … / папка внутри git-репо … / папка внутри проекта …: корнем workspace он станет папкой с проектами, а не проектом` (root add, мастер) | Корень — папка с проектами. Чтобы git-репо вне workspace стал проектом, добавьте корнем папку, в которой он лежит (команда — в сообщении); проект, который уже в workspace, и так получает настройки. Если такой корень всё-таки нужен — `--yes` (в терминале — ответ «да») |
| `… — теперь корень workspace (папка с проектами), а не проект` (sync --all, doctor) | Проект добавили корнем: записанное в него раньше действует, но не обновляется. По ошибке — `miksy root remove "<путь>"`; так и задумано — `miksy clean "<путь>"`. Цель `target: true` без git, добавленная корнем, — не здесь: её пометка перестаёт действовать, и `sync --all` убирает записанное в неё сам |
| `… — основной корень workspace (папка с проектами), а не проект` (sync --all, doctor «Записанное в основной корень workspace») | miksy раньше записал настройки в сам основной корень — например, основным корнем сделали бывший проект (или так делала старая версия miksy). Записанное действует, но не обновляется. Убрать — `miksy clean "<путь>"` |
| `Слои, которые на этой машине ни к чему не применяются` (doctor) | Таких проектов на этой машине нет — нормально, если вы их здесь не клонировали. Мастер не спрашивает их секреты и программы |
| `Части дерева слоёв, которых нет на этой машине` (doctor) | Над этими ветками `layers/tree/` нет ни одного корня workspace этой машины — они для других машин («[Несколько корней workspace](#несколько-корней-workspace)»). Нормально |
| `корень … указан дважды (… — один и тот же каталог: повтор, junction или симлинк)` | В `workspace` файла `local/machine.yaml` один каталог записан дважды (в том числе через ссылку). Оставьте одну запись |
| `tree «…» корня …` / `workspace — путь или список корней` | Неверная запись корня в `local/machine.yaml`: `tree` — имена каталогов через `/` (`Clients`, `Clients/Acme`), без `..`; элемент списка — путь или `{ path, tree }` |
| `у корня … не указана ветка дерева слоёв` / `tree: … уже у корня …` | У каждого корня, кроме основного, своя ветка дерева: допишите `tree` (`{ path: …, tree: Clients }`) или выберите другое имя («[Несколько корней workspace](#несколько-корней-workspace)»). Общее для нескольких корней — слоем в `map.yaml` |
| `ветка layers/tree/… корня … совпадает с папкой … корня …` | Ветка одного корня совпала с папкой в другом: слои этой ветки получат обе папки. Смените `tree` корня или переименуйте папку; если общее задумано — сделайте его явно, слоем в `map.yaml` |
| `корень … недоступен (нет диска / ссылка ведёт в никуда / каталога нет / пуст …)` | Корня сейчас нет (или папка пуста, а miksy в его проекты уже писал — диск не смонтирован): его проекты пропущены, записанное туда и учёт не тронуты. Подключите диск — всё вернётся. Корень больше не нужен — `miksy root remove <путь>` |
| `На недоступном диске осталось записанное miksy — N файлов в …` (clean) | Убрано всё, до чего miksy дотянулся; записи о файлах на недоступном диске оставлены. Подключите диск и повторите `miksy clean "<путь>"`. `… файлов агента codex (его нет в agents)` — агента убрали из `agents`: его файлы уберёт `miksy clean "<путь>" --agent codex` (команда — в сообщении). Данных больше нет — `miksy clean "<путь>" --forget` |
| `Проект был забыт … Skills, плагин Antigravity и opencode.json от miksy могут остаться` / `Остались файлы агентов, которых нет в agents …` (clean) | Учёт этого проекта был забыт, и `clean` убрал только то, что узнал сам. Убрать всё — все строки из сообщения по порядку: `miksy sync "<путь>"`, затем `miksy clean "<путь>"`; строки с `--agent <имя>` — для агентов, которых вы убрали из `agents`. Папка вне workspace — первой строкой `miksy root add`: верните корень, в котором она лежала. Убирали его `root remove` — путь и ветку печатал он («Убрать корень <путь> → layers/tree/<ветка>»), они же — в копии `local/machine.yaml` до него, если она ещё хранится (путь — в сообщении). Корень был основным, а основной сменил `setup --force` — путь: прежний основной (его называл тот `setup`), ветка — любая новая, которой нет в `layers/tree`. Слои его проектов под неё скопируйте, а не переносите (ветки у него не было — `layers/tree/<папка>` → `layers/tree/<ветка>/<папка>`; была — всё содержимое `layers/tree/<прежняя ветка>` → `layers/tree/<ветка>`; к привязкам `map.yaml` его папок допишите такие же с новой веткой в начале, прежние не трогайте): тогда `sync` узнает всё записанное туда, в том числе skills, и `clean` уберёт всё, а слои одноимённых папок нового основного не изменятся. На вопрос `root add` «Записать настройки проектам workspace сейчас?» ответьте «нет», после `clean` уберите корень снова (`root remove`; на вопрос «Убрать записанное…» — «нет», если остальные его проекты трогать не нужно), затем удалите копию слоёв и дописанные привязки. Вернуть его насовсем — «[Сменить основной корень](#несколько-корней-workspace)» |
| `Папки … нет (она вне workspace / её корень недоступен): записанного туда учёт не помнит, осталась только отметка «проект забыт»` (clean) | Проект «забыли», а его папки нет. Вернётся — `miksy clean "<путь>"` уберёт файлы miksy по отметке; не вернётся — `miksy clean "<путь>" --forget` уберёт отметку из учёта |
| `Корень … недоступен: в его проектах осталось записанное miksy …` (clean --all) | `clean --all` не дотянулся до проектов этого корня. Подключите диск и повторите `miksy clean --all`; данных больше нет — для дополнительного корня `miksy root remove "<корень>" --forget`, для основного — `miksy clean "<путь проекта>" --forget` для каждого проекта (команды — в сообщении) |
| `Каталога … нет: диск не подключён или данных больше нет? Забыть записанное туда?` | Вопрос `clean` (и `root remove`). «Нет» (по умолчанию) — записи останутся до возвращения диска; «да» — miksy забудет эти файлы. Если диск найдётся — команды из сообщения «забыто» («[Диск нашёлся после «забыть»](#диск-нашёлся-после-забыть)») |
| `Корень … недоступен и лежит внутри корня …: … Корень не убран` (root remove) | Подключите диск и повторите `miksy root remove`, или, если данных больше нет, — `miksy root remove "<путь>" --forget` |
| `Учёт целей недоступного корня … не проверяется` (doctor) | Записи о файлах на диске, которого сейчас нет. Диск вернётся — `miksy clean "<путь>"`; данных больше нет — `miksy clean "<путь>" --forget`. Записанное агентами, которых нет в `agents`, `clean` без `--agent` не убирает — команды `miksy clean "<путь>" --agent <имя>` в строке «Учёт агентов, которых нет в agents» |
| `Учёт целей вне workspace без каталога … каталога нет: диск не подключён или папку удалили` (doctor) | Корень этих проектов убран из workspace, а их папок нет. Диск вернётся — `miksy clean "<путь>"`; папки больше нет — `miksy clean "<путь>"` спросит, забыть ли записанное (без терминала — `--forget`). Записанное агентами, которых нет в `agents`, `clean` без `--agent` не убирает — команды `miksy clean "<путь>" --agent <имя>` в строке «Учёт агентов, которых нет в agents» |
| `Ветки корней внутри чужих мест` (doctor), `справка: … лежит внутри места …` (root add) | Ветка корня лежит внутри места, у которого есть свои настройки или папка другого корня: его проекты получат и их (перечислено). Задумано — ничего не делайте; нет — ветку вне этого места, общее — слоем в `map.yaml` |
| `… — служебный каталог miksy` (sync, explain без пути) | Каталог внутри `out/`, `local/` или `dist/` движка или конфигурации (копии, бэкапы) — настроек не получает. Запустите команду в каталоге проекта или укажите его путь |
| `… — основной корень, его нельзя убрать` (root remove) | Убрать можно только дополнительный корень. Сменить основной — `miksy setup --force` |
| `Цели учёта вне workspace` (doctor) | miksy писал в эти каталоги, а их корень убран из `workspace`: `sync` их больше не обновляет. Убрать записанное — `miksy clean <путь>` (агентам, которых нет в `agents`, — с `--agent`: команды в строке «Учёт агентов, которых нет в agents»); снова нужны — `miksy root add` |
| `корень … лежит внутри проекта …` / `… внутри группы …` | Вложенный корень внутри git-репо внешнего (файлы его целей окажутся в чужом репо) или внутри его группы (Claude прочитает и правила группы). Перенесите каталог или уберите корень |
| `… — корень workspace, а не проект` / `… — не проект: каталог без git и не цель` / `… — каталог вне workspace` (sync) | `miksy sync` без пути — для проекта или цели, в каталоге которого вы находитесь. Все проекты — `miksy sync --all`, домашние настройки — `miksy sync --global`, другой проект — `miksy sync <путь>`; каталог без git — `git init` или `miksy target`; git-репо вне workspace — корнем папку, в которой он лежит (готовая команда — в сообщении); папка с проектами вне workspace — `miksy root add .`; папка без проектов — `git init` в ней и корнем папку, в которой она лежит (команда — в сообщении) |
| `… — каталог без git и не цель: sync --all его не обновит` (sync <путь>) | Записано разово; `sync --all` и `doctor` такой каталог не видят. Чтобы обновлялся — `miksy target <путь>` или `git init` |
| `clean убирает записанное — только явно` | `clean` без пути не работает: укажите путь проекта, `--global` или `--all` |
| `Проект забыт` (doctor) | Учёт записанного в этот проект забыт («забыть» при отключённом диске), а папка на месте. `miksy sync <путь>` возьмёт файлы miksy обратно; не нужны — затем `miksy clean <путь>` |
| `Учёт агентов, которых нет в agents` (doctor, справочно) | Агента убрали из `agents` в `local/machine.yaml`, а записанное ему осталось и действует. Убрать — команды из сообщения (`miksy clean … --agent <имя>`) или верните агента в `agents` |

### Установка, окружение, обновление

| Сообщение | Что значит и что делать |
|---|---|
| `… установок несколько — используется …` (doctor, setup, install) | Программа стоит дважды (например, Bun из Homebrew и в `~/.bun/bin`): терминал, агенты и команда `miksy` могут запускать разные версии, а обновляются они по отдельности. Оставьте одну, лишнюю удалите сами. Для Bun затем — `miksy setup` (обновит команду `miksy`) и `miksy sync --global`, `sync --all` (обёртки MCP) |
| `CODEX_HOME=…` / `CLAUDE_CONFIG_DIR=…` / `XDG_CONFIG_HOME=…`: `… настройки miksy агент не увидит` (doctor) | Агент ищет настройки не в стандартном каталоге, а miksy пишет в стандартный. Уберите переменную (профиль оболочки), если она не нужна; другой каталог miksy не поддерживает |
| `Прежнее имя агента … gemini теперь antigravity` (doctor) | В `local/machine.yaml` (`agents`) или в слоях (`agents:` у MCP) осталось `gemini`. Работает как раньше; переименуйте в `antigravity`, когда удобно |
| `opencode … — версия 1.x, а miksy пишет настройки в формате opencode 2.x` (doctor, setup) | Обновите opencode до 2.x (`curl -fsSL https://opencode.ai/v2/install \| bash` или пакетом `@opencode/cli`) |
| `в движке есть незакоммиченные правки` (update) | Файлы движка изменены — обновление их не трогает и не начинается. Своё держите в конфигурации; правки движка — `git -C <движок> stash`, затем `miksy update` |
| `ветка … движка разошлась с origin/…` (update) | В движке свои коммиты, или история в удалённом репо переписана. Команды из сообщения сохранят ваши коммиты в отдельной ветке и переведут движок на удалённую |
| `… Нет доступа к репо` (update) | git не смог скачать: нет сети (прокси, VPN) или это ваша приватная копия без входа — `gh auth login`, затем `gh auth setup-git` (или SSH-адрес), и повторите |
| `движок не на ветке (… detached HEAD)` / `движок на ветке …` (update) | Движок переключён на коммит или чужую ветку: `git -C <движок> checkout stable`, затем `miksy update` |
| `учёт miksy … записан более новой версией движка` (sync, doctor) | Учёт писал движок новее этого: другая копия движка с общей конфигурацией — обновите этот (`miksy update`); вы откатились нарочно — сделайте шаги из «[Откатиться на прежнюю версию](#откатиться-на-прежнюю-версию)»: в 0.2.2 и новее `miksy setup --yes` из них уберёт и сообщение; в 0.2.1 и старше оно пропадёт, когда эта версия сама запишет учёт (первый `sync` с изменениями). Ничего не заблокировано |
| `неизвестные ключи — miksy их не читает` (sync, doctor) | В `map.yaml` или `layer.yaml` ключ, которого эта версия не знает: опечатка (исправьте) или ключ из более новой версии miksy (`miksy update`) |

## Как удалить miksy

Коротко: шаг 1 убирает всё, что записал miksy, — обычно этого хватает. Шаг 4 — удалить сам miksy; `local/`
конфигурации удаляйте последней.

**До шага 1 знайте, что пропадёт у агентов:** вместе с записанным miksy `clean` уберёт и то, что вы сами перенесли в
конфигурацию, — MCP-серверы, которые перенёс мастер или `miksy adopt`, ваши правила и skills, перенесённые в слои.
Оригинала у них нет. Вернуть — шагом 3 (копия «до miksy») или из слоёв конфигурации вручную (шаг 2). Шаг 3 нужен и
тогда, когда после шага 1 что-то работает не так, как до miksy.

**1. Уберите всё, что записал miksy** (для агентов из списка `agents` в `local/machine.yaml`; агент, которого вы оттуда
убрали, — `--agent <имя>`):

```
miksy clean --all --dry-run     # посмотреть план
miksy clean --all               # проекты и папки без git
miksy clean --global            # домашние настройки агентов
```

Если в конце `clean --all` что-то перечислил (до чего не дотянулся) — выполните команды из его вывода.

`clean` по каждой цели:
- удаляет свои файлы (skills, `.opencode/miksy.md`, плагин Antigravity, `.codex/config.toml` проекта, скрипты в
  `local/run/`), убирает свой блок из файлов правил (файл удаляется, только если вне блока ничего нет) и свои ключи
  из общих файлов (`~/.claude.json`, `~/.codex/config.toml`, `opencode.json`, `mcp_config.json`);
- возвращает **оригиналы** файлов, которые miksy когда-то заменил (если после замены файл менялся — оставляет его
  и называет путь оригинала);
- снимает своё доверие и одобрения серверов `.mcp.json` (ваши не трогает), свои строки `.git/info/exclude`,
  ненужные файлы `local/secrets/`.

Изменённое вручную `clean` не трогает (конфликт) — `--force` уберёт и его (с бэкапом). В проекте, который был
«забыт» (`clean --forget`, `root remove --forget`), а потом нашёлся, `clean` убирает только то, что узнаёт сам:
skills, плагин Antigravity, `opencode.json` могут остаться — сначала `miksy sync <путь>`, затем `miksy clean <путь>`
(вывод `clean` скажет об этом).

**2. Что остаётся после `clean`** — подробности для особых случаев:
- пустые файлы и папки, пустые разделы (`{"mcp": {}}`) в общих конфигах агентов (опустевшие записи проектов,
  созданные `sync`, уходят сами) — удалите, если мешают;
- цели, которых больше нет в конфигурации (учёт их помнит, а `clean --all` идёт по конфигурации), и папки, которых
  нет на диске, — `miksy clean <путь>` для каждой (`clean --all` и `doctor` их перечисляют). Папка была вне
  workspace (корень убран) и её нет — miksy не знает, удалили её или не подключён диск, и спросит, забыть ли
  записанное туда (без терминала — `miksy clean <путь> --forget`);
- записанное на недоступном диске (папка с проектами не подключена): учёт помнит его, `clean --all` скажет,
  сколько осталось, и даст команды. Подключите диск и повторите `miksy clean --all`. Данных больше нет: для
  дополнительной папки с проектами — `miksy root remove "<папка>" --forget` (папка уйдёт из workspace, записанное
  туда забудется); для основной (её убрать нельзя) — `miksy clean "<путь проекта>" --forget` для каждого проекта;
- MCP-серверы, которые мастер (вопрос «Ручные настройки агентов») или `miksy adopt` перенёс из настроек агентов в
  конфигурацию, `clean` у агентов **удалил**: после переноса miksy берёт такую запись себе (совпала с тем, что он
  записал бы, — «берём под учёт»; не совпала — после `sync --force`), и оригинала у неё нет. Вернуть — копией
  (шаг 3) или добавьте сервер агенту заново (определение — в слое, `mcp/<имя>.yaml`). Skills, которые miksy заменил
  своими, `clean` вернул из оригиналов. Что переносили, видно в конфигурации: `layers/global/mcp/`,
  `layers/global/skills/`, `layers/tree/mcp/` (уровень `workspace`) и слои проектов — там же и то, что было в
  стартовой конфигурации (skill `miksy`, сервер context7): его агентам возвращать не нужно;
- правила и домашние skills, которые вы сами перенесли в слои (из `~/.claude/CLAUDE.md` и т. п.), `clean` у агентов
  тоже убрал — теперь это записанное miksy. Вернуть: скопируйте текст из `layers/global/instructions/<имя>.md` обратно
  в файл агента, папку skill — из `layers/global/skills/<имя>/` в каталог skills агента (или шаг 3).

**3. Вернуть копию «до miksy»** — только если нужно (см. начало раздела) и **до** удаления `local/`: копия лежит в
нём. Копия повторяет домашний каталог: `…/before-miksy-<метка>/.codex/config.toml` — это `~/.codex/config.toml`.
Копия **затрёт** изменения, сделанные после установки в тех же файлах. Поэтому:

- `~/.claude.json` из копии **не возвращайте**: в нём Claude хранит вход, свои настройки и список проектов — команды
  ниже его пропускают. MCP-серверы Claude (их `clean` убрал, если вы переносили их в конфигурацию) верните руками:
  закройте Claude, откройте в редакторе копию `…/before-miksy-<метка>/.claude.json` и нынешний `~/.claude.json` и
  перенесите нужные записи из раздела `"mcpServers"` копии в тот же раздел нынешнего файла: общие серверы — в
  `"mcpServers"` на верхнем уровне, серверы одного проекта — в `"projects"` → `"<путь проекта>"` → `"mcpServers"`
  (в копии они там же); проверка — `claude mcp list` (в папке проекта — и его серверы);
- в `~/.codex/config.toml` и других файлах — ваши правки после установки: нужное из нынешних файлов сохраните заранее
  или верните только нужные файлы (ниже).

Где копия: `<конфигурация>/local/backups/before-miksy-<метка>/`, где `<конфигурация>` — папка конфигурации (например,
`$HOME\Projects\miksy-config`), а `<метка>` — дата и время установки. Найти метку и посмотреть, что в копии:

```
(Get-ChildItem $HOME\Projects\miksy-config\local\backups -Filter before-miksy-*).FullName              # Windows: копии, полный путь
Get-ChildItem -Recurse -Force "$HOME\Projects\miksy-config\local\backups\before-miksy-<метка>"         # что в копии
find -H ~/Projects/miksy-config/local/backups -maxdepth 1 -name 'before-miksy-*'                   # macOS, Linux: копии, полный путь
find ~/Projects/miksy-config/local/backups/before-miksy-<метка> ! -type d                           # что в копии
```

Первая команда ничего не нашла — копии нет (на вопрос 3 мастера ответили «нет» или ставили `setup --yes` без
`--backup`): вернуть прежнее можно только архивом из «Установки вручную», если вы его делали (ниже). Копий несколько —
берите самую раннюю: она сделана до первой записи miksy.

Вернуть один файл (например, конфиг Codex) — тоже после шага 1:

```
Copy-Item "$HOME\Projects\miksy-config\local\backups\before-miksy-<метка>\.codex\config.toml" "$HOME\.codex\config.toml"   # Windows
cp ~/Projects/miksy-config/local/backups/before-miksy-<метка>/.codex/config.toml ~/.codex/config.toml                          # macOS, Linux
```

Вернуть всё, кроме `~/.claude.json`, — **после шага 1** (`clean`): вернувшееся раньше него `clean` уберёт, как своё.
Команду с вашим путём печатал мастер (вопрос 3, «вернуть …»). Вывод не сохранился — возьмите команду ниже и замените
первый путь в одинарных кавычках (в команде для Windows — после `-LiteralPath`, для macOS и Linux — после `cd --`)
на полный путь своей копии (его показывает команда «копии, полный путь» выше; без `$HOME`
и `~` — в одинарных кавычках они не раскрываются). Кавычка в самом пути: в PowerShell удвойте её (`'` → `''`, так же
`’`, `‘`, `‚`, `‛`), в macOS и Linux замените `'` на `'\''`. Вернётся всё, что лежит в копии, кроме `.claude.json`. Первая команда — для Windows (PowerShell), вторая — для
macOS и Linux:

```
& { try { $c = (Get-Item -LiteralPath 'C:\Users\you\Projects\miksy-config\local\backups\before-miksy-2026-11-10T09-00-00' -Force -ErrorAction Stop).FullName.TrimEnd([char]92) } catch { Write-Host "не возвращён ни один файл: $_"; Обе возвращают файлы в домашний каталог, кроме
```
`.claude.json`, через ваши ссылки (dotfiles) тоже, а ссылки из копии — ссылками.

Команда ничего не напечатала — всё вернулось (код выхода 0; в PowerShell — `$LASTEXITCODE`). Иначе она перечисляет
файлы строками «не возвращён: …». Причины и что сделать:
- на этом месте в домашнем каталоге папка — посмотрите, что в ней; не нужна — удалите или переименуйте её;
- на Windows — ссылка на файл, которую Windows не дала создать: включите режим разработчика (Параметры → Система →
  Для разработчиков) или откройте PowerShell от имени администратора;
- файл занят (открыт агент или редактор) — закройте агентов и редакторы;
- файл «только для чтения» — снимите пометку: `attrib -r "$HOME\<файл>"` (Windows), `chmod u+w ~/'<файл>'` (macOS, Linux);
  `<файл>` — путь из строки «не возвращён» (он от домашнего каталога);
- «не возвращён ни один файл: …» — неверен путь копии: проверьте его первой командой выше.

Затем запустите ту же команду ещё раз. Повторять её можно: файлы она записывает тем же содержимым из копии, а ссылки,
которые уже на месте, пропускает.

Архив из «[Установки вручную](#установка-вручную)» — так же без `.claude.json`:
`tar xzf ~/agents-before-miksy.tgz -C ~ --exclude=.claude.json` (Windows:
`tar xzf "$HOME/agents-before-miksy.tgz" -C $HOME --exclude=.claude.json`).

Бэкапы `local/backups/<метка>/` (без `before-miksy`) для этого не годятся: хранятся только 20 последних запусков, а
секреты в них заменены заглушками `<secret:ИМЯ>`.

**4. Удалите остальное**, если оно не нужно, — в таком порядке:
- команда `miksy`: `~/.bun/bin/miksy` (на Windows — `miksy.cmd` в той же папке, `$HOME\.bun\bin`); файл
  `~/.miksy`, если есть, — в нём записано, где лежит конфигурация (его создаёт мастер, когда конфигурация лежит не
  рядом с движком);
- Bun и строка, которую мастер дописал в PATH, — если Bun нужен был только miksy: удалите папку `~/.bun`
  (`Remove-Item -Recurse $HOME\.bun` в PowerShell) и уберите `~/.bun/bin` из PATH: на macOS и Linux — две строки
  `# miksy` и `export PATH=…` в `~/.zshrc`, `~/.bash_profile` или `~/.bashrc`; на Windows — Пуск → «Изменение
  переменных среды текущего пользователя» → Path → все строки с `.bun\bin` (их мог добавить и
  установщик Bun) → «Удалить». Установщик Bun на macOS и Linux дописывает и свои строки (`# bun`,
  `export BUN_INSTALL=…`, `export PATH=…`) — уберите и их;
- программы, которые мастер ставил на вопросе «Программы для MCP-серверов» (Node.js, uv и т. п.), — если они нужны
  были только miksy; удаляются как обычные программы (на Windows — «Установленные приложения»). Что именно он
  ставил, видно в его выводе (строки «Выполнить «…»?» с ответом «y»); вывод не сохранился — в «Установленных
  приложениях» (Windows) отсортируйте по дате установки, на macOS — `brew list`; uv мастер ставит своим установщиком
  в `~/.local/bin` (Windows — `%USERPROFILE%\.local\bin`), его там и удаляйте (`uv`, `uvx`, на Windows ещё `uvw`);
- папка движка;
- `local/` конфигурации (`secrets.env`, `secrets/`, `state/`, `trust.json`; `backups/` — последней: в ней копия
  «до miksy» и оригиналы ваших файлов) и папка конфигурации (её стоит сохранить — это ваши слои).

## Особые случаи нескольких папок с проектами

### Корень недоступен

Корень недоступен, если нет его папки, нет диска (не подключён, облачное хранилище не запущено, на Linux —
ничего не смонтировано в `/media/<пользователь>/…` или `/mnt/…`) или ссылка ведёт в никуда. Команды работают:
`projects`, `sync --all` и `doctor` пропускают такой корень с предупреждением, записанное туда не трогается.
Подключите диск — всё вернётся. Так же считается **пустая папка корня, если miksy уже писал в его проекты**: на
Linux и macOS это обычно точка монтирования без диска. Корень-ссылку miksy узнаёт по пути назначения,
запомненному при последней записи.

**Убрать записанное в проекты недоступного корня** — `miksy clean "<путь проекта>"`. miksy уберёт то, до чего
дотянется (MCP-серверы проекта в настройках агентов, доверие, свои скрипты), а записи о файлах на недоступном
диске оставит: по ним он узнает свои файлы, когда диск вернётся, — тогда повторите `clean`. Данных больше нет
(диск потерян, папку удалили) — скажите это: в терминале miksy спросит «Забыть записанное туда?» (по умолчанию —
нет), без терминала — флаг `--forget`. Пустую точку монтирования, которую вы очистили сами, так же убирают из
учёта: `clean … --forget`.

**Убрать сам недоступный корень** — `miksy root remove <путь>` спросит то же: забыть записанное в его проекты?
«Нет» (по умолчанию) — корень убирается из списка, а записанное и учёт остаются: уберите их потом
`miksy clean "<путь проекта>"`, когда диск вернётся; записанное агентами, которых вы убрали из `agents`, —
`miksy clean "<путь проекта>" --agent <имя>` (команды — в выводе `root remove`). Корень внутри другого корня без «забыть» не убирается: его
папки стали бы обычными папками внешнего корня, и miksy уже не отличил бы неподключённый диск от удалённых данных.
`--dry-run` (можно с `--forget`) покажет заранее: почему корень недоступен, будет ли вопрос и сколько файлов
забудется или останется в учёте.

### Диск нашёлся после «забыть»

Учёта этих файлов у miksy больше нет, но свои он узнаёт сам. Если папка
проекта всё ещё в workspace — `miksy sync "<путь проекта>"`. Если вы убирали корень (`root remove` с «забыть»),
сначала верните его: `miksy root add "<путь корня>" --tree <ветка>`, затем `miksy sync --all` (готовую команду
miksy печатает после `root remove`; после `clean … --forget` проекта, чей корень уже убран, — шаблон: путь корня
и ветку подставьте сами).

Агент, которого вы убрали из `agents` до «забыть»: его файлы `sync` и `clean` без `--agent` не трогают. Их уберёт
`miksy clean "<путь проекта>" --agent <имя>` — его называют сообщение «забыто», `miksy doctor` («Учёт агентов, которых
нет в agents») и подсказка `clean`; выполните и строки подсказки с `--agent`.

- Файлы, которые совпадают с тем, что miksy записал бы сейчас, `sync` берёт обратно сам — строка «взять под
  учёт — файл miksy, которого не было в учёте». Изменившиеся с тех пор `sync` покажет конфликтом —
  `miksy sync "<путь проекта>" --force` перезапишет их (прежние — в бэкап). Файлы, которые miksy больше не пишет
  (правила убрали из слоёв, пока диска не было), первый `sync` (или `clean`) убирает сам, с бэкапом; у блока в
  файле правил — только блок, ваш текст вне его остаётся.
- Не нужны файлы — после `sync` уберите их: `miksy clean "<путь проекта>"` (или `root remove` корня с согласием
  убрать). `clean` без `sync` уберёт только то, что узнает сам: skills, плагин Antigravity и `opencode.json` могут
  остаться — `clean` об этом скажет.
- Доверие Claude `sync` ставит снова без вопроса, если раньше его ставил miksy, вы отвечали «да» или в слое
  `trust: true` (и команда не добавила новых хуков и т. п.). Одобрения серверов командного `.mcp.json`, которые
  ставил miksy, `sync` берёт обратно, если одобрил бы их и сейчас. Одобрения тех же серверов, данные вами в окне
  Claude, miksy от своих не отличит: они станут его, и `clean` их снимет (Claude спросит снова). Одобрения серверов,
  которые miksy сейчас не одобрил бы, — ваши: их он не трогает.
- **Копии ваших прежних файлов**, которые miksy когда-то заменил (`--force`), сами на место не вернутся: они в
  `local/backups/originals/` (сообщение «забыто» говорит, сколько их), а `clean` удалит файл miksy на их месте —
  нужное верните из копии. Копия `CLAUDE.local.md`, куда miksy только дописал свой блок, — не для возврата: файл
  ваш, miksy уберёт из него только блок.
- Свой файл miksy узнаёт только по своим уликам: пометка «Сгенерировано miksy» в начале файла, его блок правил,
  его `opencode.json`; файл без пометки (skill, `plugin.json`) — если он ровно такой, каким miksy записал бы его
  сейчас, и его уже прячет от git строка miksy в `.git/info/exclude`. Ваш файл своим не станет, даже если
  совпадает: miksy сохранит его оригиналом, и `clean` его вернёт. Файл с пометкой miksy, который miksy больше не
  пишет, он убирает, только если строка именно этого файла есть в его блоке `.git/info/exclude` (такой файл в
  другом проекте — скорее всего, ваша копия: его miksy не трогает). Не узнает miksy свой файл без пометки, который
  с тех пор поменялся или пропал из слоёв, и файлы в папке без git (там нет `.git/info/exclude`): их уберите
  вручную. У плагина Antigravity (`.agents/plugins/miksy/`) нет отдельной строки на каждый файл: ненужные файлы
  плагина после `sync` остаются — и Antigravity их читает; после `clean` их покажет git — удалите их вручную.
- Так — только в проекте, который на этой машине «забыли». В остальных файлы miksy, которых нет в учёте этой
  машины, не трогаются: в облачной папке на двух машинах у каждой свой учёт, и файл miksy другой машины выглядит
  так же.

### Одна облачная папка на двух машинах

Одна облачная папка проекта на двух машинах (miksy на обеих) — что работает сейчас:

- **Claude** — да, если конфигурация одна: в папке проекта только `CLAUDE.local.md` и skills, одинаковые на
  обеих машинах (MCP Claude — в домашнем `~/.claude.json`). Оговорки: одобрения серверов командного `.mcp.json`
  miksy пишет в `.claude/settings.local.json` проекта — если на одной машине вы ответили «да», а на другой нет,
  машины будут по очереди менять строку этого файла в `.git/info/exclude`, и git второй машины будет его
  показывать. И совпадающие файлы miksy вторая машина берёт себе в учёт, поэтому `clean` (или `root remove` с
  согласием убрать) на одной машине убирает правила Claude и у другой — до её следующего `sync`.
- **Codex, opencode, Antigravity** — нет: их файлы в проекте (`.codex/config.toml`, `opencode.json`, плагин
  Antigravity) содержат пути своей машины, и у второй машины будет конфликт «файл miksy, которого нет в учёте,
  отличается». `--force` его не решает, а перетягивает файл между машинами. Если у машин разные skills, git может
  показывать файлы другой машины. Доработка — в следующих выпусках; пока включайте эти агенты для такого проекта
  на одной машине.

### Другие случаи

- **Вложенный корень** (корень внутри другого корня) — можно: папка относится к самому глубокому корню, обход
  внешнего её пропускает. Пример: одна облачная папка на Mac лежит отдельно (`~/Library/CloudStorage/…/Clients`), а
  на Windows клиент облака положил её внутрь основного корня (`D:/Projects/Cloud/Clients`). На Windows она —
  вложенный корень с той же веткой `tree: Clients`, и конфигурация общая для обеих машин. Предупреждение — только
  если вложенный корень лежит внутри проекта или группы внешнего корня. Пока это надёжно работает только для
  Claude — «[Одна облачная папка на двух машинах](#одна-облачная-папка-на-двух-машинах)».
- **Ветка внутри чужого места** — `tree: Clients/Sub`, когда `Clients` уже ветка другого корня, или `tree: Org/Sub`,
  когда в основном корне есть папка `Org`. Проекты такого корня получат и всё, что задано для `Clients` (или `Org`).
  Так задумано — ничего не делайте; нет — возьмите ветку вне этого места (`tree: Clients-Sub`), а общее задайте
  слоем в `map.yaml`. `root add` и `doctor` подсказывают это и перечисляют, что унаследуется.
- **Один каталог дважды** — ошибка с подсказкой: оставьте одну запись. Это и тот же путь в другом написании
  (`D:/Projects` и `d:\Projects\`), и ссылка (симлинк, junction) на каталог, уже указанный корнем.
- **Ветка совпадает с папкой другого корня** — ветка корня `tree: Clients`, а в основном корне есть папка
  `Clients`: слои `layers/tree/Clients/` получат обе (`doctor` — проблема, `sync`, `projects`, `root add` —
  предупреждение). Переименуйте ветку или папку; общее — явно («[Правила нескольких корней](#правила-нескольких-корней)»). Вложенный корень на своём же месте
  (`D:/Projects/Clients` с `tree: Clients`) — не совпадение.
- **`target: true`** действует по месту в дереве: пометка `layers/tree/Clients/Acme/layer.yaml` делает целью
  `E:/Clients/Acme`. Группы считаются в пределах своего корня.
- **`doctor`** ищет «лишние» ветки дерева (слой есть, папки нет — опечатка?) только там, куда смонтированы корни этой
  машины; ветки других машин — справочно. Ветка верхнего уровня (`layers/tree/Clients`), похожая на папку
  основного корня (`Clients-old`), — тоже справочно: это может быть и опечатка, и ветка корня другой машины.
