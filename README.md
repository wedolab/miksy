# Miksy

Один источник правил, skills (готовых инструкций для отдельных задач, которые агент подключает сам, когда задача
подходит) и MCP-серверов (программ и сервисов, через которые агент получает инструменты: трекер, документацию, базу)
для нескольких AI-агентов: **Claude Code, Codex, opencode, Antigravity**.

Вы описываете настройки один раз — правила, MCP-серверы, skills, — а miksy записывает их каждому агенту в
каждом проекте: правила — в его файлы инструкций, MCP-серверы — в его конфиг, skills — в его каталог. Miksy не
работает в фоне: поменяли настройки — запустите `miksy sync`.

**Miksy — не агент.** Он ничего не выполняет вместо агентов и не стоит между вами и ними: это генератор
настроек для агентов, которые у вас уже стоят. Имя — от того, что он раскладывает: **M**CP, **I**nstructions,
**K**eys (секреты), **S**kills.

Этот репо — **движок** (программа miksy). Ваши правила, секреты и настройки машин живут отдельно — в
**конфигурации**: личном каталоге (обычно `miksy-config` рядом с движком; лучше — в своём приватном git-репо).
Движком можно делиться: ваших данных в нём нет.

[подключить MCP-сервер](#подключить-mcp-сервер) · [добавить проект](#добавить-новый-проект) ·

[проверить, всё ли в порядке](#проверить-всё-ли-в-порядке) · [обновить](#обновление-miksy) ·

## С чем работает miksy

**Агенты** — четыре: **Claude Code**, **Codex**, **opencode** (версии 2.x) и **Antigravity**. Ставить всех не
нужно: miksy пишет настройки только тем, что у вас есть. Других агентов (Cursor, GitHub Copilot, Windsurf и т. п.)
он не поддерживает и их настройки не трогает. В конфигурации и командах агенты называются `claude`, `codex`,
`opencode`, `antigravity` (прежнее имя Antigravity — `gemini` — тоже работает).

**Где запускать агентов — где удобно**: агент сам читает файлы, которые разложил miksy. Проверено в терминале (все
четыре), в редакторе Zed через ACP (Claude Code, Codex, opencode), Antigravity — в его IDE и CLI (`agy`); через ACP
в Zed Antigravity настройки от miksy пока не получает. Другие редакторы читают те же файлы, но не проверялись.

**ОС** — Windows, macOS и Linux (Ubuntu 24.04). **Нужны** git и [Bun](https://bun.sh) 1.3.14 или новее — программа,
которая запускает miksy (Bun установщик предложит поставить сам).

## Как устроен miksy

Слова, которые встречаются дальше везде.

- **Конфигурация** — ваш каталог с настройками (`miksy-config`): слои и `local/` — то, что только для этой машины.
- **Слой** — папка с правилами (`instructions/*.md`), MCP-серверами (`mcp/*.yaml`) и skills (`skills/`) для
  какого-то места: для всех агентов везде, для всех проектов, для организации, для одного проекта.
- **Workspace** — папка с вашими проектами (например, `~/Projects` или `D:\Projects`). Таких папок может быть
  несколько (второй диск, облачная папка) — каждая называется **корнем** workspace.
- **Проект** — git-репо внутри workspace, а также папка внутри workspace, где агент уже работал (вы открывали в ней,
  например, Claude). Сама папка с проектами и папки внутри репо — не отдельные проекты.
- **Цель** — куда miksy пишет настройки: проекты, домашний каталог агентов, отмеченные вами папки без git.
- **Организация** — папка с проектами внутри workspace: `~/Projects/Acme/app` — проект `app` организации `Acme`.
- **Ветка** (дерева слоёв) — имя папки в `layers/tree/` для второй и следующих папок с проектами (`--tree Clients` →
  `layers/tree/Clients/`). Это не ветка git: она нужна, чтобы слои разных папок с проектами не смешивались.
- **Команда проекта** — коллеги, которые ведут репо; их закоммиченные настройки (хуки, `.mcp.json`) miksy не трогает.
- **`sync`** — команда, которая записывает настройки. Пока вы её не запустили, агенты ничего нового не получат.
- **Доверие** — отметка агента (Claude, Codex) «этому проекту можно доверять»: без неё агент не применяет
  настройки проекта. Обычно её ставит miksy; если в проекте есть то, что агент выполнит без вопроса и что ставил не
  miksy (например, **хуки** — программы, которые агент запускает сам), решаете вы ([docs/trust.md](docs/trust.md)).
- **Учёт** — список того, что miksy записал (`local/state/manifest.json`): по нему он отличает свои файлы от ваших.

В путях можно писать `~` (и в PowerShell). Путь с пробелами — в кавычках: `miksy sync "D:\My Projects\app"`.

```
miksy-config/                 конфигурация
├── map.yaml                  какие слои глобальные, особые привязки (редко нужно)
├── layers/
│   ├── global/               ваши правила для всех агентов везде → домашний каталог
│   ├── env-windows/, env-macos/, env-linux/   правила про ОС (shell, синтаксис команд)
│   └── tree/                 → все проекты workspace — дерево слоёв
│       ├── instructions/     правила всех проектов
│       ├── mcp/context7.yaml MCP-сервер для всех проектов
│       ├── Acme/             → всё внутри ~/Projects/Acme
│       │   └── billing-api/  → только проект ~/Projects/Acme/billing-api
│       └── Personal/         → всё внутри ~/Projects/Personal
├── local.example/README.md   заметка о подготовке машины: что miksy не настраивает сам (профили облачных CLI и т. п.)
└── local/                    только эта машина, не в git:
    ├── machine.yaml          где workspace, какие агенты, пути к программам (vars)
    ├── secrets.env           значения секретов: ИМЯ=значение
    ├── secrets/, run/        файлы секретов и скрипты-обёртки для агентов (создаёт sync)
    ├── state/manifest.json   учёт — что miksy записал
    ├── trust.json            ваши решения о доверии проектам
    └── backups/              копии файлов перед изменением и оригиналы
```

**Дерево слоёв** (`layers/tree/`) повторяет workspace: проект получает все слои по своему пути сверху вниз —
`tree/`, затем `tree/Acme/`, затем `tree/Acme/billing-api/`. Правила всех слоёв складываются (сначала верхних),
а MCP-сервер или skill с тем же именем в нижнем слое заменяет верхний. Нет папки в дереве — нет слоя.

Что получит проект и из какого слоя — `miksy explain <путь>` (без пути — текущий каталог; `--global` — домашние
настройки агентов). Что ещё бывает в слое, куда miksy пишет файлы каждого агента и как он помнит записанное —
[docs/layers.md](docs/layers.md).

## Установка

Одна инструкция для всех случаев: первая машина или вторая, агенты чистые или уже настроены руками. Ваши ручные
настройки не пропадут: чужие файлы miksy не трогает, а если заменяет файл — сохраняет оригинал и возвращает его
при удалении miksy. Исключение — то, что вы сами перенесёте в конфигурацию (мастер, `miksy adopt`): это miksy берёт
себе, и удаление miksy убирает его у агентов ([docs/uninstall.md](docs/uninstall.md)).

**Что нужно:** git и хотя бы один агент (как поставить — [docs/install.md](docs/install.md#установка-агентов)). Bun
установщик предложит поставить сам. Мастер не подходит, хочется пройти шаги по отдельности —
«[Установка вручную](docs/install.md#установка-вручную)».

**Перед установкой решите, какая папка — с проектами** (workspace). Настройки получат все git-репо в ней, в том
числе рабочие: в репо miksy кладёт только файлы, которые git не отслеживает, и прячет их от git
(`.git/info/exclude`), — в коммиты они не попадут. Исключить отдельный репо внутри этой папки нельзя: репо, которым
настройки не нужны, держите вне её.

**Поручаете установку агенту** (Claude Code, Codex и т. п.)? Дайте ему ссылку на [INSTALL-AGENT.md](INSTALL-AGENT.md):
там шаги для агента — что он делает сам, а что только после вашего «да» в чате.

**Шаг 1. Скачайте miksy в папку с проектами.** Пример — для `~/Projects`; своя папка — подставьте её в обе строки
команды. Рядом мастер положит вашу конфигурацию (`miksy-config`). Можно и в другое место — мастер всё равно спросит,
где ваши проекты (будет вторая машина — раскладывайте на обеих одинаково: «[Вторая машина](#вторая-машина)»).

macOS и Linux:

```
git clone -b stable https://github.com/wedolab/miksy.git ~/Projects/miksy
cd ~/Projects/miksy && ./install.sh
```

Windows (PowerShell):

```
git clone -b stable https://github.com/wedolab/miksy.git $HOME\Projects\miksy
cd $HOME\Projects\miksy; powershell -ExecutionPolicy Bypass -File .\install.ps1
```

`-b stable` — ветка git с последним выпуском: с неё miksy обновляется командой `miksy update`.

Или одной строкой — скрипт сам спросит, куда скачать miksy (по умолчанию `~/Projects/miksy`), и поставит последний
выпуск:

```
curl -fsSL https://raw.githubusercontent.com/wedolab/miksy/main/install.sh | bash      # macOS, Linux
irm https://raw.githubusercontent.com/wedolab/miksy/main/install.ps1 | iex             # Windows (PowerShell)
```

**Шаг 2. Ответьте на вопросы мастера** `miksy setup` — его запустит установщик (сначала проверит git и поставит Bun:
покажет команду и спросит). У каждого вопроса — короткое пояснение; любой, кроме первого, можно пропустить, а
повторный `miksy setup` продолжит с несделанного. **Есть свои правила** в `~/.claude/CLAUDE.md` и т. п.? На вопрос 9
ответьте «n» и перенесите их до записи («Свои правила» ниже).

1. **Конфигурация** — выбор цифрой (Enter — отмена). «1» — своя в git (с другой машины): дайте адрес, мастер скачает
   её рядом с движком. «2» — новая из примера; на «Сделать конфигурацию git-репо и записать первый коммит?» ответьте
   «y»: без git её не перенести на другую машину. В примере — общие правила для агентов, MCP-сервер context7
   (документация библиотек) и skill `miksy`, который объясняет агентам, как менять конфигурацию.
2. **Workspace и агенты.** Папка с проектами (Enter — предложенная), по желанию — ещё папки
   ([docs/roots.md](docs/roots.md)), и найденные агенты. Агентов мастер не ставит — только говорит, каких нет.
3. **Копия настроек агентов** — один раз, до первой записи: в `local/backups/before-miksy-<метка>/`.
4. **Программы для MCP-серверов** (`npx`, `uvx`, `docker`…) — чего не хватает: покажет команду и выполнит после «y».
5. **Команда `miksy`** — создаст её в `~/.bun/bin` и, если надо, добавит этот каталог в PATH. Новый PATH действует в
   новых окнах терминала: откройте новое окно, чтобы `miksy` нашлась.
6. **Ручные настройки агентов** — MCP-серверы и skills проектов, которые вы добавляли агентам сами: по каждому
   спросит, куда перенести его в конфигурацию (его получат все агенты); «0» — оставить у агента, «s» — пропустить
   остальные. Свои **правила** и домашние skills агентов мастер не переносит — как перенести, ниже.
7. **Секреты** — каких токенов не хватает и куда их вписать (`local/secrets.env`; путь мастер печатает). Заполните
   файл и нажмите Enter (или «s» — позже). Значения мастер не спрашивает и не показывает. Стартовой конфигурации
   секреты не нужны (context7 работает без токена).
8. **План** — что будет создано и обновлено (`v` — полный план).
9. **Запись** — «Записать настройки агентам сейчас? [y/N]»: для записи ответьте «y». О доверии проектам, где в репо
   есть хуки или свои MCP-серверы, спросит по каждому ([docs/trust.md](docs/trust.md)).
10. **Проверка** — итог `miksy doctor`. Перезапустите агента (шаг 3), откройте проект и спросите «Процитируй первую
   строку раздела „## MCP“ в твоих инструкциях и вызови context7 для „bun“». Ответ «MCP-серверы подключает miksy по
   слоям…» и найденная библиотека — всё работает. Со своей конфигурацией спросите о своём правиле и своём сервере.

Вопросы 7, 8 и 10 только ждут Enter. Где вопрос только создаёт своё (2, 3, 5), Enter значит «да» (`[Y/n]`); где
меняется что-то у агентов (4, 6, 9 и «сделать конфигурацию git-репо» в вопросе 1) — «нет» (`[y/N]`).

**Шаг 3. Перезапустите открытые сессии агентов** — настройки читаются при старте.

**Сначала посмотреть, потом записать.** Хотите до записи поправить стартовые правила или перенести свои — на
вопрос 9 ответьте «n», поправьте файлы в конфигурации (на Windows — `$HOME\Projects\miksy-config\layers\…`), затем
в новом окне терминала снова `miksy setup`: он продолжит с несделанного и дойдёт до записи.

**Свои правила**, которые вы писали агентам руками (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` и т. п.), остаются
только у того агента, где были. Перенесите их в `layers/global/instructions/<имя>.md` (для всех агентов), удалите
из файлов агентов (miksy пишет свой блок между `<!-- miksy:begin … -->` и `<!-- miksy:end -->`, ваш текст — вне
его), затем `miksy sync --global`. Пока не удалите, у этого агента правило будет дважды. Свои **домашние skills**
(`~/.claude/skills/<имя>/` и т. п.) так же: скопируйте папку в `layers/global/skills/<имя>/`, удалите у агента,
затем `miksy sync --global`.

**Вернуть всё как было** — [docs/uninstall.md](docs/uninstall.md): там же — как вернуть копию из вопроса мастера
«Копия настроек агентов».

**Без терминала** (команду запускает скрипт, CI или агент): `miksy setup --yes` — без вопросов, только безопасные
шаги ([docs/install.md](docs/install.md#без-вопросов-скрипты-ci-агенты)). Каждый вопрос мастера подробно — там же,
«[Вопросы мастера по порядку](docs/install.md#вопросы-мастера-по-порядку)».

### Вторая машина

- **Те же проекты и правила** — берите свою конфигурацию из git (вопрос 1 мастера, вариант 1) и разложите папки так
  же, как на первой машине (ниже). Для этого конфигурация первой машины должна лежать в удалённом **приватном** репо
  (GitHub, GitLab и т. п.): заведите его сами, затем в каталоге конфигурации `git remote add origin <адрес>` и
  `git push -u origin HEAD` (мастер подскажет). Его адрес вы и дадите мастеру на второй машине.
- **Другой набор** (личная машина вместо рабочей, у коллеги свой) — новая конфигурация из примера (вопрос 1, вариант
  2). Нужные правила переносятся копированием слоёв.

**Правку конфигурации на одной машине — на другую:** на первой закоммитьте и отправьте её (`git add -A`,
`git commit`, `git push` в каталоге конфигурации), на второй — `git pull` там же, затем `miksy sync --global` и
`miksy sync --all`.

**Раскладка папок** должна совпадать: проекты, организации, движок и конфигурация лежат относительно workspace так
же, как на первой машине. Было `~/Projects/miksy`, `~/Projects/miksy-config` и `~/Projects/Acme/app` — так же и
здесь (сама папка workspace может называться иначе), иначе слои применятся не к тем папкам. Есть в конфигурации слой
папки движка, а движок лежит не в ней — мастер предупредит; сам он ничего не переносит.

**macOS и Windows не различают регистр в именах:** `miksy` и `Miksy` — одна папка, и `mv miksy Miksy/miksy`
переносит папку «в саму себя». Меняйте регистр через временное имя:

```
mv miksy miksy.tmp && mkdir Miksy && mv miksy.tmp Miksy/miksy                    # macOS, Linux
Rename-Item miksy miksy.tmp; mkdir Miksy; Move-Item miksy.tmp Miksy\miksy        # Windows (PowerShell)
```

Перенесли движок или конфигурацию — запустите `miksy setup` снова (обновит команду `miksy`), затем `miksy doctor`:
учёт найдёт новое место сам («[Переименовали или перенесли каталог](#переименовали-или-перенесли-каталог)»).

## Повседневные задачи

Общее правило: поменяли конфигурацию — запустите `sync`. `miksy sync --global` — если меняли `layers/global/` или
`layers/env-*/` (домашние настройки агентов — действуют во всех каталогах); `miksy sync --all` — если меняли
`layers/tree/` (проекты). Сначала посмотреть план — `--dry-run`. После записи перезапустите сессии агентов.
Коммитить конфигурацию перед `sync` не нужно — только чтобы перенести правку на другую машину.

### Добавить или изменить правило

Правило — обычный markdown-файл в папке `instructions/` нужного слоя (внутри — просто текст, заголовок и разделители
не нужны):

| Для кого правило | Где действует | Куда положить | Затем |
|---|---|---|---|
| Все агенты везде (язык, стиль) | везде, и вне проектов | `layers/global/instructions/*.md` | `miksy sync --global` |
| Про ОС (shell, синтаксис команд) | везде на машинах с этой ОС | `layers/env-windows/instructions/*.md` (и `env-macos/`, `env-linux/`) | `miksy sync --global` |
| Все проекты | только в проектах папок с проектами | `layers/tree/instructions/*.md` | `miksy sync --all` |
| Организация или проект | только в её (его) проектах | `layers/tree/<Организация>[/<проект>]/instructions/*.md` | `miksy sync --all` |

Пути — от папки конфигурации (`miksy-config`). Не уверены, куда, — `layers/tree/instructions/`. Организация во
второй папке с проектами — под её веткой: `layers/tree/<ветка>/<Организация>/`
([docs/roots.md](docs/roots.md#правила-нескольких-корней)).

Нужных папок нет — создайте их сами (для `~/Projects/Acme` — `layers/tree/Acme/instructions/`); число в начале
имени (`20-style.md`) задаёт порядок. Проверить — `miksy explain <путь проекта>`. Каждое правило — в одно место:
«для всех агентов везде» действует и в проектах, повтор в `layers/tree/` агент получит дважды.

Проекты лежат прямо в папке с проектами, без папок организаций (`D:\Projects\app1`, `D:\Projects\app2`)? Для
правила нескольких из них создайте папку организации и перенесите репо в неё (`D:\Projects\Acme\app1` → слой
`layers/tree/Acme/`; историю сессий агентов miksy при этом не переносит) или, не трогая папки, привяжите слой
шаблоном в `map.yaml` — слой тогда лежит вне дерева, в `layers/acme/`:

```yaml
# map.yaml — для app1 и app2 слой из layers/acme/
layers:
  - { match: "{app1,app2}", use: acme }      # сами проекты
  - { match: "{app1,app2}/**", use: acme }   # и папки внутри них (если в них открывают агента)
```

### Подключить MCP-сервер

Сервер — файл `mcp/<имя>.yaml` в нужном слое. Секреты — **только ссылкой** `${ИМЯ}`, а значение — в
`local/secrets.env` этой машины (в git оно не попадёт):

```yaml
# layers/tree/Acme/mcp/gitlab.yaml — сервер, который запускается у вас (stdio)
name: gitlab
command: npx
args: [-y, "@zereight/mcp-gitlab"]
env:
  GITLAB_PERSONAL_ACCESS_TOKEN: ${ACME_GITLAB_TOKEN}
  GITLAB_API_URL: https://gitlab.acme.example/api/v4
```

```yaml
# layers/tree/Acme/mcp/tracker.yaml — удалённый сервер (HTTP)
name: tracker
url: https://tracker.acme.example/mcp
headers:
  Authorization: Bearer ${ACME_TRACKER_TOKEN}
agents: { antigravity: skip } # необязательно: этому агенту не подключать
```

```
# local/secrets.env
ACME_GITLAB_TOKEN=glpat-…
ACME_TRACKER_TOKEN=…
```

Затем `miksy sync --all` (сервер в `layers/global/` — `miksy sync --global`). Пути этой машины пишите через
`${HOME}`, `${WORKSPACE}` (основная папка с проектами) или свои переменные `vars` из `local/machine.yaml`
(например, `${PYTHON}`). Готовые примеры — `examples/extra/`.

**Значений секретов нет ни в одном конфиге агента**: `sync` кладёт каждый секрет в файл `local/secrets/<ИМЯ>`
(доступ только у вас), а серверу его передаёт скрипт-обёртка из `local/run/`. Сервер
без секрета `sync` пропускает с сообщением ([docs/troubleshooting.md](docs/troubleshooting.md#секреты-и-mcp-серверы)).
Файлы в `local/secrets/` руками не удаляйте (opencode без них не запустится): уберите секрет или сервер из слоя и
запустите `sync` — лишнее он удалит сам.

### Добавить свой skill

Папка `skills/<имя>/SKILL.md` в нужном слое, затем `miksy sync --global` или `--all`:

```markdown
---
name: miksy-contract-review
description: Разбор договора перед подписанием — риски, спорные пункты, правки. Используй, когда просят проверить договор, оферту или соглашение, найти подвохи, подготовить протокол разногласий, поработать как юрист.
---

Порядок работы…
```

Агент заранее видит только `name` и `description`, поэтому в описании пишите, **когда** его использовать, словами,
которыми вы ставите задачу («проверь договор», «как юрист»), с синонимами; одна-три фразы. Имя — с префиксом, чтобы
не совпасть с skills команды в репо (`miksy-`; свой — `skill_prefix: acme-` в `map.yaml`). Дошёл ли skill до агента —
`miksy explain <путь>`, раздел Skills.

### Добавить новый проект

Склонировали репо в папку с проектами — запустите `miksy sync` в его каталоге (или в подпапке); сам по себе miksy
не запускается. То же — `miksy sync <путь>`, а `miksy sync --all` обновит все проекты сразу (новые git-репо он
находит сам). Затем перезапустите сессию агента в этом репо. В самой папке с проектами, в папке без git и вне
workspace `sync` ничего не пишет, а подсказывает, что сделать. Есть в репо хуки или MCP-серверы команды — `sync`
спросит о доверии ([docs/trust.md](docs/trust.md)).

**Репо вне папки с проектами** (например, `~/Downloads/new-repo`) проектом не считается: перенесите его в папку с
проектами, затем `miksy sync` в нём. Если рядом лежат и другие ваши проекты (второй диск, облачная папка), эту папку
можно сделать ещё одной папкой с проектами — `sync` в репо подскажет команду `miksy root add "<папка>" --tree <имя>`
([docs/roots.md](docs/roots.md)). Сделаете так с `~/Downloads` — настройки получат все репо в ней. Домашний каталог,
корень диска (`E:\`) и сам репо для этого не годятся (на сам репо `root add` объяснит и спросит).

### Папка без git: заметки, выгрузки, группа проектов

Папка без git, где агента ещё не открывали (`~/Projects/Acme/MyTasks` — заметки, выгрузки), настроек не получит:
агент откроется там без ваших правил. Чтобы miksy писал туда, как в проект, отметьте её **целью** (в сообщениях
miksy — «цель без git», над проектами — «группа»):

```
miksy target ~/Projects/Acme/MyTasks      # без пути — текущий каталог
```

Команда допишет `target: true` в `layer.yaml` её слоя (`layers/tree/Acme/MyTasks/`) и предложит записать
настройки — те же, что получил бы проект на её месте. `miksy target <путь> --remove` снимает пометку и предлагает
убрать записанное (работает и без подключённого диска). Такие папки показывает `miksy projects`; папки без git, которым пометка пригодилась бы, подсказывают `miksy sync --all` и `miksy doctor`.

**Группа** — цель над проектами. Открываете агента в `~/Projects/Acme`, когда задача задевает несколько репо, —
отметьте её (`miksy target ~/Projects/Acme`), затем `miksy sync --all`. Claude читает файлы правил и в
**родительских** папках, поэтому проект ниже группы получает для Claude только **свою часть** слоёв, а `exclude`
для Claude делайте в слое группы. Остальные агенты получают полный набор в каждой цели.

### Настроить организацию или проект отдельно

Создайте в `layers/tree/` папку по тому же пути, что в workspace (`layers/tree/NewOrg/`,
`layers/tree/NewOrg/some-project/`), и положите туда `instructions/`, `mcp/`, `skills/` или `layer.yaml`
([что в нём бывает](docs/layers.md#что-лежит-в-слое)). Затем `miksy sync --all`.

### Добавить или убрать агента

Поставили нового агента — запустите `miksy setup` ещё раз: он предложит добавить его в `local/machine.yaml`. Затем
`miksy sync --global` и `miksy sync --all`.

Перестали пользоваться агентом — сначала уберите записанное ему: `miksy clean --all --agent <имя>` и
`miksy clean --global --agent <имя>`, потом удалите его из `agents` в `local/machine.yaml`. Убрали без `clean` —
`miksy doctor` перечислит, что осталось («Учёт агентов, которых нет в agents»), и даст команды, которые это уберут.

**Внимание:** `miksy update` и `miksy setup --yes` (в том числе в шагах отката) дописывают в `agents` всех агентов,
которые найдены на машине, — и убранного вами («✓ в local/machine.yaml добавлены агенты: …»). После них уберите его
из `agents` снова, до `sync`; мастер в терминале об этом спрашивает — ответьте «n».

### Подключить skills команды из репо проекта

Команда положила skills в репо, а ваш агент их не видит? miksy доставит их вашим агентам, если включить в слое:

```yaml
# layer.yaml
import_skills: auto     # до 30 на проект; all — без лимита; [имя1, имя2]; false — выключено
```

В стартовой конфигурации импорт выключен. Доставляется только **закоммиченное**. Что лежит в проекте и кто что
видит — `miksy skills <путь>`, `miksy skills --all`.

### Поручить изменения агенту

Правила, MCP и skills удобно добавлять, попросив агента: «подключи MCP sentry для всей организации Acme».
Глобальный skill **`miksy`** из стартовой конфигурации объясняет агентам, куда что класть. Добавил агент что-то
по-своему (`claude mcp add`, skill в папке проекта) — это получит только он; `miksy doctor` покажет такие добавки
(«Добавлено агентами в обход слоёв»), а перенести их в конфигурацию для всех агентов — одна команда:

```
miksy adopt <путь проекта> <имя> --to <уровень>   # из проекта
miksy adopt --global <имя> --to <уровень>         # из домашних настроек агента
miksy sync --all
```

`<уровень>` — `global`, `workspace` (все проекты) или путь в дереве (`Acme`, `Acme/mobile`). `adopt` выносит
секреты в `local/secrets.env` (в слое — ссылка), сначала показывает план (и что похоже на секрет, но не распознано)
и записывает после подтверждения (без терминала — только с `--yes`). Домашние skills агентов он не переносит —
скопируйте папку в `layers/global/skills/<имя>/` сами. Глобальный Codex (`--global … --agent codex`): исходная запись
переходит к miksy (с бэкапом) — при удалении miksy `clean` уберёт и её.

### Переименовали или перенесли каталог

**Проект, папку без git или конфигурацию** переименовывайте свободно (проект и папку — в пределах workspace,
конфигурация может лежать где угодно): следующий `sync` (или `clean`) сам найдёт новое место, перенесёт учёт, ключи
MCP и доверие и напечатает «Учёт miksy перенесён вслед за каталогами». Пометку `target: true` перенесите сами:
`miksy target <новый путь>`. Не нашёл — `miksy clean <прежний путь>` уберёт записанное, а новая папка получит
настройки как новый проект. Историю сессий, память и разрешения агентов (они хранятся по пути папки) miksy не
переносит.

**Папку с проектами (корень workspace)** — поправьте её путь в `local/machine.yaml` (ключ `workspace`). Внутри неё
есть вложенная папка с проектами со своей веткой — поправьте и её `path:`, **до** `sync`: иначе её проекты станут
проектами основной, и `--force` из строки конфликта заменит правила её ветки правилами основной. Затем
`miksy sync --all` — учёт обычно переезжает сам. Не переехал — `miksy doctor` покажет прежние пути в «Учёт целей вне
workspace без каталога»: для каждого — `miksy clean "<прежний путь проекта>"`, на «забыть?» — «да» (без терминала —
`--forget`); подсказку «Если диск найдётся…» пропустите. Свои изменённые файлы `sync` покажет конфликтом —
`miksy sync "<проект>" --force`. Claude на новом месте может один раз спросить о доверии
([docs/trust.md](docs/trust.md)).

Не через `miksy root remove`: его вопрос «забыть?» — для отключённого диска (при переименовании ответ — «нет»). И не
через `miksy root add` нового пути: без правки `local/machine.yaml` прежний путь останется недоступным корнем.

## Проверить, всё ли в порядке

```
miksy doctor
```

Покажет, что не записано, что устарело (в том числе skills команды после `git pull`), что правили вручную, каких
секретов и программ не хватает, где нужно ваше решение о доверии. Ничего не меняет. Запускайте после правок
конфигурации, после `git pull` в проектах и время от времени.

В «Справочно» (не ошибки) — папки без git рядом с проектами и **окружение**: несколько установок одной программы,
переменные, которые уводят настройки агента в другой каталог (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME`,
`OPENCODE_CONFIG`, `GEMINI_CLI_HOME` и т. п.), конфигурация не рядом с движком (`MIKSY_CONFIG`, `~/.miksy`). Что
значит сообщение и что делать — [docs/troubleshooting.md](docs/troubleshooting.md).

## Обновление miksy

```
miksy --version          # какая версия стоит
miksy update --check     # есть ли новая (ничего не меняет и не скачивает)
miksy update             # что изменилось — и после «y» обновить
```

Номер нынешней версии перед обновлением запишите — он понадобится, если захотите откатиться. `miksy update`
показывает, что изменилось ([CHANGELOG.md](CHANGELOG.md)), обновляет движок и спрашивает, записать ли настройки
агентам; затем перезапустите сессии агентов. Убирали агента из `agents` — ответьте «n»
(«[Добавить или убрать агента](#добавить-или-убрать-агента)»). Подробно и откат — [docs/update.md](docs/update.md).

## Справочник команд

Кратко — `miksy help`. Что запускать после изменений:

| Что изменилось | Что запустить |
|---|---|
| `layers/global/`, `layers/env-<ОС>/` — домашние настройки агентов | `miksy sync --global` |
| `layers/tree/…` — настройки проектов по их месту | `miksy sync --all` или `miksy sync <путь>` (один проект) |
| `map.yaml`: `global` — `--global`; привязки `layers` — `--all` | соответственно |
| Новый проект, новая папка без git (`miksy target`) | `miksy sync` в его каталоге или `miksy sync <путь>` |
| Новая папка с проектами (`miksy root add` или `workspace` в `local/machine.yaml`) | `miksy sync --all` (`root add` предложит сам) |
| Секреты (`local/secrets.env`), новый агент, первая установка | оба: `miksy sync --global` и `miksy sync --all` |
| Вышла новая версия miksy | `miksy update` (он сам предложит `sync`) |

Не уверены — `miksy doctor`: он покажет, что устарело и какой командой это записать.

| Команда | Что делает | Что пишет |
|---|---|---|
| `setup [--yes [--backup]] [--force]` | Мастер установки ([шаги](#установка)); `--yes` — без вопросов, только безопасная часть; `--backup` — и копия настроек агентов; `--force` — заново спросить workspace и агентов | конфигурация, `local/`, команда `miksy`; после «y» на своих вопросах — копия настроек агентов, PATH, программы для MCP-серверов, перенос ручных настроек в слои, настройки агентов |
| `sync [<путь>] \| --global \| --all [--agent <id>]` | Записать настройки агентам: без пути — проекту или цели текущего каталога; вне целей — подсказка вместо записи; явный путь к папке без git, которая не цель, — запись с предупреждением, но `sync --all` её не обновит | да |
| `sync … --dry-run` | Только показать план | нет |
| `sync … --force` | Заменить и правленные вручную или чужие файлы (с бэкапом и оригиналом) | да |
| `sync --all … --yes` | Не спрашивать подтверждение | да |
| `sync [<путь> \| --global] --out <каталог> [--agent <id>]` | Сложить настройки в отдельный каталог и сравнить с нынешними (секреты скрыты); каталог — новый, пустой или созданный прежним `--out` | только `<каталог>` |
| `clean <путь> \| --global \| --all [--agent <id>] [--dry-run] [--force] [--forget]` | Убрать всё, что miksy записал (`--force` — и правленое вручную); `--forget` — забыть записанное на недоступный диск ([docs/roots.md](docs/roots.md#корень-недоступен)) | да |
| `doctor [--agent <id>] [--verbose]` | Что разошлось с конфигурацией; код 1 при проблемах | нет |
| `explain [<путь>] \| --global` | Какие слои, правила, MCP и skills получит папка и откуда | нет |
| `projects [--agent <id>]` | Какие папки miksy считает проектами и целями (и корни, если их несколько) | нет |
| `root [add [<путь>] [--tree <ветка>] [--yes] \| remove <путь> [--forget]] [--dry-run]` | Папки с проектами (корни): без аргументов — список; `add` — добавить папку (без пути — текущую), `--tree` — её ветка в дереве слоёв (в терминале спросит, Enter — имя папки без `[ ] { } * ?` и `!` в начале), затем предложит `sync --all`; папку, которая сама проект (git-репо, проект workspace, папка внутри них), `add` объясняет и спрашивает, без терминала добавляет только с `--yes`; `remove` — убрать дополнительный корень (основной — нельзя), записанное в его проекты — `clean` с вашего согласия; корень недоступен — спросит, забыть ли записанное туда (`--forget` — без вопроса). `--dry-run` говорит, что будет в этом же режиме (вопрос и ответ по умолчанию, отказ без `--yes`) | `local/machine.yaml` (только `workspace`); после «да» — как `sync --all`/`clean` |
| `target [<путь>] [--remove] [--dry-run]` | Сделать папку без git целью (без пути — текущую); `--remove` — снять пометку | `layer.yaml` слоя; после «да» — как `sync`/`clean` |
| `trust [<путь>] [--agent <id>] [--confirm \| --deny]` | Решение о доверии проектам ([docs/trust.md](docs/trust.md)); без терминала — только `--confirm` (после явного «да» пользователя) или `--deny` | `local/trust.json`, доверие агентов |
| `adopt <путь> \| --global <имя> --to <уровень> [--agent <id>] [--dry-run] [--yes]` | Перенести MCP-сервер или skill, добавленный агенту напрямую, в конфигурацию | слой, `local/secrets.env` |
| `skills <путь> \| --all` | Skills команды в репо: где лежат, ошибки, кто из агентов видит | нет |
| `update [--yes] [--main]` | Обновить движок до последнего выпуска ([docs/update.md](docs/update.md)); без терминала — только с `--yes`, `sync` не пишет | движок (git); после «y» — как `sync` |
| `update --check` | Есть ли новая версия (ничего не меняет) | нет |
| `version`, `--version` | Версия движка | нет |

Без `--agent` — агенты из `agents` в `local/machine.yaml` (не задан — все четыре); `<id>` — `claude`, `codex`,
`opencode`, `antigravity` (прежнее `gemini` тоже понимается). Флаги: `--флаг <значение>` или `--флаг=<значение>`;
ошибка в аргументах — код 2, ничего не выполняется; код 3 — были конфликты (эти места не изменены).
