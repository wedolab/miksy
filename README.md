# Miksy

Один источник правил, skills и MCP-серверов для нескольких AI-агентов:
**Claude Code, Codex, opencode, Antigravity**.

Вместо того чтобы настраивать каждого агента руками в каждом проекте, вы описываете всё
один раз — по слоям, — а miksy раскладывает это в конфиги всех агентов во всех
проектах: правила — в их файлы инструкций, MCP-серверы — в их конфиги, skills — в их
каталоги. Miksy не работает в фоне: после изменения слоёв запускается `miksy sync`.

**Miksy — не агент и не «agent harness»** (так иногда называют саму обвязку агента: цикл,
инструменты, контекст). Он ничего не выполняет вместо агентов и не стоит между вами и ними:
это генератор конфигурации для уже установленных агентов. Имя — от того, что он раскладывает:
**M**CP, **I**nstructions, **K**eys (секреты), **S**kills.

Этот репо — **движок**. Ваши слои, секреты и настройки машин живут в отдельном
**личном** каталоге конфигурации (обычно `miksy-config` рядом с движком, лучше — в
своём приватном git-репо). Движком можно делиться: ваших данных в нём нет.

> Устройство и контракт адаптеров — [DESIGN.md](DESIGN.md). Что умеет каждый агент и как
> это проверено — `adapters/<агент>/CAPABILITIES.md`. Этот файл — как пользоваться.

## С чем работает miksy

**Агенты.** Четыре: **Claude Code**, **Codex**, **opencode** и **Antigravity**. Ставить
всех не нужно — miksy пишет настройки только тем, что у вас установлены. Других агентов (Cursor,
GitHub Copilot, Windsurf и т. п.) miksy не поддерживает и их настройки не трогает. В конфигурации и командах
агенты называются `claude`, `codex`, `opencode`, `antigravity` (прежнее имя Antigravity — `gemini` — тоже
работает). opencode — **версии 2.x**: miksy пишет его настройки в формате второй версии.

**Где запускать агентов — как вам удобно.** miksy ничего не требует, кроме git и Bun: он только
раскладывает файлы настроек, а агент читает их сам, где бы ни работал. Проверено:
- в терминале (CLI) — все четыре агента;
- в редакторе Zed через ACP (протокол подключения агентов к редакторам) — Claude Code, Codex и
  opencode;
- Antigravity — в его IDE и CLI (`agy`), в том числе `agy` в терминале Zed. Через ACP в Zed Antigravity
  настройки от miksy пока не получает: адаптер не читает ни плагин проекта, ни глобальные правила.

Другие редакторы, которые подключают агентов через ACP или своими расширениями (например,
Claude Code в VS Code или JetBrains), читают те же файлы настроек — скорее всего, всё работает, но
это не проверялось.

**ОС.** Windows, macOS и Linux (Ubuntu 24.04) — проверено на настоящих машинах; все три проходят
автоматические тесты.

Версии агентов, на которых всё проверено, и что именно умеет каждый — в
`adapters/<агент>/CAPABILITIES.md`.

## Основные понятия

### Слои и дерево

Настройки лежат в каталоге конфигурации, по слоям:

```
miksy-config/
├── map.yaml                 глобальные слои, особые привязки, префикс своих skills, программы машины
├── layers/
│   ├── global/              ваши правила для всех агентов везде → ~ (домашний каталог)
│   ├── env-windows/, env-macos/, env-linux/   правила про ОС (shell, синтаксис)
│   └── tree/                → все проекты workspace
│       ├── instructions/    правила всех проектов
│       ├── mcp/context7.yaml
│       ├── Acme/            → всё внутри ~/Projects/Acme
│       │   ├── mobile/      → всё внутри ~/Projects/Acme/mobile
│       │   └── billing-api/ → только проект ~/Projects/Acme/billing-api
│       └── Personal/        → всё внутри ~/Projects/Personal
├── local.example/README.md  заметка о подготовке машины: что miksy не настраивает сам (профили облачных CLI и т. п.)
└── local/                   только эта машина, не в git:
    ├── machine.yaml         workspace, vars (пути к программам), agents (агенты машины), trust
    ├── secrets.env          значения секретов: ИМЯ=значение (dotenv)
    ├── secrets/, run/       файлы секретов и обёртки для агентов (создаёт sync)
    ├── state/manifest.json  учёт
    ├── trust.json           ваши решения о доверии
    └── backups/             бэкапы запусков и originals/
```

`layers/tree/` **повторяет workspace** (каталог с вашими проектами). Проект получает все
слои по своему пути сверху вниз: нижний дополняет и перекрывает верхний. Нет каталога
в дереве — нет слоя. Имена сравниваются без учёта регистра. Проекты лежат в нескольких не связанных
местах (второй диск, папка облачного хранилища) — [несколько корней](#несколько-корней-workspace).

Внутри каталога слоя — его содержимое (все части необязательны):

| Что | Пример |
|---|---|
| `instructions/*.md` | правила — обычный markdown; склеиваются по порядку слоёв и по имени файла |
| `mcp/<имя>.yaml` | MCP-сервер (ниже) |
| `skills/<имя>/SKILL.md` | skill |
| `layer.yaml` | `description`, `exclude`, `import_skills`, `trust`, `target` — по разделам ниже |

Эти имена зарезервированы — так нельзя назвать организацию или проект (как и `hooks/`,
`policies/`: их miksy не читает).

Убрать то, что пришло сверху, — в `layer.yaml` нижнего слоя:

```yaml
exclude: [mcp.linear, skill.deploy, instructions.20-style.md]
```

Слой не по пути, а по шаблону — особая привязка в `map.yaml`:
`layers: [{ match: "*/infra-*", use: infra }]` — слой `layers/infra/` для всех проектов,
чьё место в дереве (путь от корня workspace; у других корней — вместе с их `tree`) совпало с
шаблоном, после слоёв дерева.

`miksy explain <путь>` показывает, что получит проект и из какого слоя (без пути — текущий
каталог; каталог вне workspace — только глобальные настройки; `miksy explain --global` — домашние
настройки агентов).

### Куда miksy записывает настройки

Цель — куда miksy записывает конфиги: домашний каталог агентов (`--global`), каждый
**проект** (git-репо в workspace) и **цели без git** (каталоги с пометкой `target: true`,
[ниже](#цели-без-git)). В проект miksy пишет только
файлы, которые git не отслеживает, и скрывает их через `.git/info/exclude` — в репо
проектов ничего не попадает, а файлы команды (закоммиченные) он не трогает даже с
`--force`.

| Агент | Глобально | В проекте (вне git) |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md`, MCP в `~/.claude.json`, `~/.claude/skills/` | `CLAUDE.local.md`, `.claude/skills/`, MCP проекта в `~/.claude.json` |
| Codex | `~/.codex/AGENTS.md`, MCP в `~/.codex/config.toml`, `~/.agents/skills/` | `.codex/config.toml` (правила и MCP), `.agents/skills/` (или `.codex/skills/`) |
| opencode | `~/.config/opencode/AGENTS.md`, MCP в `opencode.json(c)`, `~/.config/opencode/skills/` | `opencode.json`, `.opencode/miksy.md`, `.opencode/skills/` |
| Antigravity | `~/.gemini/GEMINI.md`, MCP в `mcp_config.json` (CLI и IDE), `~/.gemini/config/skills/` | плагин `.agents/plugins/miksy/` (правила, skills, MCP) |

Здесь основное; полностью (запасные пути, скрипты секретов в `local/run/`) — в
`adapters/<агент>/CAPABILITIES.md`.

В общих файлах miksy меняет только своё: в файлах инструкций — блок между
`<!-- miksy:begin … -->` и `<!-- miksy:end -->` (ваш текст вокруг сохраняется), в общих
конфигах агентов (`~/.claude.json`, `~/.codex/config.toml`, `opencode.json`,
`mcp_config.json`) — только свои ключи. Сгенерированное не правьте руками — правка внутри
блока или своего файла станет конфликтом; меняйте слои.

### Цели без git

Настройки получают git-репо и каталоги, где агент уже работал. Обычный каталог без git
(`~/Projects/Acme/MyTasks` — рабочие заметки, выгрузки) настроек не получит: агент откроется там
без ваших правил и MCP. Чтобы miksy писал туда, как в проект, сделайте каталог **целью без
git**:

```
miksy target ~/Projects/Acme/MyTasks      # без пути — текущий каталог
```

Команда добавит в `layer.yaml` его слоя (`layers/tree/Acme/MyTasks/`; уже есть — допишет
строку, остальное не тронет) пометку

```yaml
target: true
```

и предложит сразу записать настройки (`sync` этого каталога). Цель получает слои от
workspace до своего уровня (`tree/` + `tree/Acme/` + `tree/Acme/MyTasks/`) — всё, что и
проект: правила, MCP, skills, доверие. `miksy target <путь> --remove` снимает пометку и
предлагает убрать записанное. `miksy projects` показывает такие каталоги с пометкой.
`sync --all` и `doctor` подсказывают каталоги без git рядом с проектами — их легко не
заметить.

Частный случай — **группа**: цель над проектами. Если вы открываете агента в `~/Projects/Acme`,
когда задача задевает несколько репо, пометьте `~/Projects/Acme` (`miksy target ~/Projects/Acme`), затем
`miksy sync --all`. Claude читает `CLAUDE.md`/`CLAUDE.local.md` и во всех **родительских**
каталогах, поэтому проект ниже группы получает для Claude только **свой отрезок** слоёв —
остальное Claude возьмёт из файла группы сам. По той же причине `exclude` для Claude делайте
в слое группы. Остальные агенты получают полный набор в каждой цели. Как считается отрезок
и когда пометка не действует — [DESIGN §6a](DESIGN.md#6a-цели-без-git-target-true).

### Несколько корней workspace

Обычно все проекты лежат в одном каталоге — workspace (`workspace: ~/Projects` в `local/machine.yaml`). Если
они разбросаны по нескольким не связанным местам — второй диск, папка облачного хранилища, — перечислите эти
места списком. Каждое место — **корень** workspace; первый — основной.

```yaml
# local/machine.yaml
workspace:
  - D:/Projects                             # основной корень — в корне дерева слоёв (layers/tree/)
  - { path: "E:/Clients", tree: Clients }   # ещё корень — его ветка дерева: layers/tree/Clients/
```

Дерево слоёв одно на все корни: проект `E:/Clients/Acme/site` получает слои `layers/tree/` (общие для всех
проектов), `layers/tree/Clients/` и `layers/tree/Clients/Acme/`, проект `D:/Projects/Org/app` — `layers/tree/`,
`layers/tree/Org/`. Конфигурация от машины не зависит: на другой машине те же папки могут лежать в других
местах — там в её `machine.yaml` свои пути с теми же `tree`.

Добавить корень — `miksy root add <путь> --tree <ветка>` (без пути — текущий каталог; в терминале ветку
спросит, по умолчанию — имя папки): команда допишет его в `workspace`, остальное в `machine.yaml` не тронет, и
предложит `miksy sync --all`. Убрать — `miksy root remove <путь>`: записанное miksy в проекты этого корня она
уберёт (`clean`) только с вашего согласия. `miksy root` — список корней. Мастер (`miksy setup`) после основного
корня спрашивает «Есть ещё папки с проектами?» (путь можно вставить в кавычках — как его копирует Проводник);
папку, которая сама проект (git-репо), он, как и `root add`, объясняет и берёт корнем только после вашего «да».

Сам корень — не цель: настройки получают проекты в нём (git-репо) и каталоги с пометкой `target: true`.
Папку без git сделайте целью: `miksy target E:/Clients/Acme` — пометка ляжет в
`layers/tree/Clients/Acme/layer.yaml`.

**Папки облачных хранилищ** (Google Drive, Яндекс Диск, OneDrive, Dropbox, iCloud Drive и т. п.): всё, что
miksy в них запишет (`CLAUDE.local.md`, `.claude/`, `.agents/`, `.codex/`, `opencode.json` — правила, список
MCP-серверов, skills), синхронизируется в облако и на другие ваши устройства, а если папка расшарена — уйдёт
всем, у кого к ней доступ. Значений секретов в этих файлах нет (они в `local/` вашей машины), но правила и
названия серверов увидят. Подключайте такую папку, только если это вас устраивает.

Правила:

- **У каждого корня, кроме основного, ветка (`tree`) обязательна и своя.** Иначе слои одной папки молча
  доставались бы папке с тем же именем в другом корне (папка `Acme` в основном корне получила бы MCP-серверы
  с токенами из `layers/tree/Acme/`, задуманные для клиента). Без `tree` или с занятой веткой `machine.yaml`
  не загрузится — ошибка скажет, что поправить. У основного корня `tree` можно не указывать (корень дерева);
  если указан — он тоже должен быть своим.
- **Общее для нескольких корней — явно.** Для всех проектов всех корней — `layers/tree/instructions/` (и
  остальное в корне дерева) или глобальный слой (`layers/global/`, действует везде). Для отдельных папок в
  разных корнях — именованный слой в `map.yaml`:

  ```yaml
  # map.yaml — слой layers/acme/ для Acme в обоих корнях (Clients и Archive)
  layers:
    - { match: "{Clients,Archive}/Acme/**", use: acme }
  ```

- **`${WORKSPACE}`** в определениях MCP — всегда основной корень, у проектов любого корня и в глобальных
  настройках. Путь в другой корень — своей переменной машины в `vars`:

  ```yaml
  # local/machine.yaml (на каждой машине — свой путь)
  vars:
    CLIENTS: "E:/Clients"
  # в слое: args: ["${CLIENTS}/tools/report.py"]
  ```

  На машине, где переменная не задана, сервер пропускается с сообщением. `miksy adopt` сворачивает в
  `${WORKSPACE}` только пути основного корня; путь в другой корень оставляет как есть и подсказывает
  завести переменную.

Особые случаи:

- **Вложенный корень** (корень внутри другого корня) — можно: папка относится к самому глубокому корню, обход
  внешнего её пропускает. Пример: одна и та же облачная папка на Mac лежит отдельно
  (`~/Library/CloudStorage/…/Clients`), а на Windows клиент облака положил её внутрь основного корня
  (`D:/Projects/Cloud/Clients`). На Windows она — вложенный корень с той же веткой `tree: Clients`, и
  конфигурация общая для обеих машин. `explain` и `doctor` показывают такой корень справочно. Предупреждение
  — только если вложенный корень лежит внутри git-проекта или цели-группы внешнего корня. Оговорка: пока это
  надёжно работает только для Claude — см. «[Одна облачная папка проекта на двух машинах](#несколько-корней-workspace)» ниже.
- **Одна облачная папка проекта на двух машинах** (miksy на обеих) — что работает сейчас. **Claude** — да, если
  конфигурация слоёв одна: в папке проекта только `CLAUDE.local.md` и skills, одинаковые на обеих машинах (MCP
  Claude — в домашнем `~/.claude.json`). Оговорка — командный `.mcp.json`: одобрение его серверов miksy пишет в
  `.claude/settings.local.json` проекта, и если на одной машине вы ответили «да», а на другой нет, машины будут
  по очереди менять строку этого файла в `.git/info/exclude`, и git второй машины будет его показывать. Ещё:
  совпадающие файлы miksy вторая машина берёт себе в учёт, поэтому `clean` (или `root remove` с согласием убрать)
  на одной машине убирает правила Claude и у другой — до её следующего `sync`. **Codex, opencode, Antigravity** — нет: их файлы в проекте
  (`.codex/config.toml`, `opencode.json`, плагин Antigravity) содержат пути своей машины, и у второй машины
  будет конфликт «файл miksy, которого нет в учёте, отличается». `--force` его не решает, а перетягивает файл
  между машинами: после `--force` на одной другая видит «изменён вручную». Если у машин разные skills или разный
  вывод, git может показывать файлы другой машины (у каждой машины своя строка в `.git/info/exclude`). Доработка —
  в следующих выпусках; пока для таких проектов включайте эти агенты на одной машине.
- **Ветка внутри чужого места** — `tree: Clients/Sub`, когда `Clients` уже ветка другого корня, или
  `tree: Org/Sub`, когда в основном корне есть папка `Org`. Проекты такого корня получат и всё, что задано для
  `Clients` (или `Org`): правила, MCP-серверы, skills. Если так и задумано — ничего делать не нужно; если нет —
  возьмите ветку вне этого места (например, `tree: Clients-Sub`), а общее задайте явно слоем в `map.yaml`.
  `root add` и `doctor` подсказывают это и перечисляют, что именно унаследуется; ошибкой это не считается.
- **Один каталог дважды** — ошибка с подсказкой: оставьте одну запись. «Один каталог» — это и тот же путь в
  другом написании (`D:/Projects` и `d:\Projects\`), и ссылка (симлинк, junction) на каталог, уже указанный
  корнем.
- **Совпадение ветки с папкой другого корня** — предупреждение (`doctor` — проблема, `sync`, `projects`,
  `root add`): ветка корня `tree: Clients`, а в основном корне есть (или появилась) папка `Clients` — слои
  `layers/tree/Clients/` получат обе. Переименуйте ветку или папку; общее — явно, как выше. Вложенный корень
  на своём же месте (`D:/Projects/Clients` с `tree: Clients`) — не совпадение.
- **Корень недоступен** — нет его папки, нет диска (не подключён, облачное хранилище не запущено) или ссылка
  ведёт в никуда: команды работают, `projects`, `sync --all` и `doctor` пропускают корень с предупреждением,
  записанное туда не трогается. Так же считается **пустая папка корня, если miksy уже писал в его проекты**:
  на Linux и macOS это обычно точка монтирования без диска (`/mnt/data`). Корень-ссылку miksy узнаёт по пути
  назначения, запомненному при последней записи.
- **Убрать записанное в проекты недоступного корня** — `miksy clean "<путь проекта>"`. miksy уберёт то, до
  чего дотянется (MCP-серверы проекта в настройках агентов, доверие, свои скрипты), а записи о файлах на
  недоступном диске оставит: по ним он узнает свои файлы, когда диск вернётся, — повторите тогда `clean`.
  Если данных больше нет (диск потерян, папку удалили), скажите это: в терминале miksy спросит «Забыть
  записанное туда?» (по умолчанию — нет), без терминала — флаг `--forget`. Пустую точку монтирования, которую
  вы очистили сами, так же убирают из учёта: `clean … --forget`.
- **Убрать сам недоступный корень** — `miksy root remove <путь>` спросит то же: забыть записанное в его
  проекты? «Нет» (по умолчанию) — корень убирается из списка, а записанное и учёт остаются: уберите их потом
  `miksy clean "<путь проекта>"`, когда диск вернётся. Корень, который лежит внутри другого корня, без
  «забыть» не убирается: его папки стали бы обычными папками внешнего корня, и miksy уже не отличил бы
  неподключённый диск от удалённых данных. Посмотреть заранее — `--dry-run` (можно с `--forget`): miksy скажет,
  почему корень недоступен, будет ли вопрос и сколько файлов забудется или останется в учёте.
- **Диск нашёлся после «забыть»** — учёта этих файлов у miksy больше нет, но свои он узнаёт сам. После
  «забыть» miksy помнит о проекте только одно: что его забыли (и ставил ли он доверие Claude этому проекту), —
  какие там были файлы, уже не помнит. Если
  папка проекта всё ещё в корне workspace — `miksy sync "<путь проекта>"`. Если вы убирали корень
  (`root remove` с «забыть»), сначала верните его: `miksy root add "<путь корня>" --tree <ветка>`, затем
  `miksy sync --all` (так же — перед откатом на 0.1.x: шаг 0 «[Откатиться на прежнюю версию](#обновление-miksy)»).
  Готовую команду с путём и веткой miksy печатает после `root remove`; после
  `miksy clean "<путь проекта>" --forget` проекта, чей корень уже убран, подсказка — шаблон: какой корень был у
  проекта и его ветку miksy к тому времени не помнит — подставьте их сами.
  Файлы, которые совпадают с тем, что miksy записал бы сейчас, `sync` берёт обратно сам — в выводе строка
  «взять под учёт — файл miksy, которого не было в учёте»; блок инструкций в `CLAUDE.local.md` и подобных — так
  же. Изменившиеся с тех пор (например, правила в слоях поменялись) `sync` покажет конфликтом —
  `miksy sync "<путь проекта>" --force` перезапишет их (прежние — в бэкап). Файлы и блоки miksy, которые он
  больше не пишет (правила убрали из слоёв, пока диска не было; в проекте появился вложенный репо), первый
  `sync` (или `clean`) после возвращения диска убирает сам, с бэкапом — строка «удалить … (файл miksy, которого не
  было в учёте, — больше не нужен)»; у блока инструкций убирается только блок, ваш текст вне блока остаётся.
  Так — только в проекте, который на этой машине забыли. В остальных проектах файлы miksy, которых нет в учёте
  этой машины, не трогаются: если одна облачная папка проекта открыта на двух машинах, у каждой свой учёт, и
  файл, который записал miksy другой машины, выглядит так же, — машина, которая его не пишет, его не удалит
  (совпадающий она берёт себе, отличающийся показывает конфликтом; что ещё ограничено в облачной папке на двух
  машинах — «[Одна облачная папка проекта на двух машинах](#несколько-корней-workspace)» выше).
  Так — у файлов, строка которых есть в блоке
  miksy в `.git/info/exclude` (`CLAUDE.local.md`, `.codex/config.toml`, `.opencode/miksy.md`). У файлов плагина
  Antigravity (`.agents/plugins/miksy/`) своей строки нет — весь каталог скрыт одной строкой: ненужные файлы
  плагина (правила, `mcp_config.json`) после `sync` остаются, и Antigravity их читает; после `clean` git их
  покажет — удалите их вручную. Доверие Claude `sync` ставит снова без вопроса, если раньше его ставил miksy,
  вы отвечали «да» на его вопрос или в слое `trust: true` (и команда не добавила новых исполняемых настроек);
  ваши ответы в окне Claude («да, больше не спрашивать») остаются вашими. Одобрения серверов командного
  `.mcp.json`, которые ставил miksy, `sync` берёт обратно, если одобрил бы их и сейчас (`trust: true` в слое или
  ваше «да»). Одобрения тех же серверов, которые
  вы дали сами в окне Claude, miksy от своих не отличит: они тоже станут его, и `clean` их снимет (Claude спросит
  снова). Одобрения серверов, которые miksy сейчас не одобрил бы, — ваши, он их не трогает. Если файлы miksy
  больше не нужны — после `sync` уберите их: `miksy clean "<путь проекта>"` (или `miksy root remove` корня с
  согласием убрать).
  **Копии ваших прежних файлов**, которые miksy когда-то заменил (`--force`), после «забыть» сами на место не
  вернутся: они лежат в `local/backups/originals/` (сообщение «забыто» говорит, сколько их), а `clean` удалит
  файл miksy на их месте. Нужное верните из копии вручную.
  Свой файл miksy узнаёт только по своим уликам: шапка «Сгенерировано miksy» в начале файла, его блок
  инструкций, его `opencode.json`; файл без метки (skill, `plugin.json`) — если он ровно такой, какой miksy
  записал бы сейчас, и его уже скрывает от git строка miksy в `.git/info/exclude` проекта. Файл, который вы
  положили сами, своим не станет, даже если совпадает с выводом miksy: он сохраняется оригиналом, и `clean`
  его вернёт. Файл с шапкой miksy, который miksy больше не пишет, он убирает, только если строка именно этого
  файла есть в его блоке `.git/info/exclude` (такой файл в другом проекте — скорее всего, ваша копия: его miksy
  не трогает). Не узнает miksy свой файл без метки, который с тех пор поменялся или пропал из слоёв (git его
  увидит; в каталоге плагина Antigravity — после `clean`), и файлы без метки в цели без git (`target: true` у
  папки без репо — там нет `.git/info/exclude`): такие файлы уберите вручную.
- **`target: true`** действует по месту в дереве: пометка `layers/tree/Clients/Acme/layer.yaml` делает
  целью `E:/Clients/Acme`. Группы (цели над проектами) считаются в пределах своего корня.
- **`doctor`** ищет «лишние» ветки дерева (слой есть, папки нет — опечатка?) только там, куда смонтированы
  корни этой машины; ветки других машин — справочно. Ветка верхнего уровня (`layers/tree/Clients`), похожая на
  папку основного корня (`Clients-old`), — тоже справочно: это может быть и опечатка, и ветка корня другой
  машины; `doctor` называет оба варианта.

### MCP-серверы и секреты

Сервер — файл `mcp/<имя>.yaml` в нужном слое. Секреты — **только ссылкой** `${ИМЯ}`,
значение — в `local/secrets.env` этой машины:

```yaml
# layers/tree/Acme/mcp/gitlab.yaml — локальный (stdio) сервер
name: gitlab
command: npx
args: [-y, "@zereight/mcp-gitlab"]
env:
  GITLAB_PERSONAL_ACCESS_TOKEN: ${ACME_GITLAB_TOKEN}
  GITLAB_API_URL: https://gitlab.acme.example/api/v4
```

```yaml
# layers/tree/Acme/mcp/tracker.yaml — удалённый (HTTP) сервер
name: tracker
url: https://tracker.acme.example/mcp
headers:
  Authorization: Bearer ${ACME_TRACKER_TOKEN}
agents: { antigravity: skip } # необязательно: не подключать этому агенту
```

```
# local/secrets.env
ACME_GITLAB_TOKEN=glpat-…
ACME_TRACKER_TOKEN=…
```

Пути машины — через `${HOME}`, `${WORKSPACE}` (основной корень workspace) или переменные `vars` из
`local/machine.yaml` (например, `${PYTHON}`). Готовые примеры — `examples/extra/`.

**Значений секретов нет ни в одном конфиге агента** — ни в проекте, ни дома. `sync`
кладёт каждый используемый секрет в файл `local/secrets/<ИМЯ>` (доступ только у вас), а в
конфиг агента записывает путь к сгенерированному скрипту в `local/run/…` — обёртке сервера,
helper-у заголовков или мосту MCP stdio ↔ HTTP; способ miksy выбирает сам по агенту и типу
сервера ([DESIGN §8.6](DESIGN.md#86-секреты-обёртки-helper-ы-мост)). Сервер, секрет
которого не доставить, `sync` пропускает с сообщением (разбор — в
[таблице ошибок](#если-что-то-пошло-не-так)). Файлы в `local/secrets/` не удаляйте руками
(opencode без них не запустится): уберите секрет или сервер из слоя и выполните `sync` —
лишние он удалит сам.

### Доверие проектов и одобрение `.mcp.json`

Claude и Codex применяют настройки проекта (хуки, разрешения, серверы `.mcp.json`,
проектный конфиг Codex) только в **доверенном** проекте. Доверие спрашивает CLI агента;
Claude в редакторе (например, в Zed через ACP) не спрашивает и без доверия этих настроек не
применит (Codex там проектный конфиг читает и так). Поэтому `sync` по умолчанию сам ставит доверие Claude и Codex там, куда
доставил этому агенту конфигурацию; своё снимает, когда основание пропало, ваше не трогает.

Исключение — **исполняемые настройки не от miksy** (хуки, разрешения, `.mcp.json`, чужой
`.codex/config.toml`): с доверием агент выполнит их без вопроса, поэтому решаете вы. `sync` в
терминале в конце покажет, что будет выполняться, и спросит `[y/N]`; то же — `miksy trust
[<проект>]`. После «да» miksy ставит доверие и одобряет для Claude серверы `.mcp.json`.
Ваши ответы в окне Claude («да, больше не спрашивать», одобрение серверов — Claude сам записывает их в
`.claude/settings.local.json` проекта) miksy считает вашими, а не настройками команды, если доверие этому
проекту ставил miksy, вы уже ответили «да» на его вопрос или в слое `trust: true`: их нет в вопросе, и доверию
они не мешают. В проекте, которому miksy не доверял (например, папку скопировали у коллеги), они в вопросе —
отдельной строкой «ответы в окне Claude («да, больше не спрашивать» и т. п.)», один раз: после вашего «да»
доверие стоит, пока не появятся новые настройки команды (или хуки и подобное в том же файле).
Так же — в цели без git (`target: true` у папки без репо, например папки, общей с коллегой): хуки, переменные
окружения и подобное в `.claude/settings.local.json` требуют вашего решения; ответы в окне Claude — как в
git-проекте: если доверие ставил miksy или вы уже ответили «да», они не в вопросе, а в новой цели, которой miksy не
доверял, — в вопросе один раз. `.codex/config.toml` такой цели, который не совпадает с записанным miksy (его
поправили или подменили), — тоже чужие настройки: доверие Codex без вашего решения снимается. Если в такой цели у
вас есть свои хуки в `.claude/settings.local.json` или вы правили её `.codex/config.toml`, после обновления на
0.2.0 `sync` один раз спросит о них.
Подкаталоги цели без git `sync` не проверяет, а Claude применяет к ним её доверие. Хуки и подобное в их
`.claude/settings.json` и `.claude/settings.local.json` и серверы их `.mcp.json` показывает `miksy doctor` — справкой, в разделе
«Исполняемые настройки в подкаталогах групп без git». Если там чужое — удалите это, сделайте подкаталог отдельным
проектом (`git init` в нём) или запретите доверие цели: `trust: { claude: false }` в её слое.
Без вопроса — `trust: { claude: true, codex: true }` в слое организации (`false` — запрет);
`trust: { claude: false }` в `local/machine.yaml` — окончательный запрет машины. Отзывайте
так или `miksy trust <проект> --deny` (`false` в самом агенте `sync` вернёт). Подробности —
[DESIGN §8.7](DESIGN.md#87-доверие-проектов-и-одобрение-mcpjson).

### Учёт, бэкапы, оригиналы

**Учёт** — `local/state/manifest.json` (рядом копия `.bak`): что и с каким содержимым записал
miksy; по нему он отличает свои файлы от чужих и ручных правок. Перед изменением файла его
копия кладётся в `local/backups/<метка запуска>/` (хранятся 20 последних запусков, секреты в
копиях заменены на `<secret:ИМЯ>`). Чужой файл, взятый под учёт (`--force` или совпавшее
содержимое), сохраняется **оригиналом** в `local/backups/originals/` вне ротации — `clean`
вернёт его на место. Оригинала нет только у файлов самого miksy, которые он узнал после «забыть»
(«[Диск нашёлся после «забыть»](#несколько-корней-workspace)»): `clean` их удаляет. «Забыть» забывает и
связь с оригиналами: копии остаются в `originals/`, но сами на место уже не вернутся — сообщение «забыто»
говорит, сколько их. Оригиналы — точные копии, со значениями секретов. Подробности —
[DESIGN §8.8–8.9](DESIGN.md#88-учёт).

## Установка

Одна инструкция для всех случаев: ставите miksy впервые или на вторую машину, агенты чистые или
уже настроены руками. Ваши ручные настройки не пропадут: чужие файлы miksy не трогает, а если
заменяет файл, сохраняет оригинал и возвращает его при удалении miksy.

**Что нужно:** git и хотя бы один агент (как поставить — «[Установка агентов](#установка-агентов)»;
opencode — версии 2.x).
Bun (1.3.14 или новее) установщик предложит поставить сам.

**Поручаете установку агенту** (Claude Code, Codex и т. п.)? Дайте ему ссылку на
[INSTALL-AGENT.md](INSTALL-AGENT.md): там шаги для агента без терминала с вопросами — что он делает
сам, а что только после вашего «да» в чате.

Сначала выберите **workspace** — каталог, где лежат ваши проекты (например, `~/Projects`), — и
скачайте miksy прямо в него. Ниже — пример для `~/Projects`; подставьте свой каталог.

**macOS и Linux:**

```
git clone -b stable https://github.com/wedolab/miksy.git ~/Projects/miksy
cd ~/Projects/miksy && ./install.sh
```

**Windows** (PowerShell):

```
git clone -b stable https://github.com/wedolab/miksy.git $HOME\Projects\miksy
cd $HOME\Projects\miksy; powershell -ExecutionPolicy Bypass -File .\install.ps1
```

`-b stable` — ветка последнего выпуска: с неё miksy обновляется командой `miksy update`
(«[Обновление miksy](#обновление-miksy)»). Можно и в подкаталог (`~/Projects/tools/miksy`) — мастер
всё равно спросит, какой каталог считать workspace.

Или одной строкой — скрипт сам спросит, куда скачать miksy (по умолчанию `~/Projects/miksy`):

```
curl -fsSL https://raw.githubusercontent.com/wedolab/miksy/main/install.sh | bash
irm https://raw.githubusercontent.com/wedolab/miksy/main/install.ps1 | iex
```

Установщик проверит git, поставит Bun (покажет команду и спросит), скачает miksy (ветку `stable`), если
запущен не из клона, и запустит **мастер** — `miksy setup`. Мастер идёт по шагам, у каждого — короткое
пояснение; любой шаг можно пропустить, а повторный `miksy setup` продолжит с несделанного. Перед
каждым изменением системы он спрашивает. У безопасных шагов (копия настроек, `machine.yaml`, команда
`miksy`, PATH) Enter значит «да» — `[Y/n]`, у остальных (установка программ, запись настроек агентам) —
«нет» — `[y/N]`:

1. **Конфигурация** — ваш личный каталог со слоями. Нужна та же, что на другой вашей машине (она в git) — дайте адрес,
   мастер скачает её рядом с движком («[Вторая машина](#вторая-машина)»). Нет — создаст из примера и предложит сделать git-репо с первым
   коммитом (удалённый репо заведите сами — мастер подскажет, как подключить).
2. **Workspace и агенты** — каталог с проектами (Enter — предложенный), по желанию — ещё папки с
   проектами и их ветка в дереве слоёв (Enter — имя папки; [несколько корней](#несколько-корней-workspace)), и найденные
   агенты. Агентов мастер не ставит — только говорит, каких нет.
3. **Копия настроек агентов** — до первой записи: глобальные файлы агентов в
   `local/backups/before-miksy-<метка>/` (раз и навсегда).
4. **Программы для MCP** — чего не хватает серверам из слоёв (`npx`, `uvx`, `docker`…): покажет
   команду установки и выполнит после «y».
5. **Команда `miksy`** — создаст её и, если надо, добавит каталог в PATH (`~/.zshrc`,
   `~/.bash_profile`/`~/.bashrc`, на Windows — пользовательский PATH).
6. **Ручные настройки агентов** — MCP и skills, добавленные в обход слоёв: по каждому спросит, куда
   перенести (глобально, workspace, организация) или оставить. Покажет конфликты первой записи.
7. **Секреты** — каких токенов не хватает и в каком файле их задать; подождёт, пока вы заполните
   `local/secrets.env` (значения мастер не спрашивает и не показывает).
8. **План** — что будет создано и обновлено, конфликты, пропущенные серверы (`v` — полный план).
9. **Запись** — `sync --global` и `sync --all`; доверие проектам с хуками спросит по каждому.
10. **Проверка** — итог `doctor` и вопрос для агента, чтобы убедиться, что всё работает.

После мастера перезапустите открытые сессии агентов — настройки читаются при старте.

**Вернуть всё как было.** Сначала уберите записанное miksy («[Как удалить miksy](#как-удалить-miksy)»),
затем верните копию из шага 3 (путь мастер печатает):

```
cp -R "<конфигурация>/local/backups/before-miksy-<метка>/." ~/                             # macOS, Linux
robocopy "<конфигурация>\local\backups\before-miksy-<метка>" $env:USERPROFILE /E            # Windows (PowerShell)
```

`miksy setup --yes` (без вопросов — для скриптов, CI и агентов) делает только безопасную часть:
конфигурацию из примера, `local/`, `local/machine.yaml` и команду `miksy`; чего не хватает (программы,
секреты) — пишет. `--yes --backup` — ещё и копия настроек агентов (шаг 3). `setup --force` спрашивает
workspace и агентов заново (прежние ответы — по умолчанию).

### Вторая машина

На второй машине можно взять ту же конфигурацию или завести другую — выбираете вы.

**Нужны те же проекты и правила?** Берите свою конфигурацию из git (шаг 1 мастера, вариант 1) и
разложите каталоги, как на первой машине — об этом ниже.

**Нужен другой набор** (другие проекты, личная машина вместо рабочей, у коллеги свой набор)? Создайте
новую конфигурацию из примера (шаг 1 мастера, вариант 2): раскладка первой машины вам не важна. Нужные
правила можно перенести между конфигурациями копированием слоёв.

Дальше — только для первого случая. Главное — **раскладка каталогов**: всё, на что
ссылаются слои дерева, — проекты, организации, цели вроде `home/Miksy` над движком и конфигурацией, —
должно лежать относительно workspace так же, как на первой машине. Было
`~/Projects/home/Miksy/{miksy,miksy-config}` и `~/Projects/Acme/app` — так же и здесь (workspace может
называться по-другому). Иначе слои применятся не к тем каталогам и тексты правил разойдутся. Мастер
предупредит, если в конфигурации есть слой каталога движка, а движок лежит не в нём; сам он ничего не
переносит.

**macOS и Windows не различают регистр в именах:** `miksy` и `Miksy` — один каталог. `mkdir Miksy`
рядом с `miksy` ничего не создаст, а `mv miksy Miksy/miksy` переносит каталог «в самого себя» и ломает
раскладку. Меняйте регистр через временное имя:

```
mv miksy miksy.tmp && mkdir Miksy && mv miksy.tmp Miksy/miksy                    # macOS, Linux
Rename-Item miksy miksy.tmp; mkdir Miksy; Move-Item miksy.tmp Miksy\miksy        # Windows (PowerShell)
```

Перенесли движок или конфигурацию — запустите `miksy setup` снова (обновит команду `miksy`), затем
`miksy doctor`: учёт найдёт новое место сам («[Переименовали или перенесли каталог](#переименовали-или-перенесли-каталог)»).

### Установка вручную

На случай, если мастер не подходит (нестандартная машина, нужно пройти шаги по отдельности). Те же
шаги, что делает мастер, — командами.

**1. Установите git, Bun (1.3.14 или новее) и агентов**, которыми пользуетесь (агенты —
[выше](#установка-агентов), что поддерживается — «[С чем работает miksy](#с-чем-работает-miksy)»).

| ОС | Как поставить Bun | Или через менеджер пакетов |
|---|---|---|
| Windows | `powershell -c "irm bun.sh/install.ps1 \| iex"` | `scoop install bun` |
| macOS | `curl -fsSL https://bun.sh/install \| bash` | `brew install oven-sh/bun/bun` |
| Linux | `curl -fsSL https://bun.sh/install \| bash` | — |

После установки откройте новое окно терминала, чтобы команда `bun` нашлась.

**2. Скачайте miksy** в workspace (каталог с проектами), например в `~/Projects`:

```
mkdir -p ~/Projects && cd ~/Projects
git clone -b stable https://github.com/wedolab/miksy.git miksy
```

Если нужна та же конфигурация, что на другой вашей машине (она в git), скачайте её рядом; если нужна
новая — пропустите этот абзац, `setup` создаст её из примера:
`git clone <адрес вашего репо конфигурации> miksy-config`. Проекты кладите по тем же путям, что
на первой машине (`~/Projects/Acme/app`), движок и конфигурацию — тоже: правила привязаны к путям
(«[Вторая машина](#вторая-машина)»).

**3. Сохраните текущие настройки агентов** — страховка: вернёте всё как было даже без miksy. Мастер
делает это сам (шаг 3); вручную — так:

```
cd ~ && tar czf ~/agents-before-miksy.tgz \
  .claude.json .claude/CLAUDE.md .claude/settings.json .claude/skills \
  .codex/config.toml .codex/AGENTS.md .agents/skills \
  .config/opencode .gemini/GEMINI.md .gemini/config
```

Если каких-то файлов нет, tar об этом напишет, но архив создаст. На Windows просто скопируйте
эти файлы из `%USERPROFILE%` в отдельную папку.

**4. Настройте машину без вопросов:**

```
cd miksy
bun src/cli.ts setup --yes
```

`setup --yes` создаст конфигурацию из примера (если её нет; по умолчанию — `miksy-config` рядом с
движком), `local/`, `local/machine.yaml` (workspace — каталог, где лежит движок или выше:
`~/Projects/miksy` → `~/Projects`; агенты — те, что нашлись) и команду `miksy`. Чего не хватает (программы, секреты) — напишет.
Поправить workspace, агентов и пути к программам можно прямо в `local/machine.yaml`; секреты — в
`local/secrets.env` (переносите через менеджер паролей, не через git или чат). Если команда `miksy`
не находится, добавьте `~/.bun/bin` в PATH.

**5. Посмотрите, что у агентов уже настроено руками:**

```
miksy doctor
```

- «Добавлено агентами в обход слоёв» — MCP-серверы и skills, которые вы добавляли сами. Нужные
  перенесите в конфигурацию: `miksy adopt --global <имя> --to global` (для проекта —
  `miksy adopt <проект> <имя> --to …`). Остальные можно не трогать — miksy их не удалит.
- «Конфликты первого sync» — ваши файлы на тех местах, куда miksy хочет писать (например,
  свой skill с тем же именем). Перенесите из них нужное в конфигурацию.

Что получит агент глобально и в проекте — `miksy explain --global` и `miksy explain ~/Projects/Acme/app`.

**6. Проверьте план, ничего не записывая:**

```
miksy sync --global --dry-run
miksy sync --all --dry-run
```

Команда покажет, какие файлы miksy создаст, обновит и где будут конфликты. Хотите увидеть
сами файлы — `miksy sync --global --out ~/miksy-preview`: miksy сложит их в отдельный каталог и
покажет разницу с текущими настройками. Повторяйте шаги 5–6, пока план вас не устроит.

**7. Запишите настройки:**

```
miksy sync --global
miksy sync --all
```

Первая команда настраивает агентов глобально, вторая — все проекты в workspace. Если проектов
много, miksy сначала покажет список и спросит подтверждение. В конце он может спросить, доверять
ли проектам, где команда настроила хуки или свои MCP-серверы, — ответьте по каждому.

Если остались конфликты «файл существует и создан не miksy» и всё нужное из такого файла уже
перенесено в конфигурацию, повторите с `--force`: miksy заменит файл, а оригинал сохранит.

**8. Проверьте, что всё работает:**

- `miksy doctor` должен написать «Всё синхронизировано»;
- перезапустите открытые сессии агентов — настройки читаются при старте;
- откройте проект и спросите агента: «Процитируй первую строку раздела „## MCP“ в твоих
  инструкциях и вызови context7 для „bun“». Если он ответит «MCP-серверы подключает miksy по
  слоям…» и найдёт библиотеку — всё работает.

**9. Если хотите вернуть всё как было** — раздел «[Как удалить miksy](#как-удалить-miksy)», затем
копия из шага 3: `tar xzf ~/agents-before-miksy.tgz -C ~` (копия мастера —
[выше](#установка)).

## Повседневное использование

### Добавить или изменить правило

| Какое правило | Куда |
|---|---|
| Для всех агентов везде (язык, стиль) | `layers/global/instructions/*.md` |
| Про ОС | `layers/env-windows/…`, `env-macos/…`, `env-linux/…` |
| Для всех проектов workspace | `layers/tree/instructions/*.md` |
| Для организации / проекта | `layers/tree/<Организация>[/<проект>]/instructions/*.md` |

```
miksy sync --global   # меняли global / env-*
miksy sync --all      # меняли layers/tree
```

### Подключить MCP-сервер

Файл `mcp/<имя>.yaml` в нужном слое (примеры — [выше](#mcp-серверы-и-секреты)),
значение секрета — в `local/secrets.env`, затем `miksy sync --all` (или `--global`).

### Настроить организацию или проект отдельно

Создайте в `layers/tree/` каталог по тому же пути, что в workspace
(`layers/tree/NewOrg/`, `layers/tree/NewOrg/some-project/`), и положите туда
`instructions/`, `mcp/`, `skills/` или `layer.yaml`. Больше ничего настраивать не надо.

### Добавить или убрать агента

Запустите `miksy setup` ещё раз: он найдёт нового агента и предложит добавить его в
`local/machine.yaml` (остальные ваши настройки не изменятся). Затем `miksy sync --global` и
`miksy sync --all` — агент получит правила, MCP и skills. Перестали пользоваться агентом —
сначала `miksy clean --all --agent <имя>` и `miksy clean --global --agent <имя>`, потом уберите его
из `agents`.

### Добавить новый проект

`miksy sync` в каталоге проекта (или в любой его подпапке), `miksy sync <путь>` или `miksy sync --all` —
git-репо в workspace miksy находит сам. `miksy sync` без пути пишет только туда, что и так цель: проекту
(git-репо или каталогу, где агент уже работал) или цели `target: true` — из их подпапок тоже. В корне
workspace, в каталоге без git, который не цель (например, папка организации с проектами внутри), и вне
workspace он ничего не пишет, а подсказывает, что сделать (`git init`, `miksy target`, `--all`, `--global`,
`miksy root add`). Если в репо есть исполняемые настройки не от miksy, доверие без вашего решения не
ставится — `sync` спросит. Каталог без git — `git init` в нём или `miksy target <путь>`
([цели без git](#цели-без-git)).

Git-репо **вне workspace** (например, только что склонированный в `~/Downloads/new-repo`): проектом он станет
внутри папки с проектами. `miksy sync` в нём подскажет готовую команду — сделать корнем папку, в которой репо
лежит: `miksy root add "<папка>"` (затем `miksy sync` в репо). Если эта папка — диск или домашний каталог,
`sync` посоветует перенести репо в папку с проектами. Сам репо корнем делать не нужно: корень — папка
с проектами, а не проект. `miksy root add` такого каталога (git-репо или проекта, который уже есть в workspace)
объяснит, что будет, и посоветует верную команду: в терминале спросит «Всё равно сделать корнем?» («нет» по
умолчанию), без терминала корень не добавит; если так и задумано — `--yes`. Если такой корень всё же добавлен,
`sync --all` и `doctor` скажут о записанном в этот каталог раньше (оно действует, но больше не обновляется) и
подскажут: `miksy root remove "<путь>"`, если корень добавлен по ошибке, или `miksy clean "<путь>"`, если так и
задумано. Цель `target: true` без git, добавленная корнем, перестаёт быть целью: записанное в неё `sync --all`
уберёт сам. Каталог без git и без проектов внутри (например, папка с заметками) `sync` тоже не советует делать
корнем: проектом его сделает `git init` и корень — папка, в которой он лежит.

### Добавить свой skill

Каталог `skills/<имя>/SKILL.md` в нужном слое, затем `miksy sync --global` или `--all`:

```markdown
---
name: miksy-contract-review
description: Разбор договора перед подписанием — риски, спорные пункты, правки. Используй, когда просят проверить договор, оферту или соглашение, найти подвохи, подготовить протокол разногласий, поработать как юрист.
---

Порядок работы…
```

Агент заранее видит только `name` и `description`, а остальной текст читает, когда решит, что
skill подходит к задаче. Поэтому от описания зависит, вспомнит ли агент о skill:

- пишите, **когда** использовать, словами, которыми вы ставите задачу: «проверь договор», «как
  юрист», «подготовь претензию» — а не только что skill делает внутри;
- добавьте синонимы и близкие запросы: агент сопоставляет смысл, но опирается на слова;
- одна-три фразы, без общих слов вроде «помогает с документами».

Проверить, дошёл ли skill до агента: `miksy explain <путь>`, раздел Skills.

### Подключить skills команды из репо проекта

Если команда положила skills в репо, а ваш агент их не видит (другой агент, нестандартный
путь), miksy доставит их вашим агентам — если включено в слое:

```yaml
# layer.yaml
import_skills: auto     # до 30 на проект; all — без лимита; [имя1, имя2]; false — выкл.
```

В стартовой конфигурации импорт выключен. Доставляется только **закоммиченное**
(незакоммиченные правки, ignored-файлы, симлинки за пределы репо — нет). Посмотреть, что
лежит в проекте и кто что видит: `miksy skills <путь>`, `miksy skills --all`.

### Поручить изменения агенту

Правила, MCP и skills удобно добавлять, попросив агента: «подключи MCP sentry для всей
организации Acme». Глобальный skill **`miksy`** из стартовой конфигурации объясняет
агентам уровни, форматы и порядок действий (имя без префикса: оно и так ни с чем не совпадёт).

Свои skills называйте с префиксом, чтобы не совпасть с командными skills в репо проектов.
По умолчанию `miksy adopt` советует `miksy-`; свой префикс — в `map.yaml`: `skill_prefix: acme-`.

Если агент добавил что-то по-своему (`claude mcp add`, skill в каталоге проекта), это
получит только он. `miksy doctor` покажет такие добавки («Добавлено агентами в обход
слоёв»), а поднять их в слой — одна команда:

```
miksy adopt <путь проекта> <имя> --to <уровень>   # из проекта
miksy adopt --global <имя> --to <уровень>         # из глобальных настроек агента
miksy sync --all
```

`<уровень>` — `global`, `workspace` или путь в дереве (`Acme`, `Acme/mobile`). `adopt`
переводит MCP в формат miksy, выносит секреты в `local/secrets.env` (в слое — ссылка),
пути машины — в переменные; skill копирует в слой без симлинков. Сначала показывает план
(и что похоже на секрет, но не распознано), записывает после подтверждения (без терминала
— только с `--yes`; `--dry-run` — только план). Для глобального Codex
(`--global … --agent codex`) исходная таблица переходит под учёт с бэкапом.

### Проверить, всё ли в порядке

```
miksy doctor
```

Покажет, что не синхронизировано, что устарело (в том числе командные skills после
`git pull`), что правили вручную, каких секретов и программ не хватает, где нужно решение
о доверии. Запускайте после изменения слоёв, после `git pull` в проектах и просто время
от времени.

В «Справочно» (не ошибки) — каталоги без git рядом с проектами и **окружение**: несколько
установок одной программы (Bun, агенты, Node.js, uv, Python — какая используется и где ещё
есть; версия opencode), переменные, которые уводят каталог настроек агента (`CLAUDE_CONFIG_DIR`,
`CODEX_HOME`, `XDG_CONFIG_HOME`, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `GEMINI_CLI_HOME`), и
конфигурация не та, что рядом с движком (`MIKSY_CONFIG`, `~/.miksy`). То же показывает мастер
`setup`; `install.sh`/`install.ps1` предупреждают о нескольких установках Bun. Miksy ничего из
этого не удаляет и не меняет.

`miksy update --check` — есть ли новая версия; `miksy update` — показать изменения и обновить
(«[Обновление miksy](#обновление-miksy)»).

## Обновление miksy

```
miksy --version          # какая версия стоит
miksy update --check     # есть ли новая (ничего не меняет)
miksy update             # что изменилось — и после «y» обновить
```

`miksy update` берёт новую версию из ветки `stable` (на ней — последний выпуск) и сначала показывает,
что изменилось: записи [CHANGELOG.md](CHANGELOG.md) между вашей версией и новой. Отдельно выделено
**«Ломает»** (что после обновления будет работать иначе) и **«После обновления»** (что запустить или
поправить в конфигурации). После «y»:

1. обновляет движок — только «вперёд» (`git merge --ff-only`): ничего не перезаписывает и не удаляет;
2. уже новой версией: безопасная часть `setup` (команда `miksy`, `local/`), `doctor` и сводка плана
   `sync --global` и `sync --all` — что изменится у агентов;
3. спрашивает «Записать настройки агентам?» — `sync --global` и `sync --all`.

Без терминала (скрипт, агент) — обновление только с `--yes`, а настройки агентам `update` не пишет:
печатает команды `sync`.

**Откажет и объяснит**, если в движке есть свои правки (не коммитьте и не правьте файлы движка — всё
своё живёт в конфигурации: слои, `map.yaml`, `layer.yaml`), если в ветке есть свои коммиты или движок
скачан не через git.

**Вы на ветке `main`** (клонировали до появления выпусков): `main` — ветка разработки, туда попадают и
промежуточные изменения. `miksy update` предложит перейти на `stable` — правок он не теряет, ваша копия
`main` остаётся. Свои незакоммиченные правки — откажет. Разработчикам: `miksy update --main` —
обновить `main` (тоже только «вперёд»).

**Откатиться на прежнюю версию** (например, `0.2.0`), если новая мешает:

```
git -C <каталог движка> checkout -B stable v0.2.0
miksy setup --yes
miksy sync --global
miksy sync --all
```

Первая команда ставит ветку `stable` на прежний выпуск (незакоммиченные правки не теряются: если
мешают, git откажет); следующий `miksy update` снова предложит новую версию. Если в «После обновления» новой
версии вы что-то меняли в конфигурации — верните это. И напишите в
[issue](https://github.com/wedolab/miksy/issues/new/choose), что пошло не так.

**С 0.2.0 на 0.1.x** — сначала подключите диски всех папок с проектами (если какая-то сейчас недоступна,
откат лучше отложить: 0.1.x забудет, что miksy записал в её проекты, и, когда диск вернётся, часть этих файлов,
возможно, придётся убирать вручную — см. «Диск нашёлся после «забыть»»). Затем, ещё версией 0.2.0, приведите
конфигурацию к тому, что понимает 0.1.x:

0. Если вы что-то «забывали» (диск был отключён, а потом нашёлся) — сначала `miksy sync --all`: проекты с такого
   диска снова получат учёт. Если «забывали» целую папку с проектами (`miksy root remove … --forget`), сначала
   верните её — `miksy root add "<путь>" --tree <ветка>`, затем `miksy sync --all`; шаг 1 уберёт её снова. 0.1.x о
   забытых проектах не знает: файлы miksy в них она сочтёт чужими — покажет конфликты, совпадающие возьмёт как
   ваши (с копией-«оригиналом»), а часть станет видна git.
1. Дополнительные папки с проектами (корни) уберите: `miksy root remove <путь>` для каждой — в терминале
   согласитесь убрать записанное в их проекты. 0.1.x знает только одну папку с проектами.
2. В `local/machine.yaml` `workspace` должен остаться одной строкой: `workspace: <путь>`. Если там список (даже
   из одной папки) или у основной папки указан `tree` — перепишите так. Веток 0.1.x не знает: её проекты получат
   слои от корня дерева (`layers/tree/<путь проекта>`), а не из ветки.
3. Если переименовывали агента `gemini` в `antigravity` (`agents` в `local/machine.yaml`, `agents:` у
   MCP-серверов в слоях) — верните `gemini`.
4. Уберите записанное для Antigravity: `miksy clean --all --agent antigravity` и
   `miksy clean --global --agent antigravity`. 0.1.x запишет его заново под своим именем — без конфликтов.

Затем — команды выше с `v0.1.1`.

Что 0.1.x не сохранит: отметки о проектах, которые вы забыли и чей диск ещё не вернулся, — первая же её запись
учёта их сотрёт. Если такой диск найдётся после отката, сначала вернитесь на новую версию и сделайте там
`miksy sync "<путь проекта>"`: совпадающие файлы miksy она возьмёт обратно, но файлы, которые miksy больше не
пишет, сама уже не уберёт (отметки нет, а их скрывает от git строка miksy в `.git/info/exclude` проекта) —
удалите их вручную. Решения о доверии, сохранённые новой версией, 0.1.x понимает — кроме целей без git: там 0.1.x
не читает `.claude/settings.local.json` и `.codex/config.toml`. Хуки и подобное в `settings.local.json` такой
цели, о которых новая версия ждёт решения или которым вы отказали, 0.1.x не увидит и поставит доверие Claude без
вопроса — перед откатом уберите чужое или запретите доверие цели (`trust: { claude: false }` в её слое). Если в такой цели есть ваши хуки в
`settings.local.json` и командный `.mcp.json`, 0.1.x снимет доверие Claude и спросит, показав только
`.mcp.json`: не отвечайте — после возврата новая версия вернёт доверие без вопроса; «да», данное в 0.1.x, она
спросит снова — уже о хуках. Правку `.codex/config.toml` в цели без git 0.1.x не заметит: доверие Codex,
поставленное miksy, останется, как было в 0.1.x. В проекте, где доверие miksy в
этот момент не стоит, а в `.claude/settings.local.json` есть ваши ответы в окне Claude, 0.1.x может спросить о
доверии снова, а после «да» — через раз снимать доверие и спрашивать опять (это ошибка 0.1.x, исправленная в
0.2.0). Ответ, данный в 0.1.x, новая версия примет без нового вопроса (кроме целей без git выше), если с тех пор вы не отвечали Claude
«больше не спрашивать» снова; иначе она спросит один раз — только о настройках команды.

Вернуться на новую версию — `miksy update`, а затем верните то, что убрали перед откатом: папки с проектами —
`miksy root add <путь> --tree <ветка>` для каждой, `tree` основной папки — в `local/machine.yaml`, имя
`antigravity` вместо `gemini` — по желанию. Сами они не вернутся, и без них проекты этих папок не получат
своих настроек. После этого — `miksy sync --all`. Он может один раз спросить о доверии Claude проектам этих
папок, где вы отвечали Claude «да, больше не спрашивать»: шаг 1 убрал записанное, и miksy уже не помнит, что
доверие ставил он. В вопросе — строка «ответы в окне Claude…»; если это ваши ответы и других настроек там нет —
ответьте «да» (`miksy trust "<путь проекта>"`), дальше вопросов не будет.

Что изменилось в каждой версии — [CHANGELOG.md](CHANGELOG.md) и
[Releases](https://github.com/wedolab/miksy/releases) на GitHub.

## Справочник команд

Кратко — `miksy help`. Что запускать после изменений:

| Что изменилось | Что запустить |
|---|---|
| Слои `layers/global/`, `layers/env-<ОС>/` — домашние настройки агентов, действуют во всех каталогах | `miksy sync --global` |
| Дерево `layers/tree/…` — настройки проектов и целей workspace по их пути | `miksy sync --all` или `miksy sync <путь>` (одна цель) |
| `map.yaml`: `global` — `--global`; особые привязки `layers` — `--all` | соответственно |
| Новый проект (склонировали репо), новая цель без git (`miksy target`) | `miksy sync` в его каталоге или `miksy sync <путь>` |
| Новый корень workspace (`miksy root add` или `workspace` в `local/machine.yaml`) | `miksy sync --all` (`root add` предложит сам) |
| Секреты (`local/secrets.env`), новый агент (`local/machine.yaml`), первая установка | оба: `miksy sync --global` и `miksy sync --all` |
| Вышла новая версия miksy | `miksy update` (он сам предложит `sync`) |

Не уверены — `miksy doctor`: он покажет, что устарело и какой командой это записать.

| Команда | Что делает | Пишет |
|---|---|---|
| `setup [--yes [--backup]] [--force]` | Мастер установки (шаги — в «[Установке](#установка)»); `--yes` — без вопросов, только безопасная часть; `--backup` — и копия настроек агентов | конфигурация, `local/`, команда `miksy`; после «y» — копия настроек, PATH, программы, слои (adopt), конфиги агентов (sync) |
| `explain [<путь>] \| --global` | Какие слои, правила, MCP и skills получит цель и откуда; без пути — текущий каталог, `--global` — домашние настройки агентов. Корень и место в дереве — если корней несколько | нет |
| `projects [--agent <id>]` | Какие каталоги miksy считает проектами и целями без git (и корни workspace, если их несколько) | нет |
| `root [add [<путь>] [--tree <ветка>] [--yes] \| remove <путь> [--forget]] [--dry-run]` | Корни workspace — папки с проектами: без аргументов — список; `add` — добавить папку (без пути — текущий каталог), `--tree` — её ветка в дереве слоёв (в терминале спросит, по умолчанию — имя папки), затем предложит `sync --all`; каталог, который сам проект (git-репо, проект workspace), `add` объясняет и спрашивает, без терминала добавляет только с `--yes`; `remove` — убрать дополнительный корень (основной — нельзя), записанное в его проекты — `clean` с вашего согласия; корень недоступен — спросит, забыть ли записанное туда (`--forget` — без вопроса) | `local/machine.yaml` (только `workspace`); после «да» — как `sync --all`/`clean` |
| `target [<путь>] [--remove] [--dry-run]` | Сделать каталог без git целью (без пути — текущий): `target: true` в `layer.yaml` его слоя, затем предложит `sync`; `--remove` — снять пометку и предложить убрать записанное. Без терминала — подсказка команды | слой дерева (`layer.yaml`); после «да» — как `sync`/`clean` |
| `skills <путь> \| --all` | Командные skills в репо: где лежат, ошибки, кто видит | нет |
| `doctor [--agent <id>] [--verbose]` | Что разошлось со слоями; код 1 при проблемах | нет |
| `sync [<путь>] \| --global \| --all [--agent <id>]` | Записать конфиги агентов; без пути — проект или цель текущего каталога (и из подпапки). В корне workspace, в каталоге без git, который не цель, и вне workspace — подсказка, а не запись. Явный `<путь>` каталога без git, который не цель, — запись с предупреждением: `sync --all` его не обновит | да |
| `sync … --dry-run` | Только план | нет |
| `sync … --force` | Перезаписать конфликтующие файлы (с бэкапом/оригиналом) | да |
| `sync --all … --yes` | Не спрашивать подтверждение (много новых целей, опасный workspace) | да |
| `sync [<путь> \| --global] --out <каталог> [--agent <id>]` | Сгенерировать в отдельный каталог (новый, пустой или уже созданный miksy) и сравнить с тем, что агент видит сейчас (секреты скрыты). Без пути — проект текущего каталога, как у `sync` (до 0.2.0 — домашние настройки; теперь это `--global --out`) | только `<каталог>` |
| `clean <путь> \| --global \| --all [--agent <id>] [--dry-run] [--force] [--forget]` | Убрать всё, что miksy записал (`--force` — и правленое вручную). Каталога нет, потому что диск не подключён, — убирает достижимое, а записи о файлах на диске оставляет до повторного `clean`; данных больше нет — `--forget` (в терминале спросит) | да |
| `adopt <путь> \| --global <имя> --to <уровень> [--agent <id>] [--dry-run] [--yes]` | Поднять добавку агента в слой | слой, `local/secrets.env` |
| `trust [<путь>] [--agent <id>] [--confirm \| --deny]` | Решение о доверии проектам с исполняемыми настройками команды | `local/trust.json`, доверие агентов |
| `update [--yes] [--main]` | Обновить движок до последнего выпуска (ветка `stable`): изменения из CHANGELOG, после «y» — fast-forward, затем новой версией `setup --yes`, `doctor`, план и вопрос о `sync`. На `main` — предложит перейти на `stable`; `--main` — обновить `main` (разработка). Без терминала — только с `--yes`, `sync` не пишет | движок (git); после — как `setup --yes`; после «y» — как `sync` |
| `update --check` | Есть ли новая версия (без `git fetch`) | нет |
| `version`, `--version` | Версия движка: `0.2.0` на выпуске, `0.2.0-3-gabc1234` — коммитов после него | нет |

Без `--agent` — агенты из `agents` в `local/machine.yaml` (не задан — все четыре); `<id>` — `claude`,
`codex`, `opencode`, `antigravity` (прежнее `gemini` тоже понимается). Флаги
строгие: ошибка в аргументах — код 2, ничего не выполняется; код 3 — были конфликты (эти
места не изменены).

## Переименовали или перенесли каталог

Проект, цель без git или конфигурацию можно переименовать или перенести (проект и цель — в
пределах workspace; пометку `target: true` перенесите в слой по новому пути: `miksy target`). Следующий `sync` (или `clean`) сам найдёт новое место по файлам, которые
miksy туда записал, перенесёт учёт, обёртки, ключи MCP и доверие и напечатает «Каталоги
переехали»; `doctor` и `--dry-run` только показывают найденное. Не нашёл — `miksy clean
<прежний путь>` уберёт записанное вне каталога, а новый каталог получит конфигурацию как
новый проект. Историю сессий, память и разрешения агентов (они хранятся по пути каталога)
miksy не переносит. Как ищется новое место — [DESIGN §8.8](DESIGN.md#88-учёт).

## Если что-то пошло не так

Не нашли ответа ниже — заведите [issue](https://github.com/wedolab/miksy/issues/new/choose) в
репо движка: шаблон подскажет, что приложить (ОС, версии, вывод `miksy doctor` — без секретов).

| Сообщение | Что значит и что делать |
|---|---|
| `КОНФЛИКТ … создан не miksy` | На этом месте чужой файл. Проверьте содержимое; если оно уже в слоях — `sync … --force` |
| `КОНФЛИКТ … изменён вручную` / `управляемый блок изменён вручную` | Кто-то поправил сгенерированное. Перенесите правку в слои, затем `--force` |
| `взять под учёт … файл miksy (блок miksy), которого не было в учёте` (sync) | Учёт этого проекта был забыт («забыть» при отключённом диске), а файл — miksy и совпадает с тем, что miksy записал бы сейчас: miksy взял его обратно. Ничего делать не нужно. Так же — в облачной папке проекта, которую раньше записал miksy другой машины |
| `КОНФЛИКТ … файл miksy (блок miksy), которого нет в учёте, отличается …` | Файл miksy после «забыть», но с тех пор слои поменялись (или файл правили). `sync … --force` перезапишет его (прежний — в бэкап). Исключение — облачная папка проекта, которую пишет miksy и другой машины: у Codex, opencode, Antigravity файл с путями машины, `--force` будет перетягивать его между машинами — включайте эти агенты для такого проекта на одной машине («[Одна облачная папка проекта на двух машинах](#несколько-корней-workspace)») |
| `удалить … (файл miksy, которого не было в учёте, — больше не нужен)`, `убрать только блок — блок miksy, которого не было в учёте, больше не нужен` (sync, clean) | Учёт проекта был забыт, а miksy этот файл (блок) больше не пишет — например, правила убрали из слоёв, пока диска не было. miksy убирает его сам, прежний — в бэкап. Ничего делать не нужно |
| `одобрение .mcp.json … взять под учёт — одобрения miksy, которых не было в учёте` (sync) | Учёт проекта был забыт, а одобрения серверов командного `.mcp.json` ставил miksy и одобрил бы их сейчас: miksy взял их обратно. Ничего делать не нужно |
| `Записанное в … забыто. Если диск найдётся: …` (clean, root remove) | miksy больше не помнит своих файлов в этих проектах. Когда диск вернётся — команды из сообщения: вернуть корень (если убирали), `sync`, а если файлы не нужны — затем `clean` («[Диск нашёлся после «забыть»](#несколько-корней-workspace)»). `Копии ваших прежних файлов (N) … остаются в …/local/backups/originals/` — miksy когда-то заменил ваши файлы; после «забыть» он их сам не вернёт, нужное возьмите из копии |
| `… отслеживается git-репо … — принадлежит команде` | Файл команды в репо (или dotfiles в `~`) — miksy его не трогает никогда. Агент получит остальное |
| `каталог … версионирует команда` | Личные и импортированные skills не кладутся в командный каталог. Codex возьмёт `.codex/skills`; если и он командный — skill в этом проекте не доставляется |
| `путь внутри вложенного git-репо` | Каталог внутри проекта — отдельный репо (submodule): exclude проекта на него не действует, miksy туда не пишет |
| `… установок несколько — используется …` (doctor, setup, install) | Программа стоит дважды (например, Bun из Homebrew и в `~/.bun/bin`): терминал, агенты и команда `miksy` могут запускать разные версии, а обновляются они по отдельности. Оставьте одну, лишнюю удалите сами. Для Bun затем — `miksy setup` (обновит команду `miksy`) и `miksy sync --global`, `sync --all` (обёртки MCP) |
| `CODEX_HOME=…` / `CLAUDE_CONFIG_DIR=…` / `XDG_CONFIG_HOME=…`: `… настройки miksy агент не увидит` (doctor) | Агент ищет настройки не в стандартном каталоге, а miksy пишет в стандартный. Уберите переменную (профиль оболочки), если она не нужна; другой каталог miksy не поддерживает |
| macOS: MCP-сервер с `npx`/`uvx` у агента в графической программе (Zed, IDE Antigravity, Codex Desktop) падает — `Connection closed`, а в терминале тот же агент работает | Программы, запущенные из Dock, Finder или Spotlight, получают урезанный PATH (`/usr/bin:/bin:/usr/sbin:/sbin`) — без Homebrew (`/opt/homebrew/bin`), `~/.bun/bin`, nvm, и `npx` не находится. Укажите программу абсолютным путём через `vars` в `local/machine.yaml` (`NPX: /opt/homebrew/bin/npx` — путь из `which npx`; в слое `command: ${NPX}`); `npx` и `uvx` сами ищут `node`/`python` по PATH — добавьте серверу `env: { PATH: "${BREW_BIN}:/usr/bin:/bin" }` (`BREW_BIN: /opt/homebrew/bin` в `vars`). Затем `sync`. Или запускайте программу из терминала, если она это умеет (её команда унаследует PATH оболочки) |
| `пропущен сервер … — не заданы переменные` | Не хватает секрета или пути: допишите в `local/secrets.env` или `vars` в `local/machine.yaml`. Записанный раньше сервер остался |

## Как удалить miksy

1. **Убрать всё записанное** (для всех агентов из `agents`; другой агент — `--agent`):

   ```
   miksy clean --all --dry-run
   miksy clean --all
   miksy clean --global
   ```

   `clean` по каждой цели:
   - удаляет свои файлы (skills, `.opencode/miksy.md`, плагин, проектный
     `.codex/config.toml`, обёртки в `local/run/`), убирает свой блок из файлов инструкций
     (файл удаляется, только если вне блока ничего нет) и свои ключи из общих файлов
     (`~/.claude.json`, `~/.codex/config.toml`, `opencode.json`, `mcp_config.json`);
   - возвращает **оригиналы** файлов, которые miksy когда-то захватил (если после
     захвата файл менялся — оставляет его и называет путь оригинала);
   - снимает своё доверие и одобрения `.mcp.json` (ваши не трогает), свои строки
     `.git/info/exclude`, ненужные файлы `local/secrets/`.

   Изменённое вручную `clean` не трогает (конфликт) — `--force` уберёт и его (с бэкапом).

2. **Что остаётся** и убирается вручную, если не нужно:
   - пустые файлы и каталоги, пустые разделы верхнего уровня (`{"mcp": {}}`) в общих
     конфигах (опустевшие записи проектов `projects[<путь>]`, созданные sync, уходят);
   - цели, которых больше нет в слоях (учёт их помнит, `clean --all` идёт по слоям) —
     `miksy clean <путь>` для каждой; каталог, которого нет на диске, — тоже
     `miksy clean <прежний путь>` (doctor их перечисляет). Если такой каталог был вне папок с проектами
     (корень убран из workspace), miksy не знает, удалили его или не подключён диск, и спросит, забыть ли
     записанное туда (без терминала — `miksy clean <прежний путь> --forget`);
   - `local/` конфигурации: `secrets.env`, `secrets/`, `backups/` (в том числе
     [`originals/`](#учёт-бэкапы-оригиналы)), `state/`, `trust.json`;
   - команда `miksy` (`~/.bun/bin/miksy`, на Windows `miksy.cmd`) и файл `~/.miksy`;
   - каталоги движка и конфигурации (конфигурацию стоит сохранить — это ваши слои).

3. Если нужно состояние «до miksy» целиком — ваша копия настроек агентов
   (`local/backups/before-miksy-<метка>/` от мастера — как вернуть, в «[Установке](#установка)»; или
   архив из «[Установки вручную](#установка-вручную)») или бэкапы `local/backups/<метка>/` первого
   запуска.
