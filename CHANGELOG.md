# Изменения miksy

Все заметные для пользователя изменения — по версиям, от новых к старым (в духе
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/)). Номера — [SemVer](https://semver.org/lang/ru/):
пока версия 0.x, «Ломает» или «Новое» поднимают вторую цифру, только «Исправлено» — третью. Как
обновиться — `miksy update` ([docs/update.md](docs/update.md)). Правила записи — [RELEASING.md](RELEASING.md).

## Не выпущено

### Новое

- `miksy secret ИМЯ -- <команда>` — miksy сам запускает команду и отдаёт ей секрет на вход, мимо чата. Пишется
  одинаково в PowerShell, cmd и bash, например `miksy secret DEV_PASS --line "dev:{}" -- ssh dev@HOST sudo chpasswd`:
  `--line` подставляет значение вместо `{}` и добавляет перевод строки, `--env PGPASSWORD` кладёт значение в
  переменную окружения команды. Раньше на Windows в PowerShell секрет можно было передать только обходом
  (`cmd /c` или Git Bash): труба PowerShell портит значение. Труба `miksy secret ИМЯ | <команда>` осталась для
  macOS, Linux и bash. Подробнее — docs/layers.md, «Секреты в skills».

### Исправлено

- Windows: в Git Bash (через него, например, выполняет команды Claude Code) команда `miksy` не находилась —
  находился только `miksy.cmd`, и пример `miksy secret ИМЯ | <команда>` не работал. Теперь `miksy update` или
  `miksy setup` кладёт рядом с `miksy.cmd` команду `miksy` для Git Bash. В PowerShell и cmd всё по-прежнему.
  `miksy doctor` напомнит, если на машине есть Git Bash, а этой команды нет.
- `miksy setup` на уже настроенной машине говорит короче. Вместо всего `local/machine.yaml` — одна строка: файл есть
  и не тронут, перезаписать — `miksy setup --force`. Список «Дальше» — только пока настройки агентам ещё ни разу не
  записывались, заметка о подготовке машины — только когда `local/machine.yaml` записан в этом запуске. В мастере
  нет лишнего «Дальше: miksy sync…» после переноса настройки агента в слои, а при отказе от записи «позже: sync» —
  одной строкой.

## 0.7.0 — 2026-11-24

### Новое

- `miksy secret <ИМЯ>` — skill может взять секрет из `local/secrets.env` прямо в команду, мимо чата:
  `miksy secret ACME_TOKEN | <команда>`. Без пути к `local/` и без чтения всего файла секретов. miksy выдаёт только
  секреты, которые вы объявили для этого места — `skill_secrets: [ACME_TOKEN]` в `layer.yaml` слоя организации или
  проекта; в папках другой организации команда их не выдаст. Это защита от ошибки, а не замок: агент, который
  перейдёт в папку другого проекта, получит и его секреты. Какие секреты доступны папке — `miksy explain <путь>`;
  объявленные, но не заданные — покажет `miksy doctor`. Подробнее — docs/layers.md, «Секреты в skills».

- Skill `miksy` (объясняет агентам, как менять настройки через miksy) теперь встроен в miksy и обновляется вместе с
  ним: `miksy update`, затем `miksy sync --global`. Раньше мастер `setup` один раз копировал его в вашу конфигурацию,
  и копия устаревала. Копия, которую вы не меняли, больше не действует — `miksy doctor` подскажет команду, чтобы её
  удалить. Изменённая копия по-прежнему заменяет встроенный; `doctor` напомнит, что она может отставать, и покажет,
  как сравнить. **Если вы удалили skill `miksy` нарочно**, он снова появится у агентов; выключить —
  `exclude: [skill.miksy]` в `layers/global/layer.yaml` конфигурации, затем `miksy sync --global`.

### Исправлено

- Перенос skill в конфигурацию (`miksy adopt` и мастер `setup`) больше не забирает файлы с ключами и паролями
  (`.env`, `*.pem`, `id_rsa` и т. п.) и служебное (`.git`, `node_modules`, `.DS_Store`): раньше они попадали в слой и
  дальше в git конфигурации. miksy перечисляет, что не скопировал, и как поступить, если файл нужен. Если пароль или
  токен записан прямо в тексте skill, miksy покажет файл, строку и что нашёл (сам текст строки — нет) и подскажет, как передать
  skill секрет, не кладя его в файлы skill: способы по порядку — в docs/layers.md, раздел «Секреты в skills».
- `miksy doctor` и `miksy sync` теперь замечают то же в skills, которые уже лежат в конфигурации (например,
  положены туда руками): файл с ключами или паролями в папке skill или пароль прямо в тексте. Текст строки не показывается — только файл, номер строки и что найдено.
  Файлы, которые git конфигурации не забирает (вписаны в `.gitignore`), не показываются.
- `miksy sync` больше не копирует агентам из папки skill файлы с ключами и паролями (`.env`, `id_rsa` и т. п.), если
  они могут попасть в git конфигурации, — и убирает уже скопированные раньше. Файл, вписанный в `.gitignore`
  конфигурации, агент получает, на macOS и Linux — с доступом только для вас; это копия в каждом месте, куда
  доставлен skill, — `sync` скажет о каждой новой копии, `doctor` покажет, сколько их. Не копируются ссылки, ведущие
  за пределы слоёв конфигурации (например, на ключ в домашней папке или на файл секретов в `local/`; если ссылка —
  сама папка skill, skill не доставляется целиком), ссылки на файл с ключами из другого skill и служебное
  (`.DS_Store`, папка `.git`); `sync` говорит, что пропустил.

## 0.6.0 — 2026-11-23

### Новое

- Codex, opencode и Antigravity: MCP-серверы проекта записываются в файл проекта всегда, даже если на этой машине для
  сервера нет секрета или он задан только для другой ОС. Папка проекта, общая для двух машин, больше не даёт конфликт
  из-за секрета, который есть только на одной.
  - **Заметно и на одной машине:** сервер, для которого на ней нет секрета, раньше просто пропускался, а теперь
    появится в агенте как не запустившийся, с причиной («не заданы переменные … — local/secrets.env»). Чтобы он
    заработал — добавьте секрет в `local/secrets.env` и выполните `miksy sync --all`; не нужен — уберите сервер из
    слоя или исключите его (`exclude: [mcp.<имя>]` в `layer.yaml`). Не нужен только на этой машине —
    `miksy mcp off <имя>`: агенты этой машины увидят его пустым, без ошибки, или не получат вовсе (вернуть —
    `miksy mcp on <имя>`). Такие серверы `miksy doctor` перечисляет в разделе «Справочно».
  - Сервер, заданный только для другой ОС (`os:`), на этой машине молча работает пустым — без инструментов и без
    ошибки. HTTP-сервер без секретов и переменных с одним адресом во всех слоях записывается как есть и на другой
    ОС работает.
  - После обновления первый `miksy sync` допишет такие серверы в файлы проектов.

### Исправлено

- Одна папка проекта на двух машинах: если файл в ней переписала другая машина с другой конфигурацией, `sync`
  теперь так и говорит — «файл переписала другая машина (общая папка)» — вместо «изменён вручную». Где видно, называет
  причину (разные MCP-серверы в слоях, другой агент, старая версия miksy) и что сделать, чтобы машины совпали.

## 0.5.1 — 2026-11-22

### Исправлено

- Одна папка проекта на двух машинах (облако, сетевой диск): машины больше не мешают друг другу — git на обеих чист, а
  `clean` на одной не удаляет файлы и одобрения, нужные другой. Обновите miksy на обеих машинах и выполните на каждой
  `miksy sync --all`; до этого `clean` не делайте ни на одной.

## 0.5.0 — 2026-11-22

### Новое

- Одна папка проекта на двух машинах (облако или сетевой диск, Windows и Mac) теперь работает и у Codex, opencode и
  Antigravity, а не только у Claude. Раньше их файлы в папке проекта содержали пути своей машины, и вторая машина
  видела конфликт. Теперь MCP-серверы с секретами и путями машины записываются туда командой `miksy mcp …`: при
  запуске она берёт настройки своей машины, а файл на обеих машинах одинаковый. Первый `sync` новой версией
  перепишет эти файлы сам. Что нужно:
  - обе машины — на этой версии miksy (`miksy update`); если файл переписала машина со старой, `sync` скажет об этом;
  - команда `miksy` у агентов — её ставит `miksy setup`; `miksy doctor` проверяет, есть ли она и видна ли агентам,
    запущенным не из терминала. Codex на Mac и Linux находит её через `~/.codex/.env` — строку туда дописывает
    `miksy sync --global` (файл с вашими строками miksy не меняет, а `doctor` подскажет, что дописать).

  Подробнее — [docs/roots.md](docs/roots.md#одна-облачная-папка-на-двух-машинах).

### Исправлено

- Команда `miksy` больше не читает `.env` и `bunfig.toml` папки, в которой её запустили: чужой проект не может
  подмешать в miksy и в MCP-серверы с секретами свои переменные и код. Команду обновит `miksy setup` (и `miksy update`).
- `miksy restore` больше не просит заранее закрыть агентов и редакторы (его может запускать и сам агент); после
  возврата он просит перезапустить агентов, чтобы они прочитали возвращённые настройки.

## 0.4.0 — 2026-11-21

### Новое

- `miksy setup --force`: выбрали корнем workspace новую папку, а прежняя на месте и в ней есть проекты, — мастер
  спросит «Оставить её основной, а новую добавить ещё одной папкой с проектами?». «Да» — прежняя остаётся как была
  (её правила, MCP и skills не меняются), новая подключается рядом со своей веткой, как `miksy root add`; переносить
  слои вручную больше не нужно. «Нет» — основной станет новая, как при переносе папки. Если диск прежней папки просто не
  подключён, мастер так и скажет и подскажет, как вернуть её.
- `miksy downgrade` — вернуть прежнюю версию miksy одной командой, если новая мешает. Без номера — ту, что стояла до
  обновления; можно указать номер (не ниже 0.3.0). Сначала покажет, что уйдёт, и спросит; затем вернёт движок и
  перепишет настройки агентов уже прежней версией. Обратно на новую — `miksy update`. Длинный рецепт отката из
  docs/update.md больше не нужен ([docs/update.md](docs/update.md#откатиться-на-прежнюю-версию)).

### Исправлено

- Windows: в имени папки проекта есть `%ИМЯ%` переменной окружения (например, `%USERNAME%`) — команда `miksy` с таким
  путём получила бы его искажённым; `miksy doctor` теперь об этом предупреждает и подсказывает, что делать.

## 0.3.2 — 2026-11-19

- Причина редких «сбоев git» — ошибка в Bun до версии 1.4.3, поэтому miksy теперь нужен Bun 1.4.3 или новее.

## 0.3.0 — 2026-11-15

### Новое

- `miksy restore` — вернуть настройки агентов из копии «до miksy» одной командой (после `miksy clean --all` и
  `--global`). Перед записью показывает, что вернётся и какие файлы затрёт, и спрашивает; затёртое сохраняет в бэкап.

  ([как удалить miksy](docs/uninstall.md#3-вернуть-копию-до-miksy)).

## 0.2.3 — 2026-11-14

### Исправлено

- Windows, встроенная учётная запись «Администратор» (она выключена по умолчанию): `local/secrets` или `local/backups` —
  ссылка на другой том — miksy считал её цель открытой, даже когда она закрыта только для вас, и отказывал: SYSTEM и
  «Администраторов» Windows добавляет файлам такой учётной записи сама. Теперь для неё эти записи — не чужой доступ (как
  и для `local/` и файлов секретов); Пользователи, Все и другие учётные записи — по-прежнему чужой.
- Диск с папкой проектов отключили насовсем вместе с буквой, а у проекта на нём был MCP-сервер Claude: «забыть»
  (`clean --forget`, `root remove --forget`) и `clean` давали конфликт `~/.claude.json`, «забыть» оставлял запись в
  учёте. Теперь «забыть» убирает сервер проекта и запись, `clean` — сервер проекта.
- Путь или ветка с `$` или `!` в готовых командах подсказок (`root add`, `clean`, `sync`) искажались оболочкой — `$1`
  подставлялся как переменная, `!` в bash и zsh давал ошибку. Теперь такие пути — в кавычках, которые их не меняют.
- `root remove`: подсказки о файлах агентов, которых нет в `agents`. Доступная папка — теперь сказано, что их файлы
  `clean` без `--agent` не убирает, и дана команда. После «забыть» и возврата диска — подсказка начинается с
  возвращения папки (`root add`), а не с `sync` для папки, которую этот же запуск убирает из workspace.
- `local/secrets` — ссылка на открытую или битую папку: `sync` пропускал только первую цель, которой нужны секреты, а
  следующие записывал со ссылкой на несуществующий файл секрета; `--dry-run` обещал «создать». Теперь пропущены все
  такие цели, одной строкой с готовой командой, а `--dry-run` говорит то же. Итог `sync` и `clean` после ошибок
  говорит, сколько целей пропущено и сколько записано (у `clean` — убрано) частично, а не «Конфликтов … эти места не
  изменены»; в `--dry-run` — в будущем времени.
- `doctor` о секретах: ссылка `local/secrets` — одна строка вместо двух; файл секрета, который не прочесть (так его
  могла оставить 0.2.1), — «не читается», а не «устарел».
- `miksy setup` без `--force` при готовом `local/machine.yaml` и движке прямо в каталоге без обычной раскладки писал
  «workspace не выбран» и не дописывал найденных агентов. Теперь workspace берётся из `machine.yaml`.
- Копия настроек «до miksy» на Windows: ссылки на папки (в том числе битые) сохраняются junction — им не нужен режим
  разработчика; раньше битый junction становился ссылкой на файл, а ссылка на папку без режима разработчика не
  копировалась.
- Подсказки `setup --force` при смене основной папки с проектами: рецепт «Вернуть его» больше не предлагает перенос,
  который снял бы правила с проектов новой основной папки (её ветка совпадает с именем папки прежней); несколько
  вложенных папок с проектами — во множественном числе.

## 0.2.2 — 2026-11-14

### Исправлено

- Windows: если в `local/` есть ссылка — в копии «до miksy» (ваши настройки агентов — ссылки на папку dotfiles:
  `~\.claude\skills`, `~\.agents\skills` и т. п.) или `local/secrets`, `local/backups` на другом томе, — все команды
  miksy (`sync`, `clean`, `setup`) падали с «local/ не закрыт», а проверка прав `local/` сбрасывала права файлов за
  ссылкой. Так было в 0.2.1, 0.2.0 и 0.1.1. Теперь miksy проверяет и закрывает права только у файлов внутри `local/` и в
  ссылки не заходит; ссылки в копии «до miksy» больше не дают предупреждений «закройте вручную» (и на macOS, Linux).
  Права, уже сброшенные прежней версией, сами не вернутся. Если задавали их вручную, проверьте цели ссылок: папку
  dotfiles, куда ведут ссылки в копии «до miksy», и цели `local/secrets`, `local/backups` — после сброса их файлы могли
  стать доступны другим учётным записям. Посмотреть права — `icacls "<папка>" /T` (Windows; `doctor` ссылки копии «до
  miksy» не проверяет). Если цель ссылки открыта другим, `sync` и `doctor` печатают готовую команду,
  которая её закроет. Откат на прежнюю версию с такими ссылками — docs/update.md, «Особенности версий».
- Бэкапы на другом томе: `local/backups` — ссылка на папку, открытую другим, или на несуществующую. Раньше на macOS и
  Linux при открытой папке отказывала только первая запись бэкапа за запуск, а копии ваших файлов (в них бывают токены:
  `.claude.json`, `config.toml`) — бэкапы других целей, оригиналы, копия «до miksy» мастера — ложились в эту папку; при
  несуществующей отказывала каждая запись бэкапа. На Windows такие команды падали ещё раньше — строка выше. Теперь все
  команды, которые пишут, останавливаются в начале, ничего не записав, и говорят, что сделать: закрыть папку готовой
  командой, исправить ссылку или заменить её обычной папкой. `--dry-run` и `doctor` говорят то же.
- Windows, `local/backups` или `local/secrets` — ссылка на папку, закрытую только для вас без наследования прав
  (`icacls … /inheritance:r`): папки и файлы, которые miksy создаёт за ней (бэкапы, оригиналы, копия «до miksy», файлы
  секретов), 0.2.1 и раньше оставляли без единой записи прав — недоступными даже вам: команды, которые пишут бэкапы,
  падали, а файл секрета агент не мог прочесть. Теперь они закрыты сразу и читаются вами. Если прежняя версия оставила
  там папки открытыми или без доступа даже для вас, команды остановятся с одной готовой командой, которая закроет папку
  бэкапов и всё в ней.
- Команда, которая возвращает копию настроек «до miksy» (мастер печатает её на вопросе 3; docs/uninstall.md,
  шаг 3), теперь сообщает, если что-то не вернулось: код выхода не 0 и строки «не возвращён: …». Ссылки из копии
  (dotfiles) возвращаются ссылками, путь с `$`, `` ` `` или `"` больше не искажается, `~/.claude.json` по-прежнему не
  возвращается. На Windows — новая команда PowerShell вместо `robocopy`: тот не возвращал ссылку на папку без прав
  администратора и считал ошибкой ссылку, которая уже на месте.
- Вы сказали «нет» доверию Claude, но одобрили серверы `.mcp.json` проекта отдельно, а потом сами сняли доверие в
  окне Claude: `sync` снимает одобрение серверов, как и раньше, но теперь говорит об этом и что будет дальше (и в
  `--dry-run`, и в `doctor`) — раньше молча.
- Подсказки после «забыть» точнее. `clean` проекта, который был забыт, а папка уже вне workspace, называет, где
  лежит копия `local/machine.yaml` до `root remove` (если она ещё хранится), и что делать, если папка ушла из
  workspace после `setup --force`; в `clean --all` папки, где остались файлы только агентов, которых нет в `agents`,
  — под своим заголовком. `clean` забытой папки, которой больше нет, говорит, что в учёте осталась отметка, а
  `miksy clean "<путь>" --forget` её убирает (раньше — «изменений нет», и отметка оставалась).
- После `setup --force`, сменившего основную папку с проектами, подсказка «Вернуть его: …» давала ветку с `[ ]` или
  `{ }` из имени папки — привязки `map.yaml` по ней не совпадали. Теперь ветка без знаков, которые ломают привязку
  (`[ ] { } * ?`, `!` в начале; так же предлагают `root add` и мастер, остальные имена — как раньше), а правило для
  `match:` — общее: и для `{…}`, и для шаблонов на `**`. Подсказка есть и когда основным выбран новый каталог, а если
  прежняя папка лежит внутри другой папки с проектами, `setup` говорит, что её проекты остаются. Прежнюю папку
  перенесли или в ней не осталось проектов — рецепта нет: учёт переедет сам при `sync --all`; была в ней ещё одна папка
  с проектами (вложенный корень) — `setup` называет её и что поправить в `local/machine.yaml`. У новой папки есть папки
  с теми же именами — рецепта тоже нет (перенос слоёв задел бы и их проекты). Папку скопировали — сказано, что сделать
  с прежней копией и с конфликтами в новой. Ветка по умолчанию
  для папки, которая уже есть на другой машине, может отличаться от ветки там — введите ту ветку.
- `root remove` недоступной папки с проектами без «забыть»: в числе файлов, которые потом уберёт `miksy clean`, —
  только агентов из `agents`; для остальных — команда `miksy clean "<путь проекта>" --agent <имя>` (раньше их файлы
  входили в число, а `clean` без `--agent` их не трогал). `--dry-run` говорит то же. Так же — строки `doctor` о
  записанном в недоступную папку и в папки вне workspace.
- Сообщение «учёт … записан более новой версией движка» после отката на эту версию убирает `miksy setup --yes` из
  шагов отката — раньше оно повторялось до первого `sync` с изменениями, а если менять нечего — всегда. Работает при
  откате на 0.2.2 и новее; на второй, необновлённой копии движка сообщение «обновите и эту» остаётся.
