# Выпуск версий miksy

Для владельца репо. Как устроено — [DESIGN §12](DESIGN.md#12-версии-ветки-и-обновление).

## Коротко о словах

- **Версия** — номер вида `0.2.1` в `package.json`. Пользователь видит его в `miksy --version`.
- **Тег** `v0.2.1` — метка в git на коммите, который стал этой версией. Тег не двигается.
- **Ветка `stable`** — всегда указывает на последний выпуск. С неё ставят и обновляются пользователи
  (`miksy update`). Двигается только вперёд и только командой выпуска.
- **Ветка `main`** — ваша работа. Промежуточные коммиты в `main` пользователям не приходят.
- **`CHANGELOG.md`** — что изменилось для пользователя, по версиям. Сверху — раздел «Не выпущено», когда есть
  невыпущенные изменения; сразу после выпуска его нет.

## Когда писать в CHANGELOG

В **том же коммите**, что и изменение, — строку в «Не выпущено», если пользователь заметит разницу или
ему нужно что-то знать или сделать. Раздела «Не выпущено» нет — создайте его над последней версией
(`## Не выпущено`) и в нём только нужный подзаголовок; пустых подзаголовков не оставляйте. Подзаголовки:

- **Новое** — новая команда, флаг, возможность;
- **Исправлено** — ошибка, которую пользователь мог встретить;
- **Ломает** — после обновления что-то перестанет работать как раньше (формат конфигурации, команда);
- **После обновления** — что запустить или поправить: `miksy sync --all`, переименовать ключ и т. п.

Тесты, рефакторинг, документация — без строки: номер версии говорит о программе. Пишите для пользователя: что изменилось у него, а не
что поменялось в коде.

## Какой будет номер

Его считает команда выпуска по «Не выпущено»:

| Что есть в «Не выпущено» | Пока 0.x | После 1.0 |
|---|---|---|
| «Ломает» | `0.2.0` → `0.3.0` | `1.2.0` → `2.0.0` |
| «Новое» (без «Ломает») | `0.2.0` → `0.3.0` | `1.2.0` → `1.3.0` |
| только «Исправлено» | `0.2.0` → `0.2.1` | `1.2.0` → `1.2.1` |

В 0.x ломающее изменение допустимо в обычном выпуске — но всегда с записью «После обновления»: что
пользователю сделать. После 1.0 ломающее — только с новой первой цифрой.

## Когда выпускать

- **Исправление, которое затрагивает пользователей**, — сразу, отдельным выпуском (номер — третья цифра).
- **Законченная и проверенная доработка** (тесты на Windows и Mac прошли) — выпуском (вторая цифра).
- **Мелочи** (документация, тексты, рефакторинг) — не повод: уедут с ближайшим выпуском.

## Как выпустить

В каталоге движка, на ветке `main`, всё закоммичено:

```
bun run release --dry-run     # номер и текст — ничего не меняет
bun run release               # то же, затем «Выпустить? [y/N]»
```

После «y» команда сама: поднимает `version` в `package.json`, превращает «Не выпущено» в
«X.Y.Z — дата» (новой пустой нет), делает коммит «Release X.Y.Z», ставит тег `vX.Y.Z` и передвигает
на него `stable`. Затем спрашивает отдельно: отправить в GitHub (`main`, `stable`, тег) и создать GitHub
Release с текстом из CHANGELOG. Ответили «нет» — она напечатает команды, выполните их позже. Без
вопросов: `bun run release --yes` (выпуск) и `--push` (сразу отправить).

Раздела «Не выпущено» нет или он пуст — команда откажет: «выпускать нечего».

## Срочное исправление, когда в `main` незаконченное

Исправление коммитится в `main` (со строкой в «Не выпущено») как обычно, затем переносится на `stable`:

```
git checkout stable
git cherry-pick <коммит исправления>
bun run release               # выпуск с ветки stable: номер — третья цифра
git checkout main
git merge stable              # вернуть выпуск в main
```

При `git merge stable` возможен конфликт в `CHANGELOG.md`: строка исправления должна остаться только
в записи новой версии, а не в «Не выпущено»; `version` в `package.json` — номер выпуска.

## Вручную (если команда недоступна)

```
# 1. package.json: "version": "X.Y.Z"; CHANGELOG.md: «## Не выпущено» → «## X.Y.Z — ГГГГ-ММ-ДД»,
#    пустые разделы убрать (новую «## Не выпущено» не добавлять)
git commit -am "Release X.Y.Z"
git tag -a --cleanup=verbatim vX.Y.Z -F <файл с текстом записи X.Y.Z>
git branch -f stable vX.Y.Z
git push --atomic origin main stable vX.Y.Z
gh release create vX.Y.Z --title "miksy X.Y.Z" --notes-from-tag
```

`stable` двигайте только вперёд (на потомка прежнего выпуска): иначе `miksy update` у пользователей
откажет («ветка разошлась»). Тег уже отправленного выпуска не переставляйте — выпустите следующий номер.
